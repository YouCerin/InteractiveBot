## 2. 执行项

### S1｜会话级发送临界区（串行链）

**目标**：把 `check → gap → send → markSent` 收进同一临界区，使 `minGapMs` 从「尽力」变成「保证」，且多来源投递不互相插队。

**改动范围**

- `src/onebot.mjs`：`SendQueue` 增加 `#chains: Map<string, Promise>`；对外只暴露"按会话执行一个投递任务"的方法（`run(chatKey, task)` 或等价的 `deliverWithPolicy`），`check`/`markSent` 降级为内部步骤（不删，保留给测试）。
- `src/bridge.mjs`：三个调用点（表情 ~6898 / ~6917、正文 ~6948、`#safeSend` ~7052）改为走同一入口。
- `#safeSend`：`{ skipGap: true }`，但**不跳过**配额计数与账本。例外写在参数里，不靠"它没调 check"这种隐性区别。

**步骤**

- [x] S1.1 `SendQueue` 加链；把现有 `check → sleep → recheck → send → markSent` 原样搬进链任务
      （★ 与表单措辞的一处**有意偏离**：没有"双跑对拍"—— 旧路径一旦留着就是一个**可被误用的旁路**，
      对拍改为在**测试里**做比较：A2 用老写法跑同一组并发断言，见 §7.2）
- [x] S1.2 链任务加**超时预算**（默认 30s）：超时 → 记 `failed`、**不 markSent**（允许后续重试），并放过链
- [x] S1.3 三个调用点切换；`#safeSend` 显式 `skipGap`
- [x] S1.4 全局限频仍用滑动窗口（`#window`），**不放进链**；两套机制的边界写进模块头注释

**验收（必须可复现，不是"看日志像对了"）**

- [x] A1 并发投递：同一 `chatKey` 同时触发两次投递（中间态 + 最终回复），断言相邻两条的**实际发送时间差 ≥ minGapMs**，且顺序与入链顺序一致
- [x] A2 变异测试：把串行链去掉（恢复"先 check 再 await send"）→ A1 **必须变红**
- [x] A3 账本：并发场景下 `delivery-ledger` 的两条记录 `chunks[].sent` 不交错，`sentCount ≤ total`
- [x] A4 超时：注入一个永不返回的 `onebot.send`，断言链在预算后被放过、该条记 `failed`、后续投递不受阻

**风险 / 回滚**

- 风险：单会话吞吐下降（N 条总耗时 ≈ Σ(发送耗时 + gap)）；链被卡死的可能（由 S1.2 兜住）
- 回滚：本项是**单提交**（`onebot.mjs` + `bridge.mjs` 调用点），`git revert` 即回到概率性 gap，无数据格式变化

### S3｜失败 / 丢弃回执给模型

**目标**：让"没发出去的第 N 条 + 原因"回到模型上下文，使模型能自我纠正；同时保证回执本身**永远不会被当成正文发出去**。

**改动范围**

- 新增 `src/delivery-receipt.mjs`（**纯函数**，可被假输入直接驱动）：`collect(dropped) → receiptText`、`shouldReceipt(dropped) → boolean`、`dedupeKey(receipt)`
- `src/bridge.mjs`：投递循环收集 `dropped[] = { index, text, reason, kind }`，循环结束后交给回执模块
- 注入点：复用"记忆回执"同款通道（下一轮上下文），不新开旁路
- `src/config.mjs`：新增 `delivery.receipt.enabled`(默认 true) / `maxPerHour`(默认 3) / `minIntervalMs`

**回执规则（写成表，避免"什么失败都回执"）**

| 丢弃原因 | 是否回执 | 理由 |
|---|---|---|
| 每分钟/每小时上限 | ✅ | 模型能改写或稍后重发 |
| 内容去重命中 | ✅ | 模型能换说法 |
| 发送异常（协议端报错） | ✅（带原因摘要） | 模型能决定是否重试 |
| 终检门 `dropped`（内部泄漏） | ❌ | 回执等于把内部信息再递一遍 |
| 空段 / 白名单外 | ❌ | 不是可自救的失败 |

**步骤**

- [x] S3.1 抽 `delivery-receipt.mjs` + 单测（纯函数，含"不该回执的三种"反例）
- [x] S3.2 投递循环收集 `dropped`（正文循环里的丢弃点全挂上，见 §7.2 的偏差说明）
- [x] S3.3 接入下一轮注入；回执文本带显式前缀（`[投递回执]`）
- [x] S3.4 限次：同 `chatKey` 每小时 ≤3 次；同一原文回执后仍失败 → 不再回执
- [x] S3.5 回执**不进** mirror / 语料库 / 投递账本（它不是"我说过的话"）

**验收**

- [x] B1 构造限频丢弃 → 下一轮上下文出现回执
- [x] B2 终检门 dropped → **无**回执（反例断言）
- [x] B3 循环保护：连续 3 次被去重丢弃 → 只回执 1 次
- [x] B4 回执不出现在 `#mirror`、`#recordCorpus`、`delivery-ledger` 的任何字段里
- [x] B5 变异测试：把 `shouldReceipt` 改成恒 true → B2 变红

**风险 / 回滚**

- 风险：回执占 token；回执措辞不当会让模型重复道歉（措辞是"给动作"而不是"报故障"）
- 回滚：`delivery.receipt.enabled=false` 即一键关闭（回执是**纯增量**，关掉等于回到今天的行为）

### S5｜出站目标来自「通道对象」而非 chatKey

**状态：✅ 已落地（2026-10-18）。**

> ⚠️ **门禁是被使用者主动跳过的，如实记在这里**：§3 写的是"S1/S3 **稳定一版**（避免结构改动叠加并发修复）"，
> 而本轮 S1/S3 刚落地、还没经过一版真实运行，使用者就说"现在就做 S5"。
> 所以 S5 是在**门禁未满足**的情况下开工的 —— 代价是"两件大改动同时在线"的排查难度；
> 收益是出站结构一次收口（不会出现"S1/S3 的表象已经稳定、但出站目标还在按会话键推"的中间态）。
> 如果之后出现投递类故障，**先怀疑两者叠加**，再按 §7 的证据链逐层排查。

**目标**：从结构上消除渠道串味（E5/E6），让"这条回复去哪个通道"由**通道对象**决定，不由会话键字符串推导。

**改动范围（分五步提交，每步可独立回滚）**

- 新增 `src/delivery-target.mjs`：`CHANNELS = ['qq-group','qq-private','game','console']`；`resolveTarget({channel, target})` 做格式与归属校验；非法 → 抛错（不静默降级）
- `src/bridge.mjs`：出站统一成 `deliver({ channel, target, text, opts })`；所有调用点改造
- 会话存储 / `#mirror` / `#recordCorpus`：增加 `channel` 字段
- 跨通道投递：独立能力 + 开关 + 白名单，**不是** `deliver` 的参数分支

**步骤**

- [x] S5a `delivery-target.mjs`（纯函数）+ 单测（**46 项**）：`qq:100000001` 不合法、`game:mc-main` 合法、空 channel 抛错

      而"还有没有地方在按 kind 发"由一条源码级检查钉住，见 §7.6）
- [x] S5c 调用点切换：正文 / 表情 / 表情包 / 中间态 / 提醒（`#safeSend`）/ 定时任务 / 服务器事件 /

- [x] S5e 跨通道能力单独成项（`delivery.crossChannel.*`：开关默认关 + 白名单 + **三连校验**：

**验收（`mocks/verify-channel-delivery.mjs`，40 项）**

- [x] C1 回归 E6：游戏内说话 → 只出现在游戏通道，QQ 私聊**零投递**（常驻回归，不是一次性验证）

## 7. 落地实录（2026-10-18）

### 7.1 §1 证据核对结果

E1–E6 **全部成立**（开工前逐行读过）：
`SendQueue.check/markSent` 的读写仍隔着一次网络往返；投递循环仍是
`check → 睡 → 复检 → 发送 → markSent`；丢弃仍只有 `log + continue`；
`#safeSend` 仍 `onebot.send` + `markSent(裸文本)`；出站签名仍是 `(kind, peerId, text)`。

### 7.2 与表单的三处差异（都是有意为之，逐条说明）

| # | 表单写的 | 实际做的 | 为什么 |
|---|---|---|---|
| 1 | S1.1 "先不删旧路径，双跑对拍" | **没有留旧路径**，改为在测试里用老写法做对照（A2） | 旧路径留着就是一个**可被误用的旁路**（E4 正是这么长出来的）。对拍的目的（"证明链真的有用"）由 A2 达成，而且更硬：它把"去掉链会怎样"变成了**常驻断言** |
| 2 | S3.2 "三个 `continue` 点全挂上" | 实际挂了**正文循环里的丢弃点**（`check` 失败 / 复检失败 / 发送异常 / 超时） | 表情与表情包那两个 `continue` 点**不是"一段正文没发出去"**，回执它们会让模型以为"我说的话丢了"（那是假信息）。如实记下 |
| 3 | S3 "回执带显式前缀便于**终检门**识别" | 前缀有了（`[投递回执]`），但**没有**在终检门里加规则 | 回执只进**提示词**、不进外发正文，终检门看的是**外发文本** —— 加规则属于"改终检门"，而 §4 明确不动它 |

### 7.3 两处**测试自己踩的坑**（写下来免得后人重犯）

1. **A3 读错字段得到"假绿"**：账本形状是 `{version, rows}`，第一版读 `ledger.deliveries`
   → 拿到空数组 → `every(...)` 对空数组恒真 → **断言绿着，其实什么都没验**。
   现在第一步就是断言"账本里有两轮记录"（前提断言），空数组会让它先红。
2. **超时定时器 `unref()` 让 `await` 永不 settle**：第一版给 30s 预算的定时器加了 `unref()`，
   于是事件循环一空 Node 就退出、`await run(...)` 永远不返回（实测报
   `Warning: Detected unsettled top-level await`）。**这个定时器必须能撑住事件循环** ——
   它正是"链被放过"的唯一途径。
3. **陌生人号码撞上机器人自己的号**：C2-1 想验 `#safeSend` 的"只对名单内的人开放"，
   把陌生人写成 `'99999'`、`self_id` 也是 `'99999'` ⇒ 事件在 `handleEvent` 最前面就被判成
   `reason: 'self'` 丢掉，**权限判定根本没进去**，而 `onebot.requests` 是空数组这件事被
   前两条断言（"前提"类）报成了第三条红。**教训**：验"权限拒绝"必须让发言人 ≠ 机器人自己，
   并且先断言"确实走到了权限判定"（日志里要有 `权限判定` 那一行），别让"事件被更早的地方丢掉"
   伪装成"权限逻辑错了"。

### 7.6 一条源码级纪律：出站只剩一个出口

S5 之后 `bridge.mjs` 里 `onebot.send(` 与 `sendQueue.run(` 各只剩**一处**（都在
`#deliverToQqChannel` 里）。这不是靠自觉保持的 —— `mocks/verify-channel-delivery.mjs`
会读源码数这两个调用的出现次数（多于一处就红），因为"某个新功能又自己发了一条"
是这个项目历史上最贵的一类缺陷（旁路 E4 就是这么长出来的）。

### 7.7 S5 抓出来的真 bug：定时任务的账本 `chatKey` 一直是 `undefined:<号码>`

`resolveScheduleTarget()` 返回的是 `{ok, sessionId, chatKey, tier, reason}` —— **没有** `kind / peerId`，
而 `runProactiveTurn()` / `runEventTurn()` 第一行就是 `const kind = target?.kind`。
于是那两个值一直是 `undefined`：投递照常（旧 `#deliver` 里 `onebot.send(undefined, peerId)` 被协议端当成
群消息的兜底撞对了），但**账本里的 `chatKey` 长期是 `undefined:100000001`**。

为什么一直没人发现：账本只被人肉看过、而"发没发出去"看的是 `peerId`。
为什么 S5 一碰就炸：`deliver()` 的**第一件事**就是校验目标 —— `kind=''` 直接抛
"kind「」不认识，无法确定通道"。

修法：`resolveScheduleTarget` 把 `kind / peerId / channel` **一起**返回；
两个回合函数改了兜底（老调用方只给 `chatKey` 时也能拆出 kind/peerId）。

★ 这一条和 §7.3 的 C2 假红是同一类：**"更早的一步把值弄丢了"，而断言落在更晚的一步**。
所以两处的修法都是同一句：**先断言"确实走到了那一步"**。

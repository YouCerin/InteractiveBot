## 1. 三层区分（这张表必须先看懂）

现在项目里"上下文/记忆"混成一团，需求也就说不清。先切开：

| 层 | 是什么 | 谁拥有 | 生命周期 | 我们能改吗 |
|---|---|---|---|---|
| **L-A 会话上下文** | DSH 的 session 消息历史（模型真正看到的那串） | **DSH** | 本进程内，重启即弃（`session-id.mjs`） | ❌ 改不了（SDK 只暴露 3 个方法） |
| **L-B 任务状态** | 当前任务做到哪了、试过什么、下一步 | **桥接** | 任务级（跨轮、跨重启） | ✅ 完全可控 |
| **L-C 长期记忆** | 用户档案 / 领域 / 配方 / 运行记忆 | **桥接** | 永久（带 TTL） | ✅ 完全可控 |

**关键洞察**：
- 需求 2（丢主线）的**根因在 L-A**——DSH 的会话越滚越长，早期内容被挤出或被压缩时，模型就丢了主线。
- 我们**够不到 L-A**，但可以**在 L-A 里放一个锚**：把 L-B 的"当前任务"每轮注入。
  于是不管 L-A 怎么滚动/压缩，**主线始终在提示词里**。这就是需求 2 的解法。
- 需求 1、3、4、5、6、7 全部落在 **L-B / L-C**，是我们可以完全掌控的。

## 2. 数据结构

### 2.1 任务台账 `runtime/tasks/<chatKey>.json`

```jsonc
{
  "taskId": "t-1790416814170-3f2b",
  "chatKey": "group:700000001",
  "goal": "帮群友查克莱德洛这个全屋定制品牌靠不靠谱",   // 一句话目标
  "status": "active",                    // active | done | abandoned | rolled_back
  "startedAt": 1790416814170,
  "updatedAt": 1790417000000,
  "currentStep": 5,                      // 步骤序号（从 1 开始）
  "steps": [
    {
      "n": 1,
      "at": 1790416814170,
      "turn": 5,                          // 对应 DSH 的 turn 号（可回溯）
      "action": "web_search",
      "args": { "queries": ["克莱德洛定制", "克莱德洛 全屋定制 品牌"] },
      "result": "3 条结果，含官网与一篇搜狐文章",
      "outcome": "ok",                    // ok | failed | blocked | superseded
      "learnt": "该品牌有官网，先看官网再找第三方评价",
      "next": "去读那篇搜狐文章"
    }
  ],
  "tried": [                              // ★ 需求 6：试过但没用/被否的方法
    { "approach": "直接搜「克莱德洛」", "why": "重名太多，搜到无关内容", "at": 1790416814170 }
  ],
  "blocked": [                            // 被权限/依赖挡住的
    { "what": "读 D 盘上的合同文件", "why": "越界（沙箱只允许工作区）", "at": 1790416820000 }
  ],
  "mainline": "已在对比官网宣传与第三方评价，下一步读搜狐那篇",
  "checkpoint": {                          // 需求 3 的锚点
    "step": 5,
    "at": 1790417000000,
    "invalidatedAfter": null              // 回退后：>N 的步骤标记为作废
  }
}
```

**`mainline` 是需求 2 的核心**：一句人话写的"当前主线"，
每轮注入，**不依赖 L-A 是否被压缩**。

### 2.2 操作日志 `runtime/oplog/<chatKey>-<yyyy-mm-dd>.jsonl`

**追加式**，一条一行，**由桥接从事件流确定性生成**（不靠模型上报）：

```jsonc
{"at":1790416814170,"turn":5,"step":1,"type":"tool/call","name":"web_search","args":{"queries":["克莱德洛定制"]},"callId":"call_00_4yjE"}
{"at":1790416814300,"turn":5,"step":1,"type":"tool/result","callId":"call_00_4yjE","ok":true,"excerpt":"3 条结果…","bytes":1024}
{"at":1790416815000,"turn":5,"step":2,"type":"approval","toolName":"pwsh","outcome":"unavailable","reason":"越界"}
{"at":1790416816000,"turn":5,"step":3,"type":"assistant","text":"…（给 QQ 的回复）","tokens":1234}
{"at":1790416817000,"turn":5,"step":-1,"type":"turn/end","reason":"completed","usage":{"input":123,"cacheRead":4567,"output":89,"lastContextTokens":98765}}
```

**为什么必须桥接自己记**：
诊断已经证明"让模型报告自己做了什么"这条路不可靠（`0.2.1-memory-diagnosis.md`）。
而**事件流里全都有**——本机实测：

```
35 step/start  35 assistant/message  35 step/end  28 tool/call  28 tool/result
tool/call  → { turn, step, callId, name, arguments }   ← arguments 是 JSON 字符串
turn/end   → { turn, reason: { kind: 'completed' } }
```

⚠️ **现状缺口**：`TurnCollector` 只保存了工具名（`session-bridge.mjs:122`
`this.toolCalls.push({ name, callId })`）—— **`arguments` 和 `tool/result` 全丢了**。
所以"记住自己干过什么"这一条，**当前连原料都没存下来**。这是 M-R1 的第一件事。

### 2.3 配方库 `memory/recipes/<slug>.json`

```jsonc
{
  "id": "search-brand-credibility",
  "trigger": {                            // ★ 需求 7：怎么匹配"同类任务"
    "keywords": ["查品牌", "靠不靠谱", "口碑", "评价", "是不是骗子"],
    "intent": "调研一个不熟悉的品牌/产品是否可信",
    "notWhen": ["已经给了明确结论且用户只是确认"]
  },
  "steps": [                              // 验证过的做法
    "先搜「品牌名 + 官网」确认主体存在",
    "搜「品牌名 + 评价/投诉/黑猫」找第三方",
    "读 2~3 篇第三方（避开官网自述与营销稿）",
    "交叉比对给出结论，并说明证据强弱"
  ],
  "pitfalls": [                           // ★ 试过但没用/踩过的坑
    "直接搜品牌名：重名多，会搜到无关内容",
    "只看官网：都是营销话术，没有判断价值"
  ],
  "verify": "结论里必须至少引用 1 条第三方证据，否则说明证据不足",
  "stats": { "used": 7, "succeeded": 6, "failed": 1, "lastUsedAt": 1790416814170 },
  "confidence": 0.86,                     // 由 succeeded/used 与最近性算出（§5）
  "source": "auto",                       // auto（任务沉淀） | manual（管理员写）
  "createdAt": 1790000000000,
  "updatedAt": 1790416814170,
  "ttl": null                             // 配方默认永不过期，只衰减置信度
}
```

**配方怎么产出**（需求 5"沉淀"）：
任务 `status: done` 后，桥接调一次小模型问"这次的做法值得记成配方吗"。
产出候选 → 与已有配方做去重（相似度 ≥0.85 则**更新**而不是新增）→ 写库。
**失败配方也记**（`succeeded` 不加），因为"这条路走不通"同样有价值。

### 2.4 用户习惯 `memory/members/<chatKey>/<QQ>.json` 的 `habits` 段

复用既有用户档案设计，**新增 `habits`**：

```jsonc
"habits": {
  "language": "中文",                     // 用什么语言回他
  "answerStyle": "要结论先行",             // 回答风格
  "verbosity": "concise",                 // concise | normal | detailed
  "activeHours": [[20, 23]],              // 他通常在什么时段活跃（小时区间）
  "asksFor": ["技术实现细节", "要可运行的命令"],
  "dislikes": ["长篇大论", "答非所问"],
  "updatedAt": 1790416814170,
  "evidence": 6                           // 从几次对话里总结出来的（越多越可信）
}
```

**来源**：回合后抽取时顺带产出（与 §2.3 的配方抽取**同一次调用**，见 §6）。
**注入**：只在"这个人本轮说话了"时注入他的 habits（与其他相关人过滤同一条规则）。

### 2.5 隐私：**双侧独立的硬闸**（需求 12，最高优先级）

**必须是两套，因为它们的失效后果不同**：

| 侧 | 位置 | 拦什么 | 失效后果 |
|---|---|---|---|
| **写入侧** `privacy.screenForStore()` | `memory` 所有写路径 + oplog | 不把隐私**存进磁盘** | 隐私躺在文件里，可能被打包分享、被读进上下文 |
| **输出侧** `privacy.screenForOutput()` | `bridge.mjs` 发送前（`#deliver` 之前） | 不把隐私**发给 QQ** | 隐私泄露给第三方，**不可撤回** |

**要拦什么**（写成"可核对的具体形状"，不写"注意隐私"这种空话）：

| 类别 | 判据 |
|---|---|
| 身份证 | 18 位数字 + 校验位算法（**做校验，不靠位数猜**） |
| 手机号 | 中国大陆 11 位（`1[3-9]xxxxxxxxx`） |
| 银行卡 | 16~19 位数字 + Luhn 校验 |
| 密码/密钥 | `password` / `passwd` / `token` / `api[_-]?key` / `secret` / `sk-` 前缀 + 高熵串 |
| 住址 | 省市区街道门牌的组合模式 |
| 健康/医疗 | 关键词表（病历、诊断、用药、精神科…） |
| 生物特征 | 人脸/指纹/声纹相关表述 |

**判定后的行为**（三档，不是简单的"拒"）：

```
命中 → ① 写入侧：**拒绝落盘**，并写审计（记"拒了一条什么类别"，**不记内容本身**）
            回执告诉模型"这条涉及隐私，我没记"
       ② 输出侧：**拦下不发送**，改为发一句安全话术
            "这条我不方便发出来——里面有隐私信息。"
            并写审计（同上，只记类别）
       ③ 用户明确要求"记住我的手机号"：
            **不存原文**，只存一条指针 "他让我记一个联系方式，我说存在他自己的备忘录里"
```

**⚠️ 已对齐的边界**：

| 标识 | 判定 | 说明 |
|---|---|---|
| **QQ 号** | ✅ **公开标识** | **可存可显示**——档案文件名与主键都用它（内存系统靠它索引，且群内本就可见） |
| 群昵称 / 群名片 | ✅ 公开 | 记忆与显示用 |
| 群号 | ✅ 公开 | 同上 |

> ★ **修订记录**：曾有一版把 QQ 号列为隐私、改用不可逆哈希 `handle` 索引 ——
> **该改动已按用户决定整体回滚**（见 `0.2.1-design-corrections.md` 文首修订记录）。
> 本设计**不引入** `handleOf()` 或 `cache/identity.json`。
> 隐私清单只有七类：身份证 / 手机号 / 银行卡 / 凭据密钥 / 住址 / 健康医疗 / 生物特征。

## 3. "回到第 N 步"——先讲清硬限制

### 3.1 事实：DSH 没有原生回滚

本机实测该会话的**全部事件类型**（35 步）：

```
step/start  step/end  assistant/message  tool/call  tool/result
turn/start  turn/end  user/message  agent/inbox/spliced
request/header  request/context  session  session/title
permission/preset  sandbox/mode  approval/policy  web/...request
```

**零条 `checkpoint` / `fork` / `revert` / `resume` / `rewind`**。
且 `session-id.mjs:13-27` 已记录：SDK 只暴露 `initialize` / `session/prompt` / `shutdown`，**没有 resume**。

**结论**：**"回到第 N 步"不可能做到"撤销 DSH 的会话状态"**。
任何声称做到的实现都是假的。所以这里给一个**诚实且真有用**的定义。

### 3.2 我们的定义：**回退任务台账到步骤 N，并回放第 N 步**

用户真正想要的不是"undo 数据库事务"，而是**"刚才那步走错了，从那里重来"**。所以：

```
输入：step = N
行为：
  ① 把 steps 里 > N 的条目标记 outcome = 'superseded'（**保留，不删**）
     同时写进 `checkpoint.invalidatedAfter = N`
  ② 生成"回退提示"注入下一轮提示词：
       【任务回退】已回到第 N 步。第 N 步是：<action> <args> → <result>
       之后的 N+1..M 步已作废，**不要把它们当成已发生的事实**。
       现在要做的：<重做 / 换方法 / 确认>
  ③ 给三种重做姿势（由调用方指定，默认 replay）：
       replay   —— 重做第 N 步（可能换参数）
       retry    —— 第 N 步失败了，换个方法再试（并把上次失败的 approach 记进 tried）
       abandon  —— 这一步不需要了，直接跳到第 N-1 步之后
  ④ `currentStep = N`，`status` 保持 active
```

### 3.3 三条必须写明的边界

| 边界 | 说明 |
|---|---|
| **DSH 的会话上下文不会回退** | 模型仍然"记得"第 N+1..M 步的内容。所以我们用 ② 的提示词**显式声明它们作废**——这是**唯一的拦截手段**，必须在实现里如实标注，不能号称"清除了" |
| **不撤销副作用** | 已经发出的 QQ 消息、已写入工作区的文件**不会回滚**。回退只针对**任务台账**。UI 必须把这句话显示给管理员 |
| **N 越界怎么办** | `N > currentStep` → 不猜、不静默失败：报"当前任务只到第 M 步"，并列出可用步骤（`AGENT.md` 第 6 条约束） |

### 3.4 谁来触发

| 入口 | 说明 |
|---|---|
| 管理员私聊说"回到第 3 步" | 桥接本地匹配（**不依赖模型**），与记忆关键词触发同一套机制 |
| 控制台「运行记忆」页 | 步骤列表上每步一个「回退到这里」按钮 |
| `--memory task --rollback 3 --inject group:700000001` | CLI |

**未来可选（不在 0.2.1）**：实测 `@deepseek-ai/dsh-session-checkpoint-policy` 存在于
`DSH_HOME/profiles/node_modules/`。若它提供真实的会话检查点，**值得单独取证**能否
做到"连 L-A 一起回退"。但 0.2.1 **不依赖它**——上面这套在没有任何 DSH 支持时也能工作。

## 4. 危险操作前置审查（需求 8）

**先查清一个事实**：桥接**已经有**审批机制——`workspace-write` 自带 `ask` 策略，
而 sdk profile 里**没人能应答审批**，所以越界操作落成 `unavailable`（自动拒绝）**且不卡死对话**
（`AGENT.md:115-117`，明确写了"这是刻意利用的行为，不是缺陷"）。

⚠️ **所以"危险操作前置审查"不能天真地实现成"桥接拦工具调用"**——
那会重复 DSH 已有的机制，还可能把 `unavailable` 的语义搞乱。正确做法是**补两个真实的缺口**：

### 4.1 缺口 A：越界被拒后，模型不知道"为什么"和"能改什么"

现在 `deniedApprovals` 只用来判断"要不要先应一声"（`session-bridge.mjs:140-143`），
**从不喂回给模型**。于是模型会**反复重试同一个越界操作**——这正是"丢主线"的一种。

**做法**：把被拒操作写进**任务台账的 `blocked[]`**，并在下一轮注入：

```
【上一轮被挡住的】
- 读 D 盘上的合同文件 → 越界（沙箱只允许工作区）
  可替代做法：请他先把文件放进工作区，或只描述内容我来分析
阻塞的是：任务目标的一部分
```

### 4.2 缺口 B：**在内**的危险操作没有审查

越界由 DSH 挡；但**工作区内的破坏性操作 DSH 不管**（写在工作区里是"允许的"）。
而桥接手里有 OneBot 连接，**这些能力通过 MCP 暴露给模型**。所以桥接侧要标注风险：

| 风险级 | 例子 | 行为 |
|---|---|---|
| **L4 不可逆且影响他人** | `qq_recall` 撤回消息、`qq_send_group_message` 到非当前会话、`set_group_leave` 退群、`delete_friend` 删好友、`set_group_name` 改群名 | **必须管理员 + 显式确认**，写审计 |
| **L3 工作区内不可逆** | 删除工作区文件、覆盖已有数据文件、`reset` 类操作 | 先备份到 `backups/`，提示用户 |
| **L2 可逆但有成本** | 联网搜索、读大文件、发消息 | 正常放行，记 oplog |
| **L1 只读** | `read` / `glob` / `grep` / `qq_group_history` | 放行 |

`mcp-qq-server.mjs` 已经有一张类似的黑名单（`:60-75`：`set_group_name` / `delete_friend` /
`set_group_leave` 等标了"会改群名""会删好友"）。**我们把它升级成正式的 L4 分级**，
并与 `roster` 的权限段联动（普通用户那一段已经写了"不要用任何方式替 TA 给别人发消息"，
`:213`）。

**审查的动作不是"再问一遍"**，而是：
1. L4 操作在**提示词里明确标注**"这是不可逆的，只在管理员明确要求时做"；
2. 桥接在工具回调里**校验发起人的 `tier`**（`applyMemoryItems` 已有 `tier` 的用法可循）；
3. 每次 L4/L3 操作**写 oplog + 审计**，管理员可查。

## 5. TTL / 衰减 / 冲突（需求 10）

### 5.1 分类 TTL

| 数据 | TTL | 到期行为 |
|---|---|---|
| 任务台账（`done`/`abandoned`） | 24 小时 | 整条移入 `runtime/archive/`（软删，可查） |
| 任务台账（`active`） | 72 小时无更新 | 标记 `stale`，注入时提示"这个任务好像搁置了" |
| 操作日志 | 7 天 | **压缩**：保留 `tool/call` 的名字+结果摘要，丢掉完整 `args`/原文 |
| 配方 | **不删** | 只衰减置信度（§5.2） |
| 用户档案印象 | 无硬 TTL | 按"最近命中"淘汰到 `memory/archive/`（已有设计） |
| 领域 notes | 无硬 TTL | 按 `useful` + 最近性淘汰 |

### 5.2 置信度衰减

```
配方：confidence = base(succeeded/used) × recency(ageDays, halfLife=60天)
      base = (succeeded + 1) / (used + 2)          # 拉普拉斯平滑，0 使用不算满分
      recency = 0.5 ^ (ageDays / 60)
      confidence < 0.3 → 注入时标注"这个做法可能过时了，请验证"
      confidence < 0.15 → 不再自动注入（但仍可检索）
```

**为什么用平滑**：只成功过 1 次就 1.0 会误导；`(s+1)/(u+2)` 让"1 次成功"= 0.67。

### 5.3 冲突处理（三种，分别处理）

| 冲突类型 | 例子 | 裁决 |
|---|---|---|
| **同键冲突** | 两个配方 `trigger` 相似度 ≥0.85 但 `steps` 不同 | **合并 + 保留两条做法并各自计数**；用哪个看 `confidence`。不删任何一条方案 |
| **事实冲突** | "他喜欢简短" vs "他说可以详细点" | **后者优先**（新证据覆盖旧），旧条目标 `supersededBy`，**保留可追溯** |
| **指令冲突** | 两条 `directive` 互相矛盾 | **不自动裁决**——两条都注入并明确标注"这两条指令有冲突"，同时**在控制台高亮告警**。指令冲突必须由人解决 |

**统一原则**：**永不静默删除**。所有裁决都写审计，且旧值可查。

## 6. 抽取调用合并（成本关键）

需求 7（习惯）、需求 5（配方）、需求 12（隐私标记）如果各调一次模型，成本翻三倍。
**所以合并成一次调用**——复用 `0.2.1-memory-prompt-plan.md` §2.6② 的"回合后抽取"，扩展它的输出：

```
触发：每 everyN=5 轮（或任务 status 变成 done 时立即触发一次）
输入：最近 24 条消息 + 当前任务台账摘要
输出（严格 JSON）：
{
  "people": [ { "who": "无忘远霞", "note": "…", "sentiment": "neutral" } ],
  "habits": { "who": "无忘远霞", "language": "中文", "answerStyle": "要结论先行",
              "verbosity": "concise" },                       // ← 需求 4
  "domain": { "name": "视频剪辑", "q": "…", "a": "…" } | null,
  "recipe": { "trigger": {…}, "steps": […], "pitfalls": […],
              "verify": "…" } | null,                          // ← 需求 5
  "tried":  [ { "approach": "…", "why": "…" } ],              // ← 需求 6
  "privacyFlags": [ { "category": "phone", "where": "user message #3" } ]  // ← 需求 12（只报类别与位置，不回传原文）
}
```

**`privacyFlags` 只报"哪里出现了哪一类"，绝不回传原文**——否则这次调用本身就成了泄露通道。

## 7. 提示词注入（需求 2 的落点）

每轮注入的**新增段落**（放在 `0.2.1-memory-prompt-plan.md` §2.10 的 `volatileSuffix` 里，
因为任务状态每轮都在变）：

```
【当前任务】帮群友查克莱德洛这个全屋定制品牌靠不靠谱
  已完成：① 搜到官网与一篇第三方 ② 读了搜狐那篇（结论：证据偏弱）
  当前在第 5 步；主线：已在对比官网宣传与第三方评价，下一步读第二篇第三方
  ⚠️ 第 6~8 步曾作废过一次（你之前试过直接搜品牌名，重名太多）—— 别再重复

【被挡住的】
  - 读 D 盘上的合同文件 → 越界；可替代：请他放进工作区

【可套用的做法】调研品牌可信度（用过 7 次，成功 6 次，置信 0.86）
  ① 先搜「品牌名 + 官网」确认主体存在
  ② 搜「品牌名 + 评价/投诉」找第三方
  ③ 读 2~3 篇第三方，避开营销稿
  坑：只搜品牌名会重名；只看官网没有判断价值
```

**为什么这样就能"不丢主线"**：不管 L-A 滚到多长、被压缩成什么，
**这三段每轮都在**。这是需求 2 的全部答案——**不靠压缩，靠锚点**。

**前缀缓存注意**：这三段都是易变的 → 必须放 `volatileSuffix`，
否则会把 `stablePrefix` 几千 token 的缓存全部打断（QQagent 踩过的坑，见 prompt-pipeline 文档）。

**为什么 M-R0 最先**：需求 12 是**唯一一条"做错了会造成不可撤回后果"**的。
而且它会**改变现有记忆的内容**（现有 `MEMORY.md` 30 条里有工作区路径、开发日志，
可能有需要拦的东西）——越早扫越好。

**与主方案的关系**：

```
0.2.1-memory-prompt-plan.md  M0 体检 → M1' 确定性写入 → M2 用户档案/领域 → M5' 技能系统 → M3 整理 → M1 注入瘦身 → M4 提示词重构

```

两条线**可并行**，唯一的交汇点：
- M-R1 与 M1' **共用**"回合后抽取"这一次调用（§6）
- M-R0 的写入侧闸门要接进 **所有**记忆写路径（含主方案的 `qq_memory_note` 等）
- M-R2 的注入段落放进 M4 的 `volatileSuffix`

**总工期**：主方案 16.5 天 + 运行记忆 15.5 天 ≈ **32 天**（有并行空间，实际约 25~28 天）。

## 11. 先做一次隐私扫描（M-R0 的第一步，只读）

现有 `MEMORY.md` 有 **30 条 / 7605 字节**，是人工手写的开发日志。里面已知包含：

- 工作区路径 `store/`、`tmp/`、`inbox/` 等
- 会话号 `group:700000001`、QQ 号 `100000001`（→ **都是公开标识，保留**）
- 一段"看 QQ 图片的可行链路"的操作描述

**需要判定**：哪些属于"隐私"（按 §2.5 的**七类**：身份证 / 手机号 / 银行卡 /
凭据密钥 / 住址 / 健康医疗 / 生物特征），哪些属于"公开标识"
（**QQ 号 / 群昵称 / 群名片 / 群号**）。
`--memory privacy --scan` 就是干这个的——**先扫，再决定闸门阈值**，
而不是先装闸门然后发现它把正常记忆全拦了。

**扫描范围**：

```
memory/**     记忆库（含 MEMORY.md）        → 目标：七类隐私零命中
runtime/**    运行记忆（任务台账/操作日志）   → 同上
logs/**       日志与审计                    → 同上
```

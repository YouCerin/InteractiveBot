## 一、这一天的四个需求，以及它们各自暴露的真问题

| 用户的话 | 表面是"加功能" | 实际暴露的问题 |
|---|---|---|
| 「能否在会话中验证对话者身份」 | 加身份核实 | **身份核实 ≠ 权限授予**（差点开出一个能把整台机器交出去的洞） |
| 「为什么 bot 显示他无法查询 bot 管理员」 | 提示词措辞 | **真正的名单从来没进过模型上下文** —— 功能做出来了却没法用 |
| 「在聊天框左边也应显示当前聊天的群/人」 | 界面显示 | **已经拿到的信息没有接通**（群名早就拉过，只是没往会话传） |
| 「如何校验他真的能记录记忆」 | 测试方法 | **测试只覆盖了存储层，没覆盖链路**，而链路每一环断了都不报错 |

★ 四个需求的共同点：**都不是"缺功能"，而是"信息/判据在错的位置"**。
这也是这一天所有修复的共同形状。

## 二、逐项：改了什么、为什么、怎么证明

### 1. 身份核实（从协议端查，而不是猜）

**新做**：`onebot.getGroupMemberInfo()`（群名片 + 群内 `role`）、`roster.listFriends()` /
`listGroups()` / `groupNameOf()`（都带缓存、都有超时）、`bridge.#verifyIdentity()`。

结果流向三处：会话镜像（`senderId/senderName/senderRole` + `senders`）、
审计日志（每轮一行）、提示词的来源标注。

**★ 唯一高风险的决定**：群内 `role`（owner/admin/member）**绝不参与权限判定**。
理由写在 `docs/identity-verification.md` §4：按"群管理=满权限"的话，
任何陌生人只要自己建个群、把机器人拉进去、给自己一个群管理，就拿到了
DSH 工作区的**写权限**。用户确认按 `access.adminUsers` 判，群角色只用于显示与留痕。

**四条硬约束**：绝不抛异常 / 显式 2 秒超时 / 查不到就 `verified:false` 且**不编名字** /
缓存 5 分钟且 TTL 到点**重查**。

### 2. "无法查询 bot 管理员" —— 功能做出来了却没法用

**根因取证**：真正的名单 `config.access.adminUsers` **从来没有进过提示词**：
提示词只给相对标签（"对方不是管理员"，谁是 —— 不说）；
`qq_group_members` 返回的 `role` 是**QQ 群角色**；
记忆侧 `FORBIDDEN_PATTERNS` 第一条就硬拦 `/管理员|管理权限|群主|全权|权限等级|admin/`；
`roster.snapshot()` 有 `admins` 数组，但只有测试与配置界面在用。

**修法（用户选最窄方案：只核实"当前正在说话的那个人"）**：权限段开头加一段自解释判据 ——
说明它是系统给的、按当前说话人判、是唯一判据；明确"群主/群管理**不是**你的管理员，
工具查到的 role 同样不是"；给出**现成结论句**；给出能力边界话术；
**禁止**说"我没有查询管理员的功能"、**禁止猜**。
唯一例外：正在说话的人本身就是管理员时，他问名单可以直接说（对主人说"没拿到名单"是假的）。

### 3. 会话名（左边那列）

群名**桥接早就拿到过**（`fetchLists` 里的 `group_name`，配置界面选群用的就是它），
只是从来没往会话传。现在 `listConversations()` 多回 `name` / `nameVerified`，
界面标题显示名字、号码放小字；核实不到就**只显示号码**并标「未核实名称」。
群名也进了来源标注：`[来自 QQ 群 700000002「摸鱼群」，发言人 …]`（**号码仍在**）。

### 4. 记忆可验证性（这一条改出了三个真缺陷）

**新增两个工具**：
* `mocks/verify-memory-roundtrip.mjs`（25 项）—— 全链路：桩 rpc 指定模型回复，
  **文件系统是真的**。覆盖剥离、落盘、回执、下轮注入、分档不串场、回滚、开关关闭。
* `src/memory-inspect.mjs` + `node src/index.mjs --memory` —— 运行时体检（**只读**），
  看此刻记着什么、下一轮注入什么、待消费回执、快照一致性。

**它们当场抓出三个真缺陷**：

| # | 缺陷 | 表现 | 根因 |
|---|---|---|---|
| ① | **关掉记忆后标记不剥离** | 模型写的 `<<<MEMORY fact …>>>` **原样发到 QQ** | 整段剥离都写在 `if (memory.enabled)` 里面 |
| ② | **控制台改记忆会被回滚** | 「我在界面上删了一条，过一会儿它自己又回来了」且不报错 | 控制台的写盘不刷新快照，被判成篡改 |
| ③ | **写了却不会被注入** | `memory/self-unknowns.md` 有 14 条，模型下一轮**读不到** | 它不在注入清单里；工具现在会主动喊出来 |

①②已修：剥离**无条件**执行（只有落盘+回执受开关约束）；控制台保存/删除成功后
**刷新快照基准**（**边界没放松**：模型用 `write` 工具绕过桥接改记忆**照样回滚**）。

## 三、这一天踩到的四个"假失败/假通过"（比功能本身更值得记）

1. **假失败：`verify-onebot` 的配额被提示词长度顶爆。**
   mock 会把整个提示词回显，回复长度正比于提示词长度。加了权威段后每条回复
   从 8 段变 10 段，一轮跑 6 次回复就刚好越过测试里的 `maxPerMinute: 60`，
   最后两轮整批被限频丢掉 —— 表现成"群里没回复"，与真实原因毫无关系。
   **教训：那个数字是提示词长度的函数。**

2. **假失败：断言写成了"整段提示词里不出现某个字符"。**
   我断言"不出现 `「`"，可发言人昵称本身就带 `「」`。
   **教训：断言要盯住被改的那个东西，而不是顺手能匹配上的任何东西。**

3. **假断言：`check(名字, true)`。** 我在两个地方写了恒真的断言（一次是
   "背景说明"，一次是回滚日志）。**恒真的断言比没有断言更坏** —— 它让人以为验过了。

4. **假失败：测试共用一个包根下的工作区。** 崩在中间会留下上一轮的 `MEMORY.md`，
   下一轮被当真实记忆注入，于是"某号码出现在提示词里"这条断言被**残留**弄红。
   已改成每个用例一份干净目录。

还有一次**工具事故**：我用 PowerShell 的 `Set-Content` 改 `PROJECT.json` 里的一个数字，
它按 GBK 重写，把整个文件的中文毁成乱码；`git checkout` 又因
`couldn't create signal pipe, Win32 error 5` 失败过一次。恢复后改用编辑工具重做全部改动。
**教训：这个坑（PS 写 UTF-8 文件）此前已踩过一次，仍然踩了 —— 这类文件一律不用 `Set-Content`。**

## 四、两个"顺序/缓存"坑（都不报错，只静默为空）

1. **会话名必须最后解析。** 第一版写在群成员查询后面，于是私聊那条路径上
   `name` 还是空的（私聊昵称来自**下面**那个好友列表查询）。
   表现是"私聊会话名一直为空"，**不报错**。
2. **身份缓存会让新字段静默为空。** 同会话第二次走缓存短路，而缓存里是
   加字段之前那次的结果。修法：缓存键加版本号（`…:v2`）。
   **教训：凡往缓存对象里加字段，就要动缓存键。**

## 六、机器人的全局记忆也更新了（并说明了为什么不能手改）

`packages/qq-bridge/workspace-qq/MEMORY.md` 追加了"本会话新增能力"一节。
**注意 `workspace-qq/` 是 gitignore 的**（那是 agent 的权限沙箱根，含运行痕迹），
所以这段记忆**不在 git 里** —— 本文才是能进 git 的那份记录。

★ 写入姿势有讲究：`verifyAndRestoreMemory` 的判据是"文件内容 == 快照"，
所以**直接手改 `MEMORY.md` 会被下一次读记忆回滚**。正确姿势是
"写文件 → 刷新 `memory/.snapshots/` → 再自校验一次"。
本次写入后立刻跑了自校验：**被判篡改 = 0、被回滚 = 0**。

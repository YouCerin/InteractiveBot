## 0. 一句话结论

hermes 值得借的**不是它的判定系统**（"该不该回"那套与我们的"触发即必答"直接冲突），
而是**三样确定性的工程件**：

1. **记忆的写侧纪律**（未完成轮次不记 / 定时蒸馏 / supersede 不覆盖）—— 正是我们缺的；
2. **投递前的终检门 + 带内标记**（`[reply:id]` / `[sticker:名]`）—— 成本最低、用户可感最强；
3. **本地语料库 + 中文全文检索**（FTS5 trigram + CJK 短词 LIKE 回退）—— 我们完全没有的一块。

而**记忆专项真正的地基**仍然是用户原需求里的那条：**"记住 X" 必须不依赖模型自觉就能落盘**
（M1' 第 1 项，仍未做）。hermes 的 10 层记忆帮不上这个忙 —— 它同样依赖 LLM 判定。

## 1. 借与不借的总原则

| | 项目 |
|---|---|
| **借** | 确定性机制（状态机、队列、账本、校验、检索、标记协议）；把"模型的强烈建议"降级为"需要复核的信号"；把策略写进**工具描述/配置**而不是散落代码 |
| **不借** | 判定价值观（should_reply / should_exit 整套 prompt）；8 层记忆 + 8 个外部 memory provider；模型/provider 配置向导；巨型单文件；README 声称但源码里不存在的东西 |
| **冲突** | 任何**放开权限**的设计（它的 Dashboard 能启停网关、写 `.env`）；任何**优化掉隐私闸门**的写法；任何**新增运行期依赖**（`node:sqlite` 是内置模块，允许） |

**三条我们的铁律在借鉴时必须先过一遍**（`AGENT.md` §3）：
不写死路径 / `permissionMode` 不得放开 / 失败必须让用户知道 —— 下面每条待做项都标了它触到哪一条。

**另外三处是我们自己的缺口，被这份文档"顺带照出来"的**（读它的 §6/§7 才去查）：

| 缺口 | 证据 | 性质 |
|---|---|---|
| 提示词**承诺了引用能力，但通道不存在** | 任务段里写着"引用回复要用【本次唤醒】/【过去状态】里带 # 的消息 id"，而**这两个段根本不存在**（真机提示词里搜不到）；`onebot.mjs` 发送只有 `[{type:'text'}]`，**没有 reply 段** —— 也就是说机器人**根本不能引用回复** | **说了做不到** → 违反"失败必须让用户知道"的精神，必须修 |

## 3. 记忆专项（用户点名的重点）—— 新增 H1–H4

> 这四条来自 hermes §10，全部是**确定性**的，不需要额外模型调用。

### H1　未完成 / 被取代的轮次要**分类处理**，不能静默丢掉 ★★

- **它的做法**：`completed/interrupted/failed/contract_retry` 时不写记忆（`memory_maintenance.py:94-107`）。
- **我们的现状（真机证据）**：`#runTurn` 里 `token.superseded`（被更新的消息取代）与
  `timedOut/aborted` **直接 `return`**，而那之后才是 `<<<MEMORY>>>` 标记的解析与落盘 ——
  也就是说**这一轮模型提议的记忆全部静默消失**，连"没记上"的回执都没有。
  这正是我们计划里那条一直没修的 **P11**。
- **要做的**（三分类，都要留痕）：
  1. `superseded`（内容仍然有效，只是这轮回复不发）→ **照常解析并落盘**，也照常写回执；
  2. `timedOut/aborted`（真的没产出）→ **不写**，但要在下一轮回执里说明"上一轮没跑完，什么都没记"；
  3. 解析失败 → 已有（回执里说明）。
- **落点**：`src/bridge.mjs`（把标记处理提到早退之前，或把三分类结果传下去）+ `memory-store.mjs` 的回执。
- **触到铁律**：第 6 条（失败必须让用户知道）。**验收**：3 条离线断言（superseded 仍落盘 / 超时不落盘但发回执 / 都有日志）。
- **工作量**：0.5 天。**这个建议第一个做** —— 它同时修掉一个真实缺陷和一条计划欠账。

### H2　定时蒸馏（每小时）★★

- **它的做法**：每小时把"未汇总的会话"蒸馏一次；理由写明"QQ 会话永远不会 `/reset`，不主动蒸馏记忆就冻住"（`memory_maintenance.py:248-278`）。
- **我们的现状**：`memory-consolidate.mjs` 已经写好（幂等、Jaccard≥0.85 合并、不跨分节、备份 + 快照刷新、53 项断言），
  但**只有 CLI 手动触发**（`--memory --compact`）。也就是说：**能力有了，触发器没有。**
- **要做的**：桥接内一个 `unref()` 的定时器（默认 1 小时 + 只在该进程有过活动时跑），
  调 `consolidateMemory`；**只在真的有变更时**记一行日志；单实例锁交给 `process-guard` 已有的机制。
- **落点**：`src/bridge.mjs`（定时器）+ `src/memory-consolidate.mjs`（已有）。
- **触到铁律**：第 6 条（静默失败）—— 失败要记日志；`unref()` 保证不阻止进程退出。
- **验收**：定时器可注入 `now` 的离线断言 ×3；真机看到一次 `[memory] 已整理 N 条`。
- **工作量**：0.5 天。**建议第二个做**（能力已就绪，只差接线）。

### H3　"最后被用上是什么时候"（间隔重复衰减）— ✅ **已按方案 B 完成，见 §18**

- **它的做法**：`recall_strength` 按 `S·R·exp(-0.693·t/S)` 衰减（`long_term.py:199-210`）。
- **我们的现状 & 冲突**：设计决策 **D9 明确写了"只做软删归档，不做强度浮点衰减"**。
  hermes 这条要引入浮点权重 → **与 D9 直接冲突**，所以我不擅自做。
- **两个可选项**（我倾向 B）：
  - **A（维持 D9）**：不做衰减；只补"最后使用时间"，用于**排序**与"长期没被用上的条目"体检提示。
  - **B（折中）**：旁挂 `memory/.usage.json`（条目 hash → `{lastUsedAt, usedCount}`），
    **不改 markdown 的可读性**；注入时按"最近用过"排序，长期未用的**只提示、不自动降权**。
- **为什么要它**：现在记忆条目**只增不减**，且没有任何"哪条真被用上了"的反馈 ——
  注入预算被死条目吃掉，而我们无从知道。
- **落点**：`src/memory-store.mjs`（读记忆时记命中）+ 新的 sidecar 读写；`--memory` 展示"最久没用过的 N 条"。
- **工作量**：1 天（选 B）/ 0.5 天（选 A）。

### H4　纠正用 **supersede** 而不是覆盖（= 计划里的 R10）

- **它的做法**：`store.py:812-881` 用 `supersedes_id` 保留历史。
- **我们的现状**：**已在主线 B 的计划里（R10：事实冲突 → 新证据覆盖旧、旧条目 `supersededBy` 可查、不删除），但未做。**
  hermes 这条的价值是给了**具体形态**（旧条目留痕 + 指向关系），而不是新需求。
- **要做的**：`memory` 的 markdown 条目在被新事实取代时追加一行
  `（此条已被更正：<新条目摘要>｜<日期>）`，并保留原条目（**不删**）；
  `memory-consolidate.mjs` 认这个标记，合并时**不把被取代的条目当成有效事实**。
- **落点**：`memory-store.mjs`（写入时判定冲突）+ `memory-consolidate.mjs`（合并时跳过/降级）。
- **工作量**：1 天。**验收**：R10 的断言（旧条目 `supersededBy` 可查、不删除、注入里不出现被推翻的结论）。

> **H4 与 H1/H2 的关系**：H1/H2 是"什么时候写、什么时候整理"，H4 是"写的时候怎么处理冲突"。三条合起来
> 正好补齐**写侧生命周期**，而它们都用不上额外模型调用。

## 4. 非记忆但 ROI 高的 —— 新增 H5–H10

### H5　投递前终检门 ★★（成本最低、用户可感最强）

- **它的四个动作**（`adapter.py:3732-3765`、`:3791-3931`）：① 内部泄漏过滤（工具 JSON、系统占位符、`/stop` 类注入）
  ② `[reply:ID]` 存在性校验 ③ 剥离 `（…）` 动作旁白与手写 CQ 码 ④ 超长 markdown 汇报**回炉改写**成人设口吻。
- **我们的现状**：`humanize.mjs` 管分条/延迟/去重，`markdownToPlain` 管格式，**没有任何"泄漏过滤"**；
  模型若把内部文本说漏，会**原样发给用户**。
- **要做的（按性价比排序）**：
  1. **内部泄漏过滤**（纯函数 + 表驱动，命中就丢该段/整条并记日志）——**最该先做**；
  2. 剥离 `（…）` 旁白与手写 CQ 码（我们已有 `text.mjs` 清洗基础）；
  3. 多行**逐行 0.6s** 节奏（我们已有分条发送，只需把间隔从"整段延迟"细化到"行间"）。
- **落点**：新增 `src/delivery-gate.mjs`（纯函数）+ `bridge.mjs` 的 `#deliver` 前调用 + 测试。
- **工作量**：1 天。**验收**：构造 8 种泄漏文本全部被拦；正常文本一字不改（防误杀）。

### H6　带内标记 `[reply:id]` / `[sticker:名]` ★★

- **它的做法**：`[QUIET]/[SILENT]` 状态标记 + `[reply:ID]` + `[sticker:名]`；
  **投递前剥离**；**只有标记没有正文时不投递**；**标记引起的状态迁移只在投递成功后提交**。
- **我们的现状（§2 已查出）**：提示词**已经在承诺**引用（指向不存在的【本次唤醒】段），
  而发送通道里**没有 reply 段**；`replyTo` 字段解析了没人用。
- **要做的**：
  1. 发送侧支持 reply 段（OneBot `reply` message segment），**带存在性校验**（消息必须属于本会话）；
  2. `[reply:ID]` / `[sticker:名字]` 标记：提示词教、投递前剥离、纯标记不发送；
  3. **把任务段里那句指向不存在段的说明改成真的**（要么提供那些段，要么改成"用 `[reply:ID]`"）。
- **落点**：`src/onebot.mjs`（发送段）+ `src/text.mjs`/新增 `src/markers.mjs`（解析）+ `bridge.mjs` + 提示词。
- **工作量**：1.5 天。**验收**：标记不外泄、纯标记不投递、非法 ID 被丢、真机能引用一条消息。

### H7　本地语料库 + 中文全文检索（`src/corpus.mjs`）★★

- **它的做法**：`corpus_messages` 落每条消息 + FTS5 `trigram` + CJK<3 走 `LIKE` + 返回 `[mid:]`/`[reply:]`；
  另有 `corpus_pairs`（触发↔回复↔是否被纠正）与 `groups_registry`（每群灵敏度）。
- **我们的现状**：**完全没有**。只有 NapCat 的实时 `qq_group_history`（拉一次算一次，无检索）。
- **前置条件**：已实测可用（§2）——`node:sqlite` + FTS5 + trigram。
- **要做的（裁到需求子集）**：
  1. `corpus_messages`：`message_id / chat_id / kind / group_id / user_id / sender_name / content_readable /
     at_targets / reply_to_id / is_bot / created_at`（**不存媒体本体**，只存引用）；
  2. 写入点在接入层（`bridge.mjs` 收到事件即落，**幂等**：`message_id` 唯一）；
  3. `search({query, chatId, limit})`：trigram → 命中 0 且含中文 → `LIKE` 回退；query ≤200 字、limit ≤100、preview ≤120 字；
  4. 暴露 **MCP 工具 `qq_search_history`**，返回带 `[mid:]` 的结果，并在描述里**明确禁止编造 ID**（照抄它的诚实约束写法）；
  5. ★ **必须过我们的隐私闸门**：落库前走 `privacy.screenForStore`（七类隐私**不落库**），
     并给 `corpus` 一个 TTL（默认 30 天）+ `--corpus-prune`。**这一条 hermes 没有，是我们必须加的。**
- **落点**：新增 `src/corpus.mjs` + `mcp/mcp-qq-server.mjs`（工具）+ `index.mjs`（CLI）。
- **工作量**：2.5 天。**验收**：中文三字/两字/英文都能检索到；隐私样本**落不进去**；MCP 工具真机可用。

### H8　凭据/端点发现加固（安全项，实际优先级最高）★

- **它的做法**（`config_discovery.py`）：只读明确的本机配置文件、从不写 `.env`、不调 WebUI、不发网络请求；
  `lstat` 拒符号链接；体积/token 长度上限；**只采纳 enabled 且 host 属于 loopback 的服务器**；
  **HTTP 与 WS 若给出不同 token 就放弃猜测**；显式 `self_id` 找不到时**直接返回 None，绝不复用到别的账号**。
- **我们的现状**：`snowluma.mjs` 已有"token 以 SnowLuma 自己的配置为准 + `tokenSource`/`tokenDiffersFromConfig` 可排查"，
  但我们**没有**"两处 token 不一致时拒绝采纳"和"显式 id 找不到就不猜"这两条硬规则。
- **要做的**：把上面 5 条规则补进 `resolveOnebotTokens` / 账号选择；不一致就**明确报错并在体检里显示**（不静默选一个）。
- **工作量**：0.5 天。**验收**：构造"HTTP/WS token 不一致"→ 拒绝；"显式 id 不存在"→ 返回 null 并给出可执行提示。

### H9　传输契约纯函数化 + 幂等 + 断线缺口标记

- **它的做法**：`transport_contract.py`（652 行）把"错误 → 是否可重试"做成**表驱动纯函数**，
  `retryable` 是**一等字段**；投递幂等键 `sha256(session|msgid|chat|reply|text)[:32]`；
  断线重连后**显式插入"⚠ 掉线期间消息丢失"占位**（宁可显式标缺口，也不假装连续）。
- **我们的现状**：`onebot.mjs` 里有重连与错误处理，但"能不能重试"的判断**散在 if 里**；没有幂等键；
  断线后**静默丢消息**（用户无从知道中间漏了）。
- **要做的**：① 抽出 `classifyOneBotError()` 纯函数（表驱动 + `retryable`）+ 离线断言；
  ② 投递幂等键；③ 断线恢复时给会话注入一行"（中间掉线 X 秒，可能有消息没收到）"。
- **工作量**：1.5 天。

### H10　EpisodeState（对话状态机，**规则版**）+ 水位/epoch

- **它的做法**：16 字段对话状态 + `decision_epoch` 双检 + 三个水位（`last_user_seq/last_consumed_seq/last_judged_seq`）；
  `go_quiet ≠ end_episode`；600s 无活动或连续 3 次静默自动脱落。
- **我们的现状**：`task` 台账管的是"**我自己在干什么**"（task-scoped），
  **没有"这段对话聊到哪了"**（conversation-scoped）；并发上已有 `#withLock(chatKey)` + `superseded` 令牌
  （等价于 epoch 的雏形，但没命名成水位，也没有 `open_loops`）。
- **要做的（**不引入语义判定**）**：新增 `src/session-state.mjs`，**纯规则**维护
  `turnCount / currentThread / openLoops / lastSpeakerRole / lastBotMoves`，
  每轮回复后更新、下一轮注入；**不花额外模型调用**（hermes 用 LLM 更新，我们先用规则）。
  同时把 `superseded` 那一套**重命名/补成显式水位**（`lastUserSeq / lastConsumedSeq`），并加断言。
- **风险（必须说清）**：它和 `tasks.mjs` 都在注入"上下文状态"，**很容易变成两套重复的东西**。
  建议边界：`tasks` 说"**我在做什么任务**"，`session-state` 说"**这段对话的走向**"；
  且**两者共用同一次注入渲染**，不各写一套提示词。
- **工作量**：1.5 天。

### 阶段② H2 每小时蒸馏 — ✅ 完成（2026-09-26）

**能力早就写好了，缺的只是"谁来按这个按钮"**：`memory-consolidate.mjs` 的规则版整理（幂等、Jaccard 合并、
不跨分节、备份 + 快照刷新）此前**只能手动跑** `--memory --compact`。

| 做了什么 | 落点 |
|---|---|
| `createConsolidateScheduler`（可注入时钟，离线可测） | `src/memory-consolidate.mjs` |

**三条约束**（都有具体理由，写进了 `AGENT.md`）：
1. **只在空闲时动手**（`isIdle` = 没有在途回合与投递）—— 整理是"读-算-写回"，而写记忆发生在回合结束时，

2. **`unref()`** —— 绝不能因为一个整理定时器拖住进程退出；
3. **只在真的有变更时记日志**（每小时一行"没变化"会把该看的那行埋掉），失败必须留证据，
   间隔有 **5 分钟下限**（防配置成 1ms 打满 CPU）。另：**必须传 `saveSnapshot`**，
   否则下次读记忆会被 `verifyAndRestoreMemory` 把整理结果回滚掉。

**测试**：`verify-memory-consolidate.mjs` 53 → **74 项**（新增 ⑬ 节：真会合并、忙时跳过、

`verify-memory-roundtrip.mjs` 新增 ⑧ 节（**桥接级**：attach 启动 / 忙时跳过 / 真的把重复条目合并了 / close 停掉）。

### 阶段③ H5 投递前终检门 — ✅ 完成（2026-09-26）

新增 `src/delivery-gate.mjs`，接在**隐私闸门之前**（因为它会改文本，而隐私判定必须落在
"最终要发出去的那串字符"上）：

```
模型输出 → markdownToPlain（格式）→ gateDelivery（内部泄漏/脏东西）→ screenForOutput（隐私）→ 分条发送
```

| 类别 | 处理 |
|---|---|
| **整条都是内部产物**：工具调用 JSON、工具结构数组、`<<<MEMORY`（第二道网） | **不发明文**，改发一句**不含任何内部信息**的诚实话术 |
| **只有个别行**：DSH 注入标记、提示词段标题（`【当前任务…`/`【…回执】`）、工具结果包装文案、**沙箱原始报错**、被注入的斜杠命令 | 只删那一行，正文照发 |

**★ 与 hermes 的三处刻意分歧**（都写进了文件头与 `AGENT.md`）：
① 它判成"静默成功"（什么都不发），我们**如实说一句** —— 静默不发在用户看来就是"机器人坏了"（第 6 条铁律）；

**★★ 这一阶段最值钱的产出是一组实测数字**：第一版判据是「更正措辞（含 换成/改成/其实）+ 相似度 ≥ 0.35」，

**差 0.013**，阈值放哪都会错一边：往低调会把「同一主体的另一件事」当成更正

新增 `src/token-discovery.mjs`：**只读、保守、宁可找不到也不猜**。四条门槛照搬参考项目

**★ 一处刻意不照搬**：它的"HTTP 与 WS token 不一致就放弃猜测"在**我们这里会让正常配置失效** ——
我们的两条通道是**同时使用、各用各的凭据**（HTTP 发消息、WS 收事件），
照搬等于把一份完全正常的配置判死。我们保留其精神：**不一致时不静默**（`differsFromConfig` + `why`）。

### ★★★ 这一阶段真正的收获：真机复验时抓到一条**活着的** bug

写完就先在**真机**上跑了一遍发现逻辑（不是只看测试），结果：

```
config.onebot.selfId  = ""                    ← 没写
snowluma/config/ 下有两个账号：
  onebot_100000001.json  (mtime 22:06，**最新**)  token 指纹 ea89b79a / 9d52b6ac  ← **使用者的 QQ**
  onebot_200000001.json  (mtime 昨天 23:56)        token 指纹 22225ecc / f6fabc49  ← **机器人自己**（与 config.json 一致）
旧逻辑（只按 mtime 取最新）→ 挑中**使用者的账号** → 401 + 机器人完全不说话
```

于是判据改成**确定性**的那条：**哪个账号文件的 token 与 `config.json` 一致，就用它**；
都不一致时才退回"最新"，并**大声警告**（列出全部候选 + 让人去写 `onebot.selfId`）；
多个账号用同一组 token → 判为"无法确定"，**不猜**。
**修复后真机复验**：`picked: matched-config:onebot_200000001.json`、`differsFromConfig: false`（修复前是使用者的账号 + `true`）。

启动时也会把凭据来源说清楚（`index.mjs`）：有警告就喊、回退就说明原因、不一致就报出来 ——
**只说来源与原因，绝不打印 token 本身**。

**测试**：新增 `mocks/verify-token-discovery.mjs`（**53 项**，含多账号三种情形与"注入 lstat 覆盖符号链接判据"）。

## 16. 阶段⑧（H9 部分）传输契约 + 幂等键 + 断线缺口 — ✅ 完成（2026-09-26）

新增 `src/transport.mjs`（**纯函数**）：

1. **`classifyTransport()`** —— 表驱动地把失败分成 `config / auth / network / timeout / http / protocol / unknown`，
   **`retryable` 是一等字段**，认证与配置类错误**附带可执行提示**
   （426 那句「端口填反」的提示**逐字保留** —— 它是排查时最有用的一句话）。
   ★ **不认识的错误不猜成「可重试」**：`unknown` + `retryable:false` ——
   猜错方向会把「其实对方已经收到了」的操作**再发一遍**。
2. **`deliveryKey()`** —— `sha256(会话|引用|表情|文本)[:32]`。修掉一个真实缺陷：
   去重键原来是**裸文本**，而 `SendQueue` 是**整个桥接共用**的 →
   **同一句话 8 秒内发给两个不同会话时，第二个会被误判成重复而丢掉**
   （测试里有端到端复现；不传键时仍按文本去重，向后兼容）。
3. **`describeGap()`** —— 断线缺口的显式标注：「**宁可标出缺口，也不假装连续**」。
   `OneBotClient` 在 `close` 时记断开时刻、重连时算时长并派 `gap` 事件；
   桥接存成**一次性**的 `#pendingGap`，下一轮插进提示词的**易变区**、**用过即清**；< 5 秒的抖动不提。

   > 【刚才断线了】事件通道断了约 42 秒，这期间对方发的消息**我们收不到**。……
   > 就说一句「刚掉线了一会儿，可能有消息没收到」并请他再说一遍 —— **不要猜他刚才说了什么**。

   ★ 缺口**进模型上下文**而不是「发一条 QQ 消息告诉他」：后者平白多一条消息（而他可能根本没说活），
   真正的危害是**模型把掉线前后当成连续对话**，然后基于错误前提回答；
   而「编一段对方没说过的话」比「请再说一遍」严重得多。

## 17. 阶段⑧-b H10 会话状态机（规则版 + 水位）— ✅ 完成（2026-09-26）

新增 `src/session-state.mjs`（**纯规则、零模型调用**）。它回答的是**"这段对话聊到哪了"**，
并且与 `tasks.mjs`（任务台账）**是两条轴**，这条边界是本阶段最要紧的交付物：

| | `tasks.mjs`（任务台账） | `session-state.mjs`（本模块） |
|---|---|---|
| 回答的问题 | **"我在做什么任务、做到哪一步"** | **"这段对话的走向"** |
| 粒度 | 任务（一次委托） | 对话（一直持续的那个会话） |
| 跨重启 | ✅ 落盘 | ❌ 只在内存（对话重启后本来就是新的） |
| 防的是 | **重复劳动** | **答非所问与复读** |

1. **为什么不花模型调用**（参考项目 hermes 每轮用一次 LLM 更新 16 字段状态机）：
   ① 本项目**没有直连模型 API 的代码**，每轮走一次 DSH 等于把成本翻倍；
   ② 更要紧的是"聊到哪了"里最有用的那几样**本来就不需要语义** —— 第几个来回、谁在说话、
   上一轮我干了哪几类事、我有没有问了他还没答。
   ★ 因此它**刻意不算"话题"**：规则硬做只会写出一条看起来像话题、其实是"用户上一句话前 20 字"
   的东西，反而误导模型；需要话题时台账的 `goal`（用户原话）已经在提示词里了。
2. **水位（watermark / epoch）** —— 每会话单调递增 `seq`，`lastUserSeq > lastConsumedSeq` = **又来了一条更新的消息**。
   这正是桥接里「旧回合作废（`superseded`）」那套机制的**显式形式**；
   显式化之后它**可以离线测**（此前要验这条路径只能真造两条并发消息）。
3. **注入**（放在**易变区**、没什么可说时**一个字都不写** —— 第 1 轮就是这种情况）：
   【对话走向（不是任务台账 —— 那个说的是"我在做什么"，这里说的是"我们聊到哪了"）】
   + 第几个来回（**报来回数，不报消息条数**）+ "你上一轮动了这些：读文件。**别重复同一类动作**"
   + "⚠️ 你上一轮问了他：「…」—— 他这一轮开口了，**先看他是不是在回答这个**"。
4. **话头判定宁可漏也不误报**：只看**最后一句**是否以问号结尾、且回复 ≤120 字
   —— 长回答里夹一个反问是"讲完了顺口一问"，不是"卡在等他回话"。把每轮都标成"我在等他回答"会让这条提示彻底失效。

★★ **本阶段抓到并修掉两个"只有走完整桥接才暴露得出来"的缺陷**（都留在注释里当教材）：

1. **话头被提前清空**：第一版 `noteUser` 会清掉"悬着的话头"（理由写的是"他一开口就算接上了"），
   可 `noteUser` 跑在**拼提示词之前** —— 于是那句"先看他是不是在回答这个"在真机上**一次也渲染不出来**。
   更糟的是**纯函数测试把这个错误行为固化了下来**，而且那条断言当时**恒真**（话头本来就是空的）。
   现在生命周期由 `noteBot` 决定：每次机器人回话要么写上新问句、要么清空，**恰好活一轮**。
2. **进度按"消息条数"渲染**：原本报 `turnCount`（每条消息都算一轮），第 3 次对话会写成"这是第 5 轮"——
   模型读到会误判"聊了很久"。现在报**来回数**并如实给出两个计数。

**测试**：新增 `mocks/verify-session-state.mjs`（**48 项**，纯函数：分类/话头边界/水位/闲置翻篇/渲染）
+ `verify-memory-roundtrip.mjs` **⑫节**（桥接级：走向段真的进提示词、与任务台账**两条轴同时在场**、
落在**易变区**、话头真的到得了模型眼前、恰好活一轮）。
全量 **1889 项 / 32 套 / 退出码 0**（链上 35 个条目，另有 3 套在受限沙箱里**跳过**，跳过不算通过）。

> **接线级测试的价值再次被证明**：这两个缺陷**纯函数测试一个都抓不到**（第一个甚至被它固化），
> 只有"走完整 Bridge + 读 `rpc.prompts`"能抓到 —— 与阶段⑥那次「任务段从未注入」是同一类。

## 18. 阶段⑨-a H3 记忆使用账本（**方案 B**，用户已拍板）— ✅ 完成（2026-09-27）

新增 `src/memory-usage.mjs` + 侧车 `memory/.usage.json`。**先说边界**：D9 写着「不做强度浮点衰减」，

没有权重、没有强度分、没有自动降权、没有自动归档、没有删除。
`verify-memory-usage.mjs` 里有一条断言直接扫账本文件，出现 `strength/weight/decay/score/priority` 就变红。

**★ 语义只到"被注入"为止**：我们能看到这条记忆**进了上下文**（`lastInjectedAt`），
**看不到**模型依赖了哪条。所以字段名**不叫** `lastUsed` —— 把"进了上下文"说成"被使用"
是一种看起来更聪明的谎话。

**★★ 它真正解决的问题（一个完全静默的失效）**：注入有 25 条上限，而新条目**追加在文件末尾**。
只按文件顺序截就会出现「用户说记住 X → 机器人回好的记住了 → 磁盘上确实有 X →
**而 X 从此再没进过任何一轮上下文**」。所以写入侧（`memory-store.appendEntry`）登记 `writtenAt`，
排序时把"刚写下的"插到最前。

**★ 第一版被测试打回的地方**（记下来，因为"更聪明的排序"在这里是错的）：
第一版让"从没进过上下文的"一律排最前 —— 听起来正是"让饿着的条目有机会"。
实际后果：老条目**每轮抢占头部**、把刚注入的挤下去，同一份记忆**每轮渲染出不同文本**，
把前缀缓存（实测命中 91%~96%）打断。现在的规则是：

| 优先级 | 条件 | 理由 |
|---|---|---|
| ① | 刚写下（`writtenAt` 在 14 天内）且还没进过上下文 | 「记住 X」的最后一步：它必须真的被看到 |
| ② | 进过上下文的，按 `lastInjectedAt` 倒序 | 还活着的条目优先 |
| ③ | 其余（从没进过、也不是刚写下） | 排最后；"谁在被饿着"由体检报出，不靠打乱提示词补救 |
| ④ | 并列 → **文件顺序** | 稳定排序；否则同内容每轮文本都变 |

**"没有数据 ≠ 没被用过"**（同一族错误的第三次）：账本刚部署时是全空的，第一版把工作区里
**65 条**全部报成"从没进过上下文" —— **数字是真的，结论是错的**。现在账本记 `startedAt`，
空账本时明确说「**无法判断**」，并且不列名单。

**测试**：新增 `mocks/verify-memory-usage.mjs`（**54 项**）+ `verify-memory-roundtrip.mjs` 第⑬节
（桥接级：写入侧登记 `writtenAt`、拼完提示词后记"被注入"、账本里没有权重字段）。
CLI：`node src/index.mjs --memory --usage`。

## 20. 阶段⑨-c H17 交付语义（"模型没产出" vs "发送失败"）— ✅ 完成（2026-09-27）

写进 `AGENT.md`「交付语义」一节，并在**代码里把两条路径分开**（原来发送失败会一路抛到
`attach()` 的兜底 catch，只留一行"处理事件时未捕获错误"）：

| 失败 | 处置 | **绝不**做 |
|---|---|---|
| 模型没产出 | 发兜底话术 | **不重跑模型**（成本翻倍，二次采样可能与第一次矛盾） |
| 回合超时/中断 | 发「请再发一次」 | 不重跑；半截内容不发 |
| **发送失败** | `stats.failed++`、`❌ [delivery] 回复没能发出去：…`、`handled:false / reason:'send-failed'`、尽力告知 | **不重发**（分片可能已发一半）、**更不重跑模型** |
| 被更新的消息取代 | 不发回复，但**照常结算记忆**（H1） | 不发过期答案 |

★ **如实写明一处例外**：发送失败时无法用同一条通道解释（通道本身坏了），
那句"请再发一次"只是尽力而为 —— 唯一可靠的痕迹是日志。

★ **为什么不做投递重试**：`SendQueue` 的限流是"延迟"不是"重试"；真正的重试要幂等键 + 投递账本（H15 未做）。
在账本落地前，自动重发的风险（重复内容）大于收益。

**测试**：`verify-memory-roundtrip.mjs` 第⑮节（4 组，共 9 条断言）。★ 写这一节时又踩了一次自己的坑：
第一版断言"`onebot.send` 只被调用一次"，但失败后那句尽力告知**也要走同一个 `onebot.send`** ——
断言把"告知"误判成"重发"。判据必须落到**内容**上（正文几次 / 告知几次），不能只数调用次数。

## 22. 阶段⑨-e H15 投递账本（发送前落账，**但不自动重发**）— ✅ 完成（2026-09-27）

新增 `src/delivery-ledger.mjs` + `runtime/delivery-ledger.json` + `--delivery`。
它的来历是一个**真实事故**：一条已经生成好（模型调用已经花过钱）的回复，因为拟人延迟 116 秒
期间使用者重启了桥接而**永远消失**，日志里只有一行「发送失败」，没人能回答丢的是哪条、给谁的。

| 做什么 | 为什么 |
|---|---|
| **发送前**落账（pending）→ 逐片 `markSent` → `done` | 发完再记一笔的话，崩溃时那一笔永远不存在 |
| 所有者 = **`pid@进程启动时刻`** | pid 会被复用：新进程会把上一个人留下的账当成自己的 → 漏发或重发 |
| 启动时把**别人**留下的 pending **大声报出来** | 真机丢回复时没有任何地方提示过；"可查"与"会被告知"是两回事 |
| ★★ **绝不自动重放** | 崩溃可能发生在"已发出但没标上"那一瞬间，此时**无法区分** → 自动重发会产生**重复回复**，而重复回复比漏一条更糟 |
| 只存每片长度 + 前 40 字 | 审计面越窄越好（与 `memory-audit.mjs` 同一条纪律） |

★ **如实说明边界**：计划里写的是 at-least-once，我们**只做到"落账 + 报告 + 人工决定"**。
这不是省事，而是"发没发出去"在崩溃那一瞬间**原理上不可判定**（分布式投递的经典难题）。

★★ **本阶段最值得记的一次事故（自己踩的）**：`--delivery` 第一版**插在 `--memory` 分支
的 async 块内部** → 直接跑 `--delivery` 时分支不命中，程序**继续往下走真的去启动了一个
新的桥接进程**（进程守护只给了一句"建议先停掉一个"的警告）。修复后把位置纪律写进
`index.mjs` 的注释与 `AGENT.md`：**新增顶层 CLI 命令一律放在 `--memory` 那一段之上，
并且跑一次确认它不会走到启动路径**。这类"参数没命中就继续往下跑"的 bug 极难发现，
因为输出看起来完全正常。

**测试**：新增 `mocks/verify-delivery-ledger.mjs`（**34 项**）+ `verify-memory-roundtrip.mjs`
第⑯节（**桥接级**：把 `onebot.send` 挂住，断言**发送还在进行中时账本里已经有 pending**
—— 这就是"落账在发送之前"；发完 → done；失败 → failed；启动时报告别人的烂账）。

★★ **上线后当场抓到的第二个缺陷（自己写的，值得单独记）**：真机第一次跑 `--delivery` 时，
它把桥接**正在投递**的那条回复报成了"上一次运行没发完"（几百毫秒后那条就 `done` 了）。
根因是 CLI 调 `orphanedDeliveries()` 时**没做存活判定**，于是任何 pending 行都被当成孤儿。
**误导性证据比没有证据更糟** —— 它会让人去翻一个根本不存在的问题。修法：按 pid 存活过滤
（判据**可注入**，与 `token-discovery` 注入 `lstat` 同一个理由），并新增 `inFlightDeliveries()`
把"有进程正在发"如实显示成**正在投递（不是失败）**。这两条都在 `verify-delivery-ledger.mjs` 里有回归锁。

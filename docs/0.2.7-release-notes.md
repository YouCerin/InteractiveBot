# 0.2.7 发布说明：让机器人能"看"视频 + 三处清理

> **一句话**：QQ 里发来的视频现在**接得上**了（直链 → 模型 → 视频识别技能抽帧 → `read_image` 看画面）；
> 顺带把表情包那条链路上几处"看起来在工作、其实不成立"的地方清干净，并把同一个开关在两个地方
> 重复出现的问题收敛成一个。

这一版**没有新功能类型**，只有一条新通道和三块清理。改动最大的一条是"视频"，其余都是
"把已经写好的东西做对"——它们都不报错，只会让人（和模型）对系统做出错误判断。

---

## 1. 用户能看到的

### 1.1 群里发的视频，现在看得懂了（方案 A）

链路：

```
QQ 视频段（SnowLuma 给 { type:'video', data:{ file, url } }，url 是带 rkey 的直链）
   → src/text.mjs 把直链带出来（以前只留 `[视频]` 三个字，地址原地丢弃）
   → src/bridge.mjs 判断"抽帧到底能不能用"（技能开了吗 / QQ 工具总开关开了吗 / 自检过了吗）
   → src/channel-prompt.mjs 在提示词里如实说：有 N 个视频 + 直链 + 该调哪个工具
   → 模型调 video-frames 技能 → 技能自己下载（自带 SSRF 守卫/大小上限/临时文件即删）
   → 帧落进工作区 → 模型 read_image 逐张读
```

**核心不下载视频**，只把直链递出去：真正取视频的那一方（技能里的 `sources.js`）已经有守卫与被测过的实现，
核心再写一份等于多一套要长期维护的下载政策。

**三个前提**（缺一个，提示词里就**不会**出现工具名，而是如实说"含 N 个视频，但当前看不到画面（原因）"）：

1. 「视频识别」技能在控制台里**已启用**；
2. 抽帧**自检通过**（装了 ffmpeg，且**路径填进了设置**或加进了 PATH）；
3. QQ 工具总开关（`mcp.enabled`）开着。

⚠️ 如实交代：**"装了 ffmpeg" ≠ "能用"** —— 技能只查"设置里的路径"与"系统 PATH"两处
（项目纪律：不猜安装位置）。`ffmpeg-…-full_build` 那种包**已经是编译好的成品**，解压后直接用
`bin\ffmpeg.exe`，**没有"再 build 一次"这一步**。

### 1.2 新技能：视频识别（`skills/video-frames/`）

上游 `video-frames` 1.0.0 的 InteractBot 适配版（上游原件逐字留档在 `reference/video-frames-1.0.0/`）。
形态与上游不同：上游是**能力提供者**，本宿主没有那套机制，所以改成**模型可调的工具**
`mcp__skills__video-frames__frames`；产物也不再是 base64（技能工具只能返回文本），而是
**帧落进工作区 + 相对路径 + `read_image`**。

**默认关**（上游默认开）：本宿主不会像上游那样静默退回"只读元信息"，默认开等于默认挂一个
"一用就报依赖缺失"的工具。

### 1.3 表情包：开关只剩一个地方

真机反馈："同一个开关放在 skill 和插件上不合理"。

- **保留登记**：`src/plugins.mjs` 里那条照旧（插件区仍然告诉你它存在、开关在哪、关掉会怎样、即时生效）；
- **去掉第二个控件**：插件卡不再渲染 Switch，改成「去技能卡上开」跳转；
- **接口层也只有一个写入口**：`toggle({type:'plugin', id:'sticker'})` 拒绝（400）——
  与 `list`/`choice` 那两条既有守卫同一条纪律。

### 1.4 名字：视频抽帧 → 视频识别

"抽帧"说的是**手段**（把视频切成一堆图），你要的是**能力**（看懂视频里有什么）；
真机上模型还答出过"我不抽帧"这类偏离问题的回答。
`id` / 目录名 / 工具全名**都不改**（仍是 `video-frames`、`mcp__skills__video-frames__frames`），
所以 `config.skills['video-frames']` 里既有的开关与 ffmpeg 路径**照旧有效**。

## 2. 修掉的三块"静默失效"

这几条都不报错，只会让人或模型对系统做出错误判断 —— 本项目最忌讳的那一类。

| # | 问题 | 症状（真实发生） | 修法 |
|---|---|---|---|
| ① | **缺 ffmpeg 的文案把"没配路径"说成"没找到 ffmpeg"** | 使用者明明装好了（只是没填路径），却以为自己的安装有问题；**模型照这句话在群里说了「这台机器上没装」**——一句假话 | 文案改成说清"**我查了什么**"，并明确"这不代表机器上没装"；工具描述里也补一句"别自己去磁盘上搜 ffmpeg" |
| ② | **卡片读的是装载时的自检快照** | 技能是"启动之后才在控制台打开"的，卡片却一直写「开关没打开」+「暂时用不了」，再也不会变 | 自检改成**现调**（`callSkillAvailable()`），`describeSkill`/`skillStatus`/桥接门控三处共用 |
| ③ | **技能自己的提示词片段在不可用时还在教模型调工具** | 端到端测试抓出来的：提示词同时说"用 xxx 抽帧"和"当前看不到画面" —— 自相矛盾，模型会去调一个必然被拒的工具 | 技能侧 `promptSections()` 自检不过就**不注入**（"提示词里写了的能力必须是真的"） |

顺带清掉的：

- **表情包技能层的 `promptSections()` 是死代码**（宿主调它时不传 `ctx`，恒返回 `[]`），
  而三处注释都说"这几行由技能贡献" —— 与实现相反。函数已删、清单写明 `prompt.source: "none"`、
  注释改成事实；连带删掉零调用方的 `stickerPromptFacts()`。
- **表情包 `session: "required"` 是一句永远无法生效的承诺**（没有工具、也不贡献片段）→ 改成 `none`。
- **`skillStatus` 的重复警告**：同一句在卡片上显示两遍 → 删掉界面里重复渲染的那一块。
- **CLI 的两处误导**：`enabled === null` 的条目（名单类 / 控件在技能卡上）原来一律打成「—（名单类）」→
  现在分开表述，并**照实打出技能卡上的当前状态**。
- **过期文档**：插件表 9 → 11 行、删掉 0.2.3 就已不存在的 `trigger` 行、sticker 行改成
  "本表只登记"；`CONFIG-UI.md` 补上 `skill` 类开关的语义行。
- **删掉劝导话术**："上一个 QQ 号就是因此被处置的"这类**不可操作**的事后叙事，
  从所有面向使用者的地方（控制台二次确认、配置告警、首次使用、配置键说明）移除；
  保留的是可操作的警示（"秒回 + 7×24 在线是行为风控最典型的特征"）。
  事故留档（`docs/implementation-plan.md` §5）**保留**。

## 3. 验证

```bash
cd packages/qq-bridge
npm test                          # 62 套（含新增的 3 套）
node mocks/verify-video-frames.mjs        # 124 项：技能契约/门控/路径收束/SSRF 守卫

node mocks/verify-video-frames-real.mjs   # 14 项：**真 ffmpeg** 端到端（没装/沙箱限制时大声跳过）
```

- **全链 62 套已跑通（退出码 0）**，而且是**放开 spawn**跑的 —— 这一点很重要，见 §5。
- 真 ffmpeg 端到端**已跑通**（本机 `ffmpeg-2026-09-28-git-84779ade26-full_build`）：
  自合成 3 秒测试视频 → 抽 4 帧 → 全部是真 JPEG（`FF D8 FF`）、时间点落在 (5%, 95%)。
- **真机验证过的**：视频段 → 直链 → 提示词 → 模型真的调了抽帧工具 → 失败被如实返回、模型没有编内容。
- **还没验到的**：填好 ffmpeg 路径后的**下载那一步**（rkey 直链能不能直接 GET、抽出的帧能不能被
  `read_image` 读到）。这两格只能在真机上再发一次视频才知道。

## 5. 发布前的最后一轮：两套"一直在跳过"的测试第一次真跑

这一节是本版**最重要的一段记录**，因为它推翻了一个此前一直被当成事实的说法（"全链 62 套全绿"）。

### 5.1 为什么之前"全绿"

`verify-onebot`、`verify-mcp`、`verify-live` 这三套都要**起带管道的子进程**。
受限沙箱里起不了，于是它们按设计**整份跳过**并打印：

```
⏭️  跳过 verify-onebot：本环境不允许启动带管道的子进程（EPERM）。
   这不是"通过" —— 请在正常 Windows 会话里重跑
```

`npm test` 用 `&&` 串联，跳过 = 退出码 0 ⇒ 链条显示"全绿"。
**跳过不是通过**，而"全绿"这个结论把两者混成了一件东西 —— 这就是下面 17 项红的藏身之处。

### 5.2 真跑之后抓到的两类问题

**① 产品问题（1 条，已修）：隐私闸的「生物特征」判据认裸词**

原判据：`/(人脸识别|面部识别|指纹(数据|信息|录入)?|声纹|虹膜|DNA|基因检测|**生物特征**)/`
—— 它把**类别名本身**和裸词都当隐私。后果：

- **我们自己的系统提示词**里有这么一句（`src/memory-store.mjs` 的写入规则）：
  "不要记隐私：…健康医疗信息、生物特征（指纹/人脸/声纹）" → **提示词自己**被判成含隐私；
- 输出侧一拦，发给对方的就是"这条我不方便发出来…"，**整条回复被吞掉**；
- 真机上更常见的撞法是：有人问"指纹锁坏了怎么办"，模型正常回答里出现"指纹"两字 → 回答被吞。

这不是保护，是坏了：命中的是"在聊这个话题"，而不是"在泄露某个人的数据"。
按本项目原有的判据纪律（"要**可核对的具体形状**，不是空话"——凭据那条早就因为同样的原因改成了
"关键词 + 高熵值"），已收紧为只认**数据形态**：`指纹数据/录入/模板/文件`、`声纹样本`、
`虹膜图像`、`人脸·面部 + 识别数据/特征/照片库`、`DNA 检测/样本/报告`、`基因检测`。
`verify-privacy.mjs` 里正例 3 条、反例 3 条（含**提示词里那一整句原文**）当锚点，防止被谁改回去。

**② 套件自身陈旧（16 条，已修）：它们从没跑过，于是慢慢与实现脱节**

| 套件 | 项数 | 症状 | 真正的原因 |
|---|---|---|---|
| `verify-onebot` | 10 | "记忆段没被拼进提示词""人设段缺失""顺序反了""第 2 轮认不出来""拒绝文案不对" | 三类：<br>· **分片时序**：替身回显的提示词被切成 8~10 条发，而用例只等"收到第一条"就取快照 → 提示词**尾部**还没发出来（改成等"这一轮发完"）；<br>· **终检门**：`【长期记忆】` 这类提示词段标题会被投递闸门**整行删掉**（这是刻意的），拿"用户收到的那条"去断言"提示词里有没有记忆段"**必然假红**（改成从原始回复取提示词，并**新增**一条"内部段标题确实被清洗掉"的断言）；<br>· **`#id`**：0.2.7 给来源标注加了可引用消息 id（`#107`），两条正则的字符类没带上 `#` |
| `verify-mcp` | 7 | "拦截 set_group_kick / set_group_ban / …"全红 | 0.2.2 起 `qq_api` 改走**只读白名单**，回绝话术从"禁用了"变成"不在允许清单里"，而断言只认前者。现在**两道闸分别断言**：白名单拦得住（行为），且这些动作**仍在黑名单里**（第二道网的存在性） |

### 5.3 这一轮之后的结论

- 62 套在**能起子进程**的会话里全链退出码 0；
- 但要知道它的**边界**：受限沙箱里那三套仍然是跳过。要复现这次结论，必须在正常 Windows 会话里跑。

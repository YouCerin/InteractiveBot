## 1. 事故经过

| 时间 | 事件 |
|---|---|
| 2026-09-27 02:2x | 为了让 `PROJECT.json` 增加一条 `persona.active` 配置键的说明，用 PowerShell 执行了一条"读进来 → 替换一处 → 写回去"的命令 |
| 同刻 | 命令**看起来成功了**（退出码 0、没有报错），文件从 ~195 KB 变成 ~289 KB |
| 02:2x | 紧接着运行 `node -e "JSON.parse(...)"` 报 `Bad control character in string literal` —— 这才发现文件坏了 |
| 02:2x–02:4x | 定位根因 → 用对照实验确认损伤模型 → 做结构修复（取证） |
| 02:4x | 按使用者决策：`git checkout HEAD` 回退到 0.2.0 清单 + **补登记项**重建 |
| 03:0x | 补上守卫（`verify-text-encoding.mjs`）与纪律（`AGENT.md` §6.6），提交 |

**那条命令**（这是事故的全部原因）：

```powershell
(Get-Content PROJECT.json -Raw) -replace '"assertions": 93', '"assertions": 97' |
  Set-Content PROJECT.json -NoNewline -Encoding UTF8
```

看起来完全无害 —— 它甚至带了 `-Encoding UTF8`。问题出在**读**的那一半：

> PowerShell 5.1 的 `Get-Content` **默认按系统 ANSI 代码页（本机 = GBK/936）解码**，
> 而不是按 UTF-8。于是：UTF-8 文件 → 被当 GBK 解码（中文全变乱码）→
> 再按 UTF-8 写回（乱码被"固化"成真字符 + 补一个 BOM）。
> `-Encoding UTF8` 只作用于**写**，救不了读。

## 2. 损伤模型（对照实验确认，不是推测）

原始文件是 UTF-8（无 BOM）。被按 GBK 读时，字节流**每 2 字节一组**被解码：

| 情形 | GBK 解码结果 | 后果 |
|---|---|---|
| 组内两字节是合法 GBK 双字节 | 一个汉字（或落到 PUA 码位） | **可逆**：按 GBK 编码回去就是原来那 2 字节 |
| 组内两字节非法（前导字节是某个 UTF-8 字符的**最后一字节**，跟随字节是 ASCII `< 0x40` 或 `0x7F`） | 一个 `?` | ★★ **吃掉这两个字节** |

也就是说，**每一处这样的位置**：

1. **丢掉一个 ASCII 字符**（实测大多是被吃掉的 `"`，其次是空格、`*`、数字）；
2. 它前面那个 UTF-8 字符**少了最后一个字节** —— 只剩前 2 字节，
   该字符有 **64 种可能**（同一前 2 字节、最后一字节 0x80–0xBF），**无法精确还原**。

实测 `PROJECT.json` 命中 **3277 处**。举一个真实片段（左：原意，右：坏掉后读到的）：

```
"_关于本文件": [           →   "_关于本文[FFFD]?: [
"这是给 agent（以及人）看"  →   "这是[FFFD]?agent（以及人）看[FFFD]?
```

（`[FFFD]` = 修复工具在那里吐出的 `U+FFFD` 占位；**坏文件里那个位置的真实字节是 `?`（0x3F）**，
这里用记号写是为了不把"替换字符"本身再抄进这份文档。）

（第二行丢的是空格与 `的` 的最后一字节 —— 所以 `的` 变成了另一个字，而"这段话读得通但不对"正是它最难被发现的地方。）

**同一根因的另外两种产物**（都会发生在别的文件上）：

* **UTF-8 BOM**：`Set-Content -Encoding UTF8`（PS 5.1）无条件写 BOM —— 实测坏文件头三个字节是 `EF BB BF`；
* **UTF-16LE**：PowerShell 的 `>` 重定向把输出编码成 UTF-16LE —— 实测头两字节 `FF FE`。

## 3. ★★ 为什么没有任何测试报警

这是整件事里最值得记住的一点：

> 乱码**仍然是合法 JSON**、合法 Markdown、合法 JavaScript 字符串。
> `npm test` 全绿（2200+ 项断言一条没红），机器人照常跑，
> 只有**人去读那几行说明文字**时才会发现"这话怎么读不通"。

所以"注意编码"这种口头纪律等于没有 —— 与本项目一贯的判定一致：
**没有断言盯着的纪律等于不存在**。这次事故的直接产出之一，就是补上那条断言（见 §6）。

## 4. 修复过程（两条路径，以及为什么最后选后者）

### 4.1 第一条路径：结构修复（**当取证用，不是最终答案**）

因为损伤是**确定性**的，可以先把它还原成"能用的文件"：

1. 把坏文件的每个字符按 **GBK 编码回字节**（= 原始字节流，只是丢字节处变成 `0x3F`）；
2. 自己走一遍 UTF-8：遇到**不完整的序列**就说明这里丢过字节 →
   吐一个 `U+FFFD` 占位（**可见、可 grep**，好过悄悄填一个错字），
   再按后一个字节推断被吃掉的 ASCII 字符（后面是 `:` `,` `}` `]` 换行 → 补 `"`；是 `*` → 补 `*`；其余 → 补空格）；
3. 输出"修复件 + 逐处损伤清单"（行/列/上下文/推断字符）。

结果：**修复件 JSON 合法、结构数据完好**（81 个配置键 / 107 个文件说明 / 51 个命令 / 版本号全在，
`verify-manifest` 与 `npm test` 全绿），但**说明文字里留下 3277 处 `U+FFFD`（无法精确还原的汉字）**。

> 结论：这条路**能救结构，救不回文字**。它适合当"取证与对照"，不适合当交付件。

### 4.2 最终选择：git 回退 0.2.0 清单 + 补登记项（使用者决策）

1. `git checkout HEAD -- packages/qq-bridge/PROJECT.json` —— 拿回 git 里那份**干净底本**
   （0.2.0：78 配置键 / 96 文件 / 50 命令）；
2. 以 `node mocks/verify-manifest.mjs` 的报错**当清单**，逐条补齐 0.2.1/0.2.2 的登记项：
   `package.version` → 0.2.2 · `config.keys` 78→80（`persona.active`、`security.allowPrivateImageHosts`，
   并把 `persona.preset`/`custom`/`callerName` 改成"老路径/已搬家"口径）· `directories` +`skills/`、`personas/`
   · `files` 96→109 · `commands` 50→57 · `invariants` +`extensionsAndPersonas`
   · `knownFailureSignatures` +4 · `verificationStatus` 补 0.2.2 验收并**如实记下"说明文字是重建的"**
   · `roadmap` 追加 0.2.2 四条并删掉已完成的 P5；
3. 结果：**0 个 `U+FFFD`**（是一份干净文件，不是"带标记的版本"），契约测试全绿。

**为什么值得重建而不是带着 3277 个占位符交付**：`PROJECT.json` 是**包契约**（给 agent 与人看的），
带占位符的版本会让每一个后来读它的人都在猜"这里原本是什么字"——那是一种长期成本。

### 4.3 同一根因的第二处：pixiv patch 落成了 UTF-16LE

`docs/0.2.2-pixiv-adaptation.patch` 早先是用 PowerShell `>` 写的 → 落成 **UTF-16LE**
（`.patch` 那样存等于废掉：`git apply` 与所有 diff 工具都按 UTF-8 读）。
**内容本身完好**（0 个 `U+FFFD`、31 个 hunk），所以只需**重新落成 UTF-8/LF**，
并与当前 diff 逐字核对一致。

## 5. ★★ 正确的方法（照这个做就不会再犯）

### 5.1 决策表：我要做什么 → 用什么

| 我要做什么 | ✅ 用这个 | 备注 |
|---|---|---|
| 读文件 | 本仓库的文件工具；或 `[System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)` | 需要文本进内存时 |
| 改**一处**字符串 | 文件工具（`edit`）；或 .NET 读→`-replace`→.NET 写 | 这一条如果当初用了，事故不会发生 |
| **整份重写** | 文件工具（`write`）；或 `[System.IO.File]::WriteAllText($p, $s, [System.Text.UTF8Encoding]::new($false))` | `$false` = **不写 BOM** |
| **生成 diff / patch** | `git diff … --output=<file>`（最保真）；或 `cmd /c "git diff … > file"` | 两者都实测逐字节一致（见 §5.2） |
| 从 git 取一份干净文件 | `git checkout <ref> -- <path>`；或 `git show <ref>:<path>` + 上面的写法 | **不要**用 `git show >`（那是 PS 的重定向） |
| 落盘 diff/日志/产物（重定向） | `cmd /c "… > file"`（cmd 的 `>` 是**字节透传**） | ⚠️ PowerShell 的 `>` **会转 UTF-16LE** |
| 批量改多个文件 | 写 Node/PowerShell 脚本，但**读写都显式指定 UTF-8 且不写 BOM** | 脚本本身也要过守卫 |
| 确认自己没弄坏 | `node mocks/verify-text-encoding.mjs`（或整个 `npm test`） | 见 §6 |
| 删除文件 | `unlinkSync`（Node）/ `Remove-Item`（PS） | ⚠️ Node 的 `rmSync(path)` 在 Windows 上有静默失败/崩进程的记录 |

### 5.2 实测证据（本次事故现场跑的对照表，不是抄来的结论）

同一份样本（含中文、`"`、`*`、反引号），四种写法：

| 写法 | 字节数 | 头 4 字节 | 判定 |
|---|---|---|---|
| `.NET WriteAllText` + `UTF8Encoding($false)` | 110 | `7b 22 6e 6f`（`{"no`） | ✅ 正确 |
| ❌ `(Get-Content -Raw) \| Set-Content -Encoding UTF8` | 143 | `ef bb bf 7b` | ❌ **UTF-8 BOM + 中文全乱码** |
| ❌ `Get-Content -Raw > file`（PowerShell 重定向） | 158 | `ff fe 7b 00` | ❌ **UTF-16LE**（26 个 `U+FFFD`、46 个 NUL） |
| `git diff --no-index --output=file` | 30519 | `64 69 66 66`（`diff`） | ✅ 正确 |
| `cmd /c "git diff --no-index … > file"` | 30519 | `64 69 66 66` | ✅ **同样正确**（cmd 的 `>` 不重编码） |
| `cmd /c "git show HEAD:README.md > file"` | 5258 | `23 20 70 72`（`# pr`） | ✅ 正确 |

结论一句话：**危险的是 PowerShell 的读/写/重定向，不是"重定向"这件事本身。**

### 5.3 黑名单（以及它们的典型产物）

| ❌ 不要用 | 产物 | 为什么危险 |
|---|---|---|
| `Get-Content <文件>`（不写 `-Encoding`） | 中文变 GBK 乱码 | PS 5.1 默认按**系统 ANSI** 解码 |
| `Set-Content -Encoding UTF8` | **UTF-8 BOM** + 若上游已是乱码则固化乱码 | 5.1 的 `UTF8` = 带 BOM |
| PowerShell 的 `>` / `>>` | **UTF-16LE** | 输出被重新编码 |
| `Get-Content -Encoding Default`（读 UTF-8 文件） | 乱码 | `Default` = ANSI |
| 直接手抄乱码文本进源码 | 语法错误 | ★ 本次真实趣事：写守卫时手抄乱码样本，**因为乱码里那个被吃掉的 `"`，字符串字面量少了一个引号**，`node --check` 报 `SyntaxError: missing ) after argument list` —— 事故现象会在你想记录它的时候再咬你一次。改用**码点构造**样本 |

## 6. ★★ 守卫：四条判据 + 标定 + 豁免纪律

`packages/qq-bridge/mocks/verify-text-encoding.mjs`（在 `npm test` 链上，**17 项**）：

| # | 判据 | 抓什么 |
|---|---|---|
| ① | 不许 **UTF-16 BOM**（`FF FE` / `FE FF`） | PowerShell `>` 的产物 |
| ② | 不许 **`U+FFFD`** | 解码丢字节的痕迹 |
| ③ | `.md/.mjs/.json/.patch/.txt` 不许误加 **UTF-8 BOM**（`.bat` 历史用法豁免但会打印） | `Set-Content -Encoding UTF8` 的产物 |
| ④ | ★ 不许**成片乱码** | **事故的第一形态** —— 前三条都可能不命中它 |

### ④ 是怎么标定的（不是拍脑袋）

* 特征字集合 = **真实现场文件**（`cache/PROJECT.json.damaged-20260927.json`）里最高频的
  **40 个 CJK 字符**：`锛 涓 銆 鍙 鐨 殑 笉 浠 級 鏈 璇 紝 …`
  —— 它们正是"UTF-8 中文被按 GBK 解码"必然产生的那些字；
* 实测：现场文件命中 **19712 / 67856 个 CJK 字符 = 29.0%**；
  **健康仓库 351 个文件里最高的一个只有 2 个（0.006%）** —— 差 **4800 倍**；
* 判据：`命中数 ≥ 30` **或** `（命中数 ≥ 5 且占比 ≥ 0.5%）`
  → 大文件里只坏几行靠前者抓（健康上限 2，15 倍余量），小文件整份坏掉靠后者抓，
  正当文本里偶尔出现这几个真字（`鏃`/`杩`/`鍚` 各一两次）两条都不命中。

### 守卫自己也必须"验过牙"

* **负对照**（§②，6 条）：把事故的四种形态喂进判据，必须抓得住。
  其中最关键的一条用的是**真实现场原文**（实测 `sig 8/17 = 47%`，且**没有 BOM、没有 U+FFFD**）——
  这条直接证明"只有判据 ④ 能抓住它"；
* **正对照**（3 条）：正常中文 / 含几个特征字的正当文本 / 英文代码 —— **一个都不许误报**；
* **这次写守卫时的真实翻车**（已固化成经验）：
  ① 判据加进全仓库扫描后，**守卫文件自己**被报成乱码（它定义了特征字集合、又内嵌乱码样本）
  → 必须显式豁免并写理由；
  ② 豁免第一版**永远匹配不上**：Windows 上 `path.relative()` 给的是反斜杠，而清单写的是正斜杠
  → 路径必须归一化（否则"豁免看着写了、实际无效"）。

**豁免纪律**（与 `verify-imports.mjs` 的白名单同一套）：每条豁免必须**写清为什么**，
并且有一条断言盯着"条目必须真实存在 + 理由不能是空话"。
当前两条：本文件（故意贴样本示教）、守卫自己（定义判据与样本）。

### 守卫**抓不到**的（如实说）

* **单个字**级别的损坏（比如 ASCII 为主的代码文件里坏了 2–3 个字）—— 判据④要求成片；
  这种情况下 ①②③ 才是主力。**它降低概率，不是保证**。
* **被 gitignore 的目录**（`cache/` `logs/` `dist/` `vendor/` `_release/` `workspace-qq/` `reference/`）
  不在扫描范围 —— 所以**不要把要长期保存的文本只放在 `cache/` 里**（那份取证就是特例：
  它是临时物证，不是要维护的文档）。

## 7. 如果再中招：恢复步骤

1. **先停手**：不要再对同一个文件做任何"写"操作（包括再跑一次那条命令想"改回来"）。
2. **留证据**：把坏文件复制一份到 `cache/`（`PROJECT.json.damaged-<日期>.json`），
   并记下你跑过的那条命令与时间。
3. **判形态**（三个问题）：头两字节是不是 `FF FE`/`FE FF`（UTF-16）？头三字节是不是 `EF BB BF`（BOM）？
   中文是不是成片的怪字/`U+FFFD`（GBK 误解码）？
4. **能回退就回退**：`git log -- <文件>` 找最近一次好的版本 →
   `git checkout <ref> -- <文件>`（**优先这条**：git 里的字节是干净的）。
5. **不能回退才做结构修复**（§4.1）：GBK 逆变换 + `U+FFFD` 占位 + 逐处清单；
   记住这条路**救不回被吃掉的字**，交付前必须让使用者知道。
6. **补齐并核对**：`node mocks/verify-manifest.mjs`（文档/契约一致）+
   `node mocks/verify-text-encoding.mjs` + `npm test`。
7. **收尾**：把这次的具体形态写进守卫的负对照（"验过牙"），
   并在本文件 §9 追加一行 —— 一份不会随事故成长的守卫，迟早会被绕过。

## 8. 一般化：这一类教训（编码之外）

这类事故的族谱是**同一个模式**：**操作"看起来成功了"，但结果已经悄悄不对**。

* `rmSync` 删单个文件：在 Windows 上**静默失败**甚至崩进程（本项目已改 `unlinkSync`）；
* 空字符串被当成 `0`：`Number('')` 是 0，于是"清空输入框"变成"上限 = 1"（已修 + 7 条断言）；
* 提示词里的段落**从来没被注入**：`chatKey` 不在作用域、被空 catch 吞掉（已修 + 接线测试）；
* 模型偷改记忆文件：被篡改检测回滚（有兜底）；
* **编码事故**：文件语法合法、测试全绿，只有人眼能发现。

对应的通用做法，本项目一直在用、这次也一样：

1. **把"看起来成功"变成"有断言的成功"**（守卫 / 接线测试 / 负对照）；
2. **写下来的教训必须可执行**（决策表 + 命令 + 实测字节），不是"注意一下"；
3. **豁免必须有理由**，且理由本身也被断言盯着；
4. **如实标注边界**（这条守卫抓不到什么），否则它会给人虚假的安全感。

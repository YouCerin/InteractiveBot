# 0.2.3 改动记录（插件化：二选一机制 / 投递 / QQ 工具档位 / 唤醒策略）

> **一句话**：把 hermes 那边**可借鉴**的功能做成 qq-bridge 的**内置插件**，冲突的两个功能
> 用**一个键的二选一**表达（界面是一排按钮，hermes 那一侧标「实验性」），
> 独立的拆成独立插件，不独立的合并进同一个插件。
>
> **范围来源**：`docs/plugin-packaging-plan.md`（划分方案）· `docs/plugin-ization-design.md`（逐块取证）
> **不动的两块**（用户明确要求）：**记忆模块**、**提示词模块**（人设段落化）。
> **不动 UI 源码**（用户明确要求）：`config-ui/src/**` 一行没改，界面要求只写进 `CONFIG-UI.md`。

## 2. S3 详解（最大件）

### 2.1 它是什么

`wake.policy` 是**一个键、两个取值**：

* `rule`（默认）= 规则唤醒 = **升级前的行为**：私聊 / 被 @ / 命中关键词 → 必答，一次额外调用都不产生；
* `semantic`（实验性）= **规则先唤醒，再由判定器否决** → 可以沉默。

为什么不做成两个开关：两者回答的是**同一个问题**（这条消息要不要回）。两个独立开关会出现
两种无意义状态 —— 两个都开（两套判据打架）与两个都关（机器人不知道该不该回）。
用一个单值键，则「启动一个自动关掉另一个」是键的**天然语义**，后端**没有任何互斥检查**。

### 2.2 三条边界（都是取证出来的，不是设想）

| # | 边界 | 依据 | 测试怎么钉住它 |
|---|---|---|---|
| ① | 判定器**只做减法** | 规则说"不回"的消息根本走不到它面前 ⇒ 它**没有任何办法让机器人多说一句话** | 群里说一句不命中关键词的话 ⇒ 断言判定器 `calls === 0` |
| ② | 闸门在 **roster 准入之后、`#runTurn` 之前** | ③ 是决定性的：DSH 的 SDK 没有 cancel/abort/steer，进了 `#runTurn` 的那一轮**注定烧完** ⇒ 只有在这里否决才真的省钱。① 防"未授权者烧判定额度"（免费 DoS 面）。② 判定 3~5 秒，放进会话锁里会队头阻塞 | 否决时断言 **`rpc.prompts.length === 0`**（一次 `session/prompt` 都没发）；群不在白名单时断言 `calls === 0` |
| ③ | 私聊与被 @ **不进判定器** | 那是"必答"；让判定器审它既浪费额度，又会让 @ 的响应平白多等几秒 | 两条各断言 `calls === 0` 且照常回复 |

**因此不需要 hermes 那一整套机器**：两级判定窗口、`decision_epoch`、退出闸门、episode 状态机
—— 它们存在的唯一理由是"判定器可以主动发起回复"。只做减法时，"什么时候该闭嘴"退化成
一个**无状态问题**。

规模实测（含注释与测试）：判定器本体 `src/wake-judge.mjs` **255 行**、
桥接侧闸门 `#ensureWakeJudge` / `#wakeContext` / `#wakeGate` **约 150 行**（`bridge.mjs:1271-1417`）
+ 调用点约 30 行（`:1195` 一带）、测试 `mocks/verify-wake.mjs` **428 行**。
移植 hermes 那套（窗口 / epoch / 退出闸门 / episode / continuation）按它自己的代码量估算是
**1000+ 行**，且会引入"机器人主动多说话"这个与既有风控立场冲突的产品变更。

### 2.3 模型通路：复用已有那条，不新造第二条

本项目**没有直连模型 API 的代码**（`src/extract.mjs` 顶部记着）。唯一取证过的"额外一次调用"
通路是**起一个一次性 `dsh --profile headless` 进程**（`runHeadless`，实测 2.8~4.4 秒，
本机 `headless` profile 确实存在）。判定器直接复用它。

为此 `runHeadless` 补了两个参数（默认值不变 ⇒ 抽取那条链路行为一个字没改）：

* `label` —— 报错文案原来硬编码「抽取」，在判定器里会变成误导（"抽取超时"）；
* `signal` —— **真的 `kill()` 子进程**。这比"race 一下就返回"强得多：后者会让被取消的调用
  **照样把 token 烧完**。触发时机：同一会话来了更新的消息（旧判定在回答一个过期的问题）、
  桥接关停。

### 2.4 ⚠️ 一处必须更正的估算（不把估算当结论）

`docs/plugin-ization-design.md` §10.1 论证过"判定比一整轮 agent 便宜一个数量级"。
那个估算的前提是**直连一个小模型** —— 而**那个前提在本项目当时不成立**（一次判定要起
node 进程并完整初始化 harness）。它**可能比一轮简单对话还贵**。

**★ 修法是补上那条通路，不是把估算改小。** 0.2.3 后来加了 `src/model-direct.mjs`
（见 §2.7），于是那句估算**才真的成立**。

**当时**为了不让这个"贵"的前提落地成默认行为，做了三件事（**现在已经不适用了，见 §2.7**）：

* `wake.policy` 默认 `rule` ⇒ **一次判定都不跑**（这一条**保留**）；
* 语义模式下 `wake.judge.shadow` 默认 true ⇒ 只记账、不改行为（**0.2.3 已改为默认 false**）；
* `wake.judge.maxPerHour`（默认 60）是**唯一挡住最坏情况**的东西（**保留**），超了**一律放过**。

### 2.5 纪律（`src/wake-judge.mjs` 顶部逐条写着）

| # | 纪律 | 违反后果 |
|---|---|---|
| 1 | 抛错 / 超时 / 解析失败 / 超预算 / 被取消 ⇒ **一律放过**（fail-open） | 判定器一坏，机器人就变哑巴，**而且没有任何报错** |
| 2 | 接受 `AbortSignal` | 新消息来了旧判定不让路 ⇒ 答非所问 + 白烧一次调用 |
| 3 | **无副作用**：只出结论，绝不自己发送 | 与 `#deliver` / `#inFlight` 打架 |
| 4 | 状态可随时丢弃（除"本小时调用几次"外无状态） | 与"DSH 不能 resume"的现实冲突 |
| 5 | 私聊 / 被 @ 根本不进来 | 浪费额度 + @ 的响应劣化 |
| 6 | 中间产物只进日志，绝不进聊天 | 内部文本泄漏 |

**注入面如实标注**：判定器读的是群里任何人写的原文，其中可能有"忽略上面的规则"这类句子。
提示词里有一段**显式的"资料 ≠ 指令"声明**，换行也被压平（防止靠换行伪造提示词结构）——
但这**不是安全保证**。真正的兜底是：`shadow` 默认开 + 预算上限 + 私聊/@ 不进来。

### 2.6 顺带修掉的一个潜伏缺陷

`src/extensions-service.mjs` 的 `toggle()` 原先只判 `list` / `enum`，对 `choice` 会走到
`setPath(raw, 'wake.policy', enabled)` —— 即**把布尔值写进一个只认字符串的键**。
配置里出现 `"policy": true`，运行期按"不是 semantic"处理 ⇒ **界面显示保存成功、实际什么都没发生**。
这正是本项目最忌讳的"说了做不到"，而且它不会报错。

现在：对 `choice` 一律 **400 + 说出可选取值**，测试断言**盘上一个字节都没写**。

### 2.7 ★★ 补上直连通路（`src/model-direct.mjs`）—— 项目里**第一处主动向外发 HTTP**

**动机**（`recipes.mjs` 与 `extract.mjs` 顶部原来都记着"本项目没有直连模型 API 的代码，
通路待定"）：`headless` 那条路能跑，但它**慢且贵**（起 node 进程 + 完整初始化 harness，
2.8~4.4 秒，还带着整套系统提示词与工具表）。判定器照抄它之后，"便宜一个数量级"
这个设计前提就塌了 —— 而**正确的修法是补通路，不是把估算改小**。

**线协议按 `dsh-llm-deepseek` 的源码逐条核对（不是猜的）**：

| 项 | 值 | 写错的后果 |
|---|---|---|
| 端点 | `${baseURL}/chat/completions`，默认 `https://api.deepseek.com` | **自己加 `/v1` 会 404** |
| 认证 | `authorization: Bearer <key>` | 401 |
| 模型 id | **原样发**（DSH 模型表里的 `id` 就是接口要的 id，无需别名翻译） | 400 Model Not Exist |
| 思考 | `thinking: { type: 'disabled' }` | reasoning 吃掉 `max_tokens`、正文被截断（看起来像"没按格式答"） |
| `response_format` | **不发** | 该适配器不认它 —— 要 JSON 只能靠提示词 + `parseLooseJson` |

★★ **安全规矩：只允许 https，或回环地址的 http。** 理由不是防 SSRF（`baseUrl` 由使用者
自己配，不像 QQ 消息里的图片地址那样由外人控制），而是**别把凭据明文发出去** ——
`Authorization` 头在明文 HTTP 上等于裸奔；回环那个例外留给本地模型服务
（Ollama / LM Studio / vLLM）。

★ **key 不新增配置字段**：复用 `credentials.mjs` 的三处来源（环境变量 → `dsh.apiKey`
→ `$DSH_HOME/.credentials.yaml`）。它们本来就是同一把账号级 key，为判定器再开一个
输入框只会多一处会漂的真值。

★ 纪律：绝不抛、有超时、接受外部 `AbortSignal`（**真的中止请求**）、
**key 不进日志与错误信息**、401/403/404 各有各的话术（含糊成"接口失败"会让人去查网络，
而真相是 key 或路径）。

★ `wake.judge.transport = 'headless'` **保留**，而且是逃生舱不是摆设：
直连那条**没有做代理发现**（Node 的 fetch 默认不认 `HTTP_PROXY`），
而且非 Chat Completions 形状的 provider 也说不了。

**真机探针（2026-09-27，跑了一次真实的极小调用）**：

```
端点 = https://api.deepseek.com · 模型 = deepseek-flash（来自 dsh.model）
key  = sk-***（长度 35，来源：凭据文件 $DSH_HOME/.credentials.yaml）
调用 = ok · status=200 · **ms=1092** · usage={prompt:420, completion:34, total:454}
原文 = {"answer": true, "reason": "消息在群里求助要报错截图，可能是在向机器人或群里人求助，不确定该沉默，倾向回答"}
解析 = answer ✔
```

两点值得记下来：① **约 1 秒**这个说法现在是**实测**的（headless 是 2.8~4.4 秒）；
② 判定器在一句**模棱两可**的话上选了 `answer`，方向是对的（fail-safe）。

**第二个真机探针：闸门在真 Bridge 里的接线**（同一天，另一次极小调用）。
为什么还要跑它：`verify-wake.mjs` 的桥接段注入的是**桩判定器**，所以
`#ensureWakeJudge` 自己（通路 / key / 模型解析、日志、失败兜底）**没有被测过** ——
本项目栽过"纯函数全绿而接线从没通"的坑。用合成群消息（关键词命中、发言人=管理员、
群在白名单）+ **真判定器 + 真模型**驱动一次，`onebot` / `rpc` / 发送全是桩
（**零外部副作用**、不会真的发 QQ 消息）：

```
[wake] 判定器已就绪：policy=semantic · shadow=**关**（判定已生效） · 通路=http
       （https://api.deepseek.com · 模型 deepseek-flash · key 来源 凭据文件 …\.credentials.yaml）
       · timeout=6000ms · 上限 60 次/小时
[wake] 群 700000001 判定=answer（消息直接叫了机器人名字小鲸鱼并在提问，明确指向机器人）541ms
handleEvent → {handled:true, reason:"answered"} · session/prompt 次数 = 1 · stats.wakeJudged=1
```

★ 这条探针同时验到两件事：① **key / 模型 / 端点的解析在桥接里确实接对了**
（那行"判定器已就绪"就是为此打的）；② 判定器在**被直呼其名并提问**时**没有把它拦掉**
（`answer`）—— 这是最要紧的方向（该回却被拦掉才是用户能感知的坏结果）。

### 2.8 ★★ 判定器到底看到了什么（上下文范围），以及一处自查发现的缺陷

用户问："真正触发对话的时候会引入上下文对话记录吗"。**会**，所以这里把范围写死，
并且顺手修掉了一个真实缺陷。

**判定器收到的东西**（`bridge.mjs` 的 `#wakeContext` + `wake-judge.mjs` 的 `buildJudgePrompt`）：

| 给它 | 不给它 |
|---|---|
| **本会话**最近 12 条 `user` / `bot` 消息（每条截断 200 字） | ❌ **模型的内部推理**（`role:'thinking'`） |
| 当前这条消息（截断 200 字） | ❌ 系统提示（`role:'notice'`，如"先应一声"） |
| 机器人可能被叫到的名字、会话类型、发言人 id/昵称、是否 @ 了它 | ❌ 记忆文件 / 任务台账 / 配方库 / 人设正文 / 工具结果 / 技能提示词段 |

★ **范围只限这一个会话**（按 `chatKey`）—— 拿不到"这个人在别的群说过什么"，
与记忆模块的隔离设计一致。
★ 上下文来源是**已有的会话镜像**（`#mirror`，在唤醒判定**之前**就写好），零新增状态；
重启即空，空着也必须正确。

**⚠️ 自查发现的缺陷（已修）**：镜像里其实有**四**种 role，不是三种 ——
`#mirrorThinking` 往**同一个 `messages` 数组**里推 `role:'thinking'`（**模型的内部推理**，
存在镜像里的唯一目的是"只给界面看"），还有 `role:'notice'`。
第一版投影**只取字段、没过滤 role**，于是三件事同时发生：

1. **判定器把模型的内部推理当成"群里某人说的话"读** —— 那段推理里经常直接写着
   "这轮不用插嘴""群里在闲聊"之类的话 ⇒ 等于**让它自己给自己投票**；
2. 身份也是错的：`buildJudgePrompt` 只认 `role === 'bot'`，其余一律标成「某人」；
3. **泄漏面**：那段推理只该给界面看（项目里对它的原话是"绝不发到 QQ"），
   而判定提示词是**发出去**的（0.2.3 起还是直连 HTTP）。

**修法（两层，都是白名单）**：`#wakeContext` 只放 `user` / `bot`；`buildJudgePrompt`
再做一次显式判断。**白名单不是黑名单** —— 以后镜像再长出别的 role（比如工具结果），
默认**不会**被喂给判定器。

**负对照验过牙**（项目纪律："守卫要'验过牙'，不然'全绿'可能只是判据写错了"）：
把两层过滤分别/同时关掉重跑，断言确实变红，报出的正是缺陷原貌：

```
❌ 判定器的 recent 里只有 user / bot 两种 role  —— ["user","thinking","bot","user"]
❌ 内部推理一个字都没有进判定提示词
   —— 某人：这轮是群里闲聊，我不用插嘴（内部推理，不该被任何人读到）
```

**⚠️ 关于"发出去"这件事必须说清的两点**（判定提示词**不过 `privacy.mjs`**）：
`privacy.mjs` 管的是**记忆落盘**与**发给 QQ 的正文**，判定提示词不在这两条路径上。
所以相对"什么都不做"，多出来的是：① 一条**最终被判为沉默**的消息，它的正文**也已经被
发出去过**（只是没回复）；② 机器人自己说过的话会被重发一次。这两点都受
`wake.judge.maxPerHour`（默认 60/小时）约束，而 `wake.policy` / `wake.judge.shadow`
两个开关可以把它整个关掉。
★ 本地那条记录（oplog 的 `type:'wake'` 行）**是过隐私筛的** —— `appendOp` 只筛
`excerpt` 字段，而原文正是放在那里。

### 2.15 ★★ 记忆"注入面"：非 `- ` 开头的行不再隐形（+ 三处读失败不再静默）

**先说性质，免得看混**：这一处（`src/memory-store.mjs`）改的是**记忆模块**，

### 2.14 ★★ 完成影子模式：报表（`src/wake-report.mjs` + `--wake`）

用户要求"完成影子模式"。原先 0.2.3 只做了**记录**（`#wakeGate` 每条判定都往 oplog 写一行），
**报表没做** —— 于是那批结论写进了 `runtime/oplog/<会话>-<天>.jsonl`，却没有任何"汇总给你看"的
入口：想看只能 `--ops` 逐会话翻，而那个渲染是**为回合设计的**（按 `{turn}/{step}` 对齐），
wake 行没有这两个字段，会打成 `t?s?`。设计文档 §10.5 的原话是
**"这个抽样复核是影子模式的全部价值所在"** —— 而它当时不存在。

**报表要回答的不是"拦了多少"，而是"拦得对不对"。** 这个区别决定了整个实现：
判错有两个方向，而**严重性差一个数量级**：

| 判错方向 | 后果 | 影子模式能看见吗 |
|---|---|---|
| 该沉默却回了 | 群里多一句废话 | ✅ 看得见（这正是"本会拦掉"那一栏） |
| **该回却沉默了** | **这件事没有发生 ⇒ 天生不可观测** | ⚠️ 只能靠**人工复核抽样** |

所以核心不是统计，是把「本会拦下」的样本**摊出来**供人逐条复核，再算出**漏回率**。

**三处最容易悄悄错的口径**（错了都不报错，只会给出一个看起来合理的数）：

1. **「本会拦掉」只算 `judged === true`** —— 兜底行的 `verdict` 也是 `answer`，
   但那是"判定失败所以放过"，把它算进来会**虚增**拦截率。
2. **影子行与生效行必须分开** —— 混在一起看，就无法回答"开了会怎样"。
3. **漏回率的分母只算「已复核」** —— 把"还没看"混进分母会让它**凭空变小**，而这是最危险的方向
   （1 miss / 2 reviewed = 50%，不是 1/4 = 25%）。算不出来时写 `—`，**绝不编一个"漏回率 0%"**。

**聚合写成纯函数**（`summarizeWakeOps()` 只吃数组、`now` 可注入、不碰盘）：正因为口径容易错，
它必须是**能离线逐条钉住**的东西 —— `mocks/verify-wake-report.mjs` 76 项断言测的全是口径，
不是"报表好不好看"。

**报表里三件它自己必须说清的事**（都来自实跑时踩到的真实状况）：

1. **实际窗口**（首行 ts ~ 末行 ts），而不是"近 N 天"。oplog 有 **7 天 TTL**
   （`OPLOG_TTL_DAYS`）；用户以为是"近 7 天"，实际可能只剩两天 ——
   而这个差别会直接把"判定器很少沉默"读成结论。
2. **`via` 分布**（模型输出是靠哪一段解析出来的：`json` / `loose` / `scan` / `phrase`）。
   缺这个字段的**早期记录进 `unknown`，不许冒充 `json`** —— 那会把"日志里没有这个字段"
   说成"模型没照格式写"。实测 6 行里就是这样，报表原话是"早期记录没有这个字段"。
3. **`它不省一分钱`** —— 影子模式下判定**照跑照花**，且它**测不出"多回一句"的代价**
   （判据错在放过方向时影子里看不见）。

**人工复核怎么记**：`--wake --ok 1,3 --miss 2,4`，写 `runtime/wake-labels.json`。
标注**按 `ts` 索引**而不是按编号 —— 编号是每次列样本时临时发的，新判定到来就会变；
按编号存会让旧标注**错位到别的消息上**（那比丢标注更坏）。

★ `--wake` 是**只读**的，只有带 `--ok`/`--miss` 的那一半会写盘，且只写这一个文件。
★ 实测（真机数据）：6 行、1 条本会拦掉、1 条兜底、窗口 `09-27 19:36~22:47`。

### 2.13 ★★★ 修「引用回复永远失效」：本机 SnowLuma 的**消息 id 是负数**

从真机日志里抓到的（`logs/bridge.log`，14:19:20 与 14:20:40 各一次）：

```
[bridge] 带内标记：[reply:#-429124262] 不是消息 id（只认数字）→ 已丢弃
```

**根因（拆开看是哪一步挡住的）**：`[reply:#-429124262]` 捕获到的片段是 `#-429124262`，
而 `markers.mjs` **本来就会去掉 `#` 前缀** ⇒ 剩下 `-429124262`，
再撞上 `ID_RE = /^\d{1,20}$/`（**只认非负整数**）⇒ 校验不过 ⇒ 引用被丢弃。

**真正的元凶是那个负号**，不是 `#`：本机 SnowLuma 的 `message_id` **就是负数**
（日志里 `qq_message_detail {"messageId":"-429124262"}` 可佐证）。

**症状为什么很难发现**：机器人**照样回话**，只是永远不引用。而提示词里那三行
"想引用就写 `[reply:…]`"看起来一直有效 —— 这是本项目最不能接受的一类问题
（提示词在承诺一个实际不工作的能力），而且它唯一的痕迹就是日志里那行"已丢弃"。

**修法（形状放宽，校验一点没放宽）**：

| 放宽的 | 说明 |
|---|---|
| 负号 | `ID_RE` → `/^-?\d{1,20}$/`（负 id 是真机常态） |
| `#` 前缀 | 一直支持（提示词给的就是带 `#` 的形式） |
| 引号 / 反引号 | 模型可能按 JSON 习惯写 `[reply:"-1"]` / `` [reply:`#-1`] `` |
| 失败提示的措辞 | 从"只认数字"改成"**只认整数，可带负号与 # 前缀**" —— 否则看日志的人会以为只能写正数 |

**没放宽的**：仍然只认整数形状（`abc` / `#` / `1.5` / `1e5` 一律丢弃并记一行）。
**绝不猜 id** —— 猜错的后果是引用指向空气、甚至指向**别人的会话**；
放宽形状**不等于**放宽校验（新增了一条断言专门钉住"没见过的**负** id 照样被丢掉"）。

**负对照验过牙**：把 `ID_RE` 临时退回"只认非负整数"后重跑，确有 6 项变红，
报出的正是缺陷原貌（`[reply:#-429124262] → replyTo: null`，且那行日志文本原样出现）。

**测试**：`verify-markers.mjs` 35 → **46 项**（新增一整节负数 id + 4 条边界反例）；
`verify-memory-roundtrip.mjs` 131 → **136 项**（新增 ⑩-2b / ⑩-3b —— **走真 Bridge 的接线断言**：
负 id 的引用真的随消息发出去、以及没见过的负 id 照样不带引用）。
★ 为什么必须有桥接级那两条：`#` 前缀、负号、白名单校验分处三个地方
（`markers` / `bridge` 的 `#seenMsgIds` / 提示词渲染），纯函数测试只能覆盖第一处。

**顺带补掉一处不实**：`PROJECT.json` 的总述写着"逐套的数字登记在 `commands[].assertions`"，
而 `verify-markers` / `verify-memory-supersede` / `verify-delivery-gate` **从来没登记进去过**
（只在 prose 里出现过）。已补登记（46 / 50 / 47），并把 prose 里几个漂了的数字按实测改正。

### 2.12 判定输出解析：从"两段"改成"**四段递降，尽量把结论救回来**"

用户指出：「判定输出不是纯 JSON 就整条丢掉」。

**问题**：原来只有两段 —— 严格 JSON + 宽松 JSON（`parseLooseJson`，它要求文本里出现
`{` 或 `[`）。认不出就 `ok:false` ⇒ **fail-open 放过**。而"放过"的代价不是报错：
消息照常回、**行为上看不出任何异常**，但**那一次模型调用白花了**，而且这个功能在
悄悄失效（该沉默的没沉默）。之前会**整条丢掉**的常见形状至少这些：

| 形状 | 例子 | 现在 |
|---|---|---|
| 没有大括号 | `answer: true, reason: 在跟我说话` | ③ 配对扫描救回 |
| 值是数字 | `{"answer": 0}` | ✅ |
| 值是中文 | `{"answer": "否"}` / `{"answer": "是"}` | ✅ |
| 键大小写不同 | `{"Answer": true}` | ✅ |
| 同义键 | `should_reply` / `reply` / `respond` / `decision` / `结论` / `沉默` | ✅ |
| 结论写在散文里 | `应当沉默` | ④ 明确短语救回 |

**修法（四段递降，每段都诚实标注 `via`）**：

1. `json` —— 严格 JSON（唯一"模型照格式写了"的证据）；
2. `loose` —— 宽松修复（裸键裸值 / 代码围栏 / 前后有废话）；
3. `scan` —— **不要求有大括号**：扫 `键 冒号/等号 值` 配对；
4. `phrase` —— 只在正文里**明说了**「应当沉默 / 应当回答」这类话时才用。

★★ **安全线：绝不猜。** 同一段文本里两种结论都出现、或一个都没出现 ⇒ 一律 `ok:false`
（回到 fail-open 放过）。猜错成"沉默"会让一个人永远等不到回复，**而且没有任何提示**。

**★ 顺带把"模型没照格式写"变成可见的**：结论带一个 `via` 一路进 oplog 行；
`via !== 'json'` 时额外打一行日志（含原文前 200 字）。
以前这件事**完全隐形**（救不回来就静默 fail-open、救回来了也没人说），
于是"提示词没被遵守"这个信号永远不会浮出水面，也就永远没人去改提示词。

**★★ 这次改动当场被测试抓出两个真 bug（都是"否定词被吃掉"）**：

| bug | 后果 |
|---|---|
| 短语兜底 `应该回答` 会命中 **`不应该回答`** | 结论正好反了 —— "不该回答"被读成"该回答" |
| 配对扫描不要求"键是一个完整的词"，于是 **`不应该回答: true`** 里的 `应该回答` 被当成键 | 同上 |

两处都补了边界：短语加 `(?<![不非])`；配对**要求键左边不是字母/数字/汉字**
（中文没有词边界，只能用这个近似）。并加了 4 条断言钉住它们（含两条对照，
防止边界修得过严、把 `应该回答` 与 `answer: true` 也一起挡掉）。

**验证**：`verify-wake.mjs` 94 → **122 项**（解析这一段从 14 条扩到 46 条），
`npm test` 49 套 / **2833 项** / 退出码 0。

### 2.10 ★★★ 真机测试暴露的失败：判据建错了维度（已修 + 已复验）

**用户真机测了两句"该沉默"的话，两次都判成 answer。** 日志原话（`logs/bridge.log`）与
oplog 的 `type:'wake'` 行都留着证据：

| 发的 | 判定器说的 | 错在哪 |
|---|---|---|
| `@100000002 小鲸鱼刚说的那个方案我看行` | answer，理由「消息**明确@了机器人**并回应它刚说的方案」 | **它没有 @ 机器人** —— @ 的是 `100000002`。我给了它一个字段 `【是否 @ 了机器人】否`，它**把这个字段忽略了**：文本里确实出现 `@数字`，而我没告诉它**@ 的是谁**、也没告诉它**机器人自己的 QQ 号** |
| `我刚跟小鲸鱼说了，它说四点开会，你们记得改时间` | answer，理由「提到机器人名字小鲸鱼并转述其说法，是在跟机器人**相关的话题**上说话」 | 它**识别对了**（"转述其说法"），却按我给的判据推出了相反结论 |

**根因（是我的错，不是模型的）**：我把"该沉默"定义在**话题维度**上了 ——

> 第一版静默条件 ①：群友之间在互相对话，**与机器人无关**

模型的理解完全合理：**提到「小鲸鱼」＝与机器人有关 ⇒ 不属于① ⇒ 该回**；
再叠上「不能确定就回答 true」，结果就是**永远 answer**。
四点判定全是 answer ⇒ **语义唤醒退化成规则唤醒，只多花了钱**。

**修法（三件事）**：

1. **判据换成收件人维度**：唯一要回答的问题变成「**这句话是说给谁听的**」；
   并显式写明两条反直觉规则 —— **"提到它的名字"本身不构成回答理由**、
   **"话题与它有关"也不构成回答理由**；
2. **补上它当时缺的两样信息**：机器人**自己的 QQ 号**，以及**本次 @ 的到底是谁**
   （结构化给出，并点明"其中**没有**机器人"）。为此给 `renderSegments` 加了 `ats`
   字段 —— 那个数据一直存在，只是没被带出来；
3. **fail-safe 收窄**：从"不能确定就 true"改成"**只在收件人确实判断不出来、且话看起来
   是在找它时**才 true"，并补上两条**真实失败样例**当反例（小模型最有效的修法）。

**★ 复验（真机探针，9 条用例）**：**9/9 命中**，你那两句原句现在都判 `silent`。

**★★ 但复验里我自己错了两次，都值得记下来**（因为它们说明"判据定了之后边界更清楚"）：

| 我原本的期望 | 实际 | 结论 |
|---|---|---|
| `小鲸鱼 哈哈哈哈` → silent（"过场话"） | **answer**：「叫了名字，收件人是机器人」 | ★ **模型对，我错**。"过场话 → 沉默"与"被点名 → 回答"**互相冲突**；"学会沉默"的目的是**不插别人之间的嘴**，不是不理叫它的人（口径与 `#wakeGate` 的"被 @ 直通"一致） |
| `下午三点开会，小鲸鱼你看到的话提醒一下大家` → silent | **answer**：「点名派活」 | ★ **模型对，我错**。它写着"**你**看到的话" |

⇒ 由此在判据里补了一条**显式的冲突裁决**：**「过场话」那条的前提是没有在跟你说话**；
叫了名字就该应一声。**判据之间会互相冲突，冲突必须挑明** —— 否则模型自己选，
行为就不可预期（这正是它第一版判错的同一种毛病：把两条冲突的规则留给模型去调和）。

**★ 新增 `mocks/probe-wake-judge.mjs`（真机探针，不进 `npm test`）**：
`verify-wake.mjs` 只能断言"提示词里有那几条规则"，**证明不了模型会不会照它判** ——
这次就是离线全绿而真机全错。探针会花真钱（每条 400~800 token）且结论非确定，
所以**刻意不进链上**（同 `probe-ui-deadcode.mjs` 的口径），那两句话永久留作回归用例。

| 你看到的行 | 含义 |
|---|---|
| `[wake] 群 … 判定=silent（…）` | 判定器真的否决了 |
| `[wake] 群 … 判定=answer（…）` | 判定器放行 |
| 完全没有 `[wake]` 行但消息被回了 | 直通（@ / 私聊）—— 判定器**没被调用** |
| `[bridge] 群 … 未唤醒（none）` | 规则拦的（没命中关键词） |
| `[wake] 本小时判定次数已达上限（60）` | 超预算，退回规则行为 |
| `[wake] 判定未成功（按放过处理）` | 判定失败但**放过了**（fail-open） |

★ **想先只观察不改行为**：把 `wake.judge.shadow` 设成 `true`（界面「扩展 → 唤醒策略 →
详细设置」，**即时生效**）。那时每句都照常回复，但日志里会多一个 `★影子：本会拦下` 标记。

★ **想复验"判得对不对"**（会花 token，约 0.01 元级）：

## 3. S5 详解：`corpus` 语料库开关

`corpus.enabled`（**新键，默认 `true`**）。★ 默认值是**升级前的行为** —— 语料库从 0.2.1
就一直在跑，0.2.3 只是**给了它一个开关**。加开关的目的是"能看见、能关"，不是顺手收紧。

**开关落在"接线"上，不在模块里**（`corpus.mjs` 本身没有 `enabled` 这个概念）：

| 位置 | 谁在读 |
|---|---|
| 写入侧 | `bridge.mjs` 的 `#recordCorpus` —— **每条消息**都过一遍 |
| 读取侧（桥接内） | `bridge.mjs` 的 `searchHistory` |
| 读取侧（MCP 工具） | `mcp-qq-server.mjs` 的 `runTool` 分派处，用 `readLiveConfig()` **每次调用现读 config.json** |

三处都是**每次使用现读**（键在活配置对象上）⇒ **hot**，取证写在 `src/plugins.mjs` 的 `why` 里。
★ 顺带取证到一件更好的事：`createCorpus()` **不碰磁盘**（`node:sqlite` 与建表都推迟到
第一次真正用）⇒ 关着时是**零 fs 成本**，测试直接断言 `corpus.sqlite` **文件都不产生**。

**两条容易做错的边界**（都有断言盯着）：

1. ★★ MCP 侧关掉时必须回「**被关掉了**」，**绝不能**回「没搜到」——
   后者会被模型转述成"语料库里没有这条记录"，那是一句**谎话**。
   守卫放在 `runTool` 分派那一层（两个入口 `qq_search_history` / `qq_forward_log` 共用），
   而不是在两个实现里各写一遍。
2. **配置读不到时按"开着"处理** —— 方向与 `runSendImage` 那边的保守**相反**。
   理由是这里**只读**：误判成"关"会让模型平白说一句"我搜不了"，误判成"开"最多是照常查一次本地库。

`--corpus` 这个排查命令**不拒绝**（只大声提醒）：关掉的是**采集**，旧数据还在，
而统计/检索/清理这些只读动作正是关掉之后更需要能用的 —— 否则"关掉"就变成了"看不见"。

### 5.1 ★★ 为什么这里**不给**「总断言数」

写这份记录的过程里抓到一件事，值得单独写下来：本文件此前在几处分别写着
**「2778 项 / 49 套」「2856 项 / 49 套」「2200+ 项 / 39 套」「2188 项 / 38 套」**
（以及本轮我一度按旧基数算出的「2932 项 / 50 套」）—— 同一个仓库，同一个时点，**五个不同的数**。

于是逐套实跑核对了一遍（不是估算，是每套真跑一遍读它自己打印的项数）：

| 类别 | 套数 | 说明 |
|---|---|---|
| 自报项数 **与登记一致** | **21** | 合计 **1184 项** —— 这是唯一**被机器核对过**的数字 |
| 自报项数与登记**对不上** | **1** | `verify-text-encoding`：登记 19、实跑 **18** ⇒ 已按实跑改正 |
| **自己根本不报项数** | **20** | 那 20 个登记数字**没有任何机器核对过**（只是人手填的） |
| **连 `commands` 条目都没有** | **8** | 登记制度之前写的套件；本次实测到其中 6 套的项数，但**故意不登记**（理由见下） |

∴ 结论**不是"算一个更准的总数"**，而是**不再发布这个数**：它需要一个没人能复核的求和，
而这个求和正是上面那五个数字的来源。**一个对不上的总数比没有总数更坏 —— 它看起来是取证过的。**

那 8 套里**故意留空**的 2 套：`verify-lifecycle`（本沙箱起不了子进程，只跑了静态防线）
与 `verify-process-guard`（同样起不了子进程，它**提前 return、连汇总都不打印**）。
把这 2 套的"沙箱截断值"当真实值登记进去，就是**把环境限制说成覆盖率**。

## 6. ⚠️ 未验证的部分（如实标注，不含糊）

1. **真实模型判得准不准没有验过** —— 那是模型行为。**直连通路本身已真机验证**
   （§2.7 的探针：HTTP 200 / 1092ms / 输出能解析），但"判得**对**"是另一回事：
   现在 `shadow` 默认 false（判定真的生效），想先观察就把它设成 `true`。
2. ~~判定链路里那次 headless 子进程在受限沙箱里跑不起来~~ —— **已过期**：
   默认通路现在是直连，真机跑通了；`headless` 那条仍只有桩 runner 的证据
   （它是逃生舱，默认不走）。
3. **headless 那条通路没有被真机跑过**（默认走直连 —— 通路由 `wake.judge.apiKey` **推导**，
   没有独立的 transport 开关；不填 key 才落到 headless，所以升级无影响）。
   ★ 0.2.3 删掉了 `wake.judge.transport` 这个显式开关：两个开关必然产生
   "说走直连但没填 key"这种自相矛盾的状态。
4. **`mcp.profile = readonly` 没有真机跑过**（默认 `full`，所以升级无回归；
   但要真收紧必须先解决"它会把 `qq_send_image` 一起藏掉"这件事）。

   实测两次输出分别是 34 与约 40 tokens，离上限很远 —— 说明 300 是安全的，但**没有在坏情况下压测过**。

   本项目自己的结论是"离线测试全绿 ≠ 功能是通的，真实运行一次不能省"。

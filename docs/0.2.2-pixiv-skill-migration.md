## 1. 两份目录的关系

```
reference/pixiv-lookup-1.1.0/          ← 你给我的原件，一个字没动（含它自己的 test/ 与文档）
skills/pixiv-lookup/                   ← 适配版：原件 + 下面 22 处改动 − 1 个删掉的文件
```

**为什么留原件**：适配是"照着某个具体版本改的"。原件在库里，diff 就永远可复算、
可审计、可重新生成；原件不在，这份记录就只能靠信任。

生成/复核 diff：

```bash
cd <仓库根>
git diff --no-index reference/pixiv-lookup-1.1.0/index.js packages/qq-bridge/skills/pixiv-lookup/index.js
git diff --no-index reference/pixiv-lookup-1.1.0/skill.json  packages/qq-bridge/skills/pixiv-lookup/skill.json
# 或者直接用存下来的那份：
git apply --check docs/0.2.2-pixiv-adaptation.patch   # 需要先有 reference/ 原件在工作区
```

## 2. 为什么必须改（先看这个，再看清单）

这个技能是按**另一个宿主**的契约写的（它在文件头自称 "QQ Agent 0.3.1/0.4 扩展规范"）。
InteractBot 与那个宿主有三处**硬差别**，不改就一定坏：

| # | 差别 | 不改的后果 |
|---|---|---|
| 1 | **工具名的拼法不同**。上游是 `pixiv-lookup__search`；InteractBot 里模型看到的是 `mcp__skills__pixiv-lookup__search`（DSH 的 MCP 客户端会加 `mcp__<服务器名>__` 前缀） | 提示词里写着旧名字 ⇒ 模型调一个**不存在**的工具，而且只会说"查不到"（失败得很安静） |
| 2 | **发图工具的名字与形状不同**。上游宿主有 `send_image(url)`；InteractBot 是 `mcp__qq__qq_send_image(url, kind, peerId)`，而且**必须显式带会话** | 发图整条链路悬空；或者模型不带 kind/peerId，被 fail-closed 拒绝 |
| 3 | **界面路径不同**。上游是「设置 → 扩展 / 设置 → 安全」；InteractBot 是「控制台 → 扩展」 | 模型/用户被指向一个不存在的菜单，排查时来回找 |

另外两处是**上游自身的隐患**，顺手一起修掉（都有据）：

| # | 隐患 | 依据 |
|---|---|---|
| 4 | `DEFAULTS.enabled = true` 与清单 `settings.enabled=false` + `enabledByDefault=false` **互相矛盾** | 宿主只拿到显式配置时，插件会把自己当成"已开启"（上游的 `_note_switch` 也承认这一点） |
| 5 | 提示词里教模型 `send_image(url, preview=true)` | 那是上游宿主的"发图前先看一眼"功能；InteractBot 没有这个参数，照写会误导模型 |

### 3.2 `skill.json`（共 6 处）

| # | 改法 | 为什么 |
|---|---|---|
| ⑰ | `"permissions": []` → `{ "net": ["www.pixiv.net","i.pximg.net"], "listen": ["127.0.0.1"], "_说明": … }` | 本规范要求如实声明"会联网到哪、会不会开本机端口"；界面会把它显示给装的人 |
| ⑱ | 新增 `"icon": "🎨"` 与 `"session": "required"` | 图标给界面；`session: required` 让宿主把 `kind`/`peerId` 加进工具入参（否则群聊白名单判定是失效的 —— MCP 调用里没有会话标识） |
| ⑲ | `_note_switch` 文案改成「控制台 → 扩展」，并补一条"开关即时生效、只有装/卸才要重启" | 与 InteractBot 的真实行为一致 |
| ⑳ | `imageBridge` / `bridgeTtlSec` 两个字段的 `description`：「设置 → 安全」→「控制台 → 扩展」；`send_image` → `mcp__qq__qq_send_image` | 这两句会**原样出现在设置表单里** |
| ㉑ | `"prompt": { "sections": [...] }` → `"prompt": { "source": "runtime", "_说明": … }` | 运行期导出的 `promptSections()` 才是唯一来源；两份都留会让同一段话出现两种措辞 |
| ㉒ | `_note_tools_is_metadata` 改写成"工具全名由宿主拼"的说明 | 免得下一个人以为清单里的 id 就是模型看到的名字 |

## 4. 怎么验证（三层，全部可离线跑）

### 4.1 结构与契约（**零外网**）

```bash
cd packages/qq-bridge
node src/index.mjs --extensions      # 技能状态 + 工具全名 + 告警
node mocks/probe-extensions.mjs --enable pixiv-lookup   # 看"提示词里到底会多出什么字"
node mocks/verify-extensions.mjs     # 扩展系统测试（含命名规则与开关语义）
```

`--extensions` 的期望输出（本机实跑）：

```
🎨 pixiv查图插件（pixiv-lookup v1.1.0）⭕ 已关闭
    ⚠️ 这个技能会**在本机开端口**（127.0.0.1）—— 装它之前请确认你知道它在做什么
    工具：mcp__skills__pixiv-lookup__search、mcp__skills__pixiv-lookup__artwork、mcp__skills__pixiv-lookup__ranking
```

`probe-extensions.mjs --enable` 里能直接看到提示词片段（**这就是模型会读到的那段字**），
关键字样是 `mcp__skills__pixiv-lookup__search` 与 `mcp__qq__qq_send_image(url, kind, peerId)`。

### 4.2 MCP 工具面（**零外网**，真子进程）

```bash
cd packages/qq-bridge
node -e "const fs=require('fs');fs.writeFileSync('cache/mcp-skills.probe.json',JSON.stringify({skillsDir:process.cwd()+'/skills',configPath:process.cwd()+'/config.json'},null,2))"
'{ "jsonrpc":"2.0","id":2,"method":"tools/list" }' | node mcp/mcp-skills-server.mjs --config cache/mcp-skills.probe.json
```

期望：`tools[]` 里是 `pixiv-lookup__search/artwork/ranking`（裸名，模型看到的是前面再加 `mcp__skills__`），
每条描述里带【权限】【如实】【来源】三类提示；**关着的时候调用会被当场拒绝**：

```json
{"content":[{"type":"text","text":"「pixiv查图插件」现在是**关闭**状态（管理员在控制台的「扩展」页里关掉了它）。…"}],"isError":true}
```

### 4.3 上游自带的自测（**零外网**，但需要一个可选依赖）

```bash
cd packages/qq-bridge/skills/pixiv-lookup
node test/run-tests.mjs
```

本机实跑结果（如实记录）：**9 节 50 项断言全部通过**，随后在第 10 节
「代理隔离（真实事故回归测试）」**硬失败**：

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'undici'
```

原因：这一节要真实验证"填了代理之后宿主自己的请求不受影响"，而插件的代理支持
依赖 `undici` 的 `ProxyAgent`（Node 内置 fetch 不认 `dispatcher`）。
`undici` 是**可选依赖**（`setup.mjs` 会尝试复制到 `vendor/node_modules`，
缺失时只告警），本机因安装受限没能带上 —— 这台机器上"代理"这条路径**没有验证过**，
如实记在这里。

装上之后即可完整通过：

```bash
cd packages/qq-bridge
npm install undici            # 需要网络
node setup.mjs                # 复制到 vendor/node_modules（并让桥接软链给技能）
node skills/pixiv-lookup/test/run-tests.mjs
```

## 5. 上游发新版本（例如 1.2.0）时怎么办

1. 把新版本解开，**放进 `reference/pixiv-lookup-<新版本>/`**（原件不要改）；
2. 对照本文档 §3 的 22 处改动，逐条在新版本上重做一遍
   （多数是字符串替换，`git diff` 出来的 hunk 可以直接照抄）；
3. 特别检查这四处**最容易漂移**的地方：
   * `DEFAULTS.enabled` 的默认值与清单是否一致；
   * 工具名常量是否又被写死在提示词/描述里（本宿主必须靠注入）；
   * `send_image` 的调用形状（本宿主是 `(url, kind, peerId)`，且**没有** `preview`）；
   * `skill.json` 的 `prompt` 是不是又变回 `sections[]`（两处都写会重复注入）；
4. 重新生成 patch：
   ```bash
   git diff --no-index reference/pixiv-lookup-<新版本>/index.js  packages/qq-bridge/skills/pixiv-lookup/index.js  > docs/0.2.2-pixiv-adaptation.patch
   git diff --no-index reference/pixiv-lookup-<新版本>/skill.json packages/qq-bridge/skills/pixiv-lookup/skill.json >> docs/0.2.2-pixiv-adaptation.patch
   ```
5. 跑 §4 的三层验证；`--extensions` 里工具清单与告警必须干净。

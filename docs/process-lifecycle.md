# 进程与生命周期治理（下一阶段的第一优先级）

> 起因：用户报过两次同一种事故 —— **上一个进程卡住且关不掉，导致 PID / 端口冲突**。
> 本文是对现有代码的审查结果：四个具体缺陷、各自的代码位置与触发场景、修法。
> 审查结论：**当前代码里没有任何"进程治理"机制**（没有 PID 记录、没有单实例锁、
> 没有强杀兜底、没有孤儿回收），所以这类事故只能靠人手动杀进程收场。

---

## 缺陷 1：`shutdown` 没有硬截止，`kill()` 又不等确认 —— 会留下存活的 DSH 子进程

**位置**：`src/index.mjs:513-541`（`shutdown`）、`src/sdk-rpc.mjs:331-348`（`shutdown` / `kill`）

```js
// index.mjs：收尾的最后两步
try { await rpc.shutdown() }        // 最多等 15s 等 DSH 回 shutdown 应答
catch { rpc.kill() }                // 只是发个 kill，不确认它到底死没死
process.exit(0)
```

`kill()` 的实现是 `this.#child.kill()`，**之后完全不检查 `exitCode`**。
在 Windows 上 `child.kill()` 默认走 `TerminateProcess`，通常有效；但当子进程卡在
内核态/驱动调用（sandbox 驱动、sqlite 写锁、文件句柄未释放）时，它可能**杀不动**。
此时桥接自己照常 `process.exit(0)` 退出，**DSH 子进程变成孤儿继续活着**。

它不是无害的：那个孤儿持有工作区（`workspace-qq`）与 DSH 的会话库
（`$DSH_HOME/sessions`）。下一次启动的新桥接会再起一个 DSH 指着同一个工作区 ——
两个 agent 进程写同一份会话/文件，表现是"回复错乱、文件写冲突、时好时坏"，
而且**没有任何一条日志指向"有两个 DSH 在跑"**。

**修法**：
- `kill()` 改成返回 Promise：发 kill 后等 `exit` 事件，超时（约 3s）再上
  `taskkill /PID <pid> /T /F`；并**如实报告**"未能确认子进程退出"。
- `shutdown` 加**硬截止**（例如总预算 20s）：到期即记录一条明确的失败日志并退出，
  绝不无限等待。**"退出慢"可以接受，"退不掉"不可以。**

## 缺陷 2：重启路径是"先起新的，再关旧的"，且端口占用只降级成警告

**位置**：`src/index.mjs:121-132`（`respawnBridge`）、`src/index.mjs:478-487`（`requestRestart`）、
`src/index.mjs:495-506`（端口绑定失败的处理）

```js
requestRestart: () => {
  respawnBridge(log)     // ← 先 spawn 新进程
  shutdown('api-restart')// ← 再关自己
}
```

代码注释里的假设是："端口不会冲突，因为新进程要先初始化 DSH（几秒），
而旧进程第一时间就关了接口"。这个假设在**旧进程收尾变慢**时就不成立，
而旧进程恰恰可能因为"有在途回复（最多等 8s）+ DSH shutdown（最多 15s）"而变慢。
更糟的是端口绑定失败被**降级**了：

```js
catch (error) { log(`⚠️ 配置接口未能启动：${error.message}`); apiServer = null }
```

于是"第二个桥接"会**看起来启动成功**（能连 QQ、能回话），只是控制台界面不可用 ——
而用户看到的界面其实是**第一个进程**的。两个桥接同时从同一个 OneBot 收事件，
同一句话可能被回答两次。这正是"PID 冲突"最典型的现场。

**修法**：
- 顺序反转为**handoff**：旧进程先关掉配置接口（释放端口），再 spawn 新进程，
  最后退出；或者新进程带**启动重试**（端口忙则等 200ms 重试，最多约 10s）。
- 端口占用时**不要静默降级**：至少要打一条 error 级日志并写进 `/api/status`，
  让界面能显示"当前有另一个桥接占着控制台端口"。

## 缺陷 3：没有任何 PID 登记 —— 出事后无法定位，也无法自动回收

**现状**：全仓库没有任何 pidfile / 进程清单。`child.pid` 只出现在日志与
`/api/snowluma/start` 的返回值里（`src/snowluma.mjs:696,702`），**不落盘**。

所以"上一个进程卡住了"这件事发生后：
- 用户不知道 PID 是多少，只能去任务管理器猜哪个 `node.exe`；
- 新进程也不知道有旧进程存在，无法提示或回收；
- `--doctor` 报不出"有多个桥接在跑"。

**修法**：新增 `src/process-guard.mjs`，维护一份进程登记（建议
`cache/processes.json`，该目录已被 gitignore）：

```
启动时：读登记 → 对每条记录用 process.kill(pid, 0) 探活
        → 已死：清掉；活着且属于本包（校验 PID + 启动时间 + 命令行）
        → 活着：**明确报告冲突**（是谁、什么时候启的、占着哪个端口），
                不要静默继续，也不要擅自杀别人的进程
运行时：写入自己的 pid / 启动时间 / profile / 端口
退出时：清掉自己的记录（含被强杀的情况 —— 用探活兜底，不依赖清理一定执行）

⚠️ 必须防 PID 复用：PID 会被系统回收再分配给无关进程，所以判定"这个 PID 还是我那个进程"
   不能只看 PID，要同时看**进程启动时间 + 命令行**（`wmic process where processid=N get
   creationdate,commandline` 或 PowerShell `Get-CimInstance Win32_Process`）。
```

有了它，`--doctor` / `/api/status` 才能回答"现在到底有几个桥接、几个 DSH 在跑"。

## 缺陷 4：SnowLuma 的"防重复启动"依赖探测成功，探测失败就会真的开出第二个实例

**位置**：`src/snowluma.mjs:483-716`（`startSnowluma`），spawn 在 `:680-692`

SnowLuma 是 `detached: true` + `unref()` 启动的（`snowluma.mjs:686,692`）——
这是**有意的**："关掉桥接不该连带杀掉 SnowLuma"。副作用是：它一旦被重复启动，
两个实例会**抢 3000/3001 端口与 QQ 登录态**，而且都不会自己退出。

现有的两道防线（① 探控制台 ② 用我们自己的 token 问 OneBot）设计是对的，
但 **② 依赖调用方传入 `detect`**：`typeof detect !== 'function'` 时整段被静默跳过。
代码里已经因此吃过一次亏（`--snowluma` 那条路漏传 detect），并留了注释与断言；
但"探测本身失败"（超时、控制台端口被改过）仍会掉到最后去 spawn。

**修法**：
- spawn 前增加**"3000/3001 端口是否已被占用"**的独立检查，作为第三条防线 ——
  端口有人应答就**不要启动**，改为提示"检测到已有实例，请确认是不是你要的那份"。
- spawn 后**记录 PID**（进缺陷 3 的登记），并在界面上给出"停止我启动的那个实例"的入口。
  现在 `startSnowluma` 只负责发起，连自己启了哪个 PID 都不留下可操作的痕迹。

## 顺带发现（不属于进程治理，但同一区域，建议一并修）

| 位置 | 问题 | 影响 |
|---|---|---|
| `src/index.mjs:545-549` | `uncaughtException` / `unhandledRejection` **只记日志不退出** | 进程会带着损坏的状态继续跑（可能已丢失半边状态），"卡住但没死"往往就是这么来的。Node 官方建议未捕获异常后**尽快退出**并让外部重启 |
| `src/index.mjs:502-506` | 端口占用只 warn | 见缺陷 2 |
| `src/sdk-rpc.mjs:186-193` | 子进程退出后**没有重启策略** | DSH 挂了以后桥接还活着但不再回话；用户看到的是"能收消息不回"。至少要在界面上显式报"DSH 已退出"并提供重启入口 |
| `src/snowluma.mjs:24` | `detached` 的取舍只写在注释里 | 用户不知道"关掉桥接 SnowLuma 还在跑"，发布说明里应写明（已在 `先读我-首次使用.txt` 提到"两个都要开"，但没讲关闭语义） |

## 建议的落地顺序

1. **缺陷 1 + 2**（都在 `index.mjs` / `sdk-rpc.mjs`，改动小、收益最大）：
   硬截止 + `kill()` 等确认 + 启动重试/握手式重启。做完就能消掉"关不掉"。
2. **缺陷 3**：`process-guard.mjs` + `--doctor` 报告 + `/api/status` 暴露。
   做完才能"看见"冲突，而不是靠猜。
3. **缺陷 4**：端口第三防线 + 记录并展示自己启动的 SnowLuma PID。
4. 顺带那几条（尤其是 `uncaughtException` 的退出策略）。

每一组都要补回归测试（`mocks/verify-*`）：现有的测试体系里已经有
"防重复启动"的断言（`verify-apitest.mjs`），新机制照同样的方式加。

## 1. 这一版解决的三类问题

| # | 以前的样子 | 现在 |
|---|---|---|
| **没有扩展点** | 所有能力都焊在桥接里（`PROJECT.json` 的 roadmap 里挂着"P5 插件/技能两型扩展系统"整整一版）；第三方能力想进来只能改源码 | `skills/<id>/skill.json` + ESM 入口就是扩展点：**发现 / 校验 / 开关 / 设置 / 提示词 / 工具**全链路打通，装卸不动源码 |
| **开关散落、关掉会怎样没人说** | 能力开关分布在 6 个页签；`mcp.enabled=false` 的后果只写在代码注释里 | `src/plugins.mjs` 把它们集中登记成"插件"，每个都写了**是什么 / 关掉会怎样 / 即时生效还是要重启（附取证位置）** |
| **"随时开关"做不到** | 配置只在启动时读一次，任何改动都要重启桥接 | 技能/插件有**专用通道**（`/api/extensions/toggle`）：写盘 + 改活配置对象，**下一轮就生效**；只有"装/卸技能"要重启，而且这条边界写在界面文案与规范里 |

另外补上的一件真事：**第三方技能要发图时缺的那个环节，这一版补齐了** ——
新增宿主工具 `qq_send_image`（自己下载、守卫校验、以 base64 段发出）与开关
`security.allowPrivateImageHosts`（默认关）。pixiv 插件的 v1.1.0 主打功能（真的把 P站图发进群）
到这一版才在 InteractBot 上成为可能。

## 2. 新增能力（都能用）

* **技能（外部能力包）**
  * 清单契约 `skill.json`（`apiVersion: 1`）：身份、入口、设置与界面 schema、工具声明、提示词来源、权限声明、会话模式；
  * 入口契约：`setup(api)` / `available()` / `promptSections()` / `dispose()` / `diagnose()`；
  * **两级校验**：`errors`（装了也不能用，拒绝装载）+ `warnings`（能跑但有隐患，**必须显示**：
    设置项没界面、界面字段没默认值、清单里带明文密钥…）；
  * 设置：清单默认值 ← 用户配置，**按 schema 收敛类型**（`"10"` → `10`，否则会变 NaN 让上限失效）；
  * 密文：`secret: true` 的字段沿用与 `/api/config` **完全一致**的语义（接口删值只回布尔、
    留空 = 不修改、`null` = 清除）；
  * 命名：工具全名 = `mcp__skills__<技能id>__<工具id>`，由 `api.toolName()` 注入 ——
    **技能不许写死工具名**（写死的后果是模型调一个不存在的工具，而且只会说"查不到"）。
* **内置插件登记表**：记忆 / 看图 / QQ 工具 / 人味层 / 唤醒 / 用量 / 人设 / 名单 八个，
  每个都有「关掉会怎样」与「即时或需重启 + 取证位置」；名单类如实标成"没有开关"。
* **发图**：`qq_send_image(url, kind, peerId)` —— 必须显式带会话（fail-closed），
  自己下载（逐跳 SSRF 校验、内容嗅探类型、大小/超时封顶），**不把 URL 交给协议端**，
  失败原因翻译成人话（含"该打开哪个开关"）。
* **离线巡检**：`node src/index.mjs --extensions`（技能状态 + 工具全名 + 清单告警 + 插件开关）。
* **人设库**（★★ 本轮的重点：**一个文件一套人设，按需切换**）：
  * 形状：`personas/<名字>.md` —— **一个文件一套人设，文件名叫什么，人设栏里就叫什么**。
    默认那两套（小鲸鱼·精简 / 小鲸鱼·完整）**也是其中两个文件**，一样能改、能复制、能删 ——
    它们不是代码里的特例。新建时**必须给名字**（名字 = 文件名 = 列表里显示的名字）。
  * 它取代了什么：原来的「`persona.preset` 三选一 + 一个 `persona.custom` 文本框」是
    *同一套人设的三个档* 的形状 —— 存不下**多套**人设，也没法给一套人设起名字。
  * ★★ **老配置行为一个字都不变**（这条是硬约束）：`persona.active` 为空 → 还是老逻辑
    （`custom` 非空就用它，否则用 `preset`）；`active` 有值 → 用那个人设文件；`active = none` → 不用人设。
    `active` 指向一个**读不到**的文件时**不静默退回内置**（那会让人以为"我的人设在用"），
    而是按"不用人设"跑并把原因**大声报出来**（控制台人设栏红色显示 + `--personas` 里能看到目录里现在有什么）。
  * ★★ **改名/删除牵着配置走**：删掉正在用的那一套，`persona.active` 同时改成 `none` ——
    这种"两处同时改"的事只有一处实现才不会漏（漏了的后果是下次启动直接变"读不到文件"）。
  * ★ **重启语义如实**：人设是**构造期缓存**的 —— 切换、改了正在用的那一套、删了正在用的那一套
    → `restartRequired: true`；新建一套、改一套没在用的 → `false`（多报让人白重启，少报让人以为生效了）。
  * ★ 目录放在**包根**（与 `skills/` 同级）而**不是工作区**：人设会被拼进系统提示词的**高优先级位置**，
    而工作区是 agent 有写权限的沙箱 —— 放进去等于让它能改自己的人格（H12 一直在防这件事）。
  * 离线巡检：`node src/index.mjs --personas`（装了哪几套、现在用哪一套、各自多大、
    哪一套没有名字块、老配置回落提示）。
* **人设页**（界面规格见 `CONFIG-UI.md` §2.2；**后端已全部落地**）：
  * 卡片 1「**目前人设**」= 列表（**「选择人设」在同一张卡里**）+ 新建 / 切换 / 改名 / 删除 /
    看全文 / 编辑 / 恢复默认两套；空态有明确的「恢复默认两套」入口。
  * 卡片 2 = 人设**正文**编辑（新建时的起手模板由后端下发，自带名字块骨架）。
  * 卡片 3 = 「什么时候回我」（原「触发」页并入，字段真值仍留在 `CONFIG-UI.md` §2.3）。
  * ★ **本页删掉的三样**：①「用户怎么叫它」（唤醒词看**触发关键词**、名字块直接改**正文**）；
    ②「它怎么称呼对方」（`persona.callUser`，**已从源码移除**，改为按人昵称）；
    ③「内置三选一」那种"同一套三个档"的说法（换成列表；`preset`/`custom` 退为**老路径**，
    界面不再碰它们，免得出现"界面写 preset、实际生效的是文件"这种两处真值）。
  * ⚠️ **正在伺服的那一份界面还是旧人设页**（它调 `GET /api/persona`）—— 那两个旧接口**已换代**，
    现在回 `410 Gone` 并指向 `/api/personas`。所以那页会显示「接口已换代」，**这是刻意的、不是 bug**：
    按指令 UI 源码本轮一个字节都没动，等后续 UI 流程按 §2.2 生成。刻意不做"让旧页面别报错"的兼容层 ——
    那会留下两套人设真值，而两处真值是本项目最贵的一类缺陷。
* **联系人昵称（按人）**（后端已实现；**界面只在规格里**，见 `CONFIG-UI.md` §2.5）：
  回答「机器人怎么称呼**某个人**」—— 取代了那个全局的 `persona.callUser`（对甲叫老板、对乙叫群友，
  一个全局框表达不了）。存在 `memory/contacts.md`（一行一人），每轮**只注入当前说话人**那一条。
  ★ 它放在 `memory/` 下是刻意的：**自动被记忆的篡改检测覆盖** —— 模型绕过桥接偷改这张表给自己起名，
  下一轮会被回滚并留日志（"模型不许自己起名"这条边界因此有兜底，不是只写在文档里，有断言验过）。
  接口 `GET/POST /api/contacts`（空昵称 = 删除；**改完下一轮就生效**，不需要重启）。
* **四条接口**：`GET /api/extensions`、`POST /api/extensions/toggle`、
  `POST /api/extensions/settings`、`GET /api/extensions/diagnose?id=`，外加 `GET/POST /api/personas`
  （人设库读/写；旧路径 `GET /api/persona`、`POST /api/persona/names` 回 `410 Gone` 并指向它）与
  `GET/POST /api/contacts`。
* **技能依赖桥**：技能要用的 npm 包由宿主从 `vendor/node_modules` **软链**到 `skills/node_modules`
  （白名单目前只有 `undici`，pixiv 的代理支持需要它）；包里没有时技能会**自己报「代理不可用」**。

### 4.1 自查记录（这一版自己抓出来的东西，如实列）

* **缺陷（已修）**：设置项的**空值**被当成 0 —— `Number('')` 是 0、`Number('  ')` 也是 0，
  而 0 在 `min: 1` 的字段上会被夹成 1。后果是"界面上把条数清空"静默变成「上限 = 1 / 返回 0 条」，
  更糟的是原实现在空值分支直接 `return 0`，**连 min/max 夹取都绕过了**，而且一条告警都不发。
  现在空值 = "没填" → 退回清单默认值且不告警；只有"确实填错了"才告警。
  （`verify-extensions.mjs` ③ 有 7 条断言钉住它 —— 其中布尔那条特意把默认值取 `true`，
  这样"退回默认"与"当成 false"才分得开。）
* **变异自检**：把 `src/extensions.mjs` 分别弄坏四处（工具命名、启用闸门、空值处理、密文置空），
  确认测试套件会红（4 / 1 / 1 / 1 项失败）。这条记录写在测试文件头部 ——
  因为断言最容易的坏法是"永远通过"，而那种坏法在全绿里看不出来。
* **措辞漂移（已修）**：`qq_send_image` 被守卫拦下时的提示原本写「控制台→安全」，
  而真正的落点是**控制台 → 扩展 → 给扩展用的安全开关**（与 pixiv 提示词、CONFIG-UI.md §2.10 统一了）。
* **悬空引用（已修）**：`skill.json` 的说明原本指向一个不存在的 `UPSTREAM-PATCH.md`，
  改为指向 `README-InteractBot.md` 与 `docs/0.2.2-pixiv-skill-migration.md`。
* **★★ 编码事故（已修，并且留下了守卫）**：一条 PowerShell 命令
  `(Get-Content PROJECT.json -Raw) | Set-Content PROJECT.json -Encoding UTF8`
  把这份**包契约**按系统 ANSI（GBK）读了、再按 UTF-8 写回 —— 中文全变乱码，**而且不报错**
  （乱码照样是合法 JSON，`npm test` 全绿）。同一条路子还把
  `docs/0.2.2-pixiv-adaptation.patch` 落成了 **UTF-16LE**（`.patch` 存成 UTF-16 等于废掉）。
  * **修法**：patch 重新落成 UTF-8/LF（内容逐字未变，仍 31 个 hunk，与当前 diff 一致）；
    `PROJECT.json` 的**结构**没受损（键名/路径/计数/版本都以代码为准），说明文字按 git 里的
    0.2.0 清单**重建**并把 0.2.1/0.2.2 的登记项补齐（配置键、文件、命令、不变量、故障特征、验收记录、路线图）。
  * **新增守卫**：`mocks/verify-text-encoding.mjs`（进 `npm test` 链，**18 项**）—— 扫全仓库文本文件：
    不许 UTF-16、不许 `U+FFFD`、`.md/.mjs/.json/.patch/.txt` 不许 UTF-8 BOM、★ 不许**成片乱码**
    （第四条用真实现场标定：现场 29.0% vs 健康仓库最高 0.006%）；
    ★ 自带**负对照**（把事故的六种形态喂进判据，必须抓得住）+ **正对照**（正常中文不许误报），
    否则"守卫全绿"可能只是判据写错了。
  * **纪律与专项记录**：不要用 PowerShell 5.1 的 `Get-Content`/`Set-Content`/`>` 改这个仓库的文本文件
    （要字节保真就用 `git --output=`、`git checkout` 或 .NET 显式编码）。已写进 `AGENT.md` §6.6；
    **完整记录（损伤模型 / 判据标定 / 「我要做什么 → 用什么」决策表 / 实测字节对照 / 恢复步骤）见
    `docs/0.2.2-project-json-incident.md`**。
  * 为什么不只写一句"注意编码"：这类损坏**不会让任何现有测试变红**，只有人去读那几行字时才会发现 ——
    **没有断言盯着的纪律等于不存在**。

## 5. 这一版**刻意不做**的事（都有理由）

| 不做 | 为什么 |
|---|---|
| **控制台的加减法**（新「扩展」页签 + 合并页签 + 清死代码） | 用户明确要求"控制台优化方案最后做，等我的指令"。所以本轮只交付规格：`CONFIG-UI.md` §2.10 是界面规格，`docs/0.2.2-console-plan.md` 是加减法提案。**唯一动过的页签是「人设」**，而它按指令也**只在指导文件里**（§2.2）—— 后端换成人设库之后，正在伺服的那一版人设页会对不上（调旧接口拿 `410`），**刻意不做兼容层**（理由见 §2） |
| **给旧人设接口做兼容/保留旧路由** | 界面上是"人设页暂时显示接口已换代"，代价明确且可恢复（按 §2.2 重新生成界面即可）。反过来保留 `GET /api/persona` + `POST /api/persona/names` 会同时存在**两套人设真值**（`persona.custom` 里的名字块 vs `personas/*.md`），而"两处真值"正是本项目最贵的一类缺陷。折中做法是：旧路径**不删而是回 `410 Gone` 并指出新路径** —— 调用方一眼知道该改什么，而不是对着 404 去改自己的路径 |
| **把工具表做成动态增删** | DSH 的 MCP 客户端在启动时读一次 `tools/list`（没有 `tools/list_changed` 的推送路径）。所以选择"工具表按已安装注册 + 开关靠 fail-closed + 提示词撤回"：**开关真的即时**，代价是关掉的技能在工具表里还留着一个名字 —— 这条边界写在界面与规范里，而不是假装它消失了 |
| **改上游 README / 安装说明（82KB）** | 逐句改成本宿主的措辞收益极低、易改错。改为新增 `skills/pixiv-lookup/README-InteractBot.md` 讲清差异 |
| **把技能放进沙箱** | 技能在宿主进程里跑，进程内无法隔离。因此如实声明（`permissions` + 界面提示），而不是给一个假的"安全"承诺 |
| **发图走回复标记 `[img:…]`** | 标记方案的失败对模型不可见（"图没发出去"没人告诉它）；工具方案能把失败原因带回模型，符合本项目"失败必须让用户知道"的纪律 |
| **组装 0.2.2 发布包** | 用户决定：下一轮再说（组装脚本已同步支持 `skills/`，并会排除 `skills/node_modules` 这个软链；本轮又加上了 `personas/` —— 漏了它的后果是发布包里一套人设都没有，而且**不会报错**） |

## 6. 已知边界与待办（如实列出）

1. **装/卸技能要重启桥接**（工具表与 profile 是启动时定的）；开关不需要。
2. **`qq_send_image` 没有真机验证**：SnowLuma 自己的文档确认支持 `base64://` 图片段，
   但本机没有真 QQ 环境跑过一次真的发图。
3. **pixiv 的代理路径没有验证**：本机装不上 `undici`（可选依赖）—— 没有代理时大陆网络本来也到不了 pixiv。
4. **`permission: write` 只是提示词层约束**（MCP 调用里没有调用者身份）；要硬拦就得把动作收回宿主工具。
5. **控制台界面尚未实现**（`CONFIG-UI.md` §2.10 已定稿）；界面完成后必须补
   `mocks/probe-ui-bundle.mjs` 的 `EXPECT` 串并重新构建 dist。
6. 技能**没有自动更新**机制：换版本 = 换目录 + 重启。
7. ★ **`mcp.enabled` 是两套 MCP 工具的总开关**（QQ 工具 + 技能工具）：关掉它 ⇒ 技能工具不会挂给模型、
   技能的提示词片段也一条都不注入（这条是自查时补的：以前只挡了挂载，指引还会照旧注入，
   等于教模型去调不存在的工具）。`--extensions` 与界面都会给出这条原因。

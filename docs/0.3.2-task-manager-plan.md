## 1. 目标场景（唯一需求依据）

**一句话**：服务器里的玩家可以随时和后端的小鲸鱼说话；服务器出问题时，小鲸鱼**在选定聊天里报告且只报告一次**，并**尝试一次重启**；重启失败就**向管理员求助并等指令**。

拆成六条，每条都是可验收的行为：

| # | 行为 | 关键性质 |
|---|---|---|
| 1 | 玩家在服务器内聊天 → 小鲸鱼在**后端**收到 → 决定要不要回、回什么 | 需要**服务端侧代码**（插件/模组/群组端插件）把游戏内事件送出来 |
| 2 | 服务器出问题 → 在**选定聊天**报告**恰好一次** | ★ "且仅会一次"是硬要求：没有重复播报 |
| 3 | 报告后**尝试一次重启** | ★ 恰好一次 —— **不是重试循环**；★ **服务端由桥接守护**（见 §6.3） |
| 4 | 重启失败 → **向管理员求助并等指令** | 不再自动做什么；等人 |
| 5 | 进服时要求玩家绑定 **UUID ↔ QQid**，并提醒一次；可以**指令改绑**；**未绑定者不能与小鲸鱼聊天** | ★ 未绑定 = 没有对话权，不是"能说但不能听"；★ **提醒与绑定回执只给本人**（§5.4） |
| 6 | 选定聊天里的群友**可以问出服务器内的情况** | 只读查询，不需要管理员权限 |

**"选定聊天"**：从**白名单**里选（见 §4）。

### 1.1 "且仅会一次"落地成三条不变量

这是本版最容易做错的地方，先立成不变量：

1. **同一个故障事件只报告一次** —— 状态机只在**状态跃迁**时产出事件（`up→down` 一次、`down→up` 一次），
   持续 `down` 不重复产出。状态**落盘**，所以桥接重启也不会重报。
   - 先例：`delivery-ledger.mjs`「绝不自动重放」、`sticker-quota` 的配额台账、任务台账的"闲置才降级"。
2. **同一个故障只重启一次** —— 重启尝试记 `attemptedAt` + `attemptSeq`（落盘）。
   重启后**又坏**了不算"同一次故障"：按新的故障事件处理，但**必须有冷却窗口**（见 §6.4）。
3. **不许静默** —— 任何一条"没做到"（报告没发出去、重启没执行、重启后没起来）都必须留痕，
   并在**下一次能说话的时候**如实说清楚。先例：`AGENT.md` 第 6 条 + 投递账本的"启动时大声报出别人的 pending"。

## 2. 切分：一套骨架 + 两个端

使用者拍板的切分是：**"监测事件"做成插件；"服务器检测"单独一个页签**。这条我接受，但要把它落成**不撑坏插件语义**的形状。

**必须先说清的事实**（`插件设计规范.md` §7，0.2.4 为表情包立的规矩）：

- 在这个项目里**插件 = 一条登记数据**（`src/plugins.mjs`），纪律是「**不改行为**」——表是纯数据 + 读取；
- **技能契约没有自主插入钩子**（只有 `setup / available / promptSections / dispose / diagnose`），
  所以"宿主自主发一条消息"这件事**技能做不到，只能由宿主在投递管线里做**。

∴ "把监测事件做成插件"的落地形状只能是：

| 部分 | 放哪 | 理由 |
|---|---|---|
| 调度器 / 事件匹配 / 主动回合 / 重启编排 | **`src/` 的引擎模块** | 要碰宿主状态机（会话锁、`#deliver`、投递账本、隐私闸门顺序） |
| 登记 / 开关 / 界面指路 | `src/plugins.mjs` 加条目 | 纯数据，符合纪律① |
| 详细设置 | 页签（见 §7） | 与 `wake-policy`（卡片 + `extensions:` 展开区）、`memory`（卡片 + 记忆页）同构 |

### 2.1 骨架模块（全部可离线测）

```
src/schedule-core.mjs      任务与事件规则的定义、下一次触发时刻、错过窗口、错过台账（纯函数）
src/schedule-runner.mjs    tick 循环 + 主动回合 + #deliver 接线（形状抄 memory-consolidate.mjs）
src/servers/rcon.mjs       RCON 协议（纯 node:net，自实现，零 npm 依赖）
src/servers/log-source.mjs 日志尾随事件源（方言表 + 增量游标）
src/servers/push-source.mjs 服务端插件/模组推送（本地 HTTP，只绑回环 + token）
src/server-monitor.mjs     采样 → 状态机 → 事件（纯函数，**不出现任何版本判断**）
src/server-restart.mjs     重启编排（停 → 等端口释放 → 等恢复 → 判定成功/失败）
src/schedule-commands.mjs  指令白名单 + 参数校验 + 留痕（**唯一有写权限的模块**）
```

**复用而非重写**（这是本版省下来的部分）：

| 要用的能力 | 已有实现 | 复用方式 |
|---|---|---|
| 定时器骨架 | `createConsolidateScheduler`（`memory-consolidate.mjs:500`） | "可注入时钟 / `unref()` / 空闲才动 / 失败留证据"整套照搬 |
| 主动消息投递 | `#deliver()`（`bridge.mjs:3659`） | **直接调用** ⇒ 分条 / 投递账本 / 拟人延迟 / 限流 / **终检门** / **隐私闸门**全继承 |
| 失败分类 | `classifyTransport()`（`transport.mjs`） | RCON 错误复用 `{layer, retryable}` 形状 |
| 凭据保守读 | `credentials.mjs` / `token-discovery.mjs` | "宁可找不到也不猜"、**密钥不进日志** |
| 落盘形状 | `recipes.mjs` / `tasks.mjs` | 一文件一条 + 原子写 + 归档是移走不是删除 |
| 唤醒词 | `personaWakeWords()` / `mergeWakeKeywords()` | 游戏内"叫它"与 QQ 内"叫它"**共用同一份判据** |
| 只读巡检 | `--extensions` / `--tasks` 的形状 | 新增 `--servers` / `--schedule` |

### 2.2 两条独立的插件登记（两个开关，各自一个写入口）

| 插件条目 | 图标 | `enabledPath` | 默认 | 详细设置 | `hot` 判据（必须取证） |
|---|---|---|---|---|---|
| `schedule` 定时与事件 | 🕒 | `schedule.enabled` | **关** | 任务页签 | `hot: true` —— runner 每跳重读 `config.schedule` |
| `servers` 服务器监测 | 🖥️ | `servers.enabled` | **关** | 服务器页签 | `hot: true` —— monitor 每次采样前重读 `config.servers`；但**单台服务器的增删**要重建连接 ⇒ 那一项标 cold（界面明说"改完需重启"） |

**★ 两个坑必须避开：**

1. **同一个键不许有两个控件**（0.2.7 真机反馈："同一个开关放在 skill 和插件上不合理" ⇒ 有了 `switchInSkill` 纪律）。
   ∴ **页签里不再放"功能总开关"**；页签只显示状态与参数。"暂停某一条任务/某一台服务器"是**条目级**操作，不是功能开关。
2. **新增页签必须同步标签表**（`ExtensionsTab.tsx:689` 的 `TAB_LABEL`），否则「→ 去 X 细调」会显示内部 id。
   同时 `App.tsx` / `Home.tsx` 的页签表与 `pathToTab` 要一起改。

## 4. 选定聊天与白名单

**"选定聊天"从白名单里选** —— 并且**镜像桥接已有的名单**，不另造一套：

| 用途 | 名单来源 | 判据 |
|---|---|---|
| 故障报告发到哪个群 | `access.adminUsers` 所在的会话 + 新增 `servers.<id>.reportTo` | 新建时**只允许从来消息过的会话里选**（避免打错号码） |
| 谁能问服务器情况 | `servers.queryAllow`（真人/群） | 缺省 = 管理员；要放开由使用者显式加 |
| 谁能下指令（重启/停服） | `access.adminUsers` | **只有管理员**，且必须私聊或群内 @ |
| 谁能和小鲸鱼对话 | **已绑定 UUID↔QQ 的玩家**（§5） | 未绑定 = 拒绝，且**明说怎么绑** |
| **谁能提交绑定码** | **不需要新名单** —— 复用 `isGroupAllowed`（群白名单）+ 指令前缀 `/绑定` | ★ 本地指令只在**已允许的群**里生效；多造一张 `bindings.groups` 只会多一处不一致（§5.2） |

> ★ **号码不猜**：报告目标必须是"曾经来过消息的会话"里选出来的，否则一个手滑就会把服务器告警发到陌生群里。
> 先例：`token-discovery.mjs`「宁可找不到，也不要猜」。

## 5. 游戏内 ↔ QQ：绑定与通道

### 5.1 UUID ↔ QQid 绑定（**已定：群内 `/绑定` 取码 → `/绑定 <码>` 确认**）

> ⚠️ **2026-10-04 实现期修正（本节的入口形状已作废，判断仍然全部有效）**
> 使用者实测后把流程改了两次，现在的口径是：
> **① 码在游戏里生成** —— 玩家在游戏内说 `\mc bind`（**反斜杠**：以 `/` 开头的输入会被
> 服务端当成命令，而那句"未知命令"**不写进任何日志**，我们看不到；`\` 在游戏里只是普通
> 字符，那句话以聊天发出、进日志）⇒ 码**只发给他本人**；
> **② 再到群里直接发** `\mc bind <码>`（**不用 @ 我** —— 这条通道跑在唤醒判定**之前**）
> ⇒ 当场绑定，并**立刻在游戏里通知他本人**；`\mc unbind <目标>` 解绑（管理员）。
> ∴ 下文凡出现 `/绑定` 的地方，**入口形状一律读作 `\mc bind`**（`/mc bind`、`//mc bind`、
> 裸 `mc bind` 代码里也认，是零代价的兜底；但**对外只写 `\mc`**）。
> 本节下面那些**判断**（前缀必须带、不新建绑定群、复用群白名单、绑给发送者本人、
> 判定点必须在唤醒判定与语义闸门之前却在群白名单之后、命中即 `return` 不走 `#runTurn`、
> 只回发起人、确定性文案）**一条都没变，全部仍是当前实现**。

**为什么必须绑**：QQ 侧的身份靠 QQ 号，游戏侧只有 UUID。没有绑定表，`/say 我是小明` 这种话无法归属到人，
**权限判定与记忆写入都会落空**（先例：`roster.decide()` 的 fail-closed —— 名单为空 = 谁都不能用）。

**为什么码提交放在"指定群聊"而不是私聊**（使用者 2026-10-XX 定的口径）：

> 私聊这条路**走不通**：`roster.decide()` 对私聊是 fail-closed，陌生人一律拒绝并回一句
> "这个机器人只对名单内的人开放"（`roster.mjs:293-299` → `bridge.mjs:1456`）。玩家是在给机器人
> 加好友还是私聊都无所谓 —— **没进名单就是进不来**。而"把玩家加进私聊白名单"等于为了绑定把门开着。
> ∴ 码走**指定群聊**，那是一条**独立、窄、确定**的通道，不碰任何一张现有名单。

**生效流程**：

```
玩家进服 → 未绑定 → 只给他本人一条提醒（tellraw，§5.4）：告诉他去群里发 `/绑定`
玩家在**群里**发 `/绑定`
   → 桥接的**本地指令**命中（§5.2）→ 生成一次性绑定码（6 位、大小写不敏感），TTL 见 §13.1
   → **只回给发起人**：一条极短的指令回应（确定性，不调模型）
玩家把码发回群里：`/绑定 <码>`
   → 校验（存在/未过期/未用过）→ 绑定成立 → **只回给发起人**：`绑好了：<QQ 昵称>`
改绑：再走一遍（同一 QQ 只能绑一个 UUID；同一 UUID 只能绑一个 QQ；改绑即覆盖并留痕）
解绑：管理员专用（控制台 / 管理员私聊）
```

**★ 为什么不需要单独的"绑定群"**（使用者 2026-10 定的口径）：

> "重新建立一个绑定群的代价很大。" —— 完全同意，而且**它本来就不必要**。
> 绑定码走 dm 是因为原来那条流程依赖"私聊"，而私聊在群里是 fail-closed；
> **只要把入口换成一个带前缀的本地指令（`/绑定`），它就能在任何一个已经在用的群里工作**，
> 不需要新群、不需要放宽任何名单、不需要动 `roster.decide()`。

**存哪**：绑定表存**桥接侧**（工作区 `runtime/bindings.json`），**不存服务端插件里**。
理由：它是 QQ 侧的事实（谁是谁），且桥接是唯一知道 QQ 号的进程。

**★ 这条路的固有代价（必须写清，不能含糊过去）**：**码要经过群聊** ⇒ 同群的人有机会看见。
我们已经尽量把它压小：**码是"一次性 + 短 TTL"，且它只是"资格"，不是最终归属**（见 §5.2 末）。

### 5.2 本地指令通道（**这是一条独立通道，不放宽任何名单**）

**先例**：这个形状在本项目里已经有 —— "回到第 N 步"就是**本地正则识别、不依赖模型**
（`tasks.mjs:490` 的 `parseRollback`，触发词表在 `AGENT.md` 里列着）。
`/绑定` 是同一个形状，只是**必须把模型那一轮整个省掉**（否则会花钱，还会冒出一句"我不太明白"）。

| 规矩 | 内容 | 为什么 |
|---|---|---|
| **入口形状** | 指令前缀一开始就定死并写进文档：`/绑定`（可留别名 `/bind`），**必须带前缀**才命中 | 带前缀 = **误伤概率天然极低**；不像裸码那样会被闲聊撞上 |
| **可用范围** | 在**已允许的群**里即可用（复用 `isGroupAllowed`），**不新造名单** | 群白名单本来就是 fail-closed 的门；本地指令**不该**另开一张名单（多一张名单就多一处不一致） |
| **归属** | 绑定/改绑**绑给发送者本人**（`senderId`） | ★★ **绝不绑给消息里写的任何人** —— 否则谁在群里看见码，就能把它绑到别人的 UUID 上 |
| **时机** | ★ 判定点在**唤醒判定之前**（`decideTrigger`）与**语义唤醒闸门之前**（`#wakeGate`），但**在群白名单之后** | ① 放在 `#wakeGate` 之后会**静默失效**（`semantic` 时可能被判"沉默"）；② 放在唤醒判定之后则要求先 @ 它，不好用；③ 放在群白名单之前等于给所有群开后门 |
| **这一轮到此为止** | 命中即 `return {handled:false, reason:'bind-command'}`，**绝不往下走 `#runTurn`** | 不然就是"花了钱 + 回一句看不懂的话" |
| **回应通道** | **只回给发起人**，用**确定性文案**，不走模型 | 群里刷屏的指令回应 = 噪音；且它的语义是"系统回执"，不该由模型自由发挥 |
| **失败话术** | 码不存在/过期/已被用 → **一句极短的话**，不吵、不重复、不猜 | 群是公共场合 |
| **留痕** | 每次绑定/改绑/解绑记一行（谁、何时、哪个群、哪个 UUID 前 8 位），**不记码本身** | 与 `memory-audit.mjs` 同一条纪律：审计不含秘密 |

**★ 代码形状**（实现时照这个判，避免"看着像接了其实没接"）：
`#maybeLocalCommand()` 返回 `{hit:boolean}`；`true` 时这一轮在**任何模型调用之前**结束。
必须有**接线级断言**：走完整桥接时，一条 `/绑定 123456` **一次 `rpc.prompt` 都没有发**。
（先例：任务段那次"从未注入过"的静默事故 —— 124 项纯函数断言一条都没抓到。）

**★ 关于"码 = 资格"而不是"码 = 归属"（这是把风险压到最小的关键）**：
绑定成立时我们并不知道这个人**在游戏里是哪个 UUID**。真正把 UUID 与 QQ 连起来的是**下一次游戏内发言**：
未绑定 UUID 说话 + 该 QQ 侧存在刚绑定过的资格 ⇒ 此时才写死对应关系。
∴ **抢到码 ≠ 抢到身份**，还必须**在游戏里用那个 UUID 说上话**；而受害者会**立刻**在游戏里收到
"你已被绑定到 QQ xx"的 `tellraw`（§5.6）。**抢绑藏不住**，这是本设计的兜底。

> ⚠️ 但这仍**不是**密码学意义上的证明：如果攻击者既看见码、又能操作那个 UUID（例如共用账号），
> 这条机制挡不住。**如实记在这里**，不假装它是强认证。

### 5.3 未绑定者的行为（硬要求）

| 玩家状态 | 能做什么 | 表现 |
|---|---|---|
| 未绑定 | **不能与小鲸鱼聊天** | 它的话**不进模型**（零成本），回一句**怎么绑**（群里发 `/绑定`），**每次进服最多提示一次** |
| 已绑定 | 可以对话 | 正常唤醒判定（与 QQ 侧共用唤醒词表） |
| 已绑定但不在白名单 | 看配置 | 默认**不参与**（与 QQ 侧 fail-closed 一致） |

### 5.4 通道选择（**已定：按内容分两条通道**）

使用者口径：**提醒与绑定回执必须只给本人，其余直接公屏。**

> ⚠️ **2026-10-04 实现期修正**：公屏那条从 `say` 改成了 **`tellraw @a`**，正文统一带
> `<小鲸鱼> ` 前缀、**不上色不高亮**。原因是使用者要求「小鲸鱼在服务器内每条发言都要
> 在前面加上 `<小鲸鱼>`、不要高亮，模仿正常玩家」——`say` 渲染出来是 `[Server] …`
> 且带服务端配色，玩家一眼就看出不是玩家，与这条要求冲突。`tellraw` 不在控制台留回显，
> 所以桥接自己补一行 `[game-chat] 说（公屏）：…` 进日志。下表括号里是原方案。

| 内容 | 通道 | 为什么必须是这条 |
|---|---|---|
| 未绑定提醒 · 绑定回执 | **`tellraw` + 选择器，只给本人**（QQ 侧那条是群内只回发起人） | 未绑定状态本身是个人信息，不该公屏广播；群里的指令回应也不该刷屏 |
| 小鲸鱼的正常回复 | **`say`（公屏）** → **现状：`tellraw @a`**（正文统一带 `<小鲸鱼> ` 前缀、**不上色**；见上方 §5.4 的修正说明） | 聊天氛围；实现最简单，全版本可用 |
| 服务器故障报告 · 求助 | **不走游戏**（发 QQ 选定聊天，§6.5） | 服务器挂了时游戏里没人看得到 |

**为什么 `tellraw` 是最优的"只给本人"手段**：它用**选择器**定向、**纯原版可用**、**不需要任何客户端模组**、
也不会打扰其他人。（`/msg` 也是私聊，但命令名在各版本不一致（`msg`/`tell`）⇒ 有方言差异；`tellraw` 反而更稳。）

**★ 代价如实记（必须写进白名单）**：`tellraw` 的参数是 **JSON**，能塞选择器与点击事件 ⇒
它是**最容易被当成"发言类"而破防**的一条命令。∴ 两条硬要求：

1. **参数只由模板生成**（点名 + 文本），**不接受模型自由填 JSON**；
2. 玩家名/UUID 作为参数时必须**由服务端侧校验过的值**注入，不接受模型拼字符串（防注入选择器）。

**★ 与隐私闸门的关系**：`say` 是全服可见的公开通道，`tellraw` 是点对点通道 ——
但两者都是"**已经发给第三方、撤不回**"。∴ **任何进入游戏的内容（包括 `say`）都必须过输出侧隐私闸**
（`privacy.screenForOutput`），命中时**换诚实话术或只发 `tellraw` 给管理员**，不许沉默地发出去。
先例：`AGENT.md` 的"投递前终检门 → 隐私闸"顺序不能换。

### 5.5 绑定的完整边界（别漏了这些）

- **绑定表是敏感数据**（UUID↔QQ 号）⇒ 属于 `user` 类受保护路径，**永不进包**；
- 它**不进游戏**（服务端只拿到"这个 UUID 绑定了没有"，拿不到 QQ 号）；
- 未绑定提醒**只给未绑定的人**、每次进服最多一次（刷屏的提示等于没有提示）；
- **能发 `/绑定` 的群 = 安全边界的一部分**：码在群里可见 ⇒ **谁能进这个群，谁就有机会抢先提交**
  （见 §5.6）。∴ 应当用**玩家彼此认识**的群；**公开大群**上这条机制会明显更弱。
- 同一 UUID 被两个人先后绑定（改绑）时，**旧绑定关系要留痕**（不是删掉就完事）——否则
  "他什么时候被顶替的"事后无从查起。

### 5.6 码被别人抢先提交（**残余风险与缓解档位**）

**风险的准确形状**（说清楚才不会过度反应）：被抢走的**不是 QQ 号**，是**那个玩家的游戏身份** ——
他之后在游戏里说的话会以绑走者的 QQ 名义进记忆与权限判定；反过来抢绑的人会读到他被算在那个人头上的记忆。
★ 但**抢到码 ≠ 抢到身份**：真正写死映射发生在"**那个未绑定的 UUID 在游戏里说了话**"那一刻（§5.2 末），
而受害者**立刻**会收到只给他本人的确认。

| 档 | 做法 | 效果 | 代价 |
|---|---|---|---|
| **A（已定）** | **短 TTL + 一次性 + 绑定/改绑都留痕 + 绑定成立时给该玩家 `tellraw` 确认** | 受害者**立刻**在游戏里看到"你已被绑定到 QQ xx" ⇒ **抢绑藏不住** | 挡不住铁了心抢的人 |
| **B**（未采纳） | A + **机器人立刻撤回那条码消息** | 缩短暴露窗口 | 撤回挡不住已经看到的人；且"消息一闪就没"很可疑，可能招来更多询问 |
| **C**（未采纳，但留了口子） | A + **第二因子**：在游戏里再确认一次 | 真正的防护 | 需要一个"这个人控制着那个 UUID"的可信判定 ⇒ 目前只能靠**服务端插件**（P3 原本打算不用它）。**作为可选硬化项留着**，不写进 v1 |

★ 关键不是"防住抢绑"，而是**让抢绑无法静默** —— 一旦绑定关系改变，受害者在游戏里会收到一条只给他本人的确认，
管理员也能在控制台看到变更记录。**这条比防更重要，因为它保证最坏情况会被看见。**

## 6. 服务器故障：报告一次 → 重启一次 → 求助

### 6.1 "出问题"的判据（先定义清楚，否则是猜）

| 故障类型 | 判据 | 可自恢复吗 |
|---|---|---|
| **进程死 / 端口拒连** | RCON `connect` 失败（`ECONNREFUSED`） | ✅ 能（重启进程） |
| **卡死** | 端口通但多次采样超时 / `tps` 低于阈值 / 采样连续丢 | ⚠️ 重启可能救，也可能只是慢 |
| **崩溃循环** | 重启后 **T 秒内**又 down | ❌ **不许再自动重启**（见 §6.4） |
| **人数/属性异常** | 超过配置阈值 | ❌ 只报告，不重启（人群问题不该重启服务器） |

**判据必须先声明**：`servers.<id>.rules` 里写清"什么算 down"。**默认只把"连不上"算 down**，
其余归到"异常报告"（只报告、不重启）—— 因为"tps 低"重启一次是**赌博**，而重启用错地方比不重启贵得多。

### 6.2 报告：恰好一次

- 状态跃迁 `up→down` ⇒ 产出一条事件 ⇒ 进主动回合 ⇒ **在选定聊天报告**。
- 报告内容（**固定模板 + 变量**，不用模型现写 —— 告警的价值在准确）：

```
⚠️ {服务器名} 连不上了（{时刻}，连续 {N} 次采样失败）
最后已知：{在线人数} 人 · TPS {tps} · 版本 {version}
我准备尝试重启一次。如果这次没起来，我会来问你。
```

- **`down→up` 也报一次**（"恢复了，停机 {时长}"）—— 否则使用者永远不知道它自己好了。

### 6.3 服务端生命周期：**桥接守护它**（已定）

★ 这一步的技术路线由使用者的决定确定下来：**服务端由机器人拉起，桥接持有它**。
于是"重启"不再是"发一条命令试试"，而是**我们真的能操作那个进程**。但有一个**必须现在设计对**的地方：

#### 6.3.1 关键设计：子进程要**比桥接活得久**（照 SnowLuma 的做法，不是反过来）

```
服务端 = spawn(启动命令, { detached: true, stdio: ['ignore', fd(log), fd(log)] })
         child.unref()          ← 让**桥接退出不带走服务端**
         running.json 落盘      ← { pid, startedAt, cmdLine 摘要, 启动来源: 'bridge' }
```

**为什么必须这样**（不这样会踩两个坑）：

| 若子进程跟着桥接一起死 | 后果 |
|---|---|
| 桥接每次重启（升级、改配置、界面点重启）都会**踢掉所有在线玩家** | 使用者会认为"这个机器人不能留" |
| 桥接重启后**再也认不出那个服务端** | 一个已在跑的服务端 + 桥接想再起一个 ⇒ 端口占用 / 世界目录被两个 JVM 打开 ⇒ **存档损坏** |

**∴ 启动时的接管逻辑（顺序不能换）**：

```
① 读 running.json → { pid, startedAt }
② 那个 pid 还活着吗？且它的启动时刻对得上吗？
   （★ 只比 pid 不够 —— pid 会被复用。先例：delivery-ledger 的所有者是 `pid@进程启动时刻`）
   是  → 「接管」：不启动新的，只挂上日志与 RCON；能力清单里 restart: ✓(adopted)
   否  → 启动一个新的，写新的 running.json
③ 端口活着但我们**没有任何 pid 记录**（例如别人手动起的）→ 标成
   **`restart: ✗(原因: 这个服务端不是我拉起来的)`** —— ★ **绝不"先杀再起"去抢它**
```

> ★★ 这一条是本节最重要的纪律：**"我们能重启它"必须由证据支撑，而不是由配置声明**。
> 认不出归属时**如实降级成"只报告、不重启"**，而不是赌一把。先例：`token-discovery.mjs`「宁可找不到，也不要猜」。

**运维含义（写进 `首次使用.txt`）**：**服务端要由机器人启动**（`start.bat` 会顺带拉起它或按配置拉起）。
已经在跑的服务端，桥接第一次启动时能"接管"（不上手、只观察 + RCON），但**重启能力在本次运行里不可用**。

#### 6.3.2 重启编排（一次，且必须交接）

> **RCON 是"先停再起"的交接，不是"重启"。** 而且服务端崩掉时 RCON 大概率也连不上 ——
> 那时唯一能拉起它的是"我们持有/知道怎么启动那个进程"。

```
1. 如果连接还在 → 用 stop 命令尝试一次优雅停服      ← 记 attemptSeq+1（落盘）
   （用不用 RCON 发 stop 都行；关键是"停"要能被观测到）
2. 等端口释放（最长 T1 秒，默认 60）—— 证明进程真的退出了
   ★ 为什么必须等：两个 JVM 同时写同一个世界目录 = **存档损坏**，比停机严重得多
3. 按 running.json 里记下的启动命令重新 spawn（并接管日志与 RCON）
4. 等恢复（最长 T2 秒，默认 180）：端口重新可连 + 一次成功的 RCON 登录
5. 成功 → 报"已恢复"（恰好一次）；失败 → §6.5 求助
```

**第 1 步的失败分支**：`stop` 发出去但端口一直不释放（服务端卡死）⇒
**记"停不下来"并进入求助**，**不做强杀** —— 强杀一个正在写世界的 JVM 正是存档损坏的成因。
（要强杀只能是管理员显式动作，并明确告知风险。）

#### 6.3.3 由此带来的一个"白拿"的好处（要写进设计，别浪费）

既然日志句柄本来就在我们手上（`stdio: ['ignore', fd, fd]`），**P3 的游戏内聊天事件源就不需要再选"日志尾随"**：
**直接读那个 fd** 就够了 —— **没有方言差异、没有"日志落没落盘"的问题、不需要服务端插件**。

| 事件源 | 何时用 | 代价 |
|---|---|---|
| **子进程 stdout（推荐）** | 服务端由桥接拉起 | 免费；与"守护"同一次决定 |
| 日志文件尾随 | 服务端**不是**我们拉起的（接管场景） | 要落盘、要方言表 |
| 服务端插件/模组推送 | 跨机部署 / 需要结构化事件 | 要写服务端代码、单独发版 |

⚠️ 但**别把话说满**：子进程输出要能识别聊天行，仍然需要**格式解析**（vanilla/Paper/Forge/Fabric/NeoForge 的
聊天行格式不同）—— 只是**不需要再操心"怎么拿到它"**。方言表仍然是 P3 的活。

#### 6.3.4 ★★ 模组服带来的四条具体约束（**这是本版确定要走的路**）

使用者已定：**服务端是模组服（Fabric 或 Forge/NeoForge）；v1 完全不写服务端代码**。
∴ 我们吃的是"子进程 stdout + RCON"，而模组服在这两样上都比原版麻烦。四条**必须在 P2 处理**：

| # | 约束 | 具体要求 | 不这么做的后果 |
|---|---|---|---|
| 1 | ★★ **stdout 必须被持续读走** | `stdio` 的读端要么**一直有人在读**、要么**直接重定向到文件句柄**（`openSync` 的 fd），**绝不留在那里没人读** | **管道缓冲区满 ⇒ 服务端 JVM 阻塞在写日志上停止推进** —— 这是"JVM 卡住"的经典成因，而且症状像服务端自己挂了，排查方向会完全错。★ 我们采用 fd 重定向（同 `snowluma-console.mjs`），所以这一条是**设计上就避掉**，不是靠"记得读" |
| 2 | ★★ **就绪要等很久** | 模组服冷启动 **2~5 分钟**是常态 ⇒ 就绪探测 = **端口在听 + 一次成功的 RCON 登录**；且**不许阻塞桥接启动** —— 桥接照常上线，服务端状态**如实报"正在启动"** | ① 恢复等待给了 180 秒就把"还在加载"误报成"重启失败"；② 反过来，为等服务端而卡住桥接 ⇒ **QQ 侧整段时间不可用**，为了服务器牺牲了机器人 |
| 3 | **能力清单必须按模组服实测** | `list` / `tps` 这些命令**在模组服上可能被覆盖、改名、甚至不存在**（很多模组动过命令表）⇒ 每项能力都要**探测后才标 ✓**，标之前是 `?` | 界面显示"能查在线人数"，实际每次调用都失败 |
| 4 | ★ **在线名单可以完全不依赖 RCON** | 玩家进出就在 stdout 里（`Steve joined the game` / `Steve left the game`）⇒ **从输出流维护名单**，`list` 只作交叉校验 | 少一条"命令被模组改掉就全废"的依赖 |

**顺带一个白拿的强化**：有了子进程输出，**第一次绑定就不需要"谁在线"这个前提**了 ——
映射发生在"未绑定的 UUID 说了话"那一刻（§5.2 末），本来就与 `list` 无关。

**两条运维事实（必须写进 `首次使用.txt`，让使用者提前知道）**：

- ★ 现在用启动脚本（`.bat`）手动拉起的模组服，**第一次要改由机器人拉起** —— 否则桥接只有"接管 + 观察"，
  **重启能力在本次运行里不可用**（§6.3.1），而"尝试一次重启"这条需求就落空了。这一次改动是**必须的、一次性的**。
- 模组服启动命令通常自带参数文件（Forge/NeoForge 的 `@args.txt`、Fabric 的启动器/安装器生成的参数）⇒
  `servers.<id>.command` 要把它**整条**记下来（我们不生成、不猜，只执行使用者给的那一条）。

### 6.4 冷却（防重启风暴）

- 重启成功后 **T3 分钟（默认 10）内**再次 down ⇒ **不再自动重启**，直接求助。
- 同一个 `attemptSeq` 只在冷却窗口外才递增；**冷却状态落盘**（桥接重启不能绕过冷却）。
- 这条是"且仅会一次"的另一半：没有它，一个坏掉的模组会让机器整夜重启。

### 6.5 求助：向管理员求助并等指令

```
❌ {服务器名} 我重启了一次，还是没起来（尝试序列 #{n}，{时刻}）
最后一次采样：{错误分类}（{layer}）
我**不再自动重启**了 —— 等你指令：`/xl status` 看详情，`/xl retry` 让我再试一次（需管理员）
```

- "等指令"是**真的等**：不再有任何自动动作，直到管理员说 `retry` / `abandon`。
- `retry` 是**管理员显式动作**，会重置冷却并递增 `attemptSeq`（留痕：谁在什么时候让它再试）。
- **不许**把求助只发到游戏内（服务器都挂了，游戏里没人看得到）⇒ **求助固定发到 QQ 选定聊天**。

## 7. 界面

### 7.1 服务器页签（新增，第 9 个页签）

| 区块 | 内容 |
|---|---|
| 服务器卡片（每台一张） | 名字 · **加载器与 MC 版本**（Fabric / Forge / NeoForge + 版本，**只用于显示与版本矩阵对照，代码里不许出现版本判断**） · 地址:端口 · RCON 端口/密码（**写进响应时脱敏**，照 `/api/snowluma/accounts` 的字段白名单纪律） · **启动命令**（模组服通常是带 `@args.txt` 的整条） · **归属**（`本机守护` / `接管（不是我起的）`） · 启用开关（**条目级**） |
| **能力清单** | `status · players · tps · say · tellraw · chatEvents · restart` 每项 `✓/✗ + 原因`。★ **数据驱动、界面不硬编码**（先例：`plugins.mjs` 的 `switchKind` 用数据表达形状）。★ **`restart` 的 ✓ 只能来自"进程归属已证实"**（§6.3.1），不是配置里勾的 |
| 事件源 | **子进程输出（推荐，服务端由桥接拉起时免费）** / 日志尾随（路径 + 方言） / 插件推送（token，脱敏）★ 「插件推送」这一条**只对同机部署成立**（桥接接口只绑回环，`api.mjs:65`）；异机要另设计 |
| 命令白名单 | 只读 / 发言 / **默认拒绝** 三档，照 §8 的表 |
| **活证据** | "上次成功采样在 X 秒前" · "上次故障 {时刻}，重启尝试 #{n}" · **"这个服务端是 12:03 由我拉起的（pid 1234）"** · 最近 20 条采样结果 |
| 探测按钮 | 「测一次连接」——**真连一次**并如实说结果（照 `--doctor` 的形状） |

## 9. 失败形状（提前写清，免得以后当 bug 报）

| 情况 | 表现 | 怎么让它不骗人 |
|---|---|---|
| 桥接没跑 | 到点什么都没发生 | 启动时对比"上次成功"⇒ **错过台账** ⇒ 下次交互如实报（**不补发**，使用者拍板） |
| 服务端没装插件 | 拿不到游戏内聊天 | **能力清单里 `chatEvents: ✗` + 原因**，界面与 `--servers` 都显示；**绝不显示成"监测中"** |
| 日志格式认不出 | 静默漏事件 | 每个事件源记 `parsed / unparsed` 计数，界面显示；认不出的行**不进模型** |
| RCON 连不上 | 监测停摆 | 状态机记 `unreachable` + 心跳"上次成功 X 秒前" + 日志喊一次 |
| 模型返回空 | 该说的没说到 | 兜底话术（**提醒类**：模板 + 原话；**告警类**：本来就是模板） |
| 重启"成功"但服务端反复崩 | 整夜重启 | §6.4 冷却 + 崩溃循环判据 |
| 玩家冒绑别人的 QQ | 权限错人 | §5.1 验证码流程（**不接受自称**）；★ 码在群里可见 ⇒ §5.6，绑定变更**必须让本人知道** |
| 绑定码被**别人抢先提交** | 那个玩家的游戏身份被顶替（不是 QQ 被盗） | §5.6 档 A：短 TTL + 一次性 + 绑定成立给该玩家 `tellraw` 确认 + 变更留痕 ⇒ **抢绑无法静默** |
| 群里闲聊**碰巧**包含 `/绑定` 字样 | 误触发 | 前缀 + **必须匹配完整指令形状**才算命中；不匹配就照常走普通聊天（§5.2） |
| 有人在**未允许的群**里发 `/绑定` | 不该生效 | 本地指令在**群白名单之后**判定（§5.2 的时机那一条）⇒ 未被允许的群一律不响应 |
| 游戏内刷屏 | 每句都触发模型 | 最小间隔 + 预算；超限记录不静默 |

★ **P2 的顺序是刻意的**：把"服务端守护 + `running.json` + 接管判定"放在 P2 而不是 P4，原因是它同时是三件事的前提 ——

③ 服务器页签要显示的"归属"字段。放在 P4 会让 P3 先去做一套将来要扔掉的日志尾随。

## 11. 代码风险点（实现时第一批要处理的）

| 风险 | 说明 | 要求 |
|---|---|---|
| ★ **主动回合被"作废"机制吃掉** | 现有作废判据是 `#pending.get(chatKey)`（`bridge.mjs:2284`）。主动回合若不标记，用户在新消息里 1 秒后的发言会把定时任务当成"同一发言人连发"而作废 ⇒ **表现是"8 点的提醒偶尔不说"** | `#runTurn` 加 `proactive: true`：**不参与 pending/作废**，只参与会话锁 |
| **主动回合与用户回合排队** | 同一会话串行（`#withLock`）⇒ 定时任务撞上长回合会等 | 如实记日志（"任务在等会话锁，等了 X 秒"），**不许静默延迟** |
| **静默时段** | 现有语义是"延迟到时段结束"（`humanize.mjs:73`） | 任务定义带 `ignoreQuietHours`（**默认对提醒开启**），并在日志/界面**如实标注这条例外** |
| **`turnStartedAt`** | `#deliver` 用它算"补时" | 主动回合传"任务触发时刻"，让拟人延迟语义与普通回复一致 |
| **首次触发** | 进程内的 `defaultInstanceTag()` 每次调用都变（`session-id.mjs:87`） | 主动回合必须用**构造期固定的** `this.sessionInstance`（`bridge.mjs:2251` 已经把这条写进注释），否则每次任务都开新会话 |
| **落盘位置** | 新状态目录若放顶层会被打进包或删掉 | **全部放 `workspace-qq/runtime/`**（现成的受保护目录），或同时登记 `PROTECTED_USER_PATHS` + `check-release-package.mjs` 的 `FORBIDDEN` |
| ★★ **子进程与桥接的生命周期** | 若服务端子进程跟着桥接一起死：① 桥接每次重启都踢掉所有在线玩家；② 桥接重启后认不出那个服务端，可能再起一个 ⇒ **两个 JVM 打开同一个世界目录** | 照 `snowluma.mjs` 的做法：`detached: true` + `unref()` + **`running.json` 记 `pid@启动时刻`**；启动时先"接管"（§6.3.1） |
| ★★ **归属认不出时不许抢** | 端口活着但没有归属证据（别人手动起的） | **如实降级成"只报告、不重启"**，`restart: ✗(原因)` 显示在能力清单里。**绝不"先杀再起"** |
| **停服必须等端口释放** | 停完立刻起 = 两个 JVM 写同一个世界 ⇒ **存档损坏**（不可逆） | §6.3.2 第 2 步；超时**不强杀**，转求助 |
| ★★ **绑定快速通道的接线** | 它必须在 `#wakeGate` **之前**（`bridge.mjs:1516`）—— 放在后面会**静默失效**：`semantic` 唤醒下玩家来绑定可能被判"沉默"，码白发了；且它**必须在这一轮 `return`**，不许继续 `#runTurn` | 要有**接线级断言**（先例：任务段"从未注入过"那次，124 项纯函数断言一条都没抓到） |
| ★★ **模组服的四条约束**（stdout 必须有人读走 / 就绪要等 2~5 分钟且不许阻塞桥接 / 能力要探测 / 名单不必依赖 RCON） | 详见 §6.3.4；第 1 条尤其危险：**管道没人读满 ⇒ 服务端 JVM 阻塞**，症状像服务端自己挂了 | P2 一并做掉；用 fd 重定向从设计上避掉"没人读" |
| **本地指令通道不许顺手放宽名单** | 它是一条**独立通道**，不是"给群开个后门" | 复用 `isGroupAllowed`、**不新造名单**；`roster.decide()` 一行都不改；判定在群白名单**之后** |

### 13.1 顺带确认的默认值（不同意就改）

| 项 | 默认 | 为什么是这个值 |
|---|---|---|
| 故障判据 | **只把"连不上"算 down**；`tps` 低等归"异常报告、**不重启**" | 重启一次是赌博；重启用错地方比不重启贵得多 |
| 重启冷却 | **10 分钟** | 没有它，一个坏模组会让机器整夜重启（§6.4） |
| 恢复等待 | **180 秒**（★ **模组服可逐台调到 300 秒以上**，见 §6.3.4 第 2 条） | 原版/插件服冷启动常常超过 60 秒；但**模组服 2~5 分钟是常态** —— 所以这一项**按服务器可配**，默认给一个对原版合理的值 |
| 采样下限 | **15 秒** | 再密只是白耗 CPU 与 RCON 连接；★ 模组服上 `list`/`tps` 若探测不可用，采样本身也要相应降频（没人问就不查） |
| 停服等待端口释放 | **60 秒** | 超时就求助，**不强杀**（§6.3.2 第 1 步的失败分支） |
| 绑定码有效期 | **5 分钟 / 一次性** | ★ 码是**发在群里**的（§5.5），所以 TTL 越短越好；5 分钟够"切窗口去群里粘贴" |
| 未绑定提醒频率 | **每次进服最多一次，且只给本人** | 刷屏的提示等于没有提示 |

### 13.2 仍然是"使用者自己填"的东西（不猜，缺了就如实报）

- 服务端**启动命令**（可执行文件 / 工作目录 / JVM 参数）—— 桥接只执行，不生成；
- **RCON 端口与密码**（要不要改由使用者定；我们只读配置，不写别人的服务端文件）；
- 选定聊天（**只能从"来过消息的会话"里选**，§4）；
- 单台服务器的启用开关与阈值。

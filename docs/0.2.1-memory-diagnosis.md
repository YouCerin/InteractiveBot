# 记忆写入路径诊断：为什么聊了这么多它一条都没记

> 专项：0.2.1 ｜ 诊断时间：2026-09-26 ｜ **只读排查，未改任何代码**
> 结论：**不是 bug，是设计缺陷**——写入路径 100% 依赖模型自觉，而模型在真实对话里明确选择了不记。

---

## 0. 一句话结论

桥接**确实把记忆指令注入了提示词**（铁证见 §2.2），
**模型也确实读到了**（它在思考里讨论过这条指令），
但它**主动决定"不用提议记忆"**（原文见 §2.3）。

这条路径上没有任何一环"坏了"——它在设计上就**没有强制力**。
所以"聊了很多却一条没记"是**必然结果，不是偶发故障**。

## 3. 机制归因（六条，按影响力排序）

| # | 原因 | 证据 | 现状 |
|---|---|---|---|
| **R1** | **没有任何强制性**：唯一写入触发是"模型在回复正文里写标记"。模型不写 → 链路完全静默 | §2.3 原文；`bridge.mjs:1062` 只在回复里找标记 | 设计缺陷 |
| **R2** | **模型拿不到 QQ 号**：`fact` 档的语义是"关于某个人/某个群的事"，但群里模型只知道昵称 | §2.4 工具表；无 `qq_memory` 工具 | 能力缺口 |
| **R3** | **指令位置错**：`bridge.mjs:1183-1221` 把记忆指令拼在 user 消息的**中段**，后面还压着 `origin`（含时间戳）、正文、图片说明 3~5 行。所有内容共用一个 text block | §2.2 注入顺序 | 设计缺陷 |
| **R4** | **语气太软 + 标准太高**：原文 `只在真正值得长期记住时才提议…；**宁少勿多**`（`memory-store.mjs:563`）——`宁少勿多` 是**劝退用语**，而它同时是唯一的触发指令 | `memory-store.mjs:546-580` | 措辞问题 |
| **R5** | **无反馈回路**：`【…记忆回执】= 0`（§2.2）。模型从没收到"你上次记的那条记上了/没记上"，自然不认为这件事有后果 | §2.2 计数 | 设计缺陷 |
| **R6** | **没有优先级**：记忆指令与人设、权限段等长段落并列。QQagent 实测过同一件事——"判据在，但动作区没提它，它就想不起来"，他们为此专门加了每轮提醒 | QQagent `prompt.js:697-714` 注释 | 设计缺陷 |

**判断**：R1 是根因，R2/R3/R5/R6 是让它"即使想记也记不成"的放大器，R4 是直接推手。

**★ 最要紧的一条判断**：
**只改措辞（R4）不会有效**。QQagent 已经用真实运行证明过——它加了工具、加了判据、加了每轮提醒，
58 次运行里 `memory_impression` 仍然是**零调用**。最后靠的是**确定性兜底**（回合结束后一次小调用）。
我们现在的处境比它更差：**连工具都没有**。

## 4. 桥接方案的可行性重估

用户要求"重新探讨用桥接做记忆的可行性"。逐条给出结论：

### 4.1 可行的部分（桥接方案的核心优势仍然成立）

| 能力 | 结论 | 理由 |
|---|---|---|
| 注入记忆到提示词 | ✅ **已验证可用** | §2.2：26 次注入，字节完整 |
| 从回复里剥离标记 | ✅ **已验证可用** | 无标记泄露记录 |
| 快照一致性 + 回滚 | ✅ 机制完整 | `memory-store.mjs:447-533` |
| 内容级过滤（身份/权限/绕过） | ✅ 机制完整 | `:75-82` |
| 分档隔离（选文件层） | ✅ 机制完整 | `:140-154` |
| 路径安全 | ✅ 机制完整 | `memory-files.mjs:59-97` |
| **确定性写入**（桥接自己记） | ✅ **完全可行，且是唯一可靠路径** | 桥接手上有全部原料：`chatKey`、`senderId`、`identity`、消息原文、`tier` |
| 给模型配记忆工具 | ✅ **可行** | MCP 通道已在（`mcp-profile.mjs`），加工具是加法 |

### 4.2 不可行的部分（原设计里假设错的地方）

| 假设 | 现实 | 结论 |
|---|---|---|
| "模型会自己记" | 11 个 turn 明确拒绝记（§2.3） | ❌ **假设不成立，必须放弃** |
| "模型知道该记谁" | 群里拿不到 QQ 号（§2.4） | ❌ 要求模型提供 `userId` 是**设计错误** |
| "软措辞能引导行为" | QQagent 58 次零调用的实证 | ❌ 单独改措辞无效 |
| "没有回执也没关系" | 回执 0 次 → 无反馈回路 | ❌ 必须闭环 |

### 4.3 结论

**桥接做记忆是可行的，而且比"指望模型"更可行** —— 但前提是**把写入从"模型自觉"改成"桥接自己做"**。
桥接手上有模型没有的东西：`chatKey`、`senderId`、核实过的 `identity`、`tier`、完整消息原文、持久工作区。
**让模型提供一个它根本拿不到的信息（QQ 号）去触发一次它并不想做的动作，是这条路径失败的根本原因。**

## 5. 修正方案

### 5.1 三层写入（替换原来的单层）

```
第 1 层 确定性关键词触发      用户明确说"记住"/"记一下"/"别忘" → 桥接必然抽取   ★ 零额外成本
第 2 层 确定性回合后抽取      每 N 轮 / 每 X 分钟一次小模型调用 → 抽取候选      ★ 可控成本
第 3 层 模型自愿提议          <<<MEMORY …>>>  +  新增 MCP 工具                  ★ 保留，作为补充
```

第 1 层是**最关键的增量**：它把"用户明确要求记住"这件事从"模型自觉"变成**确定性行为**。
用户抱怨的场景（"我让它记它没记"）由第 1 层根治，且**不花额外 token**（关键词匹配是本地字符串判断）。

第 2 层是 QQagent 验证过的兜底（回合结束后一次极小调用），但**默认关闭**，避免用户在不知情时花钱。

### 5.2 身份由桥接解析（修 R2）

**不要让模型提供 QQ 号**。桥接侧新增 `resolveMember(chatKey, hint)`：

1. `hint` 是纯数字 5~15 位 → 直接当 QQ 号
2. 否则在**本轮消息的 senderName** 里精确匹配
3. 再否则在 `roster`（群成员表）+ `memberNotes` 里模糊匹配
4. 匹配到多个 / 匹配不到 → **不猜**：落成 `unresolved` 条目并让回执说明"需要 QQ 号"

**关键**：解析的原料桥接全都有（`senderId` 就在 `#buildPrompt` 的参数里，
`applyMemoryItems` 的 `senderId` 形参**已经传了但从未使用**——`memory-store.mjs:303` vs `:309-368`）。
这是"改一处就能用"的现成缺口。

### 5.3 提示词位置 + 闭环（修 R3/R5/R6）

- 把记忆动作指令从**中段**挪到 user 消息**末尾的动作区**，紧挨"回复格式"那几行
  —— 与 QQagent `prompt.js:697-714` 的做法一致（他们把"好感判断提醒"放在变动段末尾才生效）
- 措辞从"宁少勿多"改成**明确的动作清单**（"这轮出现了 X 类事就调 `qq_memory_note`"）
- 回执修成**队列 + 可重放**（`takeReceipt` 读后即删，DSH 该轮失败就永久丢——`memory-store.mjs:410-420`）

### 5.4 可观测性（这是当前最大的工程缺口）

**现在没有任何东西能回答"它记了多少"。** 必须有：

| 手段 | 说明 |
|---|---|
| `[memory]` 日志**带会话与来源** | 现在只有一行计数，且 R1 导致从未触发 |
| `--memory --stats` | 每会话：提议数 / 接受数 / 拒绝数 / 解析失败数 / 最后写入时间 |
| **"零写入告警"** | 某会话跑满 N 轮仍然 0 次写入 → 在控制台标红。**正是本次问题的直接暴露手段** |
| 审计 `memory/audit.jsonl` | 每条变更带 `at` / `source` / `senderId` / `scope`（现在完全没有——`appendEntry` 只写 `- 内容`） |

**★ 如果 0.2.0 就有"零写入告警"，这个问题在第一天就会暴露，而不是等到"聊了很多"才被发现。**

## 6. 对 0.2.1 方案的修订

原方案 `docs/0.2.1-memory-prompt-plan.md` 的 M0-M5 需要按本次诊断重排：

| 原阶段 | 修订 |
|---|---|

| M1 注入瘦身 | 保留，但降一级（注入本来就是好的，§2.2） |
| M2 成员档案 + 好感台账 | **保留，但前面必须插入新的 M1'** |
| — | **新增 M1'：确定性写入层**（§5.1 第 1+2 层 + §5.2 身份解析 + §5.3 位置/闭环）。这是 0.2.1 的**真正核心** |
| M3 巩固归档 | 保留 |

### 修订后的验收标准（新增）

| # | 断言 |
|---|---|
| N1 | 用户说"记住 X" → **必然**产生一条记忆（不依赖模型行为） |
| N2 | 群里记某人时，模型**不需要**提供 QQ 号也能落进正确档案 |

| N6 | 审计里每条变更都能回答"谁、何时、哪个来源、什么档位" |

## 7. 需要用户决策的两个点

1. **第 2 层（回合后自动抽取）默认开还是关？**
   开 = "它真的会自己记"，代价是每 N 轮一次额外小模型调用（预估每轮 +300~800 input token）。
   关 = 只在用户明确说"记住"时记，零额外成本，但"它自己发现值得记的事"这条能力就没有。
   → 建议：**默认关，控制台给显式开关 + 费用提示**（与 §0-D5 一致）。

2. **第 2 层的触发节奏**：每 N 轮（N=5？）还是每 X 分钟（X=30？）还是"消息数累积 ≥20 条"？
   → 建议：**消息数累积 ≥20 条且距上次 ≥30 分钟**，比"每 N 轮"更贴合真实聊天密度。

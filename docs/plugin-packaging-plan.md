# 可借鉴功能 → 插件化划分方案（qq-bridge）

> **本文档回答一个问题**：把 hermes 那边可借鉴的功能做成 qq-bridge 的"插件"时，**哪些拆成独立插件、哪些必须合并、哪些互斥要二选一**。
> 依据：`src/plugins.mjs` 的既有登记契约 + 各功能的真实耦合关系。**尚未改动任何代码。**
>
> ⚠️ **术语**：这里的"插件"是 qq-bridge 自己的**内置能力块**（`src/plugins.mjs` 的 `BUILTIN_PLUGINS`，显示在控制台「扩展」页），**不是** DSH 的 cordis 插件。

---

## 0. 定稿的四条指令（用户 2026-09-27）

| # | 指令 | 落成 |
|---|---|---|
| ① | **可以安全进行**（在不动 UI 源码、不动记忆/提示词模块的前提下推进） | §5 实施顺序 |
| ② | **冲突时：把新增功能和已有功能放在一起；hermes 式那侧标「实验性」** | §2.1 定稿规则 |
| ③ | **记忆模块、提示词模块不要动** | §2.4 移出范围 |
| ④ | **只修改指导文件**（`CONFIG-UI.md` 等），不改 `config-ui/src/**` | §4.2 只写规格 |

**并澄清了一处我先前的含糊**：

> **"二选一" = 启动一个自动关闭另一个。**

这句话正好和推荐实现**天然一致**：两个选项放**同一个插槽、用同一个单值配置键**
（如 `wake.policy: 'rule' | 'semantic'`）—— 选了 B **天然**就是 A 关掉，
**不需要任何额外机制**。这也说明**不能**做成两个独立开关：那会出现
"两个都开"（两套判据打架）和"两个都关"（机器人哑掉）两种无意义状态。

## 1. 登记契约（决定了三条规则怎么落地）

`src/plugins.mjs` 的三条纪律**不是风格建议，是硬约束**：

| # | 纪律 | 出处 | 对本方案的后果 |
|---|---|---|---|
| ① | **不改行为**：这张表是纯数据 + 读取，没有 `if (plugins.x)` 去改运行时逻辑；开关仍由各处既有代码读自己的 `config.*` | `:20-21` | **登记是最后一步**，不是第一步 |
| ② | `hot` 必须**取证**（判据只有一条：那段代码是不是每轮/每条消息重读 `config.*`）；**把 cold 写成 hot 是一种恶意** | `:23-26` | 每个插件都必须先能指出"运行期在哪读这个键" |
| ③ | `enabledPath` 指向**既有配置键**，不是新键 | `:28-30` | **先有真配置键、且运行期真的读它**，才谈得上登记 |

**实测结论（这决定了工作量的形状）**：我逐个查了候选功能的配置键 ——

```
corpus / deliveryGate / deliveryLedger / markers / sessionState / wake / profile / adminTools
→ 配置里一个都没有
```

**∴ 现状是**：这些能力**已经是"模块"，但还不是"插件"** —— 它们没有开关，所以既登记不了，也谈不上"关掉会怎样"。
**每个功能做成插件 = 三步**：**(a)** 加配置键并定默认 → **(b)** 让运行期**真的读**它（这一步才产生 hot/cold）→ **(c)** 登记进 `BUILTIN_PLUGINS` 并写清 `what`/`offEffect`/`why`。

### 1.1 开关形态（`pluginSwitchKind`）

| kind | 现状 | 界面渲染 |
|---|---|---|
| `boolean` | 大多数（`x.enabled !== false` 即开） | Switch |
| `enum` | **仅 `persona.preset`**（"关" = 取值 `none`） | **仍然只渲染一个 Switch**（`ExtensionsTab.tsx:535`）+ 一句"打开时用的是默认档"（`:546-550`） |
| `list` | `access.adminUsers` 等 | 不渲染 Switch，改成「去维护」按钮（`:529-533`） |
| **`choice`**（二选一） | **✅ 0.2.3 已实现**（§4.1），**首个使用者 = `wake-policy`**（S3，2026-09-27） | 规格已写进 `CONFIG-UI.md` §2.10：**N 个并列按钮**，不渲染 Switch |

> ★ 在 `choice` 之前，"二选一按钮"在界面上**并不存在**：enum 被压成一个开关，真正的选择要去「人设」页做。
> 现在机制已就绪，**并且有了第一个真使用者**（S3 的 `wake-policy`，2026-09-27）——
> 顺带补掉了一个潜伏的缺陷：`extensions-service.mjs` 的 `toggle()` 原先对 `choice`
> 会**把布尔值写进一个只认字符串的键**（配置里出现 `"policy": true`，运行期按"不是
> semantic"处理 ⇒ 界面显示保存成功、实际什么都没发生）。现在对 `choice` 一律 **400 +
> 说出可选取值**，并且测试断言**盘上一个字节都没写**。

## 2. 划分总表

按你的三条规则：**冲突→二选一 / 独立→拆开 / 不独立→合并**。

### 2.1 冲突 ⇒ **同一个插槽 + 单值键 + 实验性标注**（定稿规则）

**定稿做法**（指令②）：把**新增功能与已有功能放在一起**（同一个插槽），用**同一个单值配置键**表达
—— 于是「启动一个自动关掉另一个」是**键的天然语义**；hermes 那一侧标注 **「实验性」**。

| 插槽（建议键） | 选项 A（= 现状） | 选项 B（hermes 式，标**实验性**） | 为什么必须是一个键、而不是两个开关 |
|---|---|---|---|
| `wake.policy` | `rule` — 规则唤醒：私聊/@/关键词 → **必答** | `semantic` — 语义唤醒：判定器决定说/不说，**可沉默** | 二者回答同一个问题「这条消息要不要回」。两个独立开关会出现"两个都开"（判据打架）与"两个都关"（机器人哑掉） |

> `memory.scope`（群聊隔离 ⟷ 跨群联想 EPI）原本也属这一类冲突，
> 按指令③**已移出本轮范围** —— 见 §2.4。

**⚠️ 第三个"冲突"：`memory.write`（记忆的写入权归谁）— 应你的提问补记在案**

| | A（= 现状） | B（= hermes 式） |
|---|---|---|
| 谁写记忆 | **桥接写**：模型只能在回复里"提议"（`<<<MEMORY …>>>` 标记），由桥接校验、筛选、落盘 | **模型写**：给模型一套 `memory_*` 工具，它自己读/写记忆库（hermes 有 22 个动作） |
| 冲突点 | **同一份记忆，谁能写** —— 二者不能并存（并存 = B 绕过了 A 的全部闸门） | |

**为什么我建议不提供 B**：B 就是那次事故的**根因**，不是"另一种风格"。
`memory-store.mjs:7-15` 记着：旧设计正是"让模型自己用 write 工具维护记忆"，
而当时 `#buildPrompt` 把每个群发言人都标成"（管理员）"，
于是**模型把一个普通群友写进记忆并标成管理员，之后每一轮都读到它**。
所以 A 是那次事故的**修复**。

→ **按你的规则**（冲突 ⇒ 放一起 + 标实验性）：将来若要动记忆，就把它做成同一插槽的第二个取值并标「实验性」。
→ **按指令③**：本轮**不动记忆模块**，这一项**不实施**。

### 2.2 不独立 ⇒ **放在一起**（合并进一个插件，内部子设置）

| 功能（hermes 借来的） | 并进哪个插件 | 为什么不能独立 |
|---|---|---|
| 两级判定窗口（对话态 1s / 旁观 5s）、`decision_epoch` 失效、群噪等级、指向证据层级、名字直呼、poke 注视、fail-closed 兜底分层 | **`wake.policy = semantic` 的内部实现** | 全部只为"语义判定"服务；脱离判定器它们没有对象 |
| continuation（对话态自动接续）、退出闸门（连续两次才准退）、LLM 版 EpisodeState | 同上，作为 **semantic 模式下的子选项** | 依赖语义判定产生的对话态；规则模式（必答）下没有"态"这回事 |
| 工具面扩充（合并转发、群管理、表情回应等）、`allow-list` 加固、危险动作档位 | **`qq-tools`** | 同一个 MCP server、同一次装配（`mcp-profile.mjs` 的标记块）—— 拆两个插件会出现"工具开着但没装配"的空转态 |
| 身份装载（SOUL「称呼」节 → 正式名/别名）、反提示词注入段 | **`persona`** | 都是"它是谁"的提示词段，同一段文本，拆开会自相矛盾 |
| 记忆增强（每小时蒸馏、检索排序、TTL/衰减、冻结前缀、supersede） | **`memory`**（**已移交另一会话**，见 `docs/memory-borrow-handoff.md`） | 同一份记忆的读写路径 |

### 2.3 独立 ⇒ **新增插件**

| 新插件（建议 id） | 它是什么 | 为什么算独立 | 前置（§1 的三步） |
|---|---|---|---|
| **`delivery`** 投递可靠性 | 出站幂等键（含来源消息 id）+ 投递账本 + 部分投递记录 | 有**自己的配置面**（幂等窗口、账本上限/保留期），且**能独立关闭** —— 关掉就退回今天的"内容去重 + 尽力发送" | 新增 `delivery.idempotencyKey`、`delivery.ledger`（设计已就绪：`docs/plugin-ization-design.md` §14） |
| **`corpus`** 本地语料检索 | 把消息落 SQLite 并支持中文全文检索 | 代码**已存在**（`corpus.mjs`，0.2.1）但**没有开关**；关掉它不影响回复质量，只影响"能不能搜过去" | 新增 `corpus.enabled`，并指出运行期在哪读它 |

> **不登记为插件的（故意的）**：投递前终检门（`delivery-gate.mjs`）、隐私双侧闸门、篡改回滚、凭据发现规则。
> 它们是**边界不是功能** —— 做成开关等于让"关掉功能"这个动作制造出新缺陷（同一理由见设计文档 §3.1）。

### 2.4 ⛔ 本轮**移出范围**的（按指令③：记忆模块、提示词模块不要动）

| 原候选 | 为什么移出 |
|---|---|
| `memory.scope` 二选一（`isolated` 群聊隔离 ⟷ `crossGroup` 跨群联想） | **记忆模块** |
| `memory.write` 二选一（`bridge` 桥接落盘 ⟷ `model` 模型直写） | **记忆模块**（见 §2.1 的说明） |
| 记忆增强（每小时蒸馏、检索排序、TTL/衰减、冻结前缀、supersede） | **记忆模块**（且已移交另一会话：`docs/memory-borrow-handoff.md`） |
| `persona.identityFromSoul` / `persona.antiInjection`（身份装载、反注入段） | **提示词模块**（属提示词段落化，`docs/plugin-ization-design.md` §13） |
| ~~`corpus` 插件（本地语料检索）~~ | ✅ **已确认不算记忆模块**（用户 2026-09-27 拍板"可以做"）⇒ 移回范围，按 S5 落地。判据：记忆是 `memory/*.md`，**模型可以提议写**（标记 + 桥接校验 + 篡改回滚）；corpus 是 append-only 的 `runtime/corpus.sqlite`，**模型只能读**（一个工具），永远写不进去。数据面、读写权、失败后果都不同。两处相邻（都写工作区、都过 `privacy.screenForStore`）不足以把它归进记忆模块 |

| name / icon | 唤醒策略 / 📣 |

## 4. "二选一"要新增的机制（两处，都很小）

### 4.1 ✅ 已做（本轮）：`enum` → `choice` 泛化

`src/plugins.mjs` 里 `pluginSwitchKind` 原先把 enum **硬编码成 `persona.preset`**，现在改为声明式：

```js
// 插件自己声明选项；没有声明时退化成今天的 boolean
/** @property {{kind:'choice', options:{value,label,desc?}[], value:unknown}|undefined} choice */
```

- `switchKind` 返回值增加 `'choice'`；

### 5.1 ★★ S3 落地时的三处收窄（都是刻意的，不是漏做）

| # | 初稿 | 实际做的 | 为什么收窄 |

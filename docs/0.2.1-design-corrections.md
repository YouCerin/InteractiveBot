### 1. 现状核实（**代码里已经是对等的**）

| 判定 | 位置 | 实现 |
|---|---|---|
| 私聊 tier | `roster.mjs:277-279` | `if (adminIds().includes(id)) return TIER.ADMIN` |
| 群聊 tier | `roster.mjs:292-294` | `return adminIds().includes(id) ? TIER.ADMIN : TIER.USER` |
| 判定入口 | `roster.mjs:302-314` | `decide({kind, peerId, senderId})` 两条分支，**同一个 `adminIds()`** |

**结论：`tier` 层面本来就同等。** 所以这条要求不是"新增能力"，而是**消除两处残余的不对等**，
并**用测试把它焊死**（否则以后会漂移）。

### 2. 两处真实的不对等

#### 2.1 `persona.callerName` 只对管理员**私聊**生效

```js
// bridge.mjs:624-628
// 私聊：优先用**主人的自称**（人设里的 callerName），因为那是他要看到的名字；
if (this.config.persona?.callerName && this.roster?.tierOfPrivate?.(uid) === 'admin') {
  chatName = String(this.config.persona.callerName)
  chatNameSource = 'persona.callerName'
}
```

**问题**：管理员在群里 @ 机器人时，`chatName` 用的是**群名**，不是他的自称。
于是"主人"在群里的待遇与私聊不同。

**但这里要小心**：`chatName` 的语义是"**这个会话叫什么**"（群名 / 对方昵称），
不是"说话人叫什么"。管理员在群里时，**会话名本来就该是群名**。

→ **判定**：这一处**不是不对等，是语义正确**。但 `callerName` 在群聊里确实完全没用上，
而 `bridge.mjs:1169-1171` 里管理员私聊会用 `callerName` 标注 `who`：

```js
const who = isAdminTier
  ? this.config.persona?.callerName && reason === REASON.PRIVATE
    ? `（${this.config.persona.callerName}，管理员）`
    : '（管理员）'
  : '（普通用户，只读）'
```

**这里才是真不对等**：管理员私聊被标注成 `（主人的自称，管理员）`，
管理员在群里只被标注成 `（管理员）`——**丢了"他是谁"**。

**修法**：两条分支合并，**按人**标注，不按会话类型：

```diff
- const who = isAdminTier
-   ? this.config.persona?.callerName && reason === REASON.PRIVATE
-     ? `（${this.config.persona.callerName}，管理员）`
-     : '（管理员）'
-   : '（普通用户，只读）'
+ // 权限标签只由 tier 决定；"他是谁"由身份核实（identity）决定，与会话类型无关。
+ // callerName 是"主人希望被怎么称呼"，所以**只要在跟主人说话就用它**，
+ // 私聊与群聊一致 —— 这正是"同等优先级"的落点。
+ const isOwner = isAdminTier && Boolean(this.config.persona?.callerName)
+   && String(identity?.userId || senderId || '') === String(this.config.access?.adminUsers?.[0] ?? '')
+ const tierLabel = isAdminTier ? '管理员' : '普通用户，只读'
+ const who = isOwner
+   ? `（${this.config.persona.callerName}，${tierLabel}）`
+   : `（${tierLabel}）`
```

⚠️ 注意 `isOwner` 的判据：原代码用 `reason === REASON.PRIVATE`（**会话类型**），
新代码用"**说话人是不是主人**"（比较 `senderId` 与主人）。后者才是对的语义，
且自然覆盖群聊场景。（`adminUsers[0]` 当主人是现有约定，见 `index.mjs:614` 的用法。）

#### 2.2 群聊里管理员**不被 @ 就不触发**

`trigger.mjs` 的群聊判定是：**被 @ 或命中关键词**（`trigger.groupEnabled` 默认 `false`）。
这与权限无关——**管理员在群里也必须 @ 或命中关键词**才会被唤醒。

**用户原话是"管理员在群内 @ 应当有同等优先级"**，所以**这一点是符合要求的**：
要求的就是"**被 @**"这个前提下的对等。

→ **判定**：不需要改。但要在文档里写明，避免被误解成"管理员在群里说任何话都触发"
（那会破坏 `trigger.groupEnabled` 的 fail-closed 设计，也会放大账号风控风险）。

### 3. 需要焊死的三条（防止以后漂移）

| # | 规则 | 为什么 |
|---|---|---|
| 1 | **禁止任何 `kind === 'private' ? … : …` 形式的权限分叉** | 群聊 vs 私聊是**会话属性**，不是**权限属性**。权限只由 `tier` 决定 |
| 2 | `buildPermissionInstructions(tier, kind)` 的 **`kind` 只允许影响"会话形态"措辞**（例如"群里别刷屏"），**不得影响权限内容** | 现状已经如此，但要加测试 |
| 3 | 任何"仅管理员"的能力，私聊与群聊都要能给 | 例如记忆写入的 `directive` 档 |

### 4. ⚠️ 但要复查一处**刻意的不对等**

`applyMemoryItems`（`memory-store.mjs:327-330`）**故意**禁止管理员在群里写 `directive`：

```js
if (kind !== 'private') {
  ignored.push({ scope, entry, why: '行为指令请在私聊里告诉我（群聊里的话会带到所有群，不适合）' })
}
```

**理由站得住**：`directive` 是**跨群生效**的行为指令，在群里下达会**当着所有人改机器人行为**，
且群聊上下文最杂、最容易被话术带偏。

**这算不算违反"同等优先级"？** 我判定**不算**，因为：
- 它是**对指令档的额外保护**，不是对管理员身份的降级；
- 管理员在群里仍然拥有**全部其它管理员能力**；
- 群聊**不是安全信道**：在群里下达跨群指令会当着所有人改机器人行为。

→ **建议保留**，但在文档里**显式标注为"刻意的例外"**，并写明理由，
避免以后被人当成 bug "修"掉。

### 5. 验收（管理员优先级对等）

| # | 断言 |
|---|---|
| **A1** | 同一管理员：私聊 @（恒响应）与群里被 @，`tier` 都是 `admin`，且 `buildPermissionInstructions` 的**权限内容**逐字相同 |
| **A2** | 权限段的差异**只允许**出现在"会话形态"措辞上，不得出现权限能力差异（测试断言逐字比对，允许白名单内的差异） |
| **A3** | 管理员在群里被 @ 时，`who` 标注包含 `callerName`（与私聊一致） |
| **A4** | 管理员在群里被 @ 可以：写文件、跑命令、发消息、写记忆 `fact`；**不能**写 `directive`（刻意的例外，测试固化） |
| **A5** | 全仓库 grep `kind === 'private'` 与 `reason === REASON.PRIVATE` 的权限分叉点，**为零**（除 §4 那条被固化的例外） |
| **A6** | 普通用户：私聊与群里被 @，权限内容逐字相同 |

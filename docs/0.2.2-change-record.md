写规范时**顺手发现并修掉两个真实缺陷**（都属于"文档说 A、代码做 B"这一类，正是规范要封的缝）：

1. **`ctx.toolName(id)` 与 `api.toolName(id)` 不同口径**（`mcp/mcp-skills-server.mjs`）：
   前者返回 MCP 服务器的**内部注册键**（`<服务器名>::<裸名>`），而模型能调的只有
   `mcp__skills__<id>__<tool>` —— 技能照着它写给模型 ⇒ 模型去调一个不存在的工具，
   **失败得很安静**（只会说"查不到"）。已改成同一个口径（命名规则仍只有一处实现），
   并在 `verify-mcp-skills.mjs` 补 2 条断言钉住（该项已从"两条口径"变回"一条"）。
2. **同 `id` 两个目录会静默撞车**（`src/extensions.mjs` 的 `discoverSkills`）：
   工具裸名是 `<id>__<工具>`，两份同 id 的目录（回滚时最常出现：正式目录旁边一个备份）
   会让 tools/list 出现两条同名工具，而派发只命中**先出现**的那条 —— readdir 顺序取决于文件系统，
   于是可能"静默跑的是备份那份"。现在**两个都标红、都不装载**（fail-closed），
   并指名道姓列出是哪几个目录、为什么危险、该怎么办；`verify-extensions.mjs` 新增一节
   **②-b**（4 条断言，含"不同 id 不受影响"的对照组）。

**另外修掉一个会随机变红的断言**（`mocks/verify-extract.mjs`）：原断言是
`Math.abs(confidence - 0.5) < 1e-9`，而置信度是 `base × 0.5 ^ (ageDays/60)`（半衰期 60 天）——
`upsertRecipe` 与 `pickRecipes` 之间隔着几次文件 IO，值必然略低于 0.5；
整套测试串跑时实测漂到 `0.4999999989303284`（差 1.07e-9），**把整条链判红**。
现在断言的是意图（不高于 base + 只允许那点时间衰减，1e-3 ≈ 该公式下跑两小时的量级，
而"算不算经验"的闸门是 0.15）。★ 这类"偶尔红"的断言比"永远绿"更坏：它会让真失败被当成噪声。

## 2. 事故与修复（本轮最重的一节）
### 2.1 `PROJECT.json` 被 PowerShell 重编码写坏

- **怎么坏的**：一条命令 `(Get-Content PROJECT.json -Raw) | Set-Content PROJECT.json -Encoding UTF8`
  —— PowerShell 5.1 的 `Get-Content` 默认按**系统 ANSI（GBK）**读，于是 UTF-8 文件被误解码、再按 UTF-8 写回。
- **损坏模型**（用对照实验确认）：原始字节流被**每 2 字节**一组按 GBK 解码；非法的组（前导字节是某个 UTF-8 字符的**最后一字节**、跟随字节是 ASCII < 0x40 或 0x7F）→ 输出一个 `?` 并**吃掉这两个字节**。
  即：每处**丢掉一个 ASCII 字符**（多为 `"`、空格、`*`），且它前面那个汉字**少了最后一个字节**（64 选 1，**无法精确还原**）。实测共 **3277 处**。
- **为什么没人发现**：乱码照样是**合法 JSON** —— `npm test` 全绿，只有人去读那几行说明文字时才发现"这话怎么读不通"。

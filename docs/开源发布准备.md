## 1. 许可证：为什么选 Apache-2.0

| 候选 | 为什么不选 / 选 |
|---|---|
| MIT | 最短最宽，但**没有显式的专利授权**与"贡献者专利报复"条款。本项目要跟 Node/DSH 生态里的 npm 包互操作，Apache-2.0 的专利条款对下游更清楚 |
| GPL-3.0 | 会传染到使用者的整套部署；一个"接自家 QQ 的桥接"没有必须 copyleft 的理由，反而挡住别人用 |
| **Apache-2.0** ✅ | 明确专利授权 + 允许商用/闭源二次开发 + 要求保留 `NOTICE` 与变更声明，与项目里已有的 MIT 依赖（`ws`、Node）兼容 |

落地文件：

- `LICENSE` —— Apache-2.0 全文（逐字，未改）
- `NOTICE` —— 版权行 + "第三方组件见 THIRD-PARTY.md"
- `THIRD-PARTY.md` —— 逐条列出第三方组件、版本、许可证、出处、**以及合规缺口**

### 2.1 发布前修补：把"跳过"和"通过"分开

开源前把 62 套拿**放开 spawn** 的会话重跑了一遍（此前一直在受限沙箱里跑），当场 17 项红 ——
这是本项目第一次知道 `verify-onebot` / `verify-mcp` / `verify-live` 里到底有没有问题：

1. **真产品问题（已修）**：隐私闸的「生物特征」判据认**裸词**（连类别名 `生物特征` 都算），
   于是**我们自己的提示词**（"不要记隐私：…生物特征（指纹/人脸/声纹）"）被判成含隐私，
   输出侧把**整条回复吞掉**。真机上"指纹锁坏了怎么办"这类正常回答同样会被吞。
   已收紧为只认**数据形态**，并在 `verify-privacy` 里留下正例 3 条 / 反例 3 条锚点。
2. **两套套件自身陈旧（已修，16 项）**：它们**从没真跑过**（受限沙箱整份跳过 ⇒ `exit 0` ⇒
   链条显示"全绿"），于是与实现慢慢脱节 —— 分片时序、投递终检门删段标题、来源标注里的 `#id`、
   `qq_api` 从黑名单改白名单后的措辞。

完整记录见 `docs/0.2.7-release-notes.md` §5。**给开源读者的一句话**：本仓库的测试链条在
受限沙箱里会**打印"跳过"并仍然退出 0** —— 那是设计上的诚实（不假装通过），但**不等于通过**，
要复现"全绿"必须在正常 Windows 会话里跑。

## 3. 真机标识 → 占位号码

原则：**只换数字，不换语义**。文档里"真机取证"的结论、行数、字节数、时间戳全部保持原样，
只有号码本身变了 —— 这样历史记录仍然可读、可复算，同时不再公开任何真实账号。

| 占位号码 | 是谁 |
|---|---|
| `200000001` | 机器人自己的 QQ（OneBot `uin`） |
| `100000001` | 使用者（管理员） |
| `100000002` | 群里的一位成员 |
| `700000001` / `700000002` | 两个群号 |

⚠️ **映射表本身不公开**（真机号码 → 占位的对应关系只存在本地 `packages/qq-bridge/cache/scrub-ids.mjs`，
而 `cache/` 在 `.gitignore` 里）。写进仓库等于换个地方公开真号码。

**替换脚本**：`packages/qq-bridge/cache/scrub-ids.mjs`（本地工具，不入库）。
两个细节是有意的：

- 按 **latin1 字节**替换，不是 utf8 字符串 —— 目标是纯 ASCII 数字，字节级替换不会破坏
  任何非 UTF-8 内容（仓库里 `snowluma-log.mjs` 的注释就含 GBK 乱码样本），也保证"没命中的字节一个都不改"。
- 带 NUL 的二进制文件整体跳过（唯一命中者是 `assets/icon.ico`，与号码无关）。

**唯一的例外**：`_release/` 里的旧发布包里还有真号码，但那些文件既不进索引也不进新历史（见 §4）。

## 4. 发布包改走 GitHub Releases + 历史重写

**为什么**：`_release/` 曾经入过库，代价被低估了：

1. 每个版本的包都进历史 → `.git` 涨到 **354.8 MB**（`git count-objects -vH` 的 `size-pack` 165.77 MiB）；
2. `vendor/node/node.exe`（85.6 MB）走 **Git LFS** → 仓库里存的只是 **133 字节指针**。
   别人 clone 后若没装 git-lfs，拿到的是一个"看起来正常"的假文件，发布包**跑不起来**，
   而报错完全指不到这里；
3. GitHub 仓库本来就不该承担二进制分发。

**怎么做**（在**本地克隆**里做，开发仓库不动）：

```bash
git clone --local <原仓库> InteractiveBot-public
cd InteractiveBot-public
# ① 把 _release/ 从**所有提交**里删掉（index-filter：只改索引，不检出树，快）
git filter-branch --force --index-filter \
  "git rm -r --cached --ignore-unmatch _release" \
  --prune-empty --tag-name-filter cat -- --all
# ② 再把**历史里**的真机号码换成占位号码（tree-filter：逐棵树检出再改内容）
git filter-branch --force --tree-filter \
  "node <本地>/scrub-ids-tree.mjs" \
  --prune-empty --tag-name-filter cat -- --all
# ③ 清 refs/original + reflog 并 gc，否则旧对象还留着、体积降不下来
git for-each-ref --format='%(refname)' refs/original | while read r; do git update-ref -d "$r"; done
rm -rf .git/refs/original && git reflog expire --expire=now --all && git gc --prune=now --aggressive
```

> 没有用 `git filter-repo`（本机没有 Python 环境，`pip` 不可用），所以走 git 自带能力。
> 两遍是刻意的：先删大目录（便宜），再改内容（贵，71 个提交逐棵树过一遍）。
> 替换脚本按 **latin1 字节**改，只认纯 ASCII 数字，因此不会破坏任何非 UTF-8 内容。

### 5.1 历史重写实测（在本地克隆里做过一遍）

| 指标 | 重写前 | 重写后 |
|---|---|---|
| `.git` 目录 | 356.2 MB | **4.2 MB** |
| `git count-objects -vH` 的 `size-pack` | 165.77 MiB | **≈4.1 MiB**（每次重打包有 10KB 级浮动，别当成精确值） |
| `git log --all -- _release` | 13 个提交 | **0** |
| `git rev-list --objects --all` 里的 `_release` 对象 | 143+ | **0** |
| `git log --all -S <真机号码>`（5 个号码逐个查） | 命中 | **全部 0** |
| `git log --format=%ae`（**提交元数据**） | `YoCerin <真机QQ>@qq.com` | **`YoCerin <150148477+YouCerin@users.noreply.github.com>`**（GitHub 匿名邮箱） |
| 提交信息正文里的号码 | 各 1 行 | **全部 0 行** |
| `git rev-parse HEAD^{tree}` | — | **与开发仓库当前 HEAD 逐字节相同** |

- **被剪掉的提交：恰好 2 个** —— 只动 `_release/` 的那两个（发布包入库那类），删掉该目录后它们变成空提交，
  被 `--prune-empty` 剪掉。源码提交一个没少。
  （这里**刻意不写"71 → 69"这种绝对数**：写完这份文档本身又是一次提交，两边都会 +1 ——
  任何"把提交总数写进文档"的做法都会立刻过期，能复算的只有"被剪掉 2 个"这个差额。）
- **HEAD 树哈希前后一致**：重写只影响历史，**不动当前内容** —— 这也是"重写没错"最硬的一条证据
  （若它变了，说明脚本误改了某个文件）。★ 这条还真抓到过一次自己的错：写完这份文档时我在示例命令里
  留了一个真机号码，**只有**它报"树哈希不一致"，并精确指出是哪个文件。
- ⚠️ **开发仓库保持原样**：重写不可逆，所以只在副本里做，推 GitHub 也从副本推（见 §7）。
  开发仓库留着完整历史，自己继续用。
- **发布包也扫过一遍**：`_release/InteractiveBot-0.2.8-win-x64/` 的真机号码**零命中**
  （用同一个替换映射逐字节扫）—— 那个 zip 是要公开下载的，不能只清仓库不管包。

### 5.2 ★ 第一版漏掉的一处：**提交元数据**里的号码

第一版重写只做了 `--tree-filter`（改**文件内容**），随后我用 `git log --all -S <号码>` 验证"零命中"就收工了。
这是**验证口径错了**：`-S` 搜的是**树的 diff**，而号码还写在两个它够不着的地方 ——

1. **每一条提交的作者/提交者邮箱**：`YoCerin <真机QQ>@qq.com`（73 条全中）。
   后果比文件内容更直接：**一 push 就进了 GitHub 的提交图**，而且 GitHub 会拿它去关联账号。
2. **提交信息正文**：有 5 条信息里各写了一行真机号码。

修法与教训（都已落进 `cache/rewrite-history.sh`）：

```bash
git filter-branch --force \
  --tree-filter "node <tree scrub>" \
  --msg-filter  "node <stdin scrub>" \   # ← 提交信息
  --env-filter  "GIT_AUTHOR_EMAIL=$(printf %s "$GIT_AUTHOR_EMAIL" | node <stdin scrub>)
                 GIT_COMMITTER_EMAIL=$(printf %s "$GIT_COMMITTER_EMAIL" | node <stdin scrub>)
                 export GIT_AUTHOR_EMAIL GIT_COMMITTER_EMAIL" \
  --prune-empty --tag-name-filter cat -- --all
```

**教训（写给以后）**：脱敏的检查面 = **文件内容 + 提交信息 + 提交元数据**，
而 `git log -S` 只覆盖第一项。要验证就必须**分别验证这三样**：

```bash
git log --all -S <号码> --oneline | wc -l          # ① 内容（树的 diff）
git log --all --format='%s%n%b' | grep -c <号码>   # ② 提交信息
git log --all --format='%ae%n%ce' | grep -c <号码> # ③ 元数据 ← 第一版漏的就是这条
```

**邮箱用哪个值（已定）**：用 **GitHub 匿名邮箱**
`150148477+YouCerin@users.noreply.github.com`（GitHub → Settings → Emails 里
"Keep my email addresses private" 给出的那个地址）。为什么不是占位号也不是真邮箱：

| 方案 | 提交挂到账号下 | 泄漏号码 |
|---|---|---|
| 真 QQ 邮箱 `YoCerin <真机QQ>@qq.com` | ✅ | ❌ 76 条提交的元数据全部公开可搜 |
| 占位号 `100000001@qq.com` | ❌（不是你的地址） | ✅ |
| **GitHub 匿名邮箱**（已采用） | ✅ | ✅ |

- 这个地址**永不可能属于别人**（它由 GitHub 按你的账号 ID 生成），所以既不会误伤第三方，
  也不会把号码写进去；**改它只需改一行**：`GIT_COMMIT_EMAIL='...' sh rewrite-history.sh ...`
  （脚本里那个环境变量就是为这件事留的）。
- 作者**名字**仍是提交时用的 `YoCerin`（与 GitHub 用户名 `YouCerin` 差一个字母）。
  名字不影响归因（GitHub 按邮箱认），要统一可以顺手改，但那属于「记录当时是谁提交的」，
  这一版**没动**。

## 6. 没做的 / 未验证的（如实列）

1. **重写后的历史没有在别的机器上 clone 验证过**（本地 `git fsck` / 树哈希 / `-S` 三样都过了，
   但没有第二台机器做一次真实 clone）。推之前建议先 `git clone` 到自己另一个目录跑一次 `npm test`。
2. **发布包里没有随附 Node.js 的 `LICENSE`**（再分发合规缺口）。原因与补法写在 `THIRD-PARTY.md`。
   尝试过联网取官方 `LICENSE`，但这台机器**没有出口网络**（DNS 都解析不了），所以没取到。
3. **没有配 CI**。62 个套件目前只能在开发机上手动 `npm test`；公开后建议加一条
   "PR 上跑离线套件"的工作流（不需要 QQ、不需要 DSH、不需要网络）。
   ⚠️ 若真加 CI，注意 `verify-onebot` / `verify-mcp` / `verify-live` 在**受限环境里会跳过并退出 0**
   （见 §2.1）—— CI 上要么给足权限真跑，要么**显式承认它们没跑**，别让绿色骗人。
4. **没有 `.github/` 下的 ISSUE 模板 / CODE_OF_CONDUCT**。
5. **`reference/` 里两份上游原件的许可证状态未确认**（上游没写许可证）。已在
   `THIRD-PARTY.md` 里声明，并写明"原作者若不同意可要求移除"。
6. **第二台干净机器上的"发布包能否跑起来"仍未验证** —— 这一条从 0.2.7 打包时就挂着，
   与开源无关，但公开时值得一起做掉。

## 7. 开放之后的三步（人工，必须做）

> 下面三条里，第 1、3 条只能由你在浏览器/账号里做；第 2 条的仓库已在本机备好（见 §5.1）。

1. 在 GitHub 建**空仓库**（不要勾 README / .gitignore / License —— 勾了首次 push 会打架）。
   仓库名建议 `InteractiveBot`，可见性先 **Private**（确认没问题再改 Public）。
2. 从那个**重写过历史的克隆**里 push（**不要**从开发仓库推，否则真机号码与发布包历史又回去了）：

   ```bash

   git push -u origin main
   ```

   ★ **`origin` 已经被占用了，别用 `git remote add`**（2026-09-30 真机踩过：报
   `error: remote origin already exists`）。原因：这份克隆是 `git clone --local <开发仓库>` 建的，
   **origin 自动指向了本机开发仓库的路径**。正确做法是**改地址**，不是再 add 一个：

   ```bash
   git remote set-url origin https://github.com/YouCerin/InteractiveBot.git
   git remote -v     # fetch 与 push 两行都必须是 github.com
   ```

   ★ 顺带清掉克隆里两个"假远端分支"：`origin/backup/0.2.4`、`origin/backup/0.2.5` 其实指向的是
   **本地开发仓库**（GitHub 上并不存在），改完地址后它们会显示成"GitHub 上的分支"——
   `git branch -a` 看到就会误导人。删掉即可（开发仓库里还留着，什么都没丢）：
   `git update-ref -d refs/remotes/origin/backup/0.2.4`（另一条同理）。

   ★ **仓库里确实有 2 个旧 tag**：`0.2.3`、`0.2.5-desktop-sealed`（内容也是重写过的 ——
   用 `-S` 查过，号码 0 命中）。`git push -u origin main` **不会**推它们；想一起推用
   `git push --tags`。**别用 `git push --mirror`**：那会把本地所有 ref（含开发仓库带过来的备份分支）
   一起推上去，而这份克隆**不是**开发仓库的镜像。

   ★★ **不要把开发仓库加成第二个 remote**：`git pull` 会把**没重写过的历史**（真机号码、发布包对象）
   拉进来，等于把刚做的脱敏悄悄作废。开发仓库有新提交时的正确做法是**重跑一次克隆 + 重写**
   （见 §4），不是 pull。

   推之前建议先自查一次（四条命令，都要是 0 / 空 / 0 / 0）：

   ```bash
   git log --all --oneline -- _release | wc -l          # 0：历史里没有发布包
   git status --short                                   # 空：工作区干净
   # 再把**你自己知道的那几个真机号码**分别丢进这三条查一遍（分别覆盖 内容 / 提交信息 / 元数据）：
   #   git log --all -S <号码> --oneline | wc -l              # ① 文件内容
   #   git log --all --format='%s%n%b' | grep -c <号码>       # ② 提交信息
   #   git log --all --format='%ae%n%ce' | grep -c <号码>     # ③ 作者/提交者邮箱
   ```

   ★ 三条缺一不可：第一版只查了 ①，于是 `YoCerin <真机QQ>@qq.com` 在 73 条提交的**元数据**里
   一路留到了推送前（详见 §5.2）。

     `git tag -a v0.2.8 -m "0.2.8 —— 改名 InteractiveBot + 发布前两处真修补" && git push origin v0.2.8`
   - 标题：`0.2.8 —— 改名 InteractiveBot（「小鲸鱼」QQ 交互式机器人）+ 发布前两处真修补`
   - 附件：`_release/InteractiveBot-0.2.8-win-x64.zip`（**33.4 MB**，本机已重打：改名 + 隐私闸修复 + 图标 + 冒烟 54/54）

   ### ★ 上传附件时的 25 MB 陷阱（2026-09-30 真机踩过）

   **25 MB 不是 Releases 的限制** —— Release 附件上限是 **2 GB**
   （[关于大文件](https://docs.github.com/pt/repositories/working-with-files/managing-large-files/about-large-files-on-github)）。
   **25 MB 是"用浏览器把文件上传进仓库 / 贴进正文"的限制**
   （[往仓库添加文件](https://docs.github.com/zh/repositories/working-with-files/managing-files/adding-a-file-to-repository)、
   [附件](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files)）。
   有人往 Release 传大文件时也被 25 MB 挡住过
   （[community #146417](https://github.com/orgs/community/discussions/146417)）—— 基本都是**走错了入口**。

   **正确入口**：Release 编辑页里那个 **"Attach binaries by dropping them here or selecting them"**
   的框（在 release notes 输入框**下面**），点它或把 zip 拖进去；**不要**用仓库首页的
   "Add file → Upload files"。

   **若那条路仍被挡**（本机没有 `gh`，但有 `curl`）：走 REST API。先建 release（不带附件），
   再拿它的 id 并上传 —— 注意上传域名是 **`uploads.github.com`**：

   ```bash
   PAT=<你的 token>            # classic: 勾 repo；fine-grained: Contents 读写
   REL=$(curl -s -H "Authorization: Bearer $PAT" \
     https://api.github.com/repos/YouCerin/InteractiveBot/releases/tags/v0.2.8)
   ID=$(echo "$REL" | grep -o '"id":[0-9]*' | head -1 | cut -d: -f2)
   curl -X POST -H "Authorization: Bearer $PAT" -H "Content-Type: application/zip" \
     --data-binary "@_release/InteractiveBot-0.2.8-win-x64.zip" \
     "https://uploads.github.com/repos/YouCerin/InteractiveBot/releases/$ID/assets?name=InteractiveBot-0.2.8-win-x64.zip"
   ```

   （装了 `gh` 的话更省事：`winget install --id GitHub.cli` → `gh auth login` →
   `gh release upload v0.2.8 _release/InteractiveBot-0.2.8-win-x64.zip`。）

   **另一条路：把包拆成两份**（本机实测过）——
   - **完整包 33.4 MB**：32 MB 几乎全是自带的 `vendor/node/node.exe`（未压缩 85.6 MB）；
   - **lite 包 1.38 MB**：同一棵源码树**去掉 `vendor/node/`**，任何上传入口都传得上去，
     代价是要求使用者**自备 Node ≥22**（`start.bat` 本来就会回落到系统 `node`）。
   建议：完整包优先（目标用户是"不想装东西"的人），lite 只作为备用资产。
   造 lite 包：复制 `_release/InteractiveBot-0.2.8-win-x64` → 删掉 `vendor\node` → `Compress-Archive`。

   ⚠️ **永远不要 `git push` 这个 zip 进仓库**：单文件 100 MB 硬限、而且我们刚把二进制从仓库历史里清出去
   （见 §4/§5.1）。

   之后把仓库从 Private 改成 Public（或先 Private 跑几天）。

## 8. 以后提交时的约定

- **不要再把真机号码写进任何受跟踪文件**（日志片段、截图文本、`PROJECT.json` 的取证描述都算）。
  需要引用时直接用占位号码。
- ★ **提交前跑一次** `node packages/qq-bridge/cache/scrub-ids.mjs`（默认只报告、不改文件；
  加 `--write` 才写）。它是本地工具，`cache/` 已忽略，所以它自己不会进仓库。
  **这条是踩出来的**：写这份文档时，我在示例命令里顺手写进了一个真机号码 ——
  而当时**唯一**抓到它的是"重写前后 HEAD 树哈希不一致"这个检查（树的差异精确指向那个文件）。
- ★ **验证脱敏要看三处，不是一处**：文件内容（`git log -S`）、提交信息（`--msg-filter`）、
  提交元数据（`--env-filter`）。第一版只看了第一处，于是作者邮箱里的真机号码一路留到推送前（§5.2）。
- ★ **以后改名时**：只改"活的位置"，历史取证文档不动，并在 README 顶部维护"曾用名"那一段；
  发布包前缀、工作区生成文件名一起改（后者的旧文件要主动清）。这次改名的清单与理由见 §2.2。
  也就是说：**"我刚刚没写号码"这种自信是不可靠的，跑一遍才可靠。**
- 发布产物继续走 Releases；`_release/` 保持被忽略。**要重新发布就必须重跑一次 §4 的克隆 + 重写**
  （开发仓库的历史永远带着旧号码与发布包，**不要**从开发仓库 push）。
- 提交信息与文档里的"为什么"照旧写清楚 —— 这个仓库的价值一半在代码，一半在这些取舍记录里。

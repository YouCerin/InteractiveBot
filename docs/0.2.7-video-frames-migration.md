## 1. 两份目录的关系

```
reference/video-frames-1.0.0/          ← 上游原件，一个字节没动（plugin.json + index.js + frames.js）
packages/qq-bridge/skills/video-frames/ ← 适配版：上面三个 + 3 个新文件 + 1 份说明
```

上游原件来自另一个项目（QQ Agent 的插件目录），**没有 README、没有自测脚本**，
所以这次没有"上游自测资产要保留"这一类东西，也不需要删任何上游文件
（pixiv 那次删了一个 import 上游宿主模块、在新环境必然 `ERR_MODULE_NOT_FOUND` 的脚本）。

生成/复核 diff：

```bash
cd <仓库根>
git diff --no-index reference/video-frames-1.0.0/frames.js packages/qq-bridge/skills/video-frames/frames.js
git diff --no-index reference/video-frames-1.0.0/index.js  packages/qq-bridge/skills/video-frames/index.js
# plugin.json → skill.json 是"换了宿主清单格式"，不是逐行改动，所以按 §3.3 逐条核对而不是 diff
```

## 2. 为什么必须改（先看这个）

### 2.1 三处**硬差别**（不改就一定坏）

| # | 差别 | 不改的后果 |
|---|---|---|
| 1 | **形态根本不同**。上游是**能力提供者**（`providers['video.frames']`），由宿主的 `src/video-reader.js` 主动取用，模型**看不到它**；InteractBot **没有能力/提供者机制**（技能能做的只有四件：注册工具、贡献提示词片段、给自己做设置界面、写日志 —— `docs/插件设计规范.md` §7） | 原样拷过来 = 装上了但**什么也不会发生**：没有工具进模型工具表、没有提示词指引，用户只会觉得"这插件没用" |
| 2 | **结果通道不同**。上游返回 base64 data URL，宿主自己把图拼进消息；InteractBot 的技能工具返回值会被 `mcp/mcp-skills-server.mjs` `String(r?.content ?? r?.text ?? '')` 掉，再包成 `{content:[{type:'text'}]}` —— **没有图片内容块通道** | 照上游那样返回 base64 = 模型读到一坨文本，**看不见任何画面**，还白烧 token |
| 3 | **界面路径不同**。上游「设置 → 扩展」；InteractBot「**控制台 → 扩展**」 | 使用者/模型被指向一个不存在的菜单，排障时来回找 |

### 2.2 两处上游自身的隐患（顺手一起修，都有据）

| # | 隐患 | 依据 |
|---|---|---|
| 4 | 清单 `settings` 里**没有 `enabled`**，只有 `enabledByDefault: true` | 宿主 `validateSkillManifest` 会给 warning：`settings 里没有 enabled 默认值`；而**warning 就是"设置项在界面上可能对不上"的那一类静默失效**。更关键的是默认值口径：`isSkillEnabled` 的优先级是 **显式配置 > enabledByDefault > settings.enabled > false**，两处只有一处写清楚时，界面与实际行为容易各说各话（pixiv 那次踩的就是这个：`DEFAULTS.enabled=true` 与清单 `settings.enabled=false` 互相矛盾） |
| 5 | 上游只产出 base64，**帧文件用完即删**（`dir = path.dirname(src)`） | 在本宿主这条路走不通：见 #2。所以必须有"帧放哪儿、怎么命名、什么时候清"的政策 |

### 2.3 一处**刻意改成不一样**的行为（有理由，不是漏做）

**默认开关：上游 `enabledByDefault: true` → 这里 `false`。**

上游敢默认开，是因为它的宿主在抽帧不可用时**静默退回"只读元信息"**（`src/video-reader.js` 的 `resolveVideoRoute`）。
本宿主**不会静默**：技能的工具一旦挂上，模型就会看到它，提示词里也会多一段指引。
而绝大多数机器上没有 ffmpeg（本机就是），默认开等于**默认挂一个"一用就报依赖缺失"的工具**
并白占一段提示词。所以默认关，由管理员在「控制台 → 扩展」里打开；
打开之后开关**即时生效**（不需要重启），只有装/卸技能才要重启。

## 3. 改动清单（逐处）

### 3.1 `frames.js`（上游 147 行 → 适配版）

| # | 改法 | 为什么 |
|---|---|---|
| ① | 保留 `run()` / `findFfmpeg()` / `resetFfmpegCache()` / `probeDuration()` / 原 `extractFrames()` 的**签名与返回形状**，一字不改 | 上游宿主的能力 `video.frames` 就吃这个形状。适配的目标是"两个宿主都能跑" |
| ② | 文件头的两段设计说明（`-ss` 要在 `-i` 之前、不让 ffmpeg 直读 URL 的 SSRF 理由）**原样保留** | 那是踩过的坑，不是文风 |
| ③ | 新增 `extractFramesToDir()`：把帧**留在 `outDir`** 并返回 `{abs, name, time, bytes}[]` | 本宿主的路子是"帧落盘 → 给相对路径 → 模型 `read_image`"（见 §2.1 #2） |
| ④ | 抽出内部 `grabFrames()`，`extractFrames()` 与 `extractFramesToDir()` 共用它 | 两条路只差"读成 base64 后删"还是"留着"，抽帧逻辑不该有两份 |
| ⑤ | 新增 `planFrameTimes()`（把时间点算法提成纯函数）、`frameFileName()` | 时间点是这套东西里**最容易悄悄跑偏**的一格（取到黑场/字幕上），提出来才能断言 |
| ⑥ | 新增 `clampCount/clampWidth/clampQuality()` | 上游只夹了 count；宽度与质量来自设置页，写错（0、负、荒唐的大数）会在 ffmpeg 那层炸得很含糊 |
| ⑦ | 新增 `siblingFfprobe()`，`probeDuration()` 的默认参数改为优先用**ffmpeg 旁边**那个 ffprobe | Windows 上官方 zip 解出来两个 exe 并排放；用户填了 `ffmpeg.exe` 却还去 PATH 找 `ffprobe` 是没道理的。**没有 ffprobe 也能抽**，只是时间点退回固定取值 |
| ⑧ | 新增 `checkFfmpeg()`（跑 `-version` 并取版本行） | 自检要能回答"它到底能不能跑"，而不是"文件在不在" |
| ⑨ | 新增 `__setRunner()` / `__resetRunner()`：把"怎么跑外部命令"变成可注入 | **本机没有 ffmpeg**（PATH、仓库里都没有），不注入就只能测"找不到 ffmpeg"这一条分支。注入的是**执行器**这一层，参数拼装/时间点/命名/清理全都在被测范围内 |
| ⑩ | `pickFfmpeg()`：设置里填了路径就用它（先 `existsSync` 判存在），没填才自动探测 | 设置项要真的有效；存在性用同步判断，这样 `available()` 能给出**准确**原因而不是"探测中" |

### 3.2 `index.js`（上游 102 行 → 适配版）

| # | 改法 | 为什么 |
|---|---|---|
| ⑪ | `setup(api)` 里用 `api.toolName('frames')` 取**模型实际看到的工具名**，存进模块级 `TOOL_FRAMES` | 名字由宿主拼（`mcp__skills__video-frames__frames`）。写死上游命名 ⇒ 模型调一个**不存在**的工具，而且失败得很安静 |
| ⑫ | `TOOL_FRAMES` 初值是**空串**，并用它当"这是不是 InteractBot"的判据：取不到就走**上游口径**的提示词片段 | 同一份代码在两个宿主里都对（pixiv 适配③的同一条思路） |
| ⑬ | `available()` 改成三段：关掉 → 说清去控制台哪开；**填了路径 → 同步判存在**（准确、不 spawn）；没填 → 与上游一致的"首次乐观 + 后台探测 + 失败 60 秒重探" | 宿主在**同步**判定链里调它（返回 Promise 会被当成"可用"）。乐观那一段是必须的，理由写在代码注释里；而"配了路径"这条能让绝大多数人拿到**准确**结论 |
| ⑭ | 新增 `execute(ctx, args)`（真正的工具实现）：定位工作区 → 建帧目录 → 清过期帧 → 解析来源 → 抽帧 → 组装中文结果 | 技能对宿主的全部影响面就是"注册工具"，所以工具实现是这次适配的主体 |
| ⑮ | 活设置一律走 `ctx.settings` / `ctx.config.skills['video-frames']`，`api.config()` 只作兜底 | `api.config()` 在 MCP 子进程里是**启动快照**（见 `src/extensions.mjs` 的 `loadSkill` 与 `mcp-skills-server.mjs` 的注释）—— 只看它，"改了设置下一轮生效"就是假的 |
| ⑯ | 新增 `promptSections()`：**本宿主口径**（含真工具名 + `read_image` + "静止截图" + 声音听不到 + token 提醒），取不到工具名时退回**上游原文** | 这一段是模型唯一会读的指引。上游原话"你看到的是抽出的 N 张截图"在本宿主里是**错的**（不调工具就没有任何画面），必须换 |
| ⑰ | 新增 `diagnose()`：把开关/工作区/ffmpeg（来源+版本）/ffprobe/帧目录现状/保留时长/参数/上次抽帧摊开 | 本技能最容易的坏法是"静默拿不到 ffmpeg"，一句笼统的"抽帧失败"查不出来。**不输出任何密钥**（本技能本来也没有） |
| ⑱ | `providers['video.frames']` 与 `video.frames.available` **保留**，改成读共享设置 + 支持设置里的 `ffmpegPath` | 保留上游宿主可跑（与 ① 同一条理由） |
| ⑲ | `internals` 扩充（新函数 + `__setHostApi` / `__setToolName` / `__resetProbe` / `__defaults`），并保留上游原有的 `__resetFfmpegCache` | 守卫套件要用；`__defaults()` 让"清单与代码默认值不漂移"可断言 |
| ⑳ | 文件头写清"两种形态"与三条 InteractBot 纪律 | 下一个人第一眼要知道这文件为什么长这样 |

### 3.3 `plugin.json` → `skill.json`（换了宿主清单格式）

| # | 改法 | 为什么 |
|---|---|---|
| ㉑ | 文件名与字段改名：`plugin.json` → `skill.json`；补 `entry`、`icon`、`category`、`session: "none"`、`author`、`description` | InteractBot 只认 `<dir>/skill.json`（`src/extensions.mjs` 的 `discoverSkills`）。`session: "none"` = 明确声明"本技能不需要知道群聊/私聊"（要判会话就必须 `required`，而它不需要 —— 别给模型添两个必填参数） |
| ㉒ | 新增 `settings.enabled: false`，`enabledByDefault: false` | 见 §2.2 #4 与 §2.3；两处口径必须一致 |
| ㉓ | 补 `configSchema` 的 `enabled`，并给**每一个**字段补 `label`；`settings` 与 `configSchema` 键集严格一致 | 宿主的两条 warning 正是"设置项不上界面"与"界面字段没默认值"；`verify-*` 里还有一条断言钉住键集一致 |
| ㉔ | 新增 `tools[]` 声明（`id: frames`、`permission: read`、`parameters`），与 `registerTool` 对齐 | 清单 `tools[]` 是说明性元数据（宿主不自动注册），但**声明的 id 与注册的对不上时界面会警告**；`declared` 标记还被用作工具元数据的兜底 |
| ㉕ | `permissions` 从上游的 `capabilities` 式声明改成**如实声明网络与落盘**：`net` = "不固定域名，模型/使用者给的任意 http(s) 直链；内网/回环/CGNAT/链路本地一律拒绝"，`write` = 工作区 `frames/` 与系统临时目录 | 本规范要求如实声明"会联网到哪、会不会开本机端口"；**本技能不开端口**（`listen` 为空），所以界面不会出现 pixiv 那条红字告警 |
| ㉖ | `prompt.sections[]` → `"prompt": { "source": "runtime" }` | 运行期导出的 `promptSections()` 才是唯一来源；两份都留会让同一段话出现两种措辞（上游宿主就是这样） |
| ㉗ | 保留 `capabilities: ["video.frames", "video.frames.available"]`，但加 `_note_capabilities` 说明本宿主不消费它 | 上游契约留档，同时不让下一个人以为"这里也支持能力机制" |
| ㉘ | 加 `_note_switch` / `_note_tools_is_metadata` / `_note_upstream` | 三处最容易让接手的人误判的地方：默认为什么关、工具名由谁拼、原件在哪 |

### 3.4 **新增**的文件（上游没有的）

| 文件 | 它解决什么 |
|---|---|
| `workspace.js` | 工作区定位（与 `src/config.mjs` 同口径）、帧目录政策、**路径收束**（拒绝盘符/UNC/`/` 开头/`..`/**符号链接逃逸**）、按来源覆盖旧帧、过期清理 |
| `sources.js` | 来源解析：工作区相对路径 **或** http(s) 直链（自己下载、落盘、抽完即删）。内含**一整套 SSRF 守卫**（协议/逐跳重定向/回环与内网地址/域名解析结果/大小与超时/重定向次数），以及"下到的东西像不像文本"这条判据 |
| `README-InteractBot.md` | 使用者与排障视角：怎么开、ffmpeg 怎么配、模型怎么用、三个边界、症状表、与上游的差别 |
| `mocks/verify-video-frames.mjs` | 122 项断言的守卫套件（见 §4.3） |

**为什么 SSRF 守卫要自己写一份、不 import 宿主的 `src/images.mjs`：**
技能契约是"**整目录拷走还能跑**"（`docs/插件设计规范.md` §11），而 `src/images.mjs` 在包内、
不在技能目录里。`mocks/verify-sticker-skill.mjs` 里有一条断言专门盯"技能 import 宿主 src"。
所以这里**复制了同一套规则**，并在文件头写清"唯一权威仍是 `src/images.mjs`，那边改了这边要跟着改"。

**为什么直链那条路刻意没有 `security.allowPrivateImageHosts` 逃生口：**
宿主的 `qq_send_image` 是 **adminOnly** 的，所以它那个口子只对管理员敞开；而技能工具的调用里
**没有调用者身份**（MCP 的 `tools/call` 只有 name+arguments），本工具又对普通用户可用
（`permission: 'read'`）—— 照抄那个口子等于给**任何群友**一个内网探针。
内网视频走"放进工作区再给相对路径"那条路。

### 3.6 **迁移之后**又修的一处（同一轮，装到真机上才暴露）

**问题**：`available()` 抄了上游的"首次乐观放行 + 后台 spawn 探测"，到了本宿主**失效**——

* `available()` 必须同步 ⇒ 第一次只能返回 `{ok:true}`；
* 而控制台卡片读的是 `loadSkill` 那一刻存下来的 `skill.available` **快照**
  （`extensions.mjs` 的 `loadSkill` 存、`describeSkill` 取），不是每次现调；
* ⇒ **明明没装 ffmpeg，卡片显示 ✅ 已启用、一句提示都没有**。实测确认：
  `describeSkill.available.ok === true`。而"去设置里填 ffmpeg 路径"正是使用者最需要看到的那句话。
  （顺带：设置项本身藏在卡片的「设置」按钮后面，默认折叠 —— 两件事叠在一起，使用者就会觉得"这技能没地方配"。）

**改法**：`available()` 不再 spawn，改成**同步扫 PATH**（`frames.js` 新增 `findFfmpegOnPathSync()`，
按 `path.delimiter` 拆 `PATH`，逐个 `existsSync` 查 `ffmpeg.exe`/`ffmpeg`）。结论是真的，而且依然同步。

**边界（如实）**：

* "PATH 上有 `ffmpeg.exe`" ≠ "它跑得起来"（架构不符/损坏/缺 DLL）。这层不由 `available()` 判 ——
  真正抽帧时 `pickFfmpeg()` → `findFfmpeg()` 会**真跑一次 `-version`**，失败会在工具结果里如实报出来；
* 只扫 PATH，**不猜安装位置**（遵守本仓库"不写死任何机器专属绝对路径"的纪律）。装在别处的，
  由使用者填设置项 `ffmpegPath` —— 那条分支同步判存在，最准；
* 因此失败形态也变了：以前是"调用后报抽帧失败"，现在是**调用前就拒绝**并给出填路径指引
  （`mcp-skills-server.mjs` 在 execute 之前会调 `available()`）。

**断言**：守卫套件 §④ 原来断言的是"没填路径时**乐观放行**"（跟着上游写错了），
现在改成用**假 PATH** 把两种情形都钉住（PATH 里放/不放一个假 `ffmpeg.exe`），
所以不依赖"这台机器装没装 ffmpeg"，今天和以后都稳定。

### 3.7 真机反馈后的三处修正（同一轮）

装上真机跑了一次之后，控制台上暴露的三件事（都有截图/日志为证）：

#### ① 卡片显示的是**装载时的自检快照**（最要紧）

真机现象：技能是**启动之后**才在控制台打开的，卡片却一直写着
「「视频识别」开关没打开（控制台 →「扩展」→ 视频识别 → 启用）」+「暂时用不了」徽标，
而且**再也不会变** —— 使用者看到的是"我明明开着，它说我没开"。

原因：`loadSkill()` 在**装载那一刻**调一次 `available()` 存进 `skill.available`，
而第一版的 `describeSkill()`／`skillStatus()` **直接读这个快照**。
同一个坑对"后来才装好 ffmpeg / 填好路径"完全一样。

修法：`src/extensions.mjs` 新增 **`callSkillAvailable(skill, config)`**（现调、同步、失败降级），
`skillStatus()` 与 `describeSkill()` 改用它；`bridge.mjs` 的 `#videoToolFacts()` 也换成同一个函数
（三处口径一致）。`loadSkill` 那份快照仍然留着（排障用），但**不再作为界面/提示词的依据**。
回归断言见 `mocks/verify-extensions.mjs`（用一个"自检依赖 config 里另一个键"的夹具，
证明只改一个配置键卡片结论就跟着变）。

#### ② 同一句警告在卡片上显示**两遍**

后端 `skillStatus()` 已经把 `available.reason` 放进 `reasons`，而界面又单独渲染了一遍
`s.available.reason`（条件完全相同）⇒ 屏幕上出现两条一模一样的黄条。
修法：删掉界面那一段，统一由 `reasons` 输出一次（`config-ui` 已重建）。

#### ③ 显示名「视频抽帧」误导 → 改成「视频识别」

理由：「抽帧」说的是**手段**（把视频切成一堆图），使用者与模型要的是**能力**
（看懂视频里有什么）。真机上模型还答出过"我不抽帧"这类偏离问题的回答。

只改**显示名**（技能名 / 工具名 / 提示词段标题 / 所有面向使用者的文案）；
**id、目录名、工具全名一律不动**（仍是 `video-frames` 与 `mcp__skills__video-frames__frames`）——
改 id 会让 `config.skills['video-frames']` 里既有的开关与 ffmpeg 路径失配。
上游那份插件自己的显示名仍叫「视频抽帧」，文档提到上游时按上游叫法写。

**顺带修的一处文案误导**（同一次真机）：原来缺 ffmpeg 时写的是「未找到 ffmpeg」，
使用者明明**已经装好**（只是没填路径），却被这句话带成"是不是我没 build 成功"；
更糟的是**模型照这句话在群里说了「这台机器上没装」**——一句假话。
现在文案说清"我查了什么"，并明确"**这不代表机器上没装**"，且有断言盯着不许改回去。

## 5. 上游发新版本（例如 1.1.0）时怎么办

1. 把新版本解开，**放进 `reference/video-frames-<新版本>/`**（原件不要改）；
2. 对照 §3 逐条重做（`frames.js` 的 ①~⑩、`index.js` 的 ⑪~⑳、清单的 ㉑~㉘）；
3. 特别检查这五处**最容易漂移**的地方：
   * `extractFrames()` 的返回形状有没有变（变了要同步 `providers` 与 §3.1 ①）；
   * 时间点算法与 `-ss` 的位置有没有被动过（`verify-video-frames.mjs` §⑤ 会抓到）；
   * 提示词片段是不是又被写死了工具名（§⑧ 会抓到）；
   * 清单是不是又变成 `prompt.sections[]`（两处都写会重复注入，§② 的"零 warning"会抓到）；
   * 默认开关与 `settings.enabled` 是否仍一致（§⑩ 会抓到）。
4. 重新生成 diff（§1 的两条 `git diff --no-index`）；
5. 跑 §4 的三层验证 + §4.4 回归。

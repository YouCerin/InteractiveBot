# 0.2.4 更新汇总（桌面程序：真正的窗口 + `.exe` 启动器）

> **给人看的版本级汇总**（这一版改了什么、怎么验、刻意不做什么、还差什么）。
> 逐条过程记录：`docs/0.2.4-change-record.md`。
>
> **这一版的两个目的**（用户原话）：
> ① 把整个 UI 移植到单独的界面，**不再依赖拉起浏览器**；
> ② 把项目的启动方式**打包为 `.exe` 文件**。

---

## 1. 一句话：以后双击的是**程序**，不是网页

```
（以前）启动机器人.bat → 起桥接 → start http://127.0.0.1:3410/ → 你的浏览器里多一个标签页
（现在）启动机器人.bat → app\InteractBot.exe → 一个真正的窗口 + 右下角托盘
```

* **窗口**：没有地址栏、没有标签页，有原生标题栏与最小化/最大化/关闭。
* **关窗口 ≠ 下线**：窗口收到右下角托盘，机器人继续收发消息。
  真要下线：托盘菜单 →「退出并停止机器人」。
* **托盘**：左键单击叫回窗口；右键菜单 = 打开控制台 / 重新连接 / 重启机器人 /
  停止机器人 / 打开 SnowLuma 控制台 / 打开日志文件夹 / 两种退出。
* **它还是启动器**：桥接没在跑就自己起；SnowLuma 没在跑就问桥接要不要起
  （起不来**不阻断**开窗口 —— 界面里能看到它到底怎么了）。

**这不是重写的界面。** 窗口加载的就是 `config-ui/dist` 那一份产物
（`loadURL('http://127.0.0.1:<端口>/')`），所以：

| 问题 | 答案 |
|---|---|
| 界面的 45 个源文件要改吗？ | **一个都没改** |
| 要加新接口吗？ | **一个都没加** |
| 两种入口（浏览器 / 窗口）会看到不同的界面吗？ | **不会** —— 同一个地址、同一份产物 |
| 改了界面要重新打包 exe 吗？ | **不要** —— 界面的改动重新 `npm run build` 就同时生效 |

★ 这条是**刻意**的：如果窗口改成直接 load 本地 `dist/index.html`，就会出现
"窗口用的那份 UI"与"桥接伺服的那份"两个真相 —— 而 UI 产物**真的脱钩过一次**
（包里旧 5 小时、1100 项测试全绿）。所以窗口只认桥接伺服的地址，构建溯源那一套
（`ui-build.json` + `--ui`）一个字都没改。

## 2. `.exe` 是怎么来的、为什么是那个形状

### 2.0 用户入口（0.2.4 收尾时按你的要求加的）

包根原来只有**一个**启动器 `启动机器人.bat`，它要判断"有没有 exe"、还要认
`--check` / `--doctor` / `--foreground` 这些开关。你要的是"一份能方便打开带独立界面的后台的文件"，
所以现在**两个入口各司其职**：

| 双击哪个 | 它做什么 |
|---|---|
| **`桌面端bot启动.bat`** ← 日常用这个 | **只干一件事**：开那个带独立界面的窗口（`app\InteractBot.exe`）。不认参数、不二次分派；缺 exe 时**明确说"这个包没有桌面程序"**并指向 `start.bat`（不静默什么都不做） |
| `启动机器人.bat` | 全能启动器：除了开窗口，还认 `--check` / `--doctor` / `--foreground` / `--no-browser` / `--no-snowluma`；万一包里没带桌面程序，它退回"浏览器里的控制台"那条老路 |

`创建带图标的快捷方式.bat` 现在生成**三个** `.lnk`（`.bat` 本身带不了自定义图标，所以这步必须）：

```
桌面端bot启动.lnk  →  桌面端bot启动.bat      ← 推荐拖到桌面/任务栏
QQbot.lnk          →  启动机器人.bat
InteractBot.lnk    →  app\InteractBot.exe    （图标是 exe 自带的）
```

三个都在真实发布包里实跑验证过（目标逐一对上）。

### 2.0.1 ★★ 加这个入口时踩出的两个真 bug（都补了机器判据）

**① 注释里一个裸 `>` 把两个启动器截成了 0 字节。**
我在注释里写 `rem  DesktopBot.lnk -> 桌面端bot启动.bat`。`>` 对 cmd 是**重定向**，
而 `rem` 只吃掉"命令"、**不吃掉重定向** ⇒ cmd 去找一个叫 `DesktopBot.lnk` 的命令，
并把**目标文件截断成 0 字节**。一次弄空了 `桌面端bot启动.bat` **和** `启动机器人.bat`
（后者是用户的主入口），而**离线测试当时全绿** —— 因为没有任何断言读这两个文件的**内容**。
⇒ `mocks/verify-text-encoding.mjs` 现在有两条新判据：**注释里不许有裸 `>` / `<`**（负对照验过牙）
＋ **这两个启动器必须 >0 字节**；`AGENT.md` 第 12 条记下这个坑。

**② `--force` 组装会在"删到一半失败"时留下半份发布包。**
组装脚本的 `--force` 是"先删旧目录、再建新的"。而 Windows 上有进程占着 `default_app.asar`
时 `rmSync` 抛 EPERM —— **已经删掉的那一半不会回来**。这次因此把两个旧发布包削成了
133/134 个文件（正常 209），而使用者**无从判断哪一份能跑**（那比"没组装"更坏）。
⇒ 现在改成**先改名到 `<目录>.deleting-<时间戳>`、确认删得掉再删**；删不掉就**明确报错并退出**，
绝不留下半份目录。已用负对照验过（对一个被锁目录跑 `--force`：报错、退出码 1、旧目录不再被削）。

### 2.1 选型（三条路，选了第三条）

| 方案 | 为什么不选 / 为什么选 |
|---|---|
| 单文件自解压 exe | 每次启动都要把 ~200 MB 解到临时目录 ⇒ **首次启动明显更慢**，用户会以为"卡住了" |
| 安装程序（NSIS） | 要多一层安装/卸载登记，且与既有的"整目录拷走就能用"发布形态不一致 |
| ★ **免安装目录版**（`app\InteractBot.exe` + 运行时文件） | 与 `_release/InteractBot-<版本>-win-x64/` 的既有形态一致；不需要注册表与管理员权限；exe 就在包内，拷到哪都能跑 |

### 2.2 技术栈：Electron 38（因为它自带 Node 22）

**为什么版本要挑**：本项目用 `node:sqlite`（本地语料库，H7），而它要求 Node **≥ 22.5**。

| Electron | 自带 Node | 能用吗 |
|---|---|---|
| 33（本机 `%LOCALAPPDATA%\electron\Cache` 里恰好躺着一份） | 20.18 | ❌ `node:sqlite` 不存在 |
| **38.8.6（本版采用）** | **22.22** | ✅ |

★ 所以 `desktop/package.json` 里 electron 版本**写死**（不是 `^`）—— 用范围很容易滑到
不能用的一档，而症状会是"桌面程序里的某个功能莫名其妙不可用"。

### 2.3 桥接仍然跑**包内那份 Node**，不是 Electron 自带的

```
InteractBot.exe（Electron，自带 Node 22.22）   ← 只负责：窗口 / 托盘 / 启动器
      └─ spawn: vendor\node\node.exe src\index.mjs --background   ← 机器人本体，跑在包内 Node 上
```

**为什么不省掉 `vendor/node`**（能省 85.6 MB）：`vendor/node` 是**已经在真机上跑通**的
那一份运行时，而 `node:sqlite` 在 Electron 的 Node 里是自编译的 —— 换过去等于把
"机器人能不能记语料库"押在一个没验过的组合上。代价 85 MB，收益是确定能跑。

### 2.4 打包链（`node scripts/assemble-desktop.mjs`）

```
① 前置检查（零运行期依赖 / Electron 运行时就位 / 源文件齐）
② stage  ── 把 5 个源文件复制到一个**没有 node_modules 的临时目录**
③ 补丁  ── 给 electron-builder 的依赖收集器打 4 处补丁（见 §5）
④ 打包  ── electron-builder --win --dir → win-unpacked/InteractBot.exe
⑤ 验收  ── 逐字节比对 app/resources/app/main.cjs 与源；断言 app 里没有
           node_modules / src / config-ui；断言 exe 存在
```

产物：`.build-desktop/pack-<时间戳>/win-unpacked/`（324 MB），
最近一次的路径记在 `.build-desktop/latest.json`（发布组装读它，**不按目录名猜**）。

## 3. 这一版真正难的地方（都在环境上）

**先说结论：这台机器的 DSH 沙箱禁止三件事，而 Electron 的打包链三件都撞上了。**

| # | 沙箱限制（实测） | 撞上时的样子 | 怎么绕 |
|---|---|---|---|
| 1 | **任何 `stdio: 'pipe'` 的 `spawn` 都被拒**（`inherit` / `ignore` / 文件描述符都行；连 `['ignore', fd, 'pipe']` 也拒） | electron-builder 收集运行期依赖时固定 `powershell → npm list` 并用管道读输出 ⇒ `⛔ spawn EPERM`，**整个打包失败** | `scripts/patch-electron-builder.mjs`：把那一处改成"子进程直接把 stdout/stderr 写文件"（4 个 hunk，**打不上就非零退出**）+ `scripts/build-tools/npm-stub.mjs` 给它一个确定性答复（零依赖）。补丁后收集器跑得完，随即回落到它自己的**纯文件遍历**通路 |
| 2 | **Chromium 的进程单例锁 / mojo 平台通道被拒**（`Lock file can not be created! Error code: 5` + `platform_channel.cc:82 Check failed: 拒绝访问`） | 我在沙箱里启动打好的 `InteractBot.exe` → 退出码 `-2147483645` | **没有绕法** —— 这就是"沙箱里跑不了 Electron 的 GUI"。★ **但真机上它是好的**：使用者双击过，留下了 `%APPDATA%\InteractBot\` 那份 profile（见 §6.2）⇒ 未验证的只剩"关窗口不下线"等几条（§6.4） |
| 3 | `%LOCALAPPDATA%\npm-cache` 在工作区之外，不可写 | `npm install` 直接 `EPERM`，连包都装不下来 | `desktop/.npmrc` 把 npm 缓存指到包内；Electron 二进制走 npmmirror 镜像（`github.com` 本机连不通，实测连接超时） |

★ **补丁是打在依赖内部实现上的**，所以 electron-builder 一升级它就会"打不上"并**明确报错**
让人来看 —— 这是刻意的：猜着改一个依赖的内部实现，比构建失败危险得多。
★ 三条限制的原始诊断脚本留在 `cache/spawn-probe*.mjs`（它们是"怎么得出这个结论"的证据，
不是产品代码）。

## 4. 顺带修掉的两个真问题

| # | 问题 | 怎么发现的 |
|---|---|---|
| 1 | **`QQ机器人.lnk` 在拷贝清单里，而包根根本没有这个文件** ⇒ 只要跑 `assemble-release.mjs` 就必然停在第③步 | 第一次组装发布包时**当场**报出来。查了来历：它只存在于 `_release/` 的两个老包里（0.2.0 是**手敲组装**的，把开发机上现成的快捷方式一起拷了进去），git 里从来没有过。而它**本来就不该随包分发** —— `.lnk` 存的是绝对路径，在别人机器上目标与图标都是坏的（`创建带图标的快捷方式.bat` 的注释里早就写着这条）。现在清单里去掉了它，改由那个脚本在**使用者的机器上**生成两个快捷方式 |
| 2 | **`asar: false` 写在 `win:` 底下，被 electron-builder 静默忽略** | 构建**成功**、exe 也出来了 —— 只是 app 变成了 `resources/app.asar`，而验收脚本去找 `resources/app/main.cjs`，报"缺 5 个文件"。这正是"配置写了但没生效"的典型：**不报错，产物却是另一个形状**。现在它在顶层，并且 `mocks/verify-desktop.mjs` 里有一条断言钉着 |

## 5. 新增的文件与它们的职责

| 文件 | 是什么 |
|---|---|
| `desktop/main.cjs` | 主进程：窗口 / 托盘 / 单实例 / 启停桥接。**三条边界**写在文件头（见 §1 的表） |
| `desktop/lib.cjs` | ★ **纯逻辑**：端口从哪来 / 包根怎么解析 / 状态怎么翻译 / 什么算"启动成功"。单独成层就是为了能被离线测 |
| `desktop/preload.cjs` | 启动页与主进程之间**唯一**的通道（白名单 6 个动作，主进程侧再判一次） |
| `desktop/splash.html` | 启动页（进度、"已等 N 秒"、失败时按钮）；失败时进度条**真的停下**，不假装还在转 |
| `desktop/electron-builder.yml` | 打包配置（★ `asar: false` 必须在顶层） |
| `scripts/assemble-desktop.mjs` | 打桌面壳（stage → 补丁 → electron-builder → 验收） |
| `scripts/patch-electron-builder.mjs` | 给收集器打"不要管道"的补丁（4 处，幂等，**打不上就失败**） |
| `scripts/build-tools/npm-stub.mjs` + `npm.cmd` | 收集器问"有哪些依赖"时的替身（答：没有）。★ `.cmd` **纯 ASCII** |
| `scripts/fetch-electron.mjs` | 下 Electron 运行时（走镜像，不用 github） |
| `mocks/verify-desktop.mjs` | **132 项**离线断言（见 §6） |

### 6.2 ★★ **真机验证：使用者已经点过了，而且成功了**

发布包打出来之后，**`InteractBot.exe` 在真机上跑起来过一次**（2026-09-28 01:00:07 本地时间，
由使用者双击启动）。留下的证据不是"我看到了窗口"这种口头断言，而是 Electron 自己的
**用户数据目录**：

```
%APPDATA%\InteractBot\   55 个文件，写入窗口 01:00:07 → 01:10:17
  ├── Code Cache\js\index-dir\…          ← ★ 控制台的 index-*.js 真的被下载并执行过
  ├── Network\Network Persistent State   ← 真的发过网络请求（连上了桥接的 3410）
  ├── Local Storage / SharedStorage / DIPS（都有内容）
  └── GPUCache / DawnWebGPUCache（270 KB 级）  ← ★ 真的在渲染（不是无头进程）
```

**可以确认的三件事**：

| 结论 | 依据 |
|---|---|
| 窗口**真的开起来了**，控制台界面**真的渲染出来了** | `Code Cache\js` 里落了 `index-*.js`、GPU 缓存 270 KB 级、Local Storage 有写入 —— 页面没渲染就不可能有这些 |
| 它**真的连上了桥接** | `Network Persistent State` + 缓存里那两个 `index-*.js`（那正是桥接伺服的那份产物，见 §1） |
| 它**活着至少 10 分钟、没有一启动就退出** | 写入从 01:00:07 持续到 01:10:17。与"关窗口只收托盘、不退出"的预期**一致**（但没有直接观察到"关窗口"这个动作，见 §6.4） |

### 6.3 ⚠️ 但我**没能自己复现**，原因是沙箱（不是程序）

我在这个 DSH 沙箱里再启动它，**每次都失败**：

```
ERROR:chrome\browser\process_singleton_win.cc:457] Lock file can not be created! Error code: 5
FATAL:mojo\public\cpp\platform\platform_channel.cc:82] Check failed: . : 拒绝访问。 (0x5)
EXIT=-2147483645
```

**原因**：Chromium 的进程单例锁与 mojo 平台通道都要**命名管道/锁文件**，而这台机器的
DSH 沙箱禁止这些（与 §3 里"任何 `pipe` 的 `spawn` 都被拒"是同一族限制）。
∴ **沙箱里跑不了 Electron 的 GUI**；我能自己验的只有"产物形状 + PE 资源 + 离线判断"。

★★ **这份文档里有一处判断必须更正**（第一版写错过）：我原先写的是
"`InteractBot.exe` **在本沙箱里起不来**（退出码 -36861）"，并据此把它整条列进"未验证"。
那个结论**只对了一半**：起不来的是**我在沙箱里发起的启动**，而**真机上它明明能起来**
（§6.2 那份 profile 就是证据）。把"我的测试环境受限"写成"这个程序没验证过"，
是**把环境限制说成产品缺陷**的反向错误 —— 两种都该避免。

### 6.5 ★★★ 真机日志抓出的**真 bug**：壳把 `app\` 当成了包根（已修）

那份日志里写着（这次不是我猜的，是它自己打的）：

```
包根 …\_release\InteractBot-0.2.4-win-x64\app          ← 指到了 app\，不是发布包根
控制台端口 3410 —— 读不到 config.json（ENOENT）—— 用默认端口 3410
```

**后果不是崩，是静默用错根**：读不到使用者的 `config.json`（于是"你在界面里改的端口"
它根本不知道）、日志写进 `app\logs\`、把 `app\` 当成了工作区与配置的所在地。

**两个原因叠在一起**：

1. 判据写的是 `app.isPackaged` —— 而 **`asar: false` 时它是 `false`**
   （Electron 看的是有没有 `app.asar`，而我们**故意**不打 asar）⇒ 我写的"打包形态"分支
   **从来没执行过**；
2. 就算执行了，`resourcesPath/..` 也**差一级**（`…\app\resources` 的上一级是 `app`）。

**修法**（从"猜目录层数"换成"看证据"）：包根改按三级判据找 ——
① 启动器设的 `INTERACTBOT_PKG_ROOT`（`启动机器人.bat` 现在会设）→
② 从 `app.getAppPath()` 逐级向上找**包根标记**（同时有 `config.example.json` 与 `src/index.mjs`）
→ ③ 找不到就返回链上真实存在的一层**并喊一声**，**绝不猜**。

**为什么离线 132 项断言没抓到**：它们只验了"参数怎么用"，**没验真实布局长什么样**。
∴ 现在那一节会**造出发布包的真实目录形状**（含 `app\resources\app`）再断言，
并覆盖六种形态（发布包布局 / `isPackaged` 两种取值答案必须一致 / 环境变量优先 /
环境变量指错时回落且喊一声 / 开发侧 `desktop/` / 找不到标记时不猜）。
并用**打包产物里那份 `lib.cjs`**在真实发布包路径上复核过：现在解析到发布包根、
能读到 `config.json`（端口来源 `config`，不再是 `default`）。

> ★ 顺带说明**为什么源代码里也能开窗口**：exe 里装的只有壳那几个文件
> （`app/resources/app/{main,preload,lib}.cjs + splash.html`），**桥接源码没进 exe** ——
> 它在发布包根的 `src/`。∴ 想改壳就直接 `npm run desktop`（跑源码、数据落源码侧），
> 只有要交付 exe 时才 `npm run desktop:pack`。详见 `AGENT.md` §2。
### 6.6 ★★ 为什么 `_release/` 下会冒出 5 个 0.2.4 目录（这一节是复盘，不是辩解）

使用者看到并问了这个问题。事实是 **5 个目录 / 928 MB**，而**不是环境造成的**，
是三个选择叠出来的：

| # | 选择 | 后果 |
|---|---|---|
| ① | `assemble-release.mjs --force` 是"**先删旧目录、再建新的**" | Windows 上有进程占着 `default_app.asar` 时 `rmSync` 抛 EPERM，而**已删掉的一半不会回来** ⇒ 第一份 `InteractBot-0.2.4-win-x64` 被削成 134 个文件（`app\` 整个没了）——它成了"半份"，却仍然看起来像一份发布包 |
| ② | 删不掉就用不了同名重建 ⇒ 我为**绕开删除失败**造了个新名字 `-b` | 一次失败变成两个目录 |
| ③ | 后续两次组装失败又各留一个空壳（`-r2` / `-r3`），再一次改名 → `-r4` | 最终 5 个 |

★★ **真正的教训（两条，都不是"环境不好"）**：

1. **不要用"换个名字"来绕开"删不掉"。** 那会把一次失败变成一串目录，
   而使用者**无从判断哪一份能跑** —— 这比"这次没组装成功"更坏。
   正确做法是**停在原地**：删不掉就报错退出，不要留下半份 ⇒ 这条**已经在 0.2.4 里修了**
   （`assemble-release.mjs` 现在先改名到 `.deleting-<时间戳>`、确认删得掉再删）。
2. **`_release/` 是易受外部占用影响的目录**，因为它把 Electron 整个运行时（含 200 MB 的
   `InteractBot.exe` 与 `default_app.asar`）平铺在包根。Defender / 搜索索引器 / 一个刚退出的
   进程实例都可能短暂占住它 ⇒ 删除、改名、覆盖全被拒。这是"发布包做成免安装目录"的固有代价，
   **但流程本该为它设计**（先构建到包内临时目录、成功后再整体就位；占用时失败而不是硬来）。

**给遗留残局收尾的工具**（0.2.4 收尾新增）：

```bash
node scripts/clean-release-residue.mjs            # 只报告：哪些是残留、该留哪一份
node scripts/clean-release-residue.mjs --apply    # 真删（删不掉的会在里面放一句话，指明该用哪份）
```

★ 它只动**当前版本**的衍生目录，**老版本一律不动**（`0.1.0` / `0.2.0` 是对照用的 ——
第一版脚本把这两版也列进清理名单，已修）。保留谁按"标准名且可用 > 可用中最新"选，
平手时比 `app\InteractBot.exe` 的时间戳（不能靠排序运气）。
★ 在本沙箱里 4 个残留**一个都删不掉**（EPERM），需要**重启后**在普通 shell 里跑一次。

## 8. 已知边界与待办（如实列出）

1. ★★ **"关窗口不下线"没有被真机验证**（§6.4）：那 10 分钟里窗口是开着的。
   要验它必须**关掉窗口、再用 QQ 发一条消息**。这是这一版最该补验的一条。
2. ~~**`logs/desktop.log` 在真机上没有落盘**~~ —— ★ **这条是我判断错了，已在 §6.5 更正**：
   日志**写了**，只是写到了 `app\logs\`（因为壳把 `app\` 当成了包根）。我先前"找不到它"
   是因为**在错的地方找**，而由此推出的"日志静默写失败"是不成立的。
   ⇒ 真正的缺陷是**包根解析错**（§6.5，已修）；顺带把 `logLine()` 那个空 `catch` 也补上了
   "写不进去就喊一声"（仍然不完美：GUI 双击时没有终端，回退到用户数据目录留作下一版）。
3. **自动重连没在真机上观察过**：壳只在"桥接是自己起的"（`startedBy === 'launcher'`）
   时才每 4 秒轮询并重拉。逻辑与判据有离线断言，但"桥接被关掉后它真的会自己回来"
   没有一条真机记录。
4. **"桌面壳自己把桥接拉起来"这条分支没被真机覆盖**：那次成功会话里桥接本来就在跑，
   走的是"直接连上去"（§6.4）。
5. **托盘气泡在部分 Windows 上不显示**（系统"通知"被关掉时）。代码里 `try/catch` 了 ——
   气泡只是提示，不影响功能。
6. **改 `ui.apiPort` 之后桌面程序要重开**：端口是**启动时**读一次的（`readUiPort`）。
   界面里改了端口并重启桥接后，请把窗口也关掉重开（或者退出托盘再双击 exe）。
   ⚠️ 这一条**没有**做热重载 —— 加了会带来"窗口连旧端口、桥接在新端口"的中间态。
7. **打包链路依赖对 electron-builder 内部实现的补丁**（§3）。它升级时补丁会打不上，
   脚本会**明确报错**（不会静默出一个坏包），届时要人工看一眼上游实现再更新补丁。
8. **`asar: false` 是刻意的**：壳的源码要能被直接读。代价是 app 目录里那几个
   `.cjs` 明晃晃躺着 —— 对这个项目（"如实、可查"）是收益不是代价。
9. **`.build-desktop/` 与旧发布包目录都可能删不掉**（Windows 上 Defender / 索引器会
   短暂占住里面的文件，实测 `EBUSY: unlink 'default_app.asar'`、以及删 `_release/<包>`
   目录时的 `EPERM`）。处理：构建产物每次换新目录、清不掉的只提示不当失败；
   发布包则可以直接用 `--out <新目录>` 另起一份。
10. **未签名的 exe** 会显示"未知发布者"（见 §7）。

# 0.2.4 更新汇总（桌面程序：真正的窗口 + `.exe` 启动器）

> **给人看的版本级汇总**（这一版改了什么、怎么验、刻意不做什么、还差什么）。
> 逐条过程记录：`docs/0.2.4-change-record.md`。
>
> **这一版的两个目的**（用户原话）：
> ① 把整个 UI 移植到单独的界面，**不再依赖拉起浏览器**；
> ② 把项目的启动方式**打包为 `.exe` 文件**。

---

## 1. 一句话：以后双击的是**程序**，不是网页

```
（以前）启动机器人.bat → 起桥接 → start http://127.0.0.1:3410/ → 你的浏览器里多一个标签页
（现在）启动机器人.bat → app\InteractBot.exe → 一个真正的窗口 + 右下角托盘
```

* **窗口**：没有地址栏、没有标签页，有原生标题栏与最小化/最大化/关闭。
* **关窗口 ≠ 下线**：窗口收到右下角托盘，机器人继续收发消息。
  真要下线：托盘菜单 →「退出并停止机器人」。
* **托盘**：左键单击叫回窗口；右键菜单 = 打开控制台 / 重新连接 / 重启机器人 /
  停止机器人 / 打开 SnowLuma 控制台 / 打开日志文件夹 / 两种退出。
* **它还是启动器**：桥接没在跑就自己起；SnowLuma 没在跑就问桥接要不要起
  （起不来**不阻断**开窗口 —— 界面里能看到它到底怎么了）。

**这不是重写的界面。** 窗口加载的就是 `config-ui/dist` 那一份产物
（`loadURL('http://127.0.0.1:<端口>/')`），所以：

| 问题 | 答案 |
|---|---|
| 界面的 45 个源文件要改吗？ | **一个都没改** |
| 要加新接口吗？ | **一个都没加** |
| 两种入口（浏览器 / 窗口）会看到不同的界面吗？ | **不会** —— 同一个地址、同一份产物 |
| 改了界面要重新打包 exe 吗？ | **不要** —— 界面的改动重新 `npm run build` 就同时生效 |

★ 这条是**刻意**的：如果窗口改成直接 load 本地 `dist/index.html`，就会出现
"窗口用的那份 UI"与"桥接伺服的那份"两个真相 —— 而 UI 产物**真的脱钩过一次**
（包里旧 5 小时、1100 项测试全绿）。所以窗口只认桥接伺服的地址，构建溯源那一套
（`ui-build.json` + `--ui`）一个字都没改。

## 2. `.exe` 是怎么来的、为什么是那个形状

### 2.1 选型（三条路，选了第三条）

| 方案 | 为什么不选 / 为什么选 |
|---|---|
| 单文件自解压 exe | 每次启动都要把 ~200 MB 解到临时目录 ⇒ **首次启动明显更慢**，用户会以为"卡住了" |
| 安装程序（NSIS） | 要多一层安装/卸载登记，且与既有的"整目录拷走就能用"发布形态不一致 |
| ★ **免安装目录版**（`app\InteractBot.exe` + 运行时文件） | 与 `_release/InteractBot-<版本>-win-x64/` 的既有形态一致；不需要注册表与管理员权限；exe 就在包内，拷到哪都能跑 |

### 2.2 技术栈：Electron 38（因为它自带 Node 22）

**为什么版本要挑**：本项目用 `node:sqlite`（本地语料库，H7），而它要求 Node **≥ 22.5**。

| Electron | 自带 Node | 能用吗 |
|---|---|---|
| 33（本机 `%LOCALAPPDATA%\electron\Cache` 里恰好躺着一份） | 20.18 | ❌ `node:sqlite` 不存在 |
| **38.8.6（本版采用）** | **22.22** | ✅ |

★ 所以 `desktop/package.json` 里 electron 版本**写死**（不是 `^`）—— 用范围很容易滑到
不能用的一档，而症状会是"桌面程序里的某个功能莫名其妙不可用"。

### 2.3 桥接仍然跑**包内那份 Node**，不是 Electron 自带的

```
InteractBot.exe（Electron，自带 Node 22.22）   ← 只负责：窗口 / 托盘 / 启动器
      └─ spawn: vendor\node\node.exe src\index.mjs --background   ← 机器人本体，跑在包内 Node 上
```

**为什么不省掉 `vendor/node`**（能省 85.6 MB）：`vendor/node` 是**已经在真机上跑通**的
那一份运行时，而 `node:sqlite` 在 Electron 的 Node 里是自编译的 —— 换过去等于把
"机器人能不能记语料库"押在一个没验过的组合上。代价 85 MB，收益是确定能跑。

### 2.4 打包链（`node scripts/assemble-desktop.mjs`）

```
① 前置检查（零运行期依赖 / Electron 运行时就位 / 源文件齐）
② stage  ── 把 5 个源文件复制到一个**没有 node_modules 的临时目录**
③ 补丁  ── 给 electron-builder 的依赖收集器打 4 处补丁（见 §5）
④ 打包  ── electron-builder --win --dir → win-unpacked/InteractBot.exe
⑤ 验收  ── 逐字节比对 app/resources/app/main.cjs 与源；断言 app 里没有
           node_modules / src / config-ui；断言 exe 存在
```

产物：`.build-desktop/pack-<时间戳>/win-unpacked/`（324 MB），
最近一次的路径记在 `.build-desktop/latest.json`（发布组装读它，**不按目录名猜**）。

## 3. 这一版真正难的地方（都在环境上）

**先说结论：这台机器的 DSH 沙箱禁止三件事，而 Electron 的打包链三件都撞上了。**

| # | 沙箱限制（实测） | 撞上时的样子 | 怎么绕 |
|---|---|---|---|
| 1 | **任何 `stdio: 'pipe'` 的 `spawn` 都被拒**（`inherit` / `ignore` / 文件描述符都行；连 `['ignore', fd, 'pipe']` 也拒） | electron-builder 收集运行期依赖时固定 `powershell → npm list` 并用管道读输出 ⇒ `⛔ spawn EPERM`，**整个打包失败** | `scripts/patch-electron-builder.mjs`：把那一处改成"子进程直接把 stdout/stderr 写文件"（4 个 hunk，**打不上就非零退出**）+ `scripts/build-tools/npm-stub.mjs` 给它一个确定性答复（零依赖）。补丁后收集器跑得完，随即回落到它自己的**纯文件遍历**通路 |
| 2 | **`Start-Process` 对 Electron 被拒**（Access is denied） | 打好的 `InteractBot.exe` **在本沙箱里起不来**（`-36861` = `0xFFFF7003`，chromium 的 `RESULT_CODE_KILLED_BAD_MESSAGE`） | **没有绕法** —— 这就是"沙箱里跑不了 GUI"。∴「双击真的会开窗口」这件事**只有使用者自己能验**（见 §6） |
| 3 | `%LOCALAPPDATA%\npm-cache` 在工作区之外，不可写 | `npm install` 直接 `EPERM`，连包都装不下来 | `desktop/.npmrc` 把 npm 缓存指到包内；Electron 二进制走 npmmirror 镜像（`github.com` 本机连不通，实测连接超时） |

★ **补丁是打在依赖内部实现上的**，所以 electron-builder 一升级它就会"打不上"并**明确报错**
让人来看 —— 这是刻意的：猜着改一个依赖的内部实现，比构建失败危险得多。
★ 三条限制的原始诊断脚本留在 `cache/spawn-probe*.mjs`（它们是"怎么得出这个结论"的证据，
不是产品代码）。

## 4. 顺带修掉的两个真问题

| # | 问题 | 怎么发现的 |
|---|---|---|
| 1 | **`QQ机器人.lnk` 在拷贝清单里，而包根根本没有这个文件** ⇒ 只要跑 `assemble-release.mjs` 就必然停在第③步 | 第一次组装发布包时**当场**报出来。查了来历：它只存在于 `_release/` 的两个老包里（0.2.0 是**手敲组装**的，把开发机上现成的快捷方式一起拷了进去），git 里从来没有过。而它**本来就不该随包分发** —— `.lnk` 存的是绝对路径，在别人机器上目标与图标都是坏的（`创建带图标的快捷方式.bat` 的注释里早就写着这条）。现在清单里去掉了它，改由那个脚本在**使用者的机器上**生成两个快捷方式 |
| 2 | **`asar: false` 写在 `win:` 底下，被 electron-builder 静默忽略** | 构建**成功**、exe 也出来了 —— 只是 app 变成了 `resources/app.asar`，而验收脚本去找 `resources/app/main.cjs`，报"缺 5 个文件"。这正是"配置写了但没生效"的典型：**不报错，产物却是另一个形状**。现在它在顶层，并且 `mocks/verify-desktop.mjs` 里有一条断言钉着 |

## 5. 新增的文件与它们的职责

| 文件 | 是什么 |
|---|---|
| `desktop/main.cjs` | 主进程：窗口 / 托盘 / 单实例 / 启停桥接。**三条边界**写在文件头（见 §1 的表） |
| `desktop/lib.cjs` | ★ **纯逻辑**：端口从哪来 / 包根怎么解析 / 状态怎么翻译 / 什么算"启动成功"。单独成层就是为了能被离线测 |
| `desktop/preload.cjs` | 启动页与主进程之间**唯一**的通道（白名单 6 个动作，主进程侧再判一次） |
| `desktop/splash.html` | 启动页（进度、"已等 N 秒"、失败时按钮）；失败时进度条**真的停下**，不假装还在转 |
| `desktop/electron-builder.yml` | 打包配置（★ `asar: false` 必须在顶层） |
| `scripts/assemble-desktop.mjs` | 打桌面壳（stage → 补丁 → electron-builder → 验收） |
| `scripts/patch-electron-builder.mjs` | 给收集器打"不要管道"的补丁（4 处，幂等，**打不上就失败**） |
| `scripts/build-tools/npm-stub.mjs` + `npm.cmd` | 收集器问"有哪些依赖"时的替身（答：没有）。★ `.cmd` **纯 ASCII** |
| `scripts/fetch-electron.mjs` | 下 Electron 运行时（走镜像，不用 github） |
| `mocks/verify-desktop.mjs` | **132 项**离线断言（见 §6） |

## 6. 怎么验（离线不花钱 / 真机那一步只能你来）

```bash
cd packages/qq-bridge
npm test                      # 全链 51 套 / 退出码 0（含新增的 verify-desktop 132 项）
npm run test:desktop          # 只跑桌面壳那一套
node scripts/assemble-desktop.mjs    # 重新打 exe（≈2 分钟）
node scripts/assemble-release.mjs    # 组装发布包（会把 app/ 平铺进去）
```

### 6.1 已经验过的（机器可复核）

| 证据 | 结果 |
|---|---|
| 桌面壳的**判断**（132 项离线断言） | ✅ 全过 |
| 发布包组装 + 验收 | ✅ 207 个文件 / 413 MB / **0 问题** |
| `app/resources/app/main.cjs` 与 `desktop/main.cjs` | ✅ **逐字节一致** |
| exe 的 PE 资源 | ✅ `ProductName=InteractBot`、`FileVersion=0.2.4`、`ProductVersion=0.2.4.0` |
| exe 的图标 | ✅ 与**原生 electron.exe 的默认图标不同**（说明用的是我们那份 `assets/icon.ico`，7 档含 256×256） |
| app 里有没有 `node_modules` / `src` / `config-ui` | ✅ 都没有（壳是零运行期依赖） |
| 全量离线测试 | ✅ 51 套全绿（3 套因沙箱跳过：`verify-rpc` / `verify-onebot` / `verify-mcp` —— **跳过不算通过**） |

### 6.2 ★★ **没验过的那一步（请你自己点一遍）**

**`InteractBot.exe` 在本沙箱里起不来**（沙箱拒绝对 Electron 的 `Start-Process`）。
所以下面三件事**只有在你自己的机器上才算验过**：

```powershell
cd _release\InteractBot-0.2.4-win-x64
.\app\InteractBot.exe      # ① 真的会开窗口吗？② 右下角真的有托盘吗？
                           # ③ 关掉窗口后，QQ 里发一条消息，机器人还回吗？
```

如实记在 `PROJECT.json` 的 `verificationStatus.notVerified`（那条比这段文字更权威）。
若窗口起不来，先看 `logs\desktop.log`（桌面程序自己的日志，与 `logs\bridge.log` 分开）。

## 7. 这一版**刻意不做**的事

| 不做 | 为什么 |
|---|---|
| **改 `config-ui/src/**`**（界面源码一行没动） | 用户从 0.2.2 起就要求"UI 改动只改指导文件"；而且这一版**不需要改** —— 窗口加载的是同一份产物 |
| **去掉 `vendor/node`**（能省 85.6 MB） | 见 §2.3：省钱换来的是一条没验过的 `node:sqlite` 组合 |
| **代码签名** | 需要证书（要买）。未签名的 exe 在 Windows 上显示"未知发布者"、首次运行可能被 SmartScreen 拦一下 —— 这是**预期内**的，不是打包出错 |
| **单文件自解压 / 安装程序** | 见 §2.1 |
| **Electron 自动更新** | 与"整目录拷走就能用"的发布形态冲突；而且更新器需要联网与签名 |
| **让桌面程序接管 SnowLuma 的登录界面** | SnowLuma 是自己的程序、自己的控制台（`127.0.0.1:5099`）。托盘的「打开 SnowLuma 控制台」已经足够，嵌进来只会多一个会过期的集成面 |
| **把托盘菜单做成可配置** | 现在那 9 项每一条都有明确的失败场景对应（打开/重连/重启/停止/看日志/退出）；配置化会带来"改坏了没有菜单可点"的死锁 |

## 8. 已知边界与待办（如实列出）

1. ★★ **`InteractBot.exe` 在本沙箱未启动过**（§6.2）—— 这是这一版最大的未验证边界。
2. **自动重连没在真机上观察过**：壳只在"桥接是自己起的"（`startedBy === 'launcher'`）
   时才每 4 秒轮询并重拉。逻辑与判据有离线断言，但"桥接被关掉后它真的会自己回来"
   没有一条真机记录。
3. **托盘气泡在部分 Windows 上不显示**（系统"通知"被关掉时）。代码里 `try/catch` 了 ——
   气泡只是提示，不影响功能。
4. **改 `ui.apiPort` 之后桌面程序要重开**：端口是**启动时**读一次的（`readUiPort`）。
   界面里改了端口并重启桥接后，请把窗口也关掉重开（或者退出托盘再双击 exe）。
   ⚠️ 这一条**没有**做热重载 —— 加了会带来"窗口连旧端口、桥接在新端口"的中间态。
5. **打包链路依赖对 electron-builder 内部实现的补丁**（§3）。它升级时补丁会打不上，
   脚本会**明确报错**（不会静默出一个坏包），届时要人工看一眼上游实现再更新补丁。
6. **`asar: false` 是刻意的**：壳的源码要能被直接读。代价是 app 目录里那几个
   `.cjs` 明晃晃躺着 —— 对这个项目（"如实、可查"）是收益不是代价。
7. **`.build-desktop/` 下会累积多份旧构建**（每份 324 MB），而且旧的可能**删不掉**
   （Windows 上 Defender / 索引器会短暂占住里面的文件，实测 `EBUSY: unlink 'default_app.asar'`）。
   组装脚本每次会尝试清旧的，清不掉只提示、不当失败。
8. **未签名的 exe** 会显示"未知发布者"（见 §7）。

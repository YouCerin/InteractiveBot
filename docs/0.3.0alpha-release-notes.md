说话方式从**两份按消息切换**变成**一份所有回合通用**，而且**这一份就写在人设文件里**
（`personas/小鲸鱼（完整带情绪）.md` 的【说话方式…】一节）—— 提示词**直接用整份人设**。

## 2. 融合的口径：把一对**相反指令**消解掉

0.3.0beta 的两态各自都"自洽"，但把它们放进**同一份提示词**就出现了这一对：

| 来源 | 那句话 |
|---|---|
| 基座人设（`personas/*.md` 的 `【别变成客服】`） | 「**但对方认真问事实、技术问题时，就认真答**」 |
| 口吻（0.3.0beta 的 `styles/闲聊.md`） | 「**极短。一句话能说完就一句话**」「**别把一句回答扩成一段**」 |

两条都是一般性指令、都指同一件事（"该说多长"），模型只能自己挑一套听 ——
于是两个方向都不稳定。

**这一版的处理不是"保留两句、让模型自己权衡"，而是把它们合成一句**：

- 默认口径仍然是**极短**（口吻那一份原文里的规则一条没删）；
- 另加**唯一**一条新增条款 `WORK_ALLOWANCE`：「**真在干活时，该说清就说清**」——
  拆解步骤、报错原因、多个结果、需要逐条对比的东西该写多长写多长，
  但**口吻不变**（不写「好的，我来帮您」开场、不写总结式收尾）。
- 判据从"这一轮是哪个态"改成"这话是不是在想把事说清" —— 与身份无关，与做什么有关。

**怎么核这件事**（不是看文档，是看提示词）：`mocks/verify-memory-roundtrip.mjs` 第 ⑱ 节里钉着一组断言。
⚠️ **第一步**那一组的做法是"先把说话方式那一段剥掉、再逐字比"，另有定向断言
（说话方式逐字在提示词里 / 只注入一次 / `WORK_ALLOWANCE` 在里面 / 反向三条不许出现双态时代的措辞）。
**第二步作废了"先剥掉再比"这条路**（理由见 §6.2）—— 现在这一节钉的是**整份提示词的逐字比对**，
外加反向三条：提示词里**不许**出现 `【怎么说话】`、`【别变成客服】`，
也不许出现「但对方认真问事实、技术问题时，就认真答」，更不许出现双态时代那句「这一轮是**闲聊**」。

**仍然认得**，但取值**全是那唯一一份**。为什么不是删掉它们：老配置里写着
`persona.preset: "mermaid-lite"` 的人（那种写法只在 `persona.active` 为空时才生效）会走
`resolveActivePersona()` 的 legacy 分支，而 `buildPersona()` / `lintPersona()` 会拿这个 id 去查表 ——

他们拿到的是这一份人设，而不是一个报错、也不是一段空白。
（`none` 保留：那是"不要人设、只用平台规则"，不是人设变体。）

**用户要改人设时改哪里**：`personas/小鲸鱼（完整带情绪）.md`（运行期读的是这个文件）。
代码里的常量只用于**首次播种**与「恢复默认」，两者有断言盯着**逐字一致** ——
改了文件若希望"恢复默认"也给出新内容，得同步常量，否则那条断言会红。
⚠️ 这条断言**原来是空的**：0.3.0alpha 第一步那几条只比"常量 vs 常量"（两个都在代码里），
所以**把 `personas/小鲸鱼（完整带情绪）.md` 改一个字、不同步常量，一条断言都不会红**。
第二步补了一条**真的读文件来比**的断言（在 `mocks/verify-persona.mjs`），这才把它钉住 ——
**改 `personas/*.md` 必须同步 `src/persona.mjs` 的 `FACTORY_PERSONA`**。

**别的没变**：人设库仍然是**多文件**的（能新建 / 复制 / 改名 / 删除，用来做变体对比），
`persona.active` 的三条回落规则没变，"读不到不许静默退回内置"没变，
改名/删除牵着配置走没变。测试里凡是要"第二套人设"的用例，改成**现建一份侧人设**。

**★ 字数上限从 4000 抬到 8000（`PERSONA_MAX_CHARS`，`src/persona.mjs`）**：说话方式搬进来之后，
出厂那份人设自己就是 **4742 字**，**已经超过旧上限** —— 于是"以出厂那份为基础新建 / 保存"

⚠️ 与上一条同样的教训：把上限改回 4000 时**原来一条断言都不红**，
是变异测试抓出来的 —— 现在 `mocks/verify-personas.mjs` 有一条
**「长度上限容得下出厂那份」**。

## 4.6 ★ 第二步：说话方式从"代码常量 + 每轮替换"改成"**就写在人设文件里**"（本版第三笔改动）

**这一节记的是一次被推翻的判断** —— 本仓库的既有风格是把它原样写下来，而不是把第一步那一段悄悄改掉。

**来回是怎么发生的**

1. 使用者的最初口径是「**把 `styles/闲聊.md` 的内容真正搬进人设文件**」。
2. **第一步**（`8cf82b0`）把它实现成了**代码常量**：新增 `src/voice.mjs` 的 `VOICE_STYLE`
   （外加 `WORK_ALLOWANCE` 与 `composeVoice()`），由 `composeVoice()` 每轮**替换**人设里的
   【怎么说话】【别变成客服】两节；另配 `src/voice-source.mjs` 做"读常量正文 / 三条守卫写回"。
   当时的理由是"说话方式与其它所有源码同一种存在形式（常量、可离线测、有守卫）"——
   但那**不是**使用者要的那种"搬进去"：内容仍然住在**代码**里，而**人设文件本身没变**。
3. 使用者随后问了一句「之前让你把闲聊.md 的数据转移到人设中，你做了什么」——
   一问就看出落点错了。他确认要按**最初那个口径**做，于是有了**第二步**（本节）。

**第二步实际改了什么**

| 项 | 第一步 | 第二步（现在） |
|---|---|---|
| 说话方式住在哪 | `src/voice.mjs` 的 `VOICE_STYLE`（**代码常量**） | `personas/小鲸鱼（完整带情绪）.md` 的【说话方式…】一节（**数据**） |
| 提示词怎么来 | `#buildPrompt` 调 `composeVoice()`：**替换**人设两节 | `#buildPrompt` **不拼任何东西**，直接用 `this.personaText`（**整份人设**） |
| 人设文件 | **一个字没改**：`2068 字 / 81 行`，而且 `a41894c`（0.3.0beta）→ `8cf82b0`（第一步）→ `7186792`（出厂收敛）**三笔提交里一直是这个数** | **4742 字 / 126 行**（说话方式那一节 **2360 字**，实测）；**4742 只出现在未提交的第三步** |
| 改口吻 | 改常量（不能含反引号 / `${` / 反斜杠，否则 `src/voice.mjs` 语法崩） | 改那个 `.md`（**没有这些约束** —— 它只是文本） |
| 形状可观测性 | `[voice]` 两行（替换 / 追加） | `[persona]` 一行（**只记日志，不拦不回落**） |
| 评审台目标 | `src/voice.mjs` | 当前那份人设文件（选项 `personaPath`） |
| 逐字基线 | **先剥掉说话方式再比** | **整份提示词逐字比**（基线 8806 → 8693 → **8751 字**，最后一次是第四步那行身份前缀说明） |

**为什么第二步更对（不是"又改回去了"）**

- **它本来就是数据**：说话方式是"这机器人怎么说话"的**内容**，和人设其余十节是同一种东西。
  把它塞进源码常量，等于让"改一句话"变成"改一个带语法陷阱的字符串字面量" ——
  第一步那三条守卫（不许反引号 / `${` / 反斜杠）本身就是这个错位的症状。
- **两处真值消失**：第一步下，**人设文件里那份口吻**与**常量里那份口吻**同时存在，
  谁是准的取决于 `composeVoice()` 替换成了没有。现在只有一处。
- **基线断言回到了它该有的样子**：说话方式在文件里 ⇒ 改它就**应该**重建基线（它是数据）；
  第一步那种"先剥掉再比"是为了"代码常量会被人反复改"才加的，见 §6.2。

**代价（如实说，别只看好处）**：提示词基线 8751 字里，**人设段占 4742 字（54.2%）**，
而说话方式（那一节 2360 字）**每一轮**都随人设进提示词（0.3.0beta 只在闲聊态注入那一份风格文件）。
可核：`node -e "const fs=require('fs');const g=[...fs.readFileSync('mocks/fixtures/prompt-golden.txt','utf8')].length;const p=[...fs.readFileSync('personas/小鲸鱼（完整带情绪）.md','utf8')].length;console.log(g,p,(p/g*100).toFixed(1))"`
→ `8751 4742 54.2`（★ 8751 是**第四步之后**的值；第四步只往提示词里加了**一行**身份前缀说明，见 §6.1 末）。
每一轮多花的量级就是"人设文件涨的那部分"：**4742 − 2068 = 2674 字**（相对 0.3.0beta 的基座人设）。
★ 这一组的数**都实测过**：0.3.0beta / 第一步 / 出厂收敛三笔提交的人设文件都是 **2068 字 / 81 行**
（✅ 复现方式见 §6 末尾的"怎么核历史版本"），第一步那个常量正文是
**3153 字**（`VOICE_STYLE`，原始含首尾换行 3154）+ **162 字**（`WORK_ALLOWANCE`）。
4742 与"2068 + 说话方式那部分"对得上量级（3153 − 被取代的两节 ≈ 358 + 少量合并调整 = 约 2900，
而文件净增 2674 —— 差的约 226 字是**合并时的收拢**，我没有逐字对上，如实标注）。
这是**有意的取舍**（换来"说话方式只有一份、看得见、改得动"）。
要省 token 就**直接精简那个人设文件里的【说话方式…】一节** ——
上限现在是 8000、出厂 4742，还有空间，**不需要为了长度去动代码**。

> **怎么核历史版本**（本机受限沙箱里 `execSync` 会 EPERM —— 沙箱禁的是**命名管道**，不是子进程；
> 给 git 一个**文件描述符**就好）：

> const fd=fs.openSync('out.txt','w');

**仍然成立的事（别写反）**：`#notePersonaShape` **只记日志**（不拦、也不回落内置）；
人设库仍是**多文件**；`persona.active` 的三条回落规则没变；"读不到不许静默退回内置"没变；

## 4.7 ★ 第四步：记忆条目带上「所记的人的 ID」（身份前缀）

**要求原话**：「**记录记忆时，加上所记的人的 ID**」（2026-10-02）。

两个口径都**当面问过**使用者，他的选择是：

1. **所有条目都加**（**包括**个人档里的）；
2. 写法是 **`（昵称 QQ 号码）`**；**查不到昵称就只写号码** `（QQ 号码）`。

### 格式与三层示例

前缀加在**正文之前**（`src/memory-store.mjs` 的 `appendEntry`），于是"这一条是谁说的"
是**文件内容的一部分** —— 跨重启、跨会话仍然查得到：

| 落点 | 实际写出来的一行 |
|---|---|
| 群档 `memory/groups/<群号>.md` | `- （忘忧 QQ 100000001）他喜欢钓鱼` |
| 个人档 `memory/people/<QQ>.md` | `- （忘忧 QQ 100000001）他希望我别走` |
| 全局 `MEMORY.md` | `- （忘忧 QQ 100000001）（全局）这家店周三休息` |
| 黑话 `memory/groups/<群号>-slang.md` | `- （忘忧 QQ 100000001）（黑话）「挖矿」指熬夜刷题` |

**★★ 为什么写成"人话 + 号码"而不是只写号码**：号码是**稳定键**（昵称会变、会有重名），
而昵称是打开文件时唯一能让人认出"这是谁"的东西。**两者都要**。

**★★ 为什么个人档也带**（它的文件名已经是 `<QQ>.md`，看起来是重复）：使用者要的是
**条目自身可查** —— 从一行条目里直接读得出是谁说的，不必回到文件名去推。所以**明知重复也照加**。

**★★ 顺序**：身份前缀在**前**、分类前缀（`（全局）`/`（黑话）`）在**后**。
两个前缀回答的不是同一个问题 —— 一个说"谁说的"，一个说"算哪一类"。

**★ 两个清洗**（都有理由，别当成多余的）：昵称里的**括号会被去掉**（`他（老板）` → `他老板`）、
**换行会被压成空格**。记忆文件是**一行一条**的格式，一个换行就等于把这条记忆写坏。
**拿不到号码时返回空串** —— 宁可不带前缀，也不写一个假的。

### 名字从哪来（三条生产通道）

| 通道 | 取名字的方式 |
|---|---|
| 桥接 `#settleMemory`（模型标记 / 关键词直写 / 情绪倾注 / 承诺**四条子通道**） | `#speakerLabel`：① 优先 `memory/contacts.md` 的**按人昵称**（使用者**亲自设的**），② 否则本轮**协议端核实过的** `identity.name`，③ 都没有就空串（只写号码，**不编名字**） |
| 桥接 `#maybePrewakeAffect`（未唤醒·情绪闸门通过那条） | 同上，也走 `#speakerLabel` |
| `src/memory-build.mjs`（控制台「整理记忆」） | person 分组按**那个人**在 `speakers` 里的名字；group/global 用 `speakers[0]`（它回答的是"**谁把它讲出来的**"） |

`applyMemoryItems` 因此新增 `speakerName` 参数；名字取不到时留空，**不是**回落成群名或"某人"。

### 三处配套改动（改前缀必须一起想，否则会出静默毛病）

1. **去重**：比较时**剥掉前缀**（`stripSpeakerPrefix`）—— 先比整行，再比"剥掉前缀后的同一句"。
   这是**迁移**判据：0.3.0alpha 之前写下的条目**没有**前缀，而"同一句话再来一次"仍然必须判成重复，
   否则每轮都会往文件里塞一条一模一样的记忆。
   ⚠️ 剥离**只用于比较**，写进文件的仍是带前缀那一行。
2. **更正**（`pickSupersedeTarget`）：`newEntry` 传的是**剥掉前缀的正文**。
3. **记忆使用账本**（`recordWrite`）：登记的是**带前缀的那一行** ——
   账本按条目文本反查"这条进过上下文没有"，登记成没前缀的正文会让两者对不上
   （表现是账本里每条都"从没进过上下文"，而它其实每轮都在注入）。

### ★★ 如实记下的一条边界：**剥前缀不改变行为**

身份前缀在两边都在时会**抬高**相似度（17 字常量给两边贡献同一串 token）——**实测**
（bigram Jaccard，前缀 `（忘忧 QQ 100000002）`）：

| 正文长度 | 剥掉前缀 | 带前缀 |
|---|---|---|
| 中等长度 | 0.375 | **0.520** |
| 短正文 | 0.167 | **0.429** |
| 长正文 | 0.600 | **0.647** |

**但这一版没有实测到任何行为差别**：门槛是 0.15，两种算法都过线；而且候选只在**同一份文件**里比
（个人档里只有他的条目，群档里两个人的前缀不同），所以前缀也不会让"配错一条别人的"。

**变异测试 6 项，如实分开**：5 项期望红全部红（不加前缀 / 查不到昵称时编名字 / 去重不剥前缀 /
昵称换行不压掉 / 反例对照），**1 项已知不改变行为** —— 把"更正判据剥前缀"去掉
**不会让任何断言红**（门槛 0.15 太低，剥不剥都过线）。这一点**已经如实写进源码注释与测试注释**，
不是隐瞒。

∴ 剥前缀的理由**不是"不剥就判不出来"**（那是夸大），而是
**别让一个与内容无关的常量污染相似度分数** —— 分数要能被读懂（"0.52"里有多少来自内容、
多少来自那 17 个字？），也要让将来调门槛有意义。

### 顺带一句边界：语料库**不**带这个前缀

`runtime/corpus.sqlite` 存的是**消息流水**，每条自带 `senderId` / `senderName` 字段，
30 天 TTL 后就不在了；记忆条目是**沉淀下来的事实**，必须跨重启自己说出"这是谁说的"，
所以身份写进了正文行首。两者判据不同，**别互相照抄**（也写进了 `AGENT.md`「本地语料库」一节）。

### 取证

```powershell
node mocks\verify-memory-store.mjs   # 第 ⑧b 节「身份前缀」：exit 0、自报「🎉 桥接托管记忆测试全部通过」
                                     # ⚠️ 这个套件**不报项数**，所以这里不写「共 N 项」
```

⑧b 一节覆盖：`speakerPrefix` 的两种形状 / 拿不到号码返回空串 / 括号被去掉 /
换行被压掉 / `stripSpeakerPrefix` 认得自己写的前缀 / 群档·个人档·全局·黑话四个落点都带 /
老条目没前缀仍判成重复 / 带前缀之后「他改口了」仍认得出 / 迁移态（老条目无前缀 + 新条目有前缀）仍认得出 /
以及那条**实测的**「前缀会抬高相似度」对照。

## 4.8 ★ 第五步：修「评审台整理没成」—— 模型 JSON 里**字符串外面**多打的引号

### 使用者报的原话

```
修复评审台整理没成：模型的 JSON 解析失败（已尝试修复 1 处仍未通过）：
Expected ',' or '}' after property value in JSON at position 2343 (line 1 column 2344)
｜位置 2343 附近：…同一条，执行时一眼能看到边界。","evidence":["5","26"]}]","notes":"评审里正面样本集中在两类：…
```

### 根因在**修复器**里，不在模型身上

那次输出里有一处形状是 `…"evidence":["5","26"]}]","notes":"…"` ——
数组收尾的 `]` 后面**多打了一个 `"`**（正确的应该是 `}],"notes"`）。

旧修复器的判据只管"**已经在字符串里**"的引号；字符串**外面**看见 `"` 就无条件开一个字符串。
于是那个多打的引号把后面的 `,` 和 `"notes"` 的开引号全变成"正文内容"
（其中一处还被转义成 `\"`，所以报错里那句「已尝试修复 1 处」是真的动过手，只是动错了地方），
最后死在 `Expected ',' or '}' after property value` —— 报错位置指着那个引号，
离真正的错处（它是多余的）反而看不出关系。

### 修法：`"` 只有在**该出现键或值**的位置才能开字符串

前一版加了 `canOpenStringAfter()`：只有在前面一个有意义的字符是 `{` `[` `,` `:`
（或什么都没有）时，`"` 才算开字符串；否则它是**多打的**，直接丢掉并计入 `fixes`。

★ 这条判据**碰不到任何本来就合法的 JSON** —— 合法 JSON 里 `"` 永远只出现在上面那几个位置。
也就是说它只可能修好、不可能修坏。这是它敢直接丢字符的理由，也是选它而不是
"猜哪一处是串位"的理由。

两条真实形状（复现与断言都用它们，见下）：

| 形状 | 结果 |
| --- | --- |
| `…"evidence":["5","26"]}]","notes":"…"` | 丢 1 个引号 ⇒ 解析成功，`via = raw+repaired` |
| `…"evidence":["5","26"]"}]","notes":"…"` | 丢 2 个引号 ⇒ 解析成功（同族，一次两处） |

### ⚠️ 刻意**不猜**的一种形状（写下来免得下次又有人顺手加）

"漏了逗号"（`{"a":1"b":2}`、`]"notes"`）**没有**修。要修它必须猜"这个引号是串位的、
还是前面少了个逗号"，猜错会把**本来能修的**输入变成修不了的 —— 而上面那条判据的
保守版本（丢掉）对已经观察到的两种形状都被验证是对的。宁可照旧失败 + 留下证据（见下）。

### 第二件事：失败时的**模型原文落盘**（这次最贵的地方）

这次报障时系统手上**只有一句报错**：模型到底写了什么形状，一个字节都没留 ——
复现只能靠**从报错片段重建形状**（本文档表格里的形状是重建的，不是原始字节；
`]` 后多一个 `"` 这个定位与报错的位置/片段一致，但原始那份输出**确实没留下**）。

## 4.11 实机验证报的错：发布包里"界面新鲜度检查"崩了，还被说成"你看到的是旧界面"

**实机现象**（用户另一台机器上解压运行）：控制台顶部一条黄色告警 ——
「你看到的是旧界面（构建溯源：没有构建标记，无法自证来源）」，正文是
`Cannot find module 'C:\InteractiveBot\scripts\ui-build-stamp.cjs'`。

**本地复现**（在刚组装好的包里跑，一行就到）：
```
$ .\vendor\node\node.exe src/index.mjs --ui
❌ 界面检查失败：Cannot find module '...\scripts\ui-build-stamp.cjs'
Require stack: - ...\src\ui-status.mjs          （退出码 1）
```

**根因**（比"少拷一个文件"深一层）：
* 发布包按设计**不含 `config-ui/src`**（只拷 `config-ui/dist`），也**不含 `scripts/`**；
* 而 `src/ui-status.mjs` 在**顶层**硬 `require('scripts/ui-build-stamp.cjs')` ⇒ 在用户机器上
  整个模块**加载失败**，被上层兜成 `unstamped`，界面再把 `unstamped` 渲染成「你看到的是旧界面」——
  **在发布包里那是一句假话**（界面一点都不旧，只是没有源码可比）。

**两个修法，只有一个对**：
| 做法 | 结果 |
| --- | --- |
| ❌ 把 `scripts/ui-build-stamp.cjs` 打进包 | 它算哈希的输入是 `config-ui/src`，包里没有 ⇒ 空哈希 ⇒ 报成 `stale`（"源码改了没重新构建"）—— **误导更强** |
| ✅ 认出发布包形态 ⇒ 新状态 `packaged` | 如实说"本机无法核对"，退出码 0，界面给一行中性说明（不告警、不喊旧界面） |

**改了什么**：
* `src/ui-status.mjs`：标记模块改成**惰性、带护栏**加载；新增 `packaged` 状态（先判"有没有
  `config-ui/src`"，再谈标记）；新增导出 `isUiFreshnessAlarm()`（`fresh` 与 `packaged` 都不算告警，
  未知状态保守地算）；`uiFreshnessTitle('packaged')` 明确说"包里只带产物、不带源码"。
* `src/index.mjs`：`--ui` 退出码 `fresh=0`、**`packaged=0`**；启动路径那次检查**包了 try/catch**
  （原来是裸 `await import`，包里那条路会炸 —— 界面新鲜度是增强信息，绝不该拦住回话）。
* `setup.mjs --release`：`packaged` 只打一行中性说明（原来它会掉进最后的 `else`，在包里打出
  一句「✅ 界面产物与源码同步」—— **也是假话**）。
* 控制台（`config-ui/src/pages/Home.tsx` + `lib/api.ts`）：横幅条件从"不是 fresh 就打"改成
  `isUiAlarm(...)`；**只有 `stale` 才说"你看到的是旧界面"**，`unstamped`/`missing`/未知各有准确标题，
  `packaged` 走中性说明。★ 改了界面源码 ⇒ 已 `npm run build`（新的 `sourceHash=bb9559d2e96d…`）。
* 文档：`CONFIG-UI.md`（状态表 3 → 4 行 + 那条"不许把 packaged 说成旧界面"）、`RELEASE.md`
  （状态表 + 退出码 + §5 第 ⑤ 步）、`README.md`（`--ui` 注释）、`PROJECT.json`（`--ui` 用途、
  `src/ui-status.mjs` 描述、新套件的 `commands` 条目）。

**为什么发布门禁没拦住它**（这是本次最该记的一条）：`check-release-package.mjs` 是**静态清单**检查
（该有的文件在不在、不该有的有没有），而这里缺的是**运行时依赖**（`src/` 运行时 `require` 到
`scripts/` 的东西）—— 清单里没有任何一行能表达这件事 ⇒ 它一路绿灯。
**修法**：给组装第 ⑤ 步加一条**会执行代码**的检查 —— 在包里真的跑一次
`src/index.mjs --ui`，**判据只有退出码**（复用 assemble-release 的既有纪律：不解析排版文本、
不用管道捕获输出）。同时新增回归套件 `mocks/verify-ui-status.mjs`（29 项，已进 test 链），
里面有一条**端到端**：把 `src/` 拷到一个**没有 `scripts/`、没有 `config-ui/src`** 的临时"包根"里，
`import ui-status.mjs` 必须成功且得出 `packaged` —— 顶层硬 require 那种写法会在这一步当场失败。

**用户机器上现有那份怎么办**：这次缺陷不影响回话（只是那条告警难看），但要看到修正后的行为，
需要**用新包重装**（`_release/InteractiveBot-0.3.0alpha-win-x64.zip` 已重新组装）。
★ 另外如实说明：实机那句友好文案（"…这是发布包自身的漏带…"）在**本仓库里不存在** ——
说明那台机器跑的不是这次组装的包（可能是更早/另一份构建）。**缺陷本身两边都成立**，已按上面修掉。

  ① **只断言模块文件**（`.mjs/.cjs/.js/.json`）—— 目录（`logs`/`cache`/`config-ui/dist`）与
     运行期产物（`.log`/`.jsonl`）本来就不该在包里，把它们也断言一遍就会天天误报，
     而误报的代价是"下次没人看它"（第一次跑真实包时正好撞出 27 条这种噪声，据此收窄的）；
  ② **豁免列表每条都写理由**且越短越好（`vendor/dsh`＝运行环境不分发、`vendor/snowluma`＝许可证、
     `vendor/__vendor_anchor__.cjs`＝`createRequire` 的锚点），不当消音器用；
  ③ 变量拼接（`join(PKG_ROOT, name)`）抽不出来时**计数并报出**，不静默当成"没问题"
     （实测 246 条引用里 14 处属于这一类）。
* ★ 还必须先**抹掉注释**：注释里会正当地写"以前是这么 require 的"（`src/ui-status.mjs`
  的事故记录、以及本模块自己的 JSDoc 示例），当成真引用就是误报。而第一版用字符级状态机做这件事，
  被**正则字面量**打穿了 —— `/'[^']*'/` 里有**三个**单引号，状态机以为进了字符串，
  于是整个文件后半段的注释都没被抹掉（自测当场抓到：本文件自己的示例被当成真引用）。改成按行处理后通过。
* 回归在 `mocks/verify-release-hygiene.mjs` 第 ⑦ 节，其中最强的一条是**拿真实发布包跑一遍**：
  对当前 `src/` + `mcp/` 的 **212 条**模块引用逐个核对（挑包时按 `package.json` 的版本号选，
  按字母序取最后一个会挑到上一版 `0.3.0beta` —— 那种误报比不查还坏）。

本节其余 6 条都按同一思路处理：**能在发布前跑的检查，就不要留给用户去撞**。

### BUG-2 ★★ 解析出来的 SnowLuma token **从没交给 OneBot 客户端**（本次"连不上"的真正原因）

**现象**：控制台「协议端不可达 · HTTP 401 unauthorized」「令牌被拒」，日志每 30 秒重连一次 401；
而启动日志赫然写着「`[凭据] 来源：SnowLuma 自己的配置（…与 config.json 一致）`」——
"来源正确"和"第一行连接就是 401"同时出现。

**根因**：`resolveOnebotTokens()`（该用哪一组 token 的判定）写得没错，但它在包里**只有两处调用、
两处都不参与建连**：`--snowluma` 分支里打印一句"两边不一致"、启动自检里打印来源。
真正建连的是 `new OneBotClient({ ...config.onebot })` —— 用的是 `config.json` 里那份**静态副本**
（模板默认空串）。而 SnowLuma 的 token 只写在它自己的 `config/onebot_<QQ>.json` 里
⇒ **客户端空手去连**。更误导的是那句"与 config.json 一致"：它的判据 `differsFromConfig`
只比较"两边都非空且不同"，所以"我们这边是空的"会走成 else 分支、打印成一行"一切正常"。

**修法**（新增 `src/token-sync.mjs`，49 项回归）：
* **建连之前**把解析结果接进运行期配置 —— 接线位置写在 `new OneBotClient(...)` 之前，
  并且**钉了一条顺序断言**（`applyOnebotTokens(...)` 的下标必须小于 `new OneBotClient(...)`：
  顺序反了 = 判定结果又被丢掉，这就是这次事故的形状）。
* **只接确定性的**：`matched-config:` / `explicit-selfId` / **只有一个账号** 三种；
  多账号且认不出自己时**只警告**，并给出两条出路（填 `onebot.selfId`，或直接填 token）。
  这条安全底线是 `token-discovery.mjs` 立的（"宁可找不到、也不要猜"）——
  接错账号等于**用别人的身份收发消息**，比连不上严重得多。
* **写回 `config.json` 用 `/api/config` 的同一套纪律**：`mergeConfigPatch` →
  `validateConfig(normalizeConfig(…))` → 备份 `.bak` → 落盘；校验出致命项时**绝不落盘**
  （宁可这次只接在内存里）。不写回的话，界面与 `--doctor` 会一直说"没有配置 accessToken"，
  与"实际能连上"自相矛盾 —— "看着没配、其实在跑"是最难排查的一种状态。
* **文案改准**：只有**真的接上了**才说"来源"；没接上就明说，并在两个 token 都为空时
  直接写出「**两个 token 都是空的**」。误导人的「与 config.json 一致」已从代码里删除
  （留了一条文本守卫：注释里可以引用它、代码行里不许再有）。
* `--snowluma` 分支的措辞同步改准：那个进程**不连 QQ**，所以它不再说"实际用的是哪一组"，
  改成"桥接启动时会以 SnowLuma 自己的为准并同步写回"。`首次使用.txt` 里"去 5099 抄 token"
  那段也改成"正常情况下不用你抄"。
* `detectSnowluma()` 多报一个 `tokenPicked`，界面据此区分"多个账号认不出自己"与"只是还没同步"。

### BUG-3 ★★ 首次登录的引导密码被丢掉 → 首次配置卡死（用户以为要"重新下载/重新注册"）

**现象**：能打开 `http://127.0.0.1:5099/`，但登录页要一个**从未展示过**的密码；
启动日志把用户引到这个页面。实测中用户的做法是"另外下载一份 SnowLuma / 重新注册一遍"。

**根因**（三条各自都合理的决定叠在一起）：
① SnowLuma 把引导密码**只写 stdout**（不写它自己的日志文件）；
② 桥接拉起它时用 `stdio: 'ignore'`（凭据在这里丢掉）；
③ 桥接**只读它自己的日志文件**（`snowluma-log.mjs`）—— 而那条路恰好是唯一没有凭据的。

**修法**（新增 `src/snowluma-console.mjs`，30 项回归，含**真 spawn 的端到端**）：
* stdout/stderr 改为**文件句柄**重定向到 `logs/snowluma-console.log`
  （`stdio: ['ignore', fd, fd]`）—— 不建管道，所以老注释里"管道一端消失后子进程写日志会 EPIPE
  而挂掉"的顾虑**仍然不成立**，同时把输出留下来了。
* ★ **纠正一条旧结论**：`snowluma-log.mjs` 原来断言"重定向到文件会变成 GBK 乱码"。
  那是**用 pipe 测出来的**，不适用于文件句柄 —— 本机实测（Node 子进程，中文与
  `initial credentials:` 行同时写 stdout/stderr）：**179 字节、UTF-8 完全正确**、
  没有替换字符、中文逐字对得上。旧结论已在源码里更正，并写清"两者分工不同"。
* **只报位置、不回显密码**：告诉用户"去哪个文件、搜 `initial credentials`"。
  少一份副本就少一个泄漏面（回归里有一条断言：提示与日志里**不许**出现密码本身）。
* 启动时就打一行"输出已写到 X"；`--open-console --wait-snowluma` 那一支在 SnowLuma 起来后
  再扫一次文件、给出**扫到凭据**的提示；`detectSnowluma()` 也带上 `bootstrap`（同样不含密码），
  控制台「协议端」页据此显示提示框。
* 未初始化时（`config/webui.json` 的 `mustChangePassword = true`）明确说：
  **再启动一次 SnowLuma 会轮换出新密码并重新打印，不需要重新下载、也不需要重新注册** ——
  直接把"重装"这条错误路径掐掉。
* `首次使用.txt` 第四步与"出问题了怎么办"两处文案与实现对齐。

### BUG-4 `start.bat` 里未转义的括号（**成功路径也一起坏**）

**现象**：双击后窗口一闪，`[!] Could not start (exit 1) -- see the message above.`，
stderr `-- was unexpected at this time.`，批处理整体退出码 **255**；
而本该打印的"Bridge started in the background / Console / SnowLuma / Logs"**一行都出不来**。

**根因**：第 144 行位于 `if not "%EXITCODE%"=="0" ( … ) else ( … )` 块内，
文案里的 `(exit %EXITCODE%)` 有个**未转义的 `)`**；cmd 在**解析期**就把整个块读完，
那个 `)` 提前闭合了块，剩下的内容被当成新命令。

**实测**（本机 cmd.exe，逐条记退出码，也是静态检查的判据来源）：
| 写法（块内） | 结果 |
| --- | --- |
| `echo A (paren) B` / `echo A ) B` / 嵌套块里的 `(x)` / 块尾 `) echo Y` | **255**，`… was unexpected at this time.` |
| `echo A (B`、行尾左括号、单行 `if 2==2 ( echo Y )`、`for %%i in (a b) do`、`))`、`) & echo Y`、双引号内、`^` 转义、`rem` 行 | 正常 |
| **顶层**的任何括号（含单独一行 `)`） | 正常 —— 顶层的括号 cmd 当普通字符 |

★ 最反直觉的一条：**即使 if 条件为假、走 else 分支也照样 255**（解析期就崩了）——
所以"机器人明明起来了，窗口却报错"和"机器人没起来，窗口什么都不说"**是同一个 bug**，
报告里那句"成功路径不受影响"是错的。

**修法**：文案去掉括号（`echo [!] Could not start. Exit code %EXITCODE% -- see the message above.`），
并新增 `src/batch-safety.mjs`（纯函数静态检查）+ 两处接线：发布验收第 ⑦ 步扫包里**每个** `.bat`
（`scripts/check-release-package.mjs`），回归 `mocks/verify-release-hygiene.mjs`（35 → 56 项，
含**事故原文那一行必须被报出来**，以及上表里所有"正常写法不许误报"）。

### BUG-5 DSH 定位规则与桌面版真实布局不匹配

**现象**：按文档装好 DSH 桌面版，桥接仍报"没找到 DSH"。**根因是两个叠加**：
① 装出来的目录名是 `DeepSeek Harness`（**带空格**），候选表只写了 `DeepSeekHarness`；
② 0.2.0-rc.2 把 CLI 打在 **`resources\app.asar`** 里，`resources\app` 这个目录**不存在**，
   而普通 node **不认 asar**（实测 `Error: Cannot find module '…app.asar\…'`）。
报告同时证明"抽出来就能用"（`--version` → 0.2.0-rc.2、`[rpc] initialize 成功`、`✅ DSH 就绪`），
所以这**不是版本不兼容**，只是少了一步。

**修法**：
* 候选表（`src/local.mjs`，`dshInstallRootCandidates` 仍是**唯一一份**）覆盖
  **两种目录名 × 三种形态**：`resources\app`、`resources\app.asar\dsh`、`resources\app.asar.unpacked\dsh`，
  Program Files 与 `%LOCALAPPDATA%\Programs` 两处都要；`kind: 'asar'` 的候选**明确不算找到**
  （普通 node 读不了它），改由新增的 `findDshAsar()` 单独检出 —— 于是"没装"与"装了但打包在 asar 里"
  能给出**两种不同的出路**，而不是同一句"没找到"。
* 新增 `src/dsh-extract.mjs` + CLI `node src/index.mjs --extract-dsh [--asar <路径>] [--target <目录>] [--force]`：
  把 CLI 安装根抽到 `vendor/dsh`（第 1 优先级候选，**抽完不用再配**）。格式与踩点写在源码里：
  文件头 8 字节是 pickle、其载荷是 header pickle 长度；header pickle 第 8 字节起是 JSON；
  **文件体偏移基准 = `8 + headerPickleSize`**；`unpacked: true` 的条目要去
  `app.asar.unpacked\<同相对路径>` 取（node-pty / sharp / sherpa-onnx / koffi 等原生模块都在这一类，
  缺了必须**报出来**）。★ 前缀**自动判定**（在归档里搜 `bin.js` 反推哪一层是安装根）——
  实测归档根下先有一层 `dsh/`，所以要剥掉它才能正好落在 `vendor/dsh`。
* **验证方式**：解析器拿**真实归档**验过 —— 本机三份 Electron 应用的 `app.asar`
  （Blockbench 359 条、kimi-desktop 903 条、百度网盘 **24572 条**）：按 `bodyOffset + offset`
  取出的 `package.json` 能 `JSON.parse` 通过；同时确认"普通 node 读 asar 内部路径"仍然失败
  （报告的决定性实验反向成立）。另外自造 asar 测了 `unpacked` 旁路、布局变化（归档根即安装根）、
  坏归档、路径逃逸（带 `..` 的条目被拒绝且不落盘）。
* 文案：`setup.mjs --check`、`--doctor`、界面「DSH 安装路径」「额外搜索路径」三处都给同一份提示
  （`dshAsarFixHint()`，单一来源）；`首次使用.txt` 里**"装完不用做任何配置"这句已删除**
  （实测不成立），改成"桌面版要抽一步"并给出可照抄的命令。

### BUG-6 `--doctor` 把"外部进程登记"算成"另一个桥接"

**现象**：拉起 SnowLuma 后体检报「❌ 同时运行的桥接数量：还有 1 个：pid …」；
单独跑 `--doctor` 时**正在跑的那个真桥接**也会被算进来。★ 危险在于它给的处置建议是
`--processes --kill <pid>` —— **照做会杀掉 SnowLuma，或杀掉唯一那个桥接**。

**根因**：`processes.filter(p => !p.isSelf)` 没有按 `profile` 过滤（SnowLuma / chat-review
也登记在同一张表里）。

**修法**：改用 `process-guard.mjs` 既有的 `runningBridges()`（`profile === 'bridge'`），
**按数量**判定（1 条正常、≥2 条才是真冲突）；非桥接的登记**另起一行**且永远是 `ok: true`
（"供参考、不算故障"），`--kill` 建议只在真冲突时出现。回归 `mocks/verify-doctor.mjs`（30 → 48 项），
覆盖三种视角：一个桥接 + 两个外部插件 → 不报；两个桥接 → 报 ❌ 且给建议；
**CLI 视角**（`--processes` 是另一个进程，`isSelf` 恒为 false）→ 唯一那条桥接不算冲突。

### BUG-7 把"默认开启的群聊"标成 ❌

**现象**：`trigger.groupEnabled = true` 是**出厂默认**，体检却给它 ❌（文案"有账号风控风险"），
于是每台按默认配置跑的机器都会看到「能启动，但上面有 ❌ 项需要处理」，第一反应是"程序坏了"。
❌ 里混进"设计如此"的项目，会训练使用者忽略 ❌。

**修法**：该行改成 `ok: true` + `level: 'warn'`，打印层把 `warn` 渲染成 **⚠️**（不是 ✅、
也不是 ❌），不计入 `allOk`（退出码仍为 0）；结论句同时改准：
「🎉 全部就绪（有 N 项提醒，不是故障）」—— 上面明明印了一个 ⚠️、下面却说"一切正常"，
用户会以为是渲染错位。回归里直接**抓 `printDoctor` 的 stdout**断言它印的是 ⚠️ 而不是 ✅/❌。

### 6.2 这条基线在这一版加了**一道**机制（另一道在第二步被取消）—— 改文案之前先读这一段

1. **基线缺失时不再自动生成**（**这一条仍然有效**）：只有包根存在 **`.regenerate-golden`**
   标记文件时才允许重建，否则判红。理由：一条**能被自己重新生成的基线等于没有基线**
   （删掉 fixture 再跑一次就"修复"了）。
   要换基线就得显式建这个标记（并在提交信息里说明为什么），换完删掉它。
2. ~~**逐字比对先把"说话方式"那一段剥掉**~~ —— ★ **第二步已取消，现在是整份提示词逐字比对**。

   而 fixture 是逐字快照 —— 不剥的话，改常量里一个逗号就会让"提示词结构没漂"这条断言变红。
   **但第二步之后说话方式在 `personas/小鲸鱼（完整带情绪）.md` 里，它是数据不是代码** ——
   数据变了，**基线就该跟着重建**（这才是逐字基线该有的纪律）。
   ∴ 定向断言（说话方式逐字在提示词里 / 只注入一次）随之取消；反向三条保留在
   `verify-memory-roundtrip.mjs` 第 ⑱ 节（提示词里不许出现 `【怎么说话】`、`【别变成客服】`、
   「但对方认真问事实、技术问题时，就认真答」与双态时代那句「这一轮是**闲聊**」）。

   **∴ 今后改说话方式的纪律**：改那句文案会让**逐字基线报红**，这是**预期的** ——
   按提示建 `.regenerate-golden`、重建、**人工检查** `mocks/fixtures/prompt-golden.txt` 的 diff 再提交。
   看到这条红**不是**结构坏了。

> 顺带说清一个技术点（下次再遇到会省时间）：会话文件是**背靠背的 zstd 帧**（没有长度前缀）。
> `zstdDecompressSync` 只能解第一帧（几十字节），流式解压器会报 `Unknown frame descriptor`；
> 正确做法是**按魔数 `28 b5 2f fd` 切帧、逐帧解**（本次 42 个会话共解出 198 KB jsonl）。

## 6. 这次的教训：**"删除"这条路没有留底**（建议的根治，待决定）

现有机制里，记忆**有**备份，但只在一种情况下产生：
`memory-consolidate.mjs:428` 的**每小时整理**会给"被改动的文件"留一份
`memory/.backups/memory__<文件>.<时间戳>.bak` —— 这就是为什么 `group-*`/`private-*` 有旧副本，
而 `MEMORY.md`（从未被整理过）**一份都没有**。

而**控制台/接口的删除**（`DELETE /api/memory/file` → unlink，并顺手 `dropMemorySnapshot`）
**不留任何副本** —— 一次误点就是永久的。这次能救回来纯属侥幸：恰好有几份手工 `.bak` 加上会话记录还在。

建议（都属于"补缺口"，10 行左右 + 一条测试）：

1. **删除前先留底**：复用现成的 `.backups/` 约定，把文件复制成 `memory__<名字>.<时间戳>.bak` 再删；
2. **界面上给二次确认 + 说明"会留一份副本在 memory/.backups/"**（不再是静默不可逆）；
3. 可选：控制台「记忆」页加一个"最近删除 / 从备份恢复"的小入口（只在 `.backups/` 里挑，不做自由路径）。

# pixiv查图插件 —— 安装教程 & 功能说明

适用：**QQ Agent 爆改版 0.4**（本项目实际路径 `D:\QQ-Agent-爆改版0.4`）
插件 ID：`pixiv-lookup`　显示名：**pixiv查图插件**　版本：**1.1.0**　类型：LLM 型技能（`skills/`）
官方站点：<https://www.pixiv.net/>

> ### 🔧 1.1.0 修了什么（本次重点）
>
> **症状**：机器人能查到 P站作品、能贴出链接，但**发不出图**，报
> `图片下载失败：域名解析到内网/本机地址，已阻止`；连百度图床、QQ 表情包也一起发不出去。
>
> **原因**（三条同时在起作用）：
> 1. `i.pximg.net` 有**防盗链** —— 请求头没有 `Referer: https://www.pixiv.net/` 一律 403；
> 2. `i.pximg.net` 在中国大陆**必须走代理**，而宿主的图片下载通道既不认系统代理也不带 Referer；
> 3. 宿主的图片下载带 **SSRF 保护**，默认拒绝"内网/本机"地址。开着 Clash/mihomo 的
>    **fake-ip** 时 DNS 会把域名解析成 `198.18.x.x` 虚拟 IP，正好落进"内网"名单 ——
>    于是**所有**图片下载一起报那句错。
>
> **修法**：插件内置一个只监听 `127.0.0.1` 的**本地图片桥** —— 由插件自己（带 Referer、
> 走你配的代理）把图取回来，再给宿主一条本地直链。宿主的下载通道对此一视同仁，
> 不需要给 QQ Agent 打补丁。
>
> **你需要多做一步**：在宿主里打开「**允许下载内网/本机图片地址**」，否则宿主的保护会挡掉
> 这条本地直链。**详见第 4.4 节**（含安全说明与怎么关掉）。

## 一、这份东西是什么

一个装在 QQ Agent 里的**查图插件**：让机器人在 Pixiv（P站）上搜插画。

装好并打开后，群里出现这类话时，机器人会自己去搜，然后报出作品名、作者和链接：

- 「帮我找初音ミク的图」
- 「有没有原神（角色名）的插画」
- 「P站上那幅XX的图发我看看」
- 「今天P站有什么好看的图」

它给出的是**作品信息**（标题 / 作者 / 标签 / 链接），并且 —— 从 1.1.0 起 ——
还能把图**真的发到群里**（见 4.4 节：结果里会多一个「发图直链」）。
插件不搬运、不转载原作文件，只在需要发图时临时把图取到内存里交给宿主发送。

## 二、安装教程（4 步）

### 前置检查

| 项目 | 要求 |
| --- | --- |
| QQ Agent | 爆改版 0.4（`D:\QQ-Agent-爆改版0.4`），并且**已经能正常跑** |
| 网络 | **能访问 `pixiv.net`**。中国大陆直连会超时，**必须有代理**（Clash / v2ray 等），见第 5 节 |
| 要发图（可选） | 宿主的「设置 → 安全 → **允许下载内网/本机图片地址**」要打开，见**第 4 步**与 4.4 节 |
| 磁盘 | 插件本身约 120 KB，无额外依赖（不用装 node、不用 npm install） |

### 第 1 步：确认插件目录已就位

插件本体在这个目录：

```
D:\QQ-Agent-爆改版0.4\skills\pixiv-lookup\
```

里面应该有这些文件：

```
index.js              ← 插件主程序（注册 3 个工具 + 提示词 + 断路器 + 图片桥接线）
image-bridge.js       ← 本地图片桥（1.1.0 新增：让宿主能真的下载 P站图）
skill.json            ← 清单：名字、设置项、工具声明
package.json          ← 只声明"本目录是 ES Module"，没有依赖
README.md             ← 插件说明（开发者视角）
安装与使用说明.md      ← 本文件
selftest.bat / .ps1   ← 一键自测（151 项，不需要外网）
test\                 ← 自测脚本 + 测试数据
```

> **如果这个目录不存在**：把 `pixiv-lookup` 整个文件夹复制到
> `D:\QQ-Agent-爆改版0.4\skills\` 下即可。目录名要保持 `pixiv-lookup`
> （清单里的 `id` 与之对应）。复制完**重启一次 QQ Agent**。

### 第 2 步：重启 QQ Agent（让加载器扫到新目录）

- 关掉 QQ Agent（托盘图标 → 退出），再双击 `启动-单号.bat`
- 或者：QQ Agent 开着也行 —— 它带热重载，会自动发现新插件。
  但**第一次装完建议重启一次**，最稳妥。

### 第 3 步：在设置里打开插件开关

1. 打开 QQ Agent 控制台 → **设置** → **扩展**
2. 找到 **pixiv查图插件**
3. 把开关**打开**
4. 点进插件详情，按需填写 **代理地址**（见下节）

默认是**关闭**状态 —— 这是故意的，避免刚装好就在没配代理的情况下乱请求。

### 第 4 步：打开「允许下载内网/本机图片地址」（**要发图就必须做**）

只查图、只发链接 → **这一步可以跳过**。
想让机器人**把图直接发到群里** → 必须打开这个开关，否则 `send_image` 会报
`图片下载失败：域名解析到内网/本机地址，已阻止` 或 `禁止访问内网/本机地址`。

打开方式（两种任选）：

**A. 界面上改（推荐）**

1. QQ Agent 控制台 → **设置 → 安全**
2. 找到「**允许下载内网/本机图片地址**」（配置名 `security.allowPrivateImageHosts`），**打开**
3. 保存 → **重启一次 QQ Agent**（或至少重载技能）

**B. 直接改配置文件**

1. **先退出 QQ Agent**（否则改动可能被覆盖回去）
2. 打开 `D:\QQ-Agent-爆改版0.4\data\config.json`
3. 找到 `security` 这一段，把 `allowPrivateImageHosts` 改成 `true`：

   ```json
   "security": {
     "allowPrivateImageHosts": true,
     "allowPrivateFetchHosts": false,
     ...
   }
   ```

4. 保存 → 重新启动 QQ Agent

> **这个开关是干什么的、安全吗？** —— 它放宽的是「图片下载」这一条通道的内网限制
> （只影响发图，不影响 `web_fetch` 那类网页抓取）。开了之后约等于告诉机器人：
> **"本机上的图源我信任"**。这正是插件图片桥（`127.0.0.1` 直链）能工作的前提。
> 代价与边界、以及"不想开怎么办"，见 **4.4 节**。

## 三、填写 Cookie（要 R-18 / 更全结果才需要）

> 不填 Cookie 也能搜图。填了才能查 **R-18** 内容、拿到更完整的结果。

### 怎么拿到 Cookie

1. 电脑浏览器登录 <https://www.pixiv.net/>（**要登录状态**）
2. 按 `F12` 打开开发者工具
3. 切到 **Application**（应用）/ **存储** 标签 → 左侧 **Cookies** → 点 `https://www.pixiv.net`
4. 找到 **`PHPSESSID`** 这一行，双击它的值全选复制
5. 回到 QQ Agent → 设置 → 扩展 → pixiv查图插件 → **Pixiv Cookie** 框，粘贴：

   ```
   PHPSESSID=你的值
   ```

   （也可以把浏览器里整行 Cookie 全选复制过来，插件会自动清洗格式）

### 填完是什么样

- 输入框是**密码框**（圆点显示），**不会把 Cookie 明文显示在界面上**
- 保存后再打开设置：框里是**空的**，提示语变成「**已设置（留空 = 不修改）**」
- 这说明「已保存」，**不是丢失**。想改就重新粘贴一次；留空直接保存 = 保持原值不变

### ⚠️ 安全须知（请认真看）

| 事项 | 说明 |
| --- | --- |
| Cookie 等于登录凭证 | 谁拿到谁就能以你的 Pixiv 身份操作。**别截图、别外发、别贴群里** |
| 存放位置 | 明文存在 `D:\QQ-Agent-爆改版0.4\data\config.json`，请保管好这个文件 |
| 界面上 | 密码框 + 只回显 `******`（已实测：连 `/api/skills` 接口响应里也搜不到明文） |
| 怎么清除 | 界面上目前**清不掉**（上游约定「空值 = 不修改」）。办法见下方 FAQ Q6 |
| 群里用 | 建议把「允许查询 R-18 内容」保持**关闭**，尤其在多人群里 |

## 四、功能说明

插件注册了 **3 个工具**给模型使用（模型看到的完整名字带前缀）：

### 工具 1：`pixiv-lookup__search` —— 搜图（最常用）

按关键词搜索插画/漫画。

**参数**

| 参数 | 说明 |
| --- | --- |
| `keyword`（必填） | 关键词。中文/日文/英文都行，按用户原话传即可 |
| `limit` | 返回条数，会被夹到「每次返回条数上限」以内 |
| `order` | 排序：`popular_d` 热度（默认）/ `date_d` 最新 / `popular_male_d` 男性向 / `popular_female_d` 女性向 等 |
| `sMode` | 匹配方式：`s_tag` 标签模糊（默认）/ `s_tag_full` 标签精确 / `s_tc` 标题或简介 |
| `page` | 页码 |
| `r18` | `true` = 只查 R-18（需要设置里打开「允许查询 R-18 内容」，否则会被拒绝并说明原因） |

**返回内容**（JSON，模型会整理成人话）

```json
{
  "关键词": "初音ミク",
  "来源": "Pixiv 搜索（order=popular_d，mode=safe，s_mode=s_tag，第 1 页）",
  "命中总数": 4707,
  "返回条数": 10,
  "结果": [
    {
      "id": "100540913",
      "标题": "……",
      "作者": "……",
      "类型": "插画",
      "日期": "2022-08-17",
      "尺寸": "1200×1877（竖图）",
      "页数": 1,
      "标签": ["原神", "……"],
      "链接": "https://www.pixiv.net/artworks/100540913",
      "缩略图": "https://i.pximg.net/...（人看的原始链接，别拿去发图）",
      "发图直链": "http://127.0.0.1:18717/i/…（★ 这一条才是能喂给 send_image 的）"
    }
  ]
}
```

> ⚠️ **中文关键词命中率偏低**：Pixiv 的标签体系以**日文**和**英文**为主。
> 中文搜不到时，让机器人换一个日文/英文说法再试一次即可（插件提示词里已经这么教模型了）。
>
> ★ **`发图直链` 是 1.1.0 新增的字段**：它是本插件在**你这台机器上**临时开的一个
> 本地图片地址。模型把这一整条照抄给 `send_image(url)` 就能把图发出去。
> 为什么需要它、需要注意什么，见 **4.4 节**。

### 工具 2：`pixiv-lookup__artwork` —— 作品详情

**参数**：`ids` —— 一个或多个作品 id / 链接。支持这几种写法：

```
100412238
100412238,100412239
https://www.pixiv.net/artworks/100412238
```

一次最多 5 个（防止把 Pixiv 打爆）。

**返回内容**：标题、作者、作者 id、类型、分级（R-18 / 全年龄）、发布日期、尺寸、页数、
**收藏数、点赞数、浏览数**、标签（最多 20 个）、简介（已把 HTML 转成纯文本）、
缩略图/大图/**原图**地址、**发图直链 / 原图直链**，多图作品还会附**每一页的原图地址**
和前 4 页的**发图直链**。

> ⚠️ `i.pximg.net` 图床有**防盗链**：图片链接只有在请求头带
> `Referer: https://www.pixiv.net/` 时才能下载。所以 `缩略图/大图/原图` 这些
> **原始地址不能直接喂给 `send_image`**（会 403 或超时）—— 发图要用「**发图直链**」。
> 插件在返回里也写明了这一点。

### 工具 3：`pixiv-lookup__ranking` —— 排行榜

**参数**

| 参数 | 说明 |
| --- | --- |
| `mode` | `daily` 日榜（默认）/ `weekly` 周榜 / `monthly` 月榜 / `rookie` 新人 / `original` 原创 / `male` 男性向 / `female` 女性向 / `*_r18`（需开启 R-18） |
| `content` | `illust` 插画（默认）/ `manga` 漫画 / `ugoira` 动图 / `complex` 不筛选 |
| `limit` | 返回前几名（受「每次返回条数上限」约束） |
| `date` | 指定日期 `yyyymmdd`，不填取最新一期 |

**返回内容**：名次、id、标题、作者、类型、日期、标签、尺寸、链接、**发图直链**。

### 4.4 发图直链：让机器人真的把 P站图发出来（**本次修复的重点**）

#### 先看结论

| 你想干什么 | 需要做什么 |
| --- | --- |
| 只让机器人报「作品名 + 链接」 | 什么额外都不用做，装好、配好代理就能用 |
| 让机器人**把图直接发到群里** | ① 插件设置里保持「**本地图片桥**」打开（默认开）<br>② 宿主打开「**允许下载内网/本机图片地址**」（安装教程第 4 步） |

#### 为什么原来发不出图

老版本（1.0.0）只给了模型 `i.pximg.net` 的**原始图片地址**，让模型把它喂给 `send_image`。
这条路上有三道坎，道道都过不去：

| 坎 | 具体表现 |
| --- | --- |
| **防盗链** | 请求头不带 `Referer: https://www.pixiv.net/` → **403**（实测：不带是 548 字节的错误页，带上才是 1.07MB 的正常 jpeg） |
| **要代理** | 宿主的图片下载通道**不认系统代理**（Node 的 fetch 不会自动走 Clash 的系统代理），大陆直连 `i.pximg.net` → 等到超时 |
| **SSRF 保护** | 宿主默认拒绝解析到"内网/本机"的地址。开着 Clash/mihomo 的 **fake-ip** 时，DNS 会把**所有**域名解析成 `198.18.x.x` 虚拟 IP，正好被判定为内网 → 于是**连百度图床、QQ 表情包都发不出去**，报的就是那句 `图片下载失败：域名解析到内网/本机地址，已阻止` |

所以模型当时只能无奈地说一句「图我这边带防盗链发不出来」。

#### 现在是怎么做的（图片桥）

1. 你让机器人发图 → 模型拿到结果里的「**发图直链**」，
   形如 `http://127.0.0.1:18717/i/AbC…`（端口可在设置里改）；
2. 模型把这条直链交给宿主的 `send_image`；
3. 宿主来下载这条直链时，插件**当场**才去 Pixiv 取图 —— **带 Referer、走你在插件里配的代理**；
4. 取到的图片字节直接回给宿主，宿主像发任何一张网图一样把它发到群里（先看一眼预览也照常工作）。

对宿主来说，这只是一条普通的本地图片地址。**不需要给 QQ Agent 打任何补丁**，
插件的代理也**不会**影响主程序（见 6.3 节）。

#### 你需要打开的那个开关

宿主的图片下载通道默认会把 `127.0.0.1` 当成"内网地址"拒掉。所以要去
**设置 → 安全 → 允许下载内网/本机图片地址**（`security.allowPrivateImageHosts`）打开它。
**只影响"发图"这一条通道**，不影响 `web_fetch` 那一类网页抓取
（那个是另一个开关 `allowPrivateFetchHosts`）。

**开了它，风险是什么？** 直说：

- 放宽之后，模型如果能被诱导着去拿某个**内网图片地址**（比如你路由器管理页、局域网里的
  图床），理论上有可能把那张图发到群里。图片内容仍要过魔数校验（HTML 页面会被拒绝）。
- 插件自己的图片桥**只监听 `127.0.0.1`、只服务本进程刚随机生成的短 id、只允许
  `*.pximg.net` 域名** —— 它本身变不成"任意地址代理"，别人也连不上（外网/局域网都访问不到）。
- 这是个人电脑上的自用机器人，且只有管理员能改设置。**能接受就开**；不能接受就**别开发图**
  （只发链接），或者干脆把插件设置里的「本地图片桥」也关掉。

**不想开宿主开关时会发生什么？** `send_image` 会返回
`错误：图片下载失败：禁止访问内网/本机地址`（或带"域名解析到内网"的那句）。
这不是插件坏了，是宿主的保护在按设计工作 —— 让管理员开开关即可。

#### 验证它真的通了（一条命令）

```powershell
$env:ELECTRON_RUN_AS_NODE = '1'
Set-Location 'D:\QQ-Agent-爆改版0.4'
& '.\node_modules\electron\dist\electron.exe' '.\skills\pixiv-lookup\verify-image-bridge.mjs'
Remove-Item Env:ELECTRON_RUN_AS_NODE
```

它会在**真机**上跑四条链路（需要外网 + 你那个本地代理）：

```
✅ 插件能通过代理查到作品，并给出「发图直链」
✅ 开关关着时：宿主的保护确实会挡掉本地直链（复现你看到的那句报错）
✅ 开关打开后：宿主能下载到真图片（JPEG 魔数 + 体积合理）
✅ 直接调用宿主的 send_image 工具：图片数据真的交给了发送器
（对照组）✅ 不经过图片桥、直接下 i.pximg.net 裸链：必定失败
=== 结论：12 项符合预期，0 项不符合 ===
```

- 默认会自动找本地代理（`--proxy http://127.0.0.1:7890` 可手动指定）
- 加 `--skip-raw` 可跳过"裸链必定失败"那一步（那步要等一次约 20 秒的超时）
- ⚠️ 结尾那句「结论」才是判据：Windows 下 electron 会往 stderr 打一行
  `registration_protocol_win.cc ... CreateFile: 拒绝访问`，PowerShell 可能因此把退出码显示成 1，
  **这是 electron 自己的噪声，不是脚本失败**。

#### 发图的几个细节（实测过的）

| 细节 | 说明 |
| --- | --- |
| 图是**大图**不是缩略图 | 搜索/榜单接口只给 250×250 的方形缩略图；插件会按 Pixiv 的公开路径规则换算成 **master1200**（长边 1200），发出去才清晰 |
| 直链**有有效期** | 默认 30 分钟（设置里可调）。过期后再发会提示"重新查一次" |
| 直链**只在本次运行内有效** | 插件重载 / QQ Agent 重启后旧直链失效（这是有意的，不留后门） |
| 一次能发几张 | 由宿主决定（设置 → 聊天 → 发图，默认「一次处理最多 2 张」，你这份配置里是 5 张） |
| 「原图」可能发不出去 | 原图常有 3~10MB，超过宿主的「单张图片上限」（默认 5MB）会被拒；日常发图请用「发图直链」（大图） |
| 预览（先看一眼）也走这条路 | `send_image(url, preview=true)` 下载的是同一条本地直链，视觉接口能正常识别 |
| 百度图床/表情包发不出去 | 现在也一起修好了：开了宿主那个开关后，fake-ip 导致的"内网"误判不再拦图 |

> 填了代理之后插件会通过它出网。代理软件要在同一台机器上跑着。
>
> **为什么推荐填 `auto` 而不是一个具体端口**：Clash / mihomo 这类客户端（包括"兰科云"这种
> 套壳客户端）**常常把混合端口设成每次启动随机**，配置文件里的 `mixed-port` 每次都不一样。
> 写死一个端口当时能用，过两天代理一重启就失效 —— 而表现只是"插件突然连不上"，
> 很难联想到是端口变了。填 `auto` 之后插件会自己找：
>
> | 顺序 | 探测方式 | 说明 |
> | --- | --- | --- |
> | ① | 宿主的 Electron 会话代理 | 和浏览器/system 用同一套规则，端口变了它也知道（最可靠） |
> | ② | Windows 系统代理（注册表） | 要求代理软件开着"系统代理"（`ProxyEnable=1`） |
> | ③ | 扫常见本地端口 | `7890 / 7897 / 10809 / 2080 / …`（前两条都不行时兜底） |
>
> 三条都探测不到就**退化成直连**（不会把插件搞成不可用），并在报错里写明
> 「当前代理状态：自动探测没找到本机代理」—— 这时把端口填死即可
> （端口号在代理软件的界面上能看到）。
>
> ✅ **这个代理只作用于本插件自己的 Pixiv 查询，绝对不会影响 QQ Agent 主程序**
> （包括主程序调用模型 API）。这一点由代码保证并用 8 项自测钉住，详见第 6.3 节。

## 六、查图上限 与 连续失败强制终止（两个「闸」）

这一节讲两个和"别失控"有关的功能。它们刻意做成两个独立开关，因为管的不是同一件事：
**一个限制「每次要多少条」，一个限制「失败后还要不要继续试」。**

### 6.1 查图上限

「查图上限」= **每次返回条数上限（`maxResults`）**。它是**硬上限**，服务端会二次夹紧：

```
模型传 limit=999   →  夹到 maxResults（例如 10）  →  再过滤 R-18  →  最终 ≤ 10
模型传 limit=4     →  允许调小  →  返回 4 条
模型不传 limit     →  用 maxResults
```

「最大翻页数」是第二道闸：模型最多能翻到第 N 页。

另外两道内置保险：

- 作品详情一次最多查 **5 个** id
- R-18 过滤：`allowR18` 关闭时，搜索结果里带 R-18 标记的条目会被剔除，并在返回里写明「已过滤 N 条」

**想让机器人少发点图** → 把「每次返回条数上限」调到 3~5。

### 6.2 连续失败强制终止（断路器，默认打开）

**它解决的真实问题**：Pixiv 连不上时，每次查询都要等满 `timeoutMs`（默认 20 秒）。
模型拿到"超时"结果后的常见反应是**换个关键词再试** —— 试 3 次就是 1 分钟，
而且它经常把一整轮的 12~20 次工具调用预算全耗在重试上，**群里最后一条回复都没有**。
用户看到的现象是"机器人卡死后装死"，而不是"它说了句连不上"。

**打开后（默认打开）的行为**：

```
第 1 次失败  → 正常报错，提示配代理
第 2 次失败  → 正常报错
第 3 次失败  → 达到阈值：返回里附带
               「⛔ 插件已强制停止后续查询」
               「不要再调用任何 pixiv 工具，立刻用一句自然的中文把情况告诉对方」
第 4 次起    → 冷却期内【一个请求都不发】（不再等超时），直接返回终止说明
冷却结束后   → 自动放行一次试探，成功就完全恢复正常
```

也就是说：它不只是"报错更快"，而是把**「停止调用工具、直接回话」这句话明确塞回给模型**，
逼它把话说出来。插件同时在系统提示词里也教了模型这件事，两层一起保证。

**哪些失败会被计数**（代表"上游现在不行"，再试也是白等）：

- 请求超时（连接超时 / 读超时）
- DNS 解析失败、连接被拒绝或中断
- HTTP 403（风控）、429（限流）、5xx（服务端错误）
- 返回的是网页而不是数据（被风控页 / 登录页接管）
- Pixiv 返回 `error: true` 的业务报错

**哪些失败不会被计数**（代表"这次请求本身有问题"，换个参数就能成）：

- 作品 404 / 不存在 / 已删 / 转私密
- 没传 id、id 格式不合法、关键词为空
- `r18=true` 但「允许查询 R-18 内容」没打开（被闸门拒）
- 搜到了但结果是 0 条

> 这个区分很关键：不然群里手滑打错一个作品号，就可能让整个插件"被封"一分钟，
> 别人正常查图也一起被拒 —— 那就成了新的静默故障。

**其它细节**

| 行为 | 说明 |
| --- | --- |
| 冷却期内真的不发请求 | 被拦下的调用耗时是 **0 毫秒**，不是"快速失败" |
| 跨工具生效 | search / artwork / ranking 共用一道闸（它们走同一条网络通道） |
| 成功即清零 | 任意一次成功都说明上游恢复了，计数立刻归零 |
| 自动恢复 | 冷却结束自动放行一次试探，成功就完全恢复正常 |
| 冷却下限 5 秒 | 防止被误设成 0 而变成"永久封死" |
| 冷却期内**换关键词**也拦 | 这是故意的：连不上跟关键词无关 |

**怎么确认它动作了**：

- 报错文案里会出现「已完成终止」或「插件已强制停止后续查询」
- 跑 `verify-in-agent.mjs`（见第 7 节）或 `diagnose()`，会看到类似：
  `断路器: 已触发（终止中） · 连续失败 3/3 · 冷却 42s/60s · 最近原因：请求 Pixiv 超时…`

**想关掉**：把「多次查询失败时强制终止」关掉即可，行为退回"每次失败都照实报错、绝不拦截"。

**调参建议**

| 场景 | 建议 |
| --- | --- |
| 网络偶尔抖一下 | 阈值调到 5，避免一两次抖动就终止 |
| 代理经常抽风 | 冷却调到 120~300 秒，免得它一直重试一直失败 |
| 想让它"再试几次" | 阈值调大（比如 6），代价是失败时等得更久 |
| 完全不想被拦 | 关掉这个开关 |

### 6.3 「代理地址」和主程序是隔离的（重要）

**先说结论**：插件里填的代理**只用于本插件自己的 Pixiv 查询**。
无论你把代理填成什么（包括填错、填一个不存在的地址），
QQ Agent 主程序调用模型 API 都**不受任何影响**。

**为什么专门写这一节**：早期版本犯过一个严重错误 —— 插件用了**进程级**的方式设置代理：

```js
undici.setGlobalDispatcher(new ProxyAgent(proxy))   // ← 改的是整个进程
process.env.HTTPS_PROXY = proxy                     // ← 也是整个进程
```

等于把宿主 QQ Agent 的**所有**出网请求（包括主程序去调模型 API）都改道到了这个代理上。
后果是：用户填了一个连不上的代理地址之后，整个机器人直接不可用，报

```
qq agent模型请求失败：connect ECONNREFUSED 216.236.43.142:443
```

而且因为改的是**全局状态**，就算把插件里的代理地址删掉，进程不重启就一直坏着 ——
一个"查图插件"把整个机器人搞挂，这是不可接受的。

**现在的做法**（已实测，并有回归测试钉住）：

| 做法 | 效果 |
| --- | --- |
| 代理以 `dispatcher` 参数**逐请求**传给 undici 的 fetch | 只影响这一条 Pixiv 请求 |
| **不写**任何 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量 | 主程序完全感知不到 |
| **不调用** `setGlobalDispatcher` | 主程序的网络配置原封不动 |
| 没填代理时连 `undici` 都不 import | 零副作用 |
| 代理地址无效时 | 只让**这次 Pixiv 查询**报错并说明，不计入断路器、不封插件 |

**怎么自己验证**（插件里带了脚本，会用**真实的 undici**、在填着死代理的情况下实测）：

```powershell
$env:ELECTRON_RUN_AS_NODE = '1'
Set-Location 'D:\QQ-Agent-爆改版0.4'
& '.\node_modules\electron\dist\electron.exe' '.\skills\pixiv-lookup\verify-proxy-isolation.mjs'
Remove-Item Env:ELECTRON_RUN_AS_NODE
```

期望输出（7 项通过）：

```
  ✅ 插件确实尝试走了代理并失败（说明代理参数真的生效了）
  ✅ undici 全局 dispatcher 没被替换
  ✅ process.env.HTTPS_PROXY 没被改写
  ✅ process.env.HTTP_PROXY 没被改写
    → HTTP 401                      ← 主程序侧真的连上了模型 API 域名
  ✅ 主程序侧请求**没有**被插件代理劫持（不是 ECONNREFUSED 216.236.43.142）
  ✅ 清空代理后插件仍能正常发起请求（走直连）
  ✅ 清空代理后全局状态依旧没变
=== 结论：7 项通过，0 项失败 ===
```

**如果你已经中过这个招**（主程序报 ECONNREFUSED）：

1. **升级到这个版本的插件**（本包已修好）
2. 清掉「代理地址」这个设置（或填成正确的本地代理）
3. **重启一次 QQ Agent** —— 旧版本是全局改的，只有重启才能把进程里的残留清掉

| 机器人回了一句「连不上」就不查了 | 同样是断路器：它按插件的指令停止重试并如实说明 | 同上。这是**期望行为** —— 好过耗尽调用预算后一条都不回 |

## 九、常见问题 FAQ

**Q1：为什么默认是关的？**
A：刚装完还没配代理时，一开就会是一堆超时。先配代理再开，体验最好。

**Q2：一定要填 Cookie 吗？**
A：不一定。不填能搜普通内容。**填了**才能查 R-18 类内容、拿到更完整的结果。普通聊天群通常不用填。

**Q3：为什么中文关键词搜不到东西？**
A：Pixiv 的标签以**日文和英文**为主，中文命中率本来就低。这是站点的数据结构问题，不是插件坏了。
让机器人换个日文/英文说法再试一次即可。

**Q4：机器人报的链接点不开图？**
A：`i.pximg.net` 有防盗链，需要带 `Referer: https://www.pixiv.net/` 才能下载。
**作品页链接**（`https://www.pixiv.net/artworks/<id>`）是能正常点开的。
想让它**直接把图发到群里**，见下面 Q4-b。

**Q4-b：怎么让它把图直接发出来，而不是只给链接？**
A：三步：
1. 插件设置里「**本地图片桥**」保持打开（默认就是开的）；
2. 宿主里打开「**设置 → 安全 → 允许下载内网/本机图片地址**」（安装教程第 4 步）；
3. 重启一次 QQ Agent。

之后群里说一句「去P站找张 XX 的图发我」，它就会调用 `send_image` 把图发出来。
原理与安全说明见 **4.4 节**；一条命令验收见 **验证 4**。

**Q4-c：开「允许下载内网/本机图片地址」安全吗？会不会被拿去看我内网的东西？**
A：这个开关只放宽**图片下载**这一条通道（不改网页抓取那条），含义是"本机上的图源我信任"。
插件的图片桥只监听 `127.0.0.1`（外网/局域网都连不上）、只服务本进程刚随机生成的短 id、
只允许 `*.pximg.net` 域名，所以它本身不可能变成"任意地址代理"。
残留的理论风险是：模型被诱导去取某个内网**图片**地址并转发到群里（非图片内容会被魔数校验拒掉）。
个人自用机器人 + 只有管理员能改设置，通常可以接受；不接受就别开发图（把「本地图片桥」也关掉，
退回"只给链接"）。详见 4.4 节。

**Q4-d：为什么发出去的图是 1200 长边，而不是原图？**
A：发图默认走 **master1200**（长边 1200）：它清晰度和体积最平衡，宿主默认「单张图片上限 5MB」
几乎总能过，预览（视觉接口）也吃得下。要原图的话，插件也会给一条「原图直链」，
但原图常有 3~10MB，可能超过宿主上限而发不出去 —— 那是宿主的限制，不是插件。

**Q5：怎么让它一次少发点图？**
A：设置里把「**每次返回条数上限**」改成 3~5。

**Q6：Cookie 填错了 / 想清掉怎么办？**
A：界面上目前清不掉（上游约定：密文字段收到空值或 `******` = 不修改）。三个办法：
1. **直接停用插件**（关开关）—— 最省事
2. 打开 `D:\QQ-Agent-爆改版0.4\data\config.json`，找到 `skills` → `pixiv-lookup` → `"cookie"`，把值改成 `""`，
   保存后**重启 QQ Agent**（改配置前先退出 QQ Agent，避免被它覆盖回去）
3. 重新粘贴一条新的有效 Cookie（等于替换）

**Q7：会不会把 R-18 图发到群里？**
A：插件默认**过滤** R-18 条目（`allowR18` 关了），并且提示词里明确要求模型不要据此生成露骨内容。
但请注意：这是**内容层面的约束**，最终发什么话仍由模型决定 —— 多人群里建议保持 `allowR18` 关闭。

**Q8：听说有个「查图上限」，具体在哪？**
A：就是设置里的「**每次返回条数上限**」（默认 10，最大 50）。详见 6.1。

**Q8-b：设置里那个「多次查询失败时强制终止」是什么？默认是开的，要不要关？**
A：那是**断路器**，默认开着是有原因的。Pixiv 连不上时每次查询要等 20 秒，
模型常常换个关键词再试，试三次就一分钟、还会把整轮调用预算耗光，最后群里一条回复都没有。
打开它之后：连续失败到阈值（默认 3）就停止一切查询，并明确要求模型"别再调工具了，直接说一句连不上"。
**建议保持打开**。什么时候该调：
- 网络偶尔抖 → 把「连续失败几次后终止」调到 5
- 代理常抽风 → 把「终止后冷却多少秒」调到 120~300
- 就是想让它一直重试 → 关掉这个开关（不推荐，会回到"卡死后装死"的老样子）

详见 6.2。

**Q8-c：为什么日志/界面里说"已强制停止"，是不是插件出错了？**
A：不是错误，是**保护生效**。说明它已经连续失败到阈值了。真正该处理的是网络/代理。
冷却（默认 60 秒）过后会自动放行一次试探，成功就立刻恢复正常，不用重启。
想确认当前状态，跑 `verify-in-agent.mjs --diagnose` 看「断路器:」那一行。

**Q8-d：为什么"搜到 0 条"和"作品不存在"不会触发终止？**
A：因为那是**请求本身的问题**（关键词不合适、id 打错），换个参数就能成，
不该因此把插件封掉一分钟、连带别人也查不了 —— 那就成了新的静默故障。
断路器只统计"上游不行"类失败：超时、DNS、连接被拒、403、429、5xx、风控页。

**Q9：能批量下载原图吗？**
A：插件本身不落盘、不建图库。但 1.1.0 起它会**按需把图取到内存**再交给宿主发送
（发图桥，见 4.4 节）—— 发几张就取几张，发完就丢。要**保存到本地**请自行带
`Referer: https://www.pixiv.net/` 抓取，并注意 Pixiv 的使用条款与作者授权。

**Q10：Pixiv 改版了插件还能用吗？**
A：插件用的是 Pixiv 的**非官方 Web 接口**，Pixiv 前端改版可能导致字段变化。届时更新插件的解析逻辑即可。

**Q11：机器人报「Pixiv 限流 429」，等一会儿再试又变成「已强制停止」了？**
A：429 也算"上游不行"，会被断路器计数。连着触发 3 次就会进冷却。
这是有意为之（429 说明确实该停手），但如果你的用法很密集，可以把阈值调大或冷却调长。

**Q12：点「保存设置」报「失败：Skill 不存在：settings」，怎么办？**
A：这是 QQ Agent 核心的**路由顺序 bug**（不是插件问题），**本包已经修好了**。
`src/app.js` 里 `/api/skills/:id` 这条通配路由排在 `/api/skills/settings` 前面，
于是把 `settings` 当成了一个技能 id 吃掉，返回
`404 {"ok":false,"error":"Skill 不存在：settings"}` —— 界面就显示"保存设置失败"。
已把 settings 的处理**上移到通配路由之前**，并删掉后面那份重复的。
以后再覆盖安装新版 QQ Agent 若又出现这个错，按第十一节的说明再改一次即可。

**Q13：我在插件里填了代理地址，会不会影响 QQ Agent 自己连模型？**
A：**不会**。插件的代理是**逐请求**挂上去的，只作用于那一次 Pixiv 查询；
不写任何 `HTTP_PROXY`/`HTTPS_PROXY` 环境变量，也不调用 `setGlobalDispatcher`。
没填代理时连 `undici` 都不加载。自查脚本见第 6.3 节（7 项断言，含真实访问模型 API 域名）。

**Q14：我主程序报过 `connect ECONNREFUSED 216.236.43.142:443`，是插件搞的吗？**
A：**是旧版插件的锅，已经修好了。** 旧版用 `setGlobalDispatcher` 把整个进程的出网
改道到了你在插件里填的那个代理上，于是主程序连模型 API 也被带过去了。
处理办法：升级到本版 → 清空「代理地址」→ **重启一次 QQ Agent**（旧版改的是进程全局状态，
不重启不清）。详见 6.3 节。

## 十、卸载 / 回退

**临时停用**：设置 → 扩展 → pixiv查图插件 → 关掉开关（推荐，配置会保留）

**彻底卸载**：

1. 退出 QQ Agent
2. 删掉目录 `D:\QQ-Agent-爆改版0.4\skills\pixiv-lookup\`
3. （可选）打开 `data\config.json`，删掉 `skills` 里的 `"pixiv-lookup"` 节点，
   这样 `data\config.json` 里存的 Cookie 才会一并消失
4. **建议**：把 `security.allowPrivateImageHosts` 改回 `false`
   （它是为了让插件图片桥能工作才打开的；插件删了就没必要继续放宽这一条通道）
5. 重新启动 QQ Agent

统一返回形状 `{ error, message, body }`；搜索的列表在 `body.illustManga.data`。

### 权限与依赖

- **声明权限**：无（`permissions: []`）
- **依赖**：无（`requires: []`）—— 不依赖任何其它插件
- **外部依赖**：无。不用装 node、不用 npm install、不用 Python
- **出网**：只用 Node 内置 `fetch`；仅在填了代理时才动态 `import('undici')` 来挂代理
  （宿主 `node_modules` 里本来就带 undici）
- **监听端口**：图片桥在本机 `127.0.0.1` 上开一个端口（默认 18717），
  插件被停用/重载时立即关闭；只认本进程随机生成的短 id，不做任何形式的转发代理

### 设计上刻意做的几件事

1. **`available()` 只判开关，且必须同步**
   上游在 `isActive()` 里同步调用它。如果因为「网络不通」就返回不可用，上游会把整个技能连同工具一起摘掉，
   用户只会看到「功能凭空消失、没有任何解释」。所以网络问题一律留到 `execute()` 里，
   返回**写明原因和怎么办**的中文报错。
2. **Cookie 永不回显**
   日志、报错、`diagnose()` 只输出「有没有、长度多少、含不含 PHPSESSID」。进请求头前会去掉控制字符，
   防止 HTTP 头注入。
3. **不信任模型参数**
   条数、页码、id 数量、id 格式全部在服务端二次夹紧。模型很容易传 `limit=999`。
4. **出网只有一个出口**
   `httpJson()` 统一处理超时、代理、错误分类。测试用导出的 `__setTransport()` 替换成假实现，
   因此**在没有外网的机器上也能完整验证解析逻辑**。
5. **失败分两类，只有一类会进断路器**
   `httpJson()` 的返回值带 `userError` 标记，区分「请求本身的问题」（404、作品不存在）与
   「上游现在不行」（超时/403/429/5xx/风控页）。只有后者计数 ——
   否则群里手滑打错一个作品号就可能把插件封掉一分钟，那是新的静默故障。
6. **断路器是进程级状态（故意如此）**
   `breaker` 是模块级变量，跨工具、跨轮次共享 —— 不然"连续失败"根本统计不出来。
   代价是它同时作用于所有会话，但这正符合真实故障场景（代理挂了是所有群一起挂）。
   因此专门导出了 `__resetBreaker()` 供测试重置。
7. **"终止"不只是报错更快，而是把指令塞回给模型**
   触发时返回的文本里明确写着「不要再调用任何 pixiv 工具」+「立刻用一句自然的中文说明情况」
   +「不要编造作品名或链接」。弱模型很容易一直重试，光靠"报错"是拦不住的 ——
   必须把"现在该做什么"也告诉它。同时系统提示词片段里也写了这条，两层一起保证。
8. **图片桥把"防盗链 / 代理 / SSRF"三件事各自解决掉**（1.1.0）
   这三件事都不在插件的能力边界内 —— 插件改不了宿主的下载通道，也不该去改
   （改了就丧失可移植性，还会把宿主的全局状态弄脏）。于是反过来做：
   **把图取到插件这边**，再给宿主一个它天然能下载的本地地址。设计约束：
   - 只监听 `127.0.0.1`（外网/局域网扫不到）
   - 直链 = 本进程内存里随机生成的短 id（144 位随机、只对应一张 pximg 图、有有效期）
   - 取图时**再校验一次**域名白名单（只认 `*.pximg.net`）→ 永远不可能变成通用代理
   - 取图带 `Referer: https://www.pixiv.net/`，Accept **不索要 webp/avif**
     （图站会按 Accept 内容协商，回了 webp 会让本机视觉接口 400，连"先看一眼"都做不了）
   - 同一张图在直链有效期内有内存缓存：模型"先 preview 再正式发"只去 Pixiv 取一次

- 工具注册面 / 工具名前缀 / 参数 schema

### 关于「查到了图但发不出去」（1.0.0 → 1.1.0 的修复）

**症状**：模型能报出作品名和链接，但一发图就是
`图片下载失败：域名解析到内网/本机地址，已阻止`；严重时**连百度图床和 QQ 表情包都发不出去**。

**根因**（三个叠在一起，缺一个都不会"全挂"）：

1. `i.pximg.net` 有防盗链，宿主的下载通道不带 `Referer` → 403；
2. `i.pximg.net` 大陆必须走代理，而宿主的下载通道不认系统代理 → 超时；
3. 宿主的 SSRF 保护把"内网/本机"地址全部拒绝，而 Clash/mihomo 的 **fake-ip**
   会让 DNS 把任何域名解析成 `198.18.0.0/15` 的虚拟 IP —— 于是**所有**图片下载都被拦，
   报错正是用户看到的那一句。

**修法**：插件加了一个只监听 `127.0.0.1` 的本地图片桥（`image-bridge.js`），
自己带 Referer、走插件代理把图取回来，再给宿主一条本地直链；
同时在工具返回里明确告诉模型"**用发图直链，别用 pximg 裸链**"。
宿主侧只需要打开一次「允许下载内网/本机图片地址」。
完整说明见 **4.4 节**，验收见 **验证 4**。

### 关于「代理把主程序搞挂」（ECONNREFUSED）

**已修复**，见第 6.3 节。一句话：旧版用 `undici.setGlobalDispatcher()` 和
`process.env.HTTPS_PROXY` 这种**进程级**方式设代理，把宿主所有出网都改道了；
现在改成**逐请求** `dispatcher`，全局状态一个字节都不动。

### 关于「保存设置失败：Skill 不存在：settings」

**已修复**。这不是插件的问题，是 QQ Agent 核心的一个**路由顺序 bug**，本包已经改掉了。

**病根**：`src/app.js` 里这两条路由的位置反了 ——

```js
const skillIdMatch = /^\/api\/skills\/([^/]+)$/.exec(pathname);   // 通配，先匹配
if (skillIdMatch && method === 'POST') { ... }                    // ← "settings" 也被它吃掉
if (pathname === '/api/skills/settings' && method === 'POST') { ... }  // 永远到不了
```

界面保存设置时 `POST /api/skills/settings`，被上面的通配路由当成
「一个叫 settings 的技能」→ 返回 `404 {"ok":false,"error":"Skill 不存在：settings"}`
→ 前端显示「保存设置失败：Skill 不存在：settings」。

**改法**：把 `/api/skills/settings` 的处理**上移到通配路由之前**，并删掉后面那份重复的。
改动前已用 `electron --check` 做语法校验；改完重启验证：

| 请求 | 改前 | 改后 |
| --- | --- | --- |
| `POST /api/skills/settings` | 404 Skill 不存在：settings | **200 ok** |
| `POST /api/skills/pixiv-lookup` | 200 | 200（不受影响） |
| `POST /api/skills/zzz-nope` | 404 | 404（不受影响） |

> 如果你以后覆盖安装了新版 QQ Agent，而"保存设置"又开始报这个错，
> 就按上面的思路再改一次（找 `src/app.js` 里那两个 `pathname === '/api/skills/settings'`）。

### 三个开发时踩过的坑（留给后来人）

1. **宿主加载器用 `?t=` 破坏模块缓存**
   `plugin-loader` 是 `import(entryUrl + '?t=' + Date.now())` 加载入口的，所以从外面
   `import('index.js')` 拿到的是**另一份模块实例**，`__setTransport` 打不到工具实际用的那份上
   （现象：假 transport 没生效，脚本真的去连了 20 秒网络）。
   → 端到端测试要自己 import + 自己 `setup()`（`breaker-e2e.mjs` 就是这么做的）；
   验证宿主加载则用 `verify-in-agent.mjs`（只查注册与状态，不注入 transport）。
2. **`.ps1` 必须纯 ASCII，且不要把带单引号的路径当参数传**
   - Windows PowerShell 5.1 按 GBK 读非 ASCII 的 `.ps1`，中文会变乱码并报「字符串缺少终止符」
   - 用户目录可能是 `C:\Users\mu'geng`，这种路径作为**命令行参数**传给 electron 会被截断成
     `C:\Users\mu`，Node 报 `Cannot find module`。
     → `selftest.ps1` 因此自己去往上两级找 QQ Agent 目录、用导入 `import.meta.url` 定位，
     而且 staging 目录只挑"路径里没有单引号"的位置。
3. **代理只能用 `dispatcher` 逐请求挂，绝不能碰全局**
   这是最贵的一次教训（把用户的整个机器人搞挂了）。写网络相关的插件时，
   凡是看到 `setGlobalDispatcher` / `process.env.*_PROXY` / `setDefaultResultOrder`
   这类**进程级** API，都要先问一句："这是不是我一个插件该动的？"
   宿主还有别的流量（模型 API、OneBot、本地小模型），我们无从知道，也无权改。
   → 用 `undici.fetch(url, { dispatcher: new ProxyAgent(p) })`；没代理就别 import undici。
   并且**必须**有一条"填个死代理，验证宿主侧还活着"的回归测试（`verify-proxy-isolation.mjs`）。

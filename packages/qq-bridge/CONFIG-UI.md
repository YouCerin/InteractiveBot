## ★★ 2.1.1 用量与成本卡片（概览页，新增需求）

界面参考形态：顶部 5 张数字卡（估算成本 / 调用次数 / 输入 token / 输出 token / 缓存命中率），
下面两张表（按天 / 按会话）。**但那份参考图里的数字口径有三处是错的**，
照着抄会显示错误的账，所以下面把口径逐条钉死。

### 先讲清楚数据是从哪来的（决定界面的可信度）

桥接**本来就收到了**精确的 token 用量。取证：

- DSH 的 `assistant/message` 事件带 `usage` 字段，形如
  `{ inputTokens, outputTokens, totalTokens, cacheReadTokens, cacheWriteTokens?, reasoningTokens? }`
- 桥接的 `TurnCollector` **已经在收**（`src/session-bridge.mjs`）
- **实测**：真实桥接会话 `qq-eff12cd760f2` 的一轮里 15 个步骤全部带 usage，
  且带路由 `deepseek-official/deepseek-flash`

所以 **token 数是"量出来的"，不是估的**。这一点和成本不同（见下）。

### ⚠️ 三个必须做对的口径（做错了账会差几十倍）

#### ① `totalTokens` **不能求和** —— 不是因为它大，而是因为它是别的东西

实测原样数据（一轮真实对话，共 15 个步骤）：

```
step  1: input= 1,210  cacheRead= 7,296  output=246  total= 8,752
step  2: input=   543  cacheRead= 8,704  output=334  total= 9,581
step  5: input=   200  cacheRead=13,184  output=304  total=13,688
step 14: input=16,632  cacheRead=17,536  output=232  total=34,400
step 15: input=   252  cacheRead=34,176  output=281  total=34,709
```

**⚠️ 一个反直觉的实测结果，别被它骗了**：这一轮里

- 把 15 个 `totalTokens` 相加 = **252,418**
- 而按正确口径（`input + cacheRead + output` 分别求和）= **252,418**

**两者几乎相等。** 所以在这一轮里，"求和 totalTokens" 恰好不会算错。

**但这不是可以偷懒的理由**，因为两者的**单位不同**：

| | `totalTokens` | `input + cacheRead + output` |
|---|---|---|
| 含义 | **这一步上下文有多大**（一个快照） | 每一步**实际消耗**了多少 |
| 例 | `8,752` 是"第 1 步时上下文有 8752 token" | `8,752` 是"第 1 步烧了 8752 token" |

它们之所以在这一轮数值巧合地接近，是因为**上下文几乎是线性增长的**（每步只加一点）。
一旦出现"上下文被裁剪（compaction）然后重新增长"，`totalTokens` 会**回落**，
两者就立刻分道扬镳 —— 求和的 totalTokens **会凭空少算**。

**正确口径**：`totalTokens` 只用来显示"**当前上下文占用**"（取**最后一步**的值），
成本与总量一律用 `input / cacheRead / output` 三项分别求和。

#### ② `inputTokens` 是**未命中缓存的**输入，不是全部输入

用实测数据验证这个恒等式，**15 个步骤全部成立**：

```
inputTokens + cacheReadTokens + cacheWriteTokens + outputTokens === totalTokens
   1,210    +     7,296       +        0          +     246      ===   8,752   ✅
  16,632    +    17,536       +        0          +     232      ===  34,400   ✅
```

所以 **`inputTokens` 是"没吃到缓存的输入"**，缓存命中的部分单独在 `cacheReadTokens`。

**这一个字段的区别，就是整个卡片有没有价值的关键**。看实测那一轮的真实成本构成：

| 项目 | token 量 | 空闲时段费用 | 占比 |
|---|---|---|---|
| 未缓存输入 | 25,049 | ¥0.0250 | **57%** |
| 缓存命中 | 223,744 | ¥0.0045 | **10%** |
| 输出 | 3,625 | ¥0.0145 | **33%** |
| 合计 | 252,418 | **¥0.0440** | 100% |

**缓存命中的 token 量是未缓存的 9 倍，却只花了 1/5 的钱**（命中价 0.02 元/M vs 未命中 1 元/M，差 50 倍）。

> **所以界面上建议把"输入"拆成两张卡（未缓存 / 缓存命中）。**
> 参考图只给一个"输入 token 2,536,109"总数，看的人**完全看不出钱花在哪** ——
> 而"缓存命中率高不高"恰恰是这套系统省不省钱的核心指标。

**正确口径**：

| 界面上的名字 | 用哪个字段 | 含义 |
|---|---|---|
| 未缓存输入 | `inputTokens` | 贵的那部分 |
| 缓存命中 | `cacheReadTokens` | 便宜的那部分（约 1/50 价） |
| 输出 | `outputTokens` | |
| **全部输入** | `inputTokens + cacheReadTokens` | 上下文规模 |

**★ `reasoningTokens` 是 `outputTokens` 的一部分，不是额外的一项。**
实测那一轮 `output=3,625` 里含 `reasoning=1,000`。
所以它**可以显示**（让人知道思考花了多少），但**绝对不能再加一遍进总量** —— 那会重复计费。

#### ③ 缓存命中率的分母是**全部输入**，不是 miss

```
命中率 = cacheReadTokens / (inputTokens + cacheReadTokens)
```

用实测那一轮验算：`223,744 / (25,049 + 223,744) = 89.9%`。

**参考图里那个 `70.5%` 用的就是 `缓存命中 / (命中 + 未命中)`** —— 这个口径是对的，
照它做即可。（下面那张 `1,788,056 / 2,536,109` 也是同一个算法。）

### ★ 成本：DSH **不提供**价格，必须由使用者自己维护

这一点务必在界面上说清楚，否则用户会以为是官方账单。

**取证**：DSH 的 `dsh-token-meter` 有"价格"相关代码，但那是**视觉 token 折算**
（把图片折算成多少 token），**不是人民币价目表**。
`dsh-llm-deepseek` 里也没有单价。**DSH 从头到尾不给钱数。**

代价是：价格必须我们维护，而它是**会变的**。所以：

> **成本只能叫"估算"，界面上必须有"估算"字样，并且要能一键看到计价依据。**

#### 价目表放在配置里，不放代码里

| 字段路径 | 类型 | 说明 |
|---|---|---|
| `usage.pricesFile` | 路径 | 价目表 JSON 的路径（相对本包根目录）。**改它不需要重启桥接** |
| `usage.costEnabled` | 开关 | 关掉则界面只显示 token，不算钱（价格没维护时建议关掉） |

价目表**故意做成独立文件**（默认 `prices.json`），原因：
价格会变、要能改、改了**不该重启机器人**。放进 `config.json` 就会触发"改配置要重启"。

`prices.json` 的形状（**结构是约定，具体数字请你按官方页面填**）：

```json
{
  "_说明": "单价单位：元 / 百万 tokens。峰谷价与时段规则见 DeepSeek 官方定价页。",
  "_来源": "https://api-docs.deepseek.com/zh-cn/quick_start/pricing/",
  "_更新日期": "2026-09-25",
  "routes": {
    "deepseek-official/deepseek-flash": {
      "cacheHitPerM":   { "offPeak": 0.02, "peak": 0.04 },
      "cacheMissPerM":  { "offPeak": 1,    "peak": 2 },
      "outputPerM":     { "offPeak": 4,    "peak": 8 }
    }
  },
  "peak": {
    "_说明": "高峰时段 = 下列窗口内。窗口外（含周末）按空闲价。",
    "timezone": "Asia/Shanghai",
    "windows": [{ "start": "09:00", "end": "12:00" }, { "start": "14:00", "end": "18:00" }],
    "days": [1, 2, 3, 4, 5],
    "holidays": []
  }
}
```

**★ 关于 `holidays`（必须如实告诉用户的一件事）**：
官方规则是"周一至周五**不含法定节假日**"。节假日**无法靠日期算出来**，
所以 `holidays` 是一张要人工维护的日期表，默认空。
空着时，节假日会被**当成高峰**计价 —— 也就是**偏保守（可能偏高）**。
界面上的计价说明里要写出这一条，不要假装精确。

**计价公式**（每一项分别按当时所属时段取价）：

```
成本 = 未缓存输入/1e6 × cacheMiss
     + 缓存命中  /1e6 × cacheHit
     + 输出      /1e6 × output
```

**⚠️ 时段要按"每一次调用发生的那一刻"判定，不能按查询那一刻判定。**
所以记账时就要把"当时是峰还是谷"算好**存在记录里**，
否则回头查 7 天的账会因为"现在几点了"而变动 —— 那就不是账，是幻觉。

**★ 拿不到价目表时怎么办**：对应的卡片显示 `—` 而不是 `¥0.00`。
`¥0.00` 会被读成"免费"，`—` 才是"不知道"。这是两件完全不同的事。

### ★★ 顶部状态条：当前时段指示灯（**新增需求**）

界面**最顶部**（与"运行状态 / 已登录 QQ"同一行的那条状态栏）显示当前计费时段：

```
当前：高峰时段      ← 高峰
当前：低谷时段      ← 低谷
时段未知            ← 拿不到价目表时
```

**样式建议**：

| 状态 | 颜色 | 为什么 |
|---|---|---|
| `当前：高峰时段` | 🟠 橙/琥珀 | 贵。让人下意识想"这事要不等会儿再说" |
| `当前：低谷时段` | 🟢 绿 | 便宜。这是**省钱窗口**，值得让人看见 |
| `时段未知` | ⚪ 灰 | 见下方第 ④ 条 |

**这个灯为什么值得做**：价格差 **2 倍**（高峰 `2元/M` vs 空闲 `1元/M` 未缓存输入）。
它同时是**给用户看的信息**和**行为引导** —— 用户看到"高峰"，就会把
"帮我读一下那个大文件""把整个仓库过一遍"这类**烧 token 的活**挪到低谷时段。
**这比成本卡片更能省钱**，因为成本卡片是事后看的，这个是事前提醒的。

#### ★ 时段由**界面**按浏览器时间算（按这个做）

**判定用浏览器自己的时钟**，不调后端。数据来源是价目表里的 `peak` 规则段：

```
取价目表：GET /api/usage/prices  →  拿 peak 这一段（windows / days / holidays / timezone）
每一分钟用浏览器时间判一次，得到 indicator
```

**照抄这个函数**（只要 `peak` 那一段，不需要别的）：

```js
/** 判断此刻属于高峰还是低谷。now 默认取浏览器当前时间。 */
function computePeriod(peak, now = new Date()) {
  const tz = peak?.timezone || 'Asia/Shanghai'

  // ★ 必须用 Intl 取"该时区的墙上时间"，不能直接读 now.getHours()
  //   直接读拿到的是【浏览器本地时区】的小时；用户若不在北京就会判错。
  //   （已实测：进程时区设成 UTC / America/New_York / Asia/Tokyo，结果都不变）
  //   另：`hour12:false` 在个别 locale 下午夜会输出 "24:00"，那会让解析出错。
  //   实测 en-CA 在 Node 24 下输出 "00"，无此问题 —— 但换 locale 时请复验。
  const f = new Intl.DateTimeFormat('en-CA', {
    timeZone: tz, hour12: false,
    year: 'numeric', month: '2-digit', day: '2-digit',
    hour: '2-digit', minute: '2-digit', weekday: 'short',
  })
  const p = {}
  for (const part of f.formatToParts(now)) p[part.type] = part.value
  const wd = { Sun: 0, Mon: 1, Tue: 2, Wed: 3, Thu: 4, Fri: 5, Sat: 6 }[p.weekday]
  const ymd = `${p.year}-${p.month}-${p.day}`

  const holidays = new Set(peak?.holidays ?? [])
  const days = peak?.days ?? [1, 2, 3, 4, 5]
  const windows = peak?.windows ?? []

  const toMin = (hm) => { const [h, m] = String(hm).split(':').map(Number); return h * 60 + m }
  const cur = toMin(`${p.hour}:${p.minute}`)

  // 判定顺序：节假日 → 周末 → 窗口内
  let period, reason
  if (holidays.has(ymd)) { period = 'offPeak'; reason = 'holiday' }
  else if (!days.includes(wd)) { period = 'offPeak'; reason = 'weekend' }
  // ★ 左闭右开：09:00 算高峰，12:00 算低谷。否则整点那一刻有两个答案。
  else if (windows.some((w) => cur >= toMin(w.start) && cur < toMin(w.end))) {
    period = 'peak'; reason = 'window'
  } else { period = 'offPeak'; reason = 'outside-window' }

  return {
    period, reason,
    isPeak: period === 'peak',
    indicator: period === 'peak' ? '当前：高峰时段' : '当前：低谷时段',
  }
}
```

**★ 六条必须做对的：**

**① 必须用 `Intl` 按 `peak.timezone` 取时间，不能直接 `now.getHours()`。**
`getHours()` 给的是**浏览器本地时区**的小时数。你的机器在北京所以现在看不出区别，
但只要有人把系统时区改成别的（或将来跑到另一台机器上），
它就会拿"当地下午 3 点"去套"北京高峰窗口"。**这是那种没人报障、但账一直错的 bug。**

**② 节假日表来自后端，不是浏览器。** `peak.holidays` 是配置的一部分，
所以必须**先拉到价目表**。拉不到就显示「时段未知」——见第 ④ 条。

**③ 窗口边界左闭右开**（见上面代码里的注释）。这条我逐点验过：

| 时刻 | 结果 |
|---|---|
| 08:59 | 低谷 |
| **09:00** | **高峰** ← 左端归高峰 |
| 11:59 | 高峰 |
| **12:00** | **低谷** ← 右端归低谷 |
| 13:00 | 低谷（午休） |
| **14:00** | **高峰** |
| 17:59 | 高峰 |
| **18:00** | **低谷** |
| 周六/周日 任意 | 低谷（`weekend`） |

**④ 拉不到价目表时显示「时段未知」，不要显示「低谷」。**
拿不到规则时我们**不知道**现在是什么时段。显示"低谷"是撒谎 ——
万一正好在高峰，用户会以为便宜而放心烧 token。
**用假的好消息换真损失，是最不划算的一种错。**

**⑤ 每分钟重算一次。** 跨过 `09:00 / 12:00 / 14:00 / 18:00` 这四个点时会变。
建议**搭在既有的状态轮询上**，不要另起一个定时器。

**⑥ `peak.holidays` 为空时，在 `indicator` 后面加一个小问号。**
节假日表默认是空的，法定节假日会被判成**高峰**（保守计价，偏高）。
用户明知自己在放假，界面却说"高峰"，会显得很蠢。悬停给一句解释：

> 节假日表未维护，节假日会按高峰计价。今天的判定可能有偏差。

#### ★ 账目上的时段仍然由桥接判定 —— 这是刻意分开的

**灯 = 浏览器时间（给人看的）；账 = 桥接判定（记在数据里的）。**

为什么记账不跟着浏览器走：**账本不应该依赖"当时有没有网页打开"**。
一个人没开界面的时候消息照样在回，那些回合也必须被正确计价。

**两边会不会打架？** 在你现在这个场景（浏览器和桥接同一台机器、同一块系统时钟）
**不会**。真要较真，两者也只是同一时刻的两种取法，正常情况一致。

**桥接检测到明显偏差时的行为**（后端实现，界面不用管）：
如果桥接自己的钟和"浏览器报的钟"差得离谱（例如超过 5 分钟），
**记一条警告日志**，但**照常用桥接自己的钟记账**。
日志是给人排查用的，不是用来改账的 —— 账改来改去就不叫账了。

> **界面顺带可以做的小事**：把 `period` 一起显示在 tooltip 里
> （`reason=window` / `weekend` / `holiday` / `outside-window`），
> 用户一看就知道"为什么现在是低谷"。

**★ 一个容易搞混的地方（界面上最好也写一句）**：
这个灯反映的是**现在**。而成本卡片里的历史数字，用的是
**每次调用发生的那一刻**的时段 —— 所以你会看到"现在是低谷，但今天的账里有一半按高峰算"。
**这是正常的，不是 bug。**

### ⚠️ 两条必须写进界面的说明

**① 重启桥接会丢历史吗？—— 不会，但原因和你想的不一样。**
用量记账**落盘在一个追加写的文件里**（不是内存），所以重启后"近 7 天"仍然完整。
这与 §2.9「对话」页签的内存镜像**完全不同**——那个重启就清空，别混为一谈。

原因有三个，都要如实说，不要掩饰：
1. 峰谷时段判定依赖人工维护的节假日表（默认空，节假日会按高峰算，偏高）
2. 价格会变，`prices.json` 里的数字可能已过期
3. 上游计费可能有它自己的取整规则

所以措辞用「**估算**」，不要用「账单」「消费」。**用户拿它对账会失望，拿它看趋势才有用。**

| 字段路径 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `trigger.private` | 开关 | 开 | 私聊是否响应 |
| `trigger.mention` | 开关 | 开 | 群里被 @ 是否响应 |
| `trigger.keyword` | 开关 | 开 | 群里命中关键词是否响应 |

**★★ 唤醒规则（界面上要把这张表写清楚）**：

| 场景 | 回不回 | 说明 |
|---|---|---|
| 私聊 | **回**（除非 `trigger.private` 关掉） | 一对一找它说话，**不看关键词** |
| 群里 **被 @** | **回** | `trigger.mention` 关掉则不回 |
| 群里 **命中关键词** | **回** | `trigger.keyword` 关掉则不回 |
| 群里 其余任何情况 | **不回** | **零成本**：连关键词都不扫，不建会话、不调模型 |
| 群聊总开关关着 | **一律不回** | **即使 @ 了也不回**（fail-closed） |

> **群里只有这两种唤醒方式，没有"自动搭话""随机插嘴"。** 这是刻意的：
> 群里最容易被当成机器人、也最容易惹人烦。

**★ `trigger.groupEnabled` 的界面提示：**

> 群聊回复涉及**账号风控风险**。上一个 QQ 号就是因此被处置的。
> 开启前请确认你了解这一点。
>
> 开启后机器人**只会在被 @ 或说到关键词时**回答，不会自己冒出来说话。

**★ 关掉总开关时，界面要把另外三个开关一起变灰** —— 否则会让人以为
"@ 开关还开着，那 @ 它应该会回"。实际上总开关一关，**@ 也不回**。

**`trigger.keywords` 的界面提示**：包含匹配，**且只在群聊里生效**（私聊不受它影响）。
**不要**填单字或群聊高频词（如"我""哈哈"），那等于让机器人对每句话都响应 ——
在群里这既是烧钱也是打扰。

**UI 增强建议**：关键词输入框对以下情况实时标黄警告——
长度为 1 的词、以及"哈哈""草""笑死""在吗"这类高频词。
另外建议显示一句**成本提示**：每个命中关键词的群消息都会产生一次模型调用。

### ★ 长任务"先应一声"（`humanize.interim`）

**解决什么问题**：实测有一轮花了 **40.8 秒、20 次工具调用**（联网搜索）。
这期间桥接一声不响 —— 使用者会以为机器人坏了，甚至重复发消息。

**机制**：回合开始后计时，超过 `afterMs`（默认 8 秒）还没结束，就先发一条短消息；
回合结束时照常发最终回复。

**⚠️ 三组话术必须分成三个输入框，不要合并**：

| 键 | 什么时候用 | 为什么不能混 |
|---|---|---|
| `messages.web` | 已经调了联网工具 | 只有这时说"我搜一下"才是真话 |
| `messages.working` | 调了其他工具（读文件、跑命令） | 这时说"搜索"是**在骗使用者** |
| `messages.thinking` | 什么都没调（纯思考） | 这时既没搜也没跑 |

**UI 说明文字建议直接写**：

> **不要写死具体动作**（比如三个数组都填"我在搜"）。
> 机器人只在真的联网时才说"搜"，这样使用者才信它。

**话术是轮换的**（不是随机），所以不会连着两次说同一句。建议每组填 2~3 句。

### ★ 连发多条消息时的行为（**没有配置项**，但界面必须正确反映）

使用者在等待期间又发了一条消息时，桥接这样处理：

| 情况 | 桥接行为 | 界面上会看到 |
|---|---|---|
| 新消息与**正在处理的那条**相同 | 直接忽略 | 用户那条消息出现，但**没有对应回复**（正在跑的那条会给答案） |
| 新消息与**刚回复过的那条**相同 | 直接忽略 | 同上 |
| 新消息是**新内容** | 旧回合"作废"：不再等它、也不发它的回复；转去处理新消息 | 旧回合的"先应一声"可能已经出现在消息流里，随后是**新消息的回复**，中间**没有**旧问题的答案 |

**⚠️ 界面必须注意两点：**

1. **不要因为"某条用户消息没有回复"就显示异常标记。** 那是刻意的去重行为，不是故障。
   如果你要提示，用中性措辞，例如"（重复内容，已跳过）"。

2. **`notice` 与 `bot` 的区分在这里更重要。** 旧回合可能已经发过一条"先应一声"，
   然后它的正式回复永远不来了 —— 如果 `notice` 看起来像正式回复，
   使用者会一直等一个不会来的答案。

> **关于"取消"的一个诚实说明。**
> DSH 的 SDK 只暴露 `initialize` / `session/prompt` / `shutdown`，**没有 cancel/abort**；
> 内部投递用的是 `agent.followup()`（追加队列，不打断当前回合）。
> 所以**正在执行的那一轮无法中止，它会把 token 烧完** —— 我们能做的是
> "不再等它、也不再为它发回复"。**界面上不要承诺"已取消"这类措辞**，
> 那是不准确的。

#### ★★ 先讲清楚记忆系统是怎么工作的（界面文案必须和这个一致）

> **⚠️ 这一节已按"桥接托管记忆"改写（此前是"模型自己读写文件"）。**
> 改的原因是一次实测事故：模型把普通群友写进了记忆并标成"管理员" ——
> 根因是**写入权在模型手里、判据却在桥接手里**，位置对不上。

**它仍然没有数据库、没有向量检索。** 但现在**写入权在桥接**：

```
每一轮消息进来
   → 桥接先查篡改（与快照比对，不一致就回滚）
   → 桥接读出该会话该看的记忆，**内容**直接注入提示词（不含任何文件路径）
   → 模型在回复里用标记"提议"记什么：
        <<<MEMORY fact 要记的事>>>            （群聊写本群 / 私聊写本人）
        <<<MEMORY slang 词 = 意思>>>          （只写本群）
        <<<MEMORY directive 以后遇到 X 就这样做>>>  （仅管理员私聊，跨群生效）
   → 桥接剥掉标记、按**发起人身份**与内容规则校验、落盘、留快照
   → 结果写成"回执"，在下一轮提示词里告诉模型到底记上没有
```

**所以：**

| 问题 | 答案 |
|---|---|
| 谁写记忆？ | **桥接**。模型只能提议，判据是代码（`roster` 按 `access.adminUsers` 判定 tier） |
| 怎么读取？ | 桥接每轮**直接注入**（不再让模型自己去读文件 —— 少一次工具往返，也不会漏读） |
| 存哪？ | **两层**：全局记忆 `MEMORY.md`（对**所有聊天**生效）+ 本会话专属 `memory/private-<QQ>.md` / `memory/group-<群号>.md` / 黑话 `memory/group-<群号>-slang.md`；另有管理员专属 `memory/directives.md`（行为指令）与内部目录 `memory/.snapshots/`、`memory/.receipts/` |
| 重启会丢吗？ | **不丢**。工作区是磁盘上的普通目录 |
| 每轮都注入吗？ | **是**，但内容很短（条数上限 25 条/文件），且**不含路径** —— 保住 DeepSeek 的前缀缓存（实测命中率 91%~96%） |

**★ 四档作用域（写错会串场）**

| 档位 | 落到哪 | 谁可写 | 生效范围 |
|---|---|---|---|
| `global` | `MEMORY.md` | **任何人**（全局是共享层） | **所有聊天**（私聊 + 每个群） |
| `fact` | 本会话那层 | 任何人 | 只在本会话（群聊只本群、私聊只本人） |
| `slang` | `memory/group-<群号>-slang.md` | 任何人 | 只在本群 |
| `directive` | `memory/directives.md` | **仅管理员、且仅私聊** | 跨群（改行为，所以判据最严） |

⚠️ **`global` 与 `fact` 的区别是界面必须讲清的**：global 谁都看得到，所以只放
"普遍成立、且不含任何人私事"的内容；涉及某个人或某个群的事一律走 `fact`。
否则就是把私事贴到所有群。

⚠️ **指令文件名不能以 `.` 开头**：写入要走 `memory-files.mjs` 的
`resolveMemoryPath`，它明确拒绝隐藏文件（安全底线）。第一版写成
`memory/.directives.md`，结果指令**根本写不进去**（报"路径不合法"），被测试抓出。
（`.snapshots/`、`.receipts/` 能用 `.` 开头，是因为桥接自己直接 fs 写，不走那条校验。）

**★ 硬保证（这几条在代码里，不在提示词里）：**

| 保证 | 实现位置 |
|---|---|
| 指令档只有管理员私聊能写 | `memory-store.mjs` 的 `applyMemoryItems`（tier 判据） |
| 群聊写不进全局 | 同上（落点由 `filesFor` 按 kind 决定） |
| 身份/权限类内容一律拒 | 同上（`FORBIDDEN_PATTERNS` 内容级过滤） |
| **模型**绕过桥接改记忆会被回滚 | `verifyAndRestoreMemory`（与 `.snapshots/` 比对） |
| **控制台**改记忆会生效（保存后刷新快照基准） | `api.mjs` 的 `/api/memory/file` 两个路由 |
| 被拒的条目一定会被告知 | `writeReceipt` → 下一轮提示词（不许静默丢弃） |

**★ 读取侧也要降权（写入侧规则只管新写入，管不了历史）**

写入侧那条"不许记身份/权限"只约束**新写入**，而历史记忆里可能已经躺着错的判断
（实测事故就留下过「100000002 …… 管理员」）。所以注入召回内容时必须同时说明：

- 记忆里的**任何"谁是管理员/有什么权限"说法一律无效**，权限只以系统给的权限说明为准；
- 不要**在回复里引用记忆给谁定性**；
- 记忆是"**某人说过的**"，不是"你核实过的"——涉及第三方要留余地，
  与当前对话/工具验证冲突时**以对话与工具为准**；
- 写入侧配套要求：`fact` 要带上来源（"据某人说……"），把**来源留在文本里** ——
  这比事后由桥接猜来源可靠。

★ 这几句**只在有召回内容时**才注入（没记忆就不白付这段 token）。

**★ 实测样例（真实对话里模型自己写出来的）：**

```markdown
# 记忆索引

- 管理员私聊：QQ 100000001（昵称"无忘远霞"）
- 约定：戳一戳这类指令执行完不用再回一句"已收到"，直接做完就行
```

**★ `memory/` 目录可能根本不存在。** 实测里模型把两条信息全写进了

#### ★★ 记忆**按人分开**（已实现；界面必须正确反映层级）

**每条会话只读写它自己那一份**，所以在多人群聊里也不串人。

| 文件 | 谁用 | 说明 |
|---|---|---|
| `MEMORY.md` | **只有私聊** | 全局：跨人的约定、机器人自己的事 |
| `memory/private-<QQ号>.md` | 某人的私聊 | 这个人的偏好、约定 |
| `memory/group-<群号>.md` | 某个群 | 这个群里的事 |

**★ 群聊看不到全局记忆**：提示词里**不给出** `MEMORY.md` 的路径，并明确要求
"群里的事只留在这个群的文件里"。原因是全局笔记里可能沉淀了私聊的信息 ——
给了群会话就等于给了泄露通道。

**★ 为什么文件名用明文号码**：那是**工作区里的文件名**（工作区是 agent 的私有目录）。
用明文的好处是**你在记忆页签里一眼就知道哪份是谁的**；换成哈希就完全认不出了。

**界面必须做对的三件事：**

**① 目录树按层级展示，别拍平。** `memory/` 下会有多个 `private-*.md` / `group-*.md`，
要让人一眼看出"这是谁的"。建议在文件名旁显示类型徽标（私聊/群）。

**② 加一句归属说明**（放在记忆页签顶部）：

> 记忆**按会话分开**：每人的私聊、每个群各有自己的一份笔记。
> 「全局记忆」（`MEMORY.md`）只在私聊里可见，**群里看不到**。

**③ 不要承诺"绝对读不到"。** 这句要如实说：

> 隔离是靠**提示词告诉模型只读自己那份**实现的，不是文件系统层面的强制。
> 模型有工作区里所有文件的读写权限（那是它干活的必要条件）。
> 所以这是**防误伤**（避免它顺手混用），不是防恶意 —— 别把它当成安全边界。

**★ 建议显示"记忆占用"**：`totalBytes` 已经给了。多份记忆时，
让使用者能看出"哪份在膨胀"（对应 `memory/` 里最大的那个文件）。

#### ★★ 昵称（按人）：**机器人怎么称呼某个人**（0.2.2 新增，**界面/源码都已做**）

> **它取代的东西**：原来是**人设页**上一个全局的「它怎么称呼对方」（旧的 `callUser` 配置键，0.2.2 已移除）——
> 一个"全机器人统一怎么称呼对方"的框。那件事其实**是某个人的属性**，不是全局设置：
> 对甲叫"老板"、对乙叫"群友"，用一个框表达不了。所以改成**按人**，落在记忆页。

**归属与生效范围**：跟 **QQ 号**绑定，**私聊与群聊对同一个人都生效**（同一个号在哪都叫他这个）。

**存在哪**：`memory/contacts.md`，**一行一个人**：

```
# 联系人昵称（机器人怎么称呼他们）
- 100000001 = 老板
- 100000002 = 阿滚
```

| 为什么这么定 | 理由 |
|---|---|
| 用**记忆文件**而不是配置 | 它是"关于某人的一条事实"，和记忆同一套生命周期（可看、可编辑、可删、有快照与审计）；**并且已经纳入记忆的篡改检测**：模型绕过桥接偷改这张表会被**回滚并留日志**（"模型不许自己起名"这条边界因此是**有兜底**的，不是只写在文档里） |
| 不用 `config.json` | 配置是"机器人怎么运行"的东西；按人增删的形状塞进配置，会跟着"整份保存/回滚"一起被折腾，而且 UI 得为它单开一套读写 |
| 不做成"记忆条目" | 记忆条目是模型可提议、可 supersede 的自然语言；昵称要**结构化 + 只由人编辑**，混进条目里就会被模型改写 |

**接口（★ 0.2.2 已实现，界面直接用；不要自己在界面上拼那个文件格式）**：

| 方法 | 路径 | 请求体 | 返回 |

| POST | `/api/contacts` | `{qq, nickname}` | 增改；★ **`nickname` 空串 = 删除这个号码**。返回新的整表 + `saved:true`、`restartRequired:false`（**下一轮就生效**） |

  两边各写一套的后果是"界面存进去了、注入时读不出来"（静默失效）。

**注入规则（这一条是行为，写清楚）**：

* 每轮只注入**当前说话人**那一条（群里也是只注发言人，**不列全群**——那是隐私面）；
* 形式（放在记忆段附近，一行）：

  > 〔称呼〕他希望你叫他「老板」。不用每句都带这个称呼，自然的时候用一下就行。

* **改了下一轮就生效**（记忆是每轮现读文件的，不需要重启）。

**★ 四条边界（必须写进界面，也必须写进代码）**：

1. **昵称不是身份**：权限只看 `access.adminUsers` 里那个**号码**，跟昵称毫无关系 ——
   把"叫他老板"当成"他是管理员"是**权限旁路**（本项目踩过"被标注成管理员"的坑）。
2. **可以与协议端昵称不一致**：协议端给的昵称（好友昵称/群名片）是**事实**，
   这里填的是**希望的叫法**。冲突时以这里为准（是主人显式设的），但界面上要把两个都显示出来，别让人以为"改了没生效"。
3. **把关只有一处实现**（`src/contacts.mjs` 的 `cleanNickname`）：≤12 字、不能换行、不能带 `【】[]{}<>`、
   含"忽略/指令/设定"这类词的**拒绝保存**并说明原因（它最终会被拼进系统提示词）。★ 界面上**不许**自己再写一份判据 ——
   两边判据不一致的后果是"界面拦了、注入时没拦"或者反过来（静默失效）。
4. **只由人在界面里填**：**模型不许给自己起名写这一栏**（它不是记忆标记的一种）——
   否则群里随便谁都能让机器人给他安个称呼，甚至诱导它写出像指令的东西。

**界面（记忆页里的一张卡）**：

┌─ 昵称（它怎么称呼某个人）─────────────────────────────────┐

#### ★★ 记忆写入统计与「零写入告警」（0.2.1 新增；**界面待做**）

#### ★★ 隐私拦截（0.2.1 新增；**界面待做**）

> **实现状态**：双侧硬闸与 CLI 扫描**已实现**；**界面卡片尚未接**（本文件先写清要求）。

隐私是**双侧硬闸**（写入侧拒绝落盘 + 输出侧拒绝发送），七类：身份证 / 手机号 /

|---|---|

**★ 这条与"记忆写入统计"卡片并列放**：两者都是"记忆系统在不在正常工作"的观测面。

**左边一棵文件树，右边一个编辑器。**

```
记忆（工作区 workspace-qq）
├─ MEMORY.md                168 B   2 分钟前
└─ memory/                  （空 / 按需出现）
   ├─ private-100000001.md
   └─ group-700000002.md
```

| 区域 | 要求 |
|---|---|
| 文件树 | 显示**相对路径 + 大小 + 最后修改时间**。空目录要显示"（空）"，不要显示成错误 |
| 编辑器 | 多行 Markdown，**可直接编辑并保存** |
| 保存 | `Ctrl+S` 与按钮都要有 |
| 新建 | 允许新建 `.md`（模型将来可能按人名分文件，用户也可能想自己加） |
| 删除 | 允许，但**必须二次确认**（这是记忆，删了机器人就真的不记得了） |
| 「打开记忆目录」 | 一个按钮，调系统文件管理器打开工作区 |
| 字符数 | 编辑器下方实时显示（和 `persona.custom` 一样） |

**★ 三条必须做对的：**

**① 冲突检测（这一条最重要，不做会静默丢数据）。**

**模型随时可能在写这些文件** —— 你不可能知道它什么时候决定"这事值得记住"。
所以会出现：**你打开编辑器时读到的是旧内容，你保存时把模型刚写的东西覆盖掉。**

**那份记忆就此消失，而且没有任何提示。**

正确做法：读文件时**记下一个版本标识**，保存时带上它。

```
GET  /api/memory/file?path=MEMORY.md   →  返回 { content, sha256, mtime }
POST /api/memory/file { path, content, expectedSha256 }
   → 若磁盘上的 sha256 与 expectedSha256 不一致：
     返回 409，界面提示：
     「这份记忆在你编辑期间被机器人改过了。」[重新载入] [仍然覆盖]
```

`sha256` 的具体算法由后端定，界面**只管原样回传**，不要自己算。

**② 保存后不需要重启。** 记忆文件是模型运行时读的普通文件，
改完**立刻生效**（下一次它决定读笔记时就读到新的）。
**不要显示"需要重启"** —— 那是配置类改动的提示，两回事。

**③ 关掉 `memory.enabled` 时，编辑器仍然要能用。**
关掉只是不再注入那段提示词（模型不再被提示去读写），
**文件还在、还能看、还能改**。界面别把整块功能灰掉。

**★ 界面必须解释清楚的四件事：**

1. **记忆存在哪**：`<工作区>/MEMORY.md`（指令档，跨群）与 `<工作区>/memory/`
   （按人/按群的 facts 与 slang）—— 现在**由桥接按模型的提议落盘**，不再由模型直接写。
2. **换工作区 = 换记忆**（旧记忆留在旧目录里，不会跟过来）。
3. **在这个界面里改是生效的；被回滚的只有"绕过桥接的改动"**（★ 这条改过，别照旧文案写）：
   桥接每次写入都留快照（`memory/.snapshots/`），读记忆前比对，不一致就恢复成快照那一版。
   * **模型**用它手里的 `write` / `edit` 工具直接改 `memory/*.md`（绕过标记协议）
     → **会被回滚**，这是这条机制真正要防的东西。
   * **你在这个界面里保存/删除** → 保存成功后桥接会**同步刷新快照基准**，
     所以你的编辑**会留下来**。
   > ⚠️ 历史上这里曾经把界面编辑也当篡改回滚，表现是
   > 「我在界面上删了一条，过一会儿它自己又回来了」而且不报错。
   > 那是缺陷不是安全 —— 控制台是桥接给主人的界面，不是"绕过"。
   > 界面文案**不要**再写"手动改会被回滚"。
4. **改这里等于直接改机器人的长期记忆** —— 它是修正错误记忆的入口。
   另一种做法是让管理员在私聊里用自然语言纠正（"别记那个了""这条记错了"），
   桥接会落成新条目；两种方式都可以，按使用者的习惯来。

### ★★ 界面产物与源码是"同一份"要靠什么保证（构建溯源）

**先说一个必须纠正的旧说法**：界面源码留在项目里、只有 `dist` 出货 ——
但**"只有 dist 出货"不等于"dist 不进仓库"**。这两件事以前被混在一起，
后果是 `git clone` 出来的仓库没有界面、也构建不出界面。

#### 出货有两条路，而它们脱钩过一次（实测）

| 路径 | 谁在用 | 在 git 里 |
|---|---|---|
| `config-ui/dist` | 开发机桥接伺服的就是它 | ✅ 已入库 |
| `_release/<包>/config-ui/dist` | **用户拿到的** | ✅ 已入库 |

那次脱钩：发布包里源码与 UI 都比工作区旧约 5 小时，而 **1100 项测试全绿** ——
因为"`dist/index.html` 在不在"这种检查**答不了"这份 dist 是不是当前源码构建的"**。

#### 判定方式：构建溯源标记

* 构建时把**源码树内容哈希**写进 `config-ui/dist/ui-build.json`（`sourceHash`）；
* `node src/index.mjs --ui` 重算并比对；`setup.mjs --release` 也接了同一条判定。
* 哈希逻辑只有一份（`scripts/ui-build-stamp.cjs`）—— 两边各写一套必然分叉。

**三种状态必须分开显示，不要混成一句"界面不同步"**：

| 状态 | 含义 | 修法 |
|---|---|---|
| `fresh` | 与当前源码一致 | — |
| `stale` | 源码改了没重新构建 | `cd config-ui && npm run build` |
| `unstamped` | 没有标记，**无法自证来源** | **重新构建也没用**，删掉重建 |

> **给界面生成者的要求**：`GET /api/status` 的 `ui` 字段就是这份信息
> （`{status, distDir, stamp:{builtAt,sourceHash}, why, advice}`）。
> 如果状态不是 `fresh`，界面上应该**明确提示**"你看到的是旧界面"，
> 并给出 `advice` 里那句可执行的做法 —— 而不是什么都不说。
> 原因很实际：使用者拿着旧界面报 bug，排查会从完全错误的前提出发。

### ★★ 2.5.1 看图（`image`）— 让机器人真的"看见"图片

**先纠正一个曾经写在界面上的错误说法**：旧版提示词里写的是
「这条消息里含 N 张图片，**当前通道未启用看图能力**」。那句话是**错的** ——
能力一直都在，是桥接把图片地址丢了。现在的真实情况是下面这样。

#### 为什么它是通的（界面文案必须和这个一致）

| 环节 | 结论 | 取证 |
|---|---|---|
| 模型会看图吗 | **会** | `dsh-llm-deepseek` 里 `deepseek-flash`（= DeepSeek-V41-Flash）写着 `inputModalities: ["text","image"]` |
| SDK 收图片吗 | **收** | `dsh-sdk-jsonrpc-server` 的 `session/prompt` 吃 `{type:'image', data:<base64>, mimeType}` |
| 附件库在吗 | **在** | `sdk` profile = `dsh-base` + `dsh-sdk-app`，`dsh-base` 挂着 `attachment-local` |
| 有读图工具吗 | **有** | `dsh-tool-fs` 在 `ctx.inject(['attachments'])` 里注册 `read_image` |

**所以缺的从来不是"能力"，是"把图片递进去"。** 桥接现在做的是：
把 QQ 图片下载到 `<工作区>/inbox/`，再把路径（或图片本身）交给模型。

| 字段路径 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `image.enabled` | 开关 | 开 | 总开关。关掉 = 图片只显示成 `[图片]`，且**一次网络请求都不会发** |
| `image.mode` | 单选 | `on-demand` | ★ `on-demand`（只给路径，模型按需自己看） / `auto`（直接把图塞给模型） |
| `image.maxCount` | 数字 | 4 | 单条消息最多处理几张。DSH 附件库单条上限 **20**，超过会被**整批**拒绝 |
| `image.maxBytes` | 数字(字节) | 10485760 | 单张上限（10MB）。DSH 附件库单张上限 **20MB**，配更大没有意义 |
| `image.timeoutMs` | 数字(ms) | 15000 | 单张下载超时 |
| `image.maxRedirects` | 数字 | 3 | 最多跟随几次重定向。★ **每一跳都会重新校验目标地址** |
| `image.retentionHours` | 数字(小时) | 72 | ★ inbox 保留多久。**这是唯一的清理机制** |
| `image.maxTotalBytes` | 数字(字节) | 104857600 | inbox 总量上限（100MB），超过就按**最旧**的开始删 |

#### ★★ 两种模式的取舍（这是**成本**取舍，界面必须讲明白）

```
on-demand（默认）
  QQ 图片 ──下载──▶ <工作区>/inbox/<内容哈希>.png
  提示词里写： 「已存到工作区：inbox/a1b2….png。需要看内容时用 read_image 读，
                 确定用不上就别读 —— 读图是要花 token 的。」
  模型自己决定读不读。

auto
  同上落盘，并且额外把图片转成 base64 直接附在这条消息上。
  → 更快、更准（不用多一次工具往返），但**每张图都计 vision token**。
```

**为什么默认是 `on-demand` 而不是 `auto`**（这条要写进界面，否则用户会以为"默认=最好"）：

> QQ 里**大量是表情包**。`auto` 等于每个表情包都花一次 vision token，
> 而且图片会留在**会话历史**里、后面每一轮都重复计费。
> `on-demand` 给的是一个**纯文本路径**，留在历史里几乎不花钱。

**界面文案建议**（用原话，别自己发挥）：

- `auto` 选项旁注明：**更快更准，但每张图片都会计费**。
- 切到 `auto` 时弹一次确认，说明"表情包很多时成本会明显上升"。
- `retentionHours` 旁注明：**这是唯一的清理机制**。图片必须落在工作区内
  才能被 `read_image` 读到，所以清理只能由桥接负责；填 `0` = 不清理。

#### ⚠️ 安全：这是本项目**唯一**一处"外部输入能指挥进程发网络请求"

图片地址来自**消息发送者**。所以后端有一整套硬限制，**界面不要提供任何
"自定义地址/放行内网/关闭校验"的开关** —— 那不是可配置项，是安全边界：

1. 只允许 `http` / `https`（`file:`、`data:` 一律拒）
2. **逐跳**校验重定向（只在第一跳查等于没查：攻击者让公网域名 302 到内网即可）
3. 拒绝回环 / 私有 / 链路本地 / CGNAT / 组播地址，**含 IPv4 映射进 IPv6 的写法**（`::ffff:127.0.0.1`）
4. 域名**先解析**再校验，任一解析结果落在内网就拒（挡 `127.0.0.1.nip.io` 这类"看着像域名"的）
5. 大小上限 + 超时 + 重定向次数上限

**已知边界（如实告知，不要写成"已完全防住"）**：校验时解析一次、`fetch` 时又解析一次，
理论上存在 DNS rebinding 的窗口。彻底堵住要把解析结果钉住再连接（自建 agent），
代价明显更大，因此**未做**。

#### 界面元素

1. 一个分组「看图」，一个总开关 + `on-demand`/`auto` 两个大按钮（像速度三档那样）。
2. 开关下方实时显示当前配置的**效果**：
   「单条最多 4 张 · 单张 ≤10MB · inbox 保留 72 小时 / ≤100MB」。
3. **一个「现在的 inbox」小卡片**（可选，但很有用）：
   显示 `inbox/` 里的文件数、总占用、最旧一个的时间。
   ~~数据可以走记忆文件接口 `GET /api/memory/tree`~~ —— 实测不可行：
   tree 只列 `MEMORY.md` 与 `memory/`，不列 `inbox/`。所以新增了
   `GET /api/inbox`（只读，目录不存在回 `count:0`）。
4. `image.enabled = false` 时，下面的细项**仍然要能看能改**（和 §2.5 第 ③ 条同理）。

#### 图片在「对话」页签里怎么显示

会话镜像里的**用户消息**现在会带一个 `images` 数组（见 §2.9）：

```json
{
  "role": "user",
  "text": "这是我做的图[图片]",
  "at": 1790362342184,
  "images": [
    { "ok": true,  "path": "inbox/a1b2c3d4e5f60718.png", "mediaType": "image/png", "bytes": 46 },
    { "ok": false, "reason": "HTTP 403" }
  ]
}
```

界面要求：

- `ok:true` 的用 `path` 去取图显示（路径是**工作区相对路径**；
  取图通道是 `GET /api/workspace-file?path=…` —— 记忆文件接口只放行 `.md`，取不了图）。
- `ok:false` 的**不要静默丢掉** —— 显示成一个小占位块并附上 `reason`。
  取图失败是很常见的（图片过期、格式不支持），用户需要看到"这里本来有张图"。
- 图片**不要**内联进 `text`。`text` 里那个 `[图片]` 是**原始消息的忠实还原**，
  删掉它会让"用户到底发了什么"变得不可考。

### 2.6 QQ 原生功能（`mcp`）— ★ 让机器人能"动手"而不只是"说话"

> **0.2.2 起：这一页不再单独存在 —— 它变成「扩展」页里的一张插件卡**（见 §2.10）。
> 本节保留为**字段与语义的唯一真值**；界面上的位置与呈现方式以 §2.10 为准。
> 卡上必须显示「关掉会怎样」（含"技能工具会一起失效"）与「★ 需要重启」。

**解决什么问题**：默认情况下模型**只能发文字**。它不能戳一戳、发 QQ 表情、
撤回自己说错的话、查群成员、读群历史 —— 因为模型跑在 DSH 子进程里，
**看不到**桥接手上的 OneBot 连接，而 SDK 也没有"调用工具"这条通道。

**做法**：桥接把一个 **QQ 工具服务器**（MCP 协议）挂到 DSH 的 sdk profile 上，
于是这些动作会进模型的工具表，它能像调 `read`/`bash` 一样调它们。

**配置项只有两个**：

| 字段路径 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `mcp.enabled` | 开关 | 开 | 关掉 = 模型退回"只能说话" |
| `mcp.toolTimeoutMs` | 数字(ms) | 20000 | 单个 QQ 动作的超时 |

**⚠️ 三条必须在界面上说明的（尤其是第 1 条和第 3 条）：**

**① 改 `mcp.*` 之后需要重启的是"DSH 子进程"，界面无法直接控制。**
它由桥接拉起，所以**让用户重启桥接**即可（现有"重启"按钮就够）。

**② 这是"默认放行、黑名单拦截"，不是白名单。**
给了模型几乎全部 OneBot 动作，只拦会**伤害他人或账号**的那些：
踢人、禁言、改群名片/群名、退群、删好友、改机器人资料、发群公告…

> **界面提示建议**：如果做「高级」或单独一块，写清"机器人能调哪些 QQ 动作"，
> 并说明**危险动作已被拦**。**不要给每个动作做开关** —— 那会让用户以为
> 自己能精细控制，实际清单在代码里（`mcp/mcp-qq-server.mjs` 的 `BLOCKED_ACTIONS`）。

**③ 工具调用发生在"思考"阶段，界面上看不到过程。**
模型调 `qq_poke` 时不会产生可见消息。所以**消息流里可能只出现结果**
（例如对方收到一个戳），而界面上什么都没发生 —— 这是正常的，不是 bug。

**是否要在「对话」页签显示工具调用？**
接口目前**不返回**工具调用记录（只有 `user` / `bot` / `notice` 三类消息）。
如果你觉得需要，告诉我，我加一个字段 —— **但不要在 UI 层自己猜**。

**★ 本包不包含 SnowLuma —— 界面必须主动告诉用户这件事**

§3(d) 还要求公开发布衍生版须事先取得书面许可。所以随包分发是**不允许**的。

界面要做到（方案 A：手填 + 检测，不做目录选择器）：

1. 协议端页签里，`SnowlumaCard` 探测到 `det.launch.cmd` **为空**（= 一个候选位置都没找到）时，
   显示一条醒目提示：

   > **还没检测到 SnowLuma。**本包不含它 —— 它的许可证不允许随第三方安装包分发。
   > 请到 [GitHub Releases](https://github.com/SnowLuma/SnowLuma/releases) 下载 `win-x64` 版
   > （完整版自带 Node），解压到固定目录后回来点「重新检测」。
   > 也可以直接把入口文件路径填到下面「启动入口」里，例如 `…\snowluma\index.mjs`。

2. 提示里带一个**「前往下载页」**按钮（打开浏览器即离开本页，不影响桥接运行）。
3. **不做"点按钮选文件夹"**：浏览器出于安全不允许网页拿到用户所选目录的绝对路径，
   所以那个交互做不到"把绝对路径填进配置"。正确做法就是**手填 + 点「重新检测」验证**。
4. 检测结果必须显式显示**来源**（`det.launch.from`），因为"我明明装了却说是旧的/错的那份"
   是这个项目历史上最贵的一个故障（见 §5 的 401 事故）。

**★ 这个字段会覆盖自动发现（界面上必须写清楚，否则用户会照错的说明去做）**

自动发现（`src/local.mjs` 的 `findSnowluma`）的规则是：**优先 `index.mjs`，找不到才用 `launcher.bat`**。
理由很实在：`launcher.bat` 里是裸的 `node ./index.mjs`，**依赖系统 PATH 里有 Node**，而且它最后一行是
`pause`（天生会开一个控制台窗口）；用 `index.mjs` 则由**包内自带的 node** 启动
（`vendor/node/node.exe`），不需要系统装 Node，窗口也不会冒出来。

而 `snowluma.launchCmd` **一旦非空就会完全绕过上面这套**：

```js
// src/snowluma.mjs
const useAuto = !launchCmd
const cmdRaw = useAuto ? locate.cmd : launchCmd   // ← 填了就一定用你填的那个
```

**这个坑真实发生过**：本项目的 `config.json` 里 `launchCmd` 曾被填成
`…/project_InteractBot/snowluma/launcher.bat`，于是"优先 `index.mjs` + 包内 node"
这个决定**从来没有生效过** —— 实测进程命令行是 `node ./index.mjs`（系统 node），
父进程是 `cmd /c "…\snowluma\launcher.bat"`。而该字段当时的说明还写反了
（写成「留空 = 用 `launcher.bat`」），照它做正好得到相反的结果。

所以界面要求：

1. 默认留空，并在这个输入框旁写：**留空即可，除非你确定要指定别的入口**。
2. 用户填了非空值时，显示一行提示：
   「已指定入口 → **自动发现被跳过**（将不再使用包内 node）」。
3. `launch.from` 字段会把真实来源报出来（`config.snowluma.launchCmd`
   或自动发现的来源名），排查时以它为准，不要靠猜。

### ★★★ 2.7.0 SnowLuma 必须「钩住 QQ」，否则 OneBot 端口根本不会开

**这是排查「机器人不在线」时应该第一个看的东西**，而且它和桥接、和配置都没关系 ——
是 SnowLuma 自己的工作机制。

#### 机制（取证自 `snowluma\index.mjs`）

SnowLuma 不是"直接连 QQ 服务器"，而是**把原生模块注入正在运行的 QQ 客户端**
（`native\snowluma-win32-x64.node`），通过命名管道与它通信。
**只有钩上之后，它才会启动 OneBot 的 HTTP/WS 服务**：

```
[App]  SnowLuma starting
[WebUI] listening http://127.0.0.1:5099          ← 控制台先起来
[Hook]  login detected: PID=<QQ进程> UIN=<号>     ← ★ 钩上了
[Hook]  pipe connected: PID=<QQ进程>
[OneBot] session started: UIN=<号>
[OneBot.HTTP] [http-default] listening 127.0.0.1:3000/
[OneBot.WS-Server] [ws-default] listening 127.0.0.1:3001/
```

**没有 `[Hook]` 那两行 ⇒ 3000/3001 永远不会监听 ⇒ 桥接永远连不上 ⇒ 机器人不在线。**
（桥接侧的表现是 `Unexpected server response: 401` 或 `Unable to connect`。）

#### 两个必须做对的前提

| # | 前提 | 怎么判断 | 怎么修 |
|---|---|---|---|
| ① | **`hookAutoLoad` 必须为 `true`** | SnowLuma 启动时会打印 `hook auto-load enabled: every discovered QQ process will be injected`；没有这行就是关的 | 改 SnowLuma 自己的 `config/runtime.json` 的 `hookAutoLoad`（或用环境变量 `SNOWLUMA_HOOK_AUTOLOAD=1`），然后重启 SnowLuma |
| ② | **必须先起 SnowLuma，再启动 QQ** | 注入挂在**管道发现事件**（`pipeWatcher.on("process-discovered")`）上，不是定时扫进程 | 顺序反了（QQ 已在跑）时，**重启一次 QQ** 即可 |

> ⚠️ 这就是为什么"SnowLuma 明明在跑、QQ 明明登录着，机器人却不在线"：
> 两者都在，但**中间那根管道没接上**。
> 2026-09-26 实测：`hookAutoLoad` 默认是 `false`，所以**每次都得手动在控制台里注入**；
> 而一旦顺序反了（先开 QQ 后开 SnowLuma），连手动都补不回来，必须重启 QQ。

#### 界面要求

1. 协议端页签里增加一行状态：**「是否已钩住 QQ」**
   - 已钩住 = `3000` 端口在监听（或 `/api/snowluma/detect` 返回 `connected` / `up-not-logged-in`）
   - 未钩住 = 5099 在、但 3000 不在 → 文案要说清是 **"SnowLuma 在跑但没钩住 QQ"**，
     **不要**说成"SnowLuma 没在跑"（那是两回事，排查方向完全不同）
2. 未钩住时给出**可执行**的提示，按顺序：
   「① 在 SnowLuma 控制台（5099）里确认已加载；② **先起 SnowLuma 再开 QQ**；③ 顺序反了就重启一次 QQ。」
3. **不要把这两个前提做成桥接的配置项** —— `hookAutoLoad` 是 SnowLuma 自己的设置，
   两处都能改就一定会漂移（本项目已经因为 token 存在两处而踩过坑）。

**★★ 还有一个必须知道的规则：填了 `launchCmd`，工作目录就用「入口自己所在的目录」**


`launch.cwd` 的取值顺序是：`snowluma.launchCwd`（显式）→ 入口所在目录 → 发现到的安装目录。

**为什么要单独讲这一条**：它和上面那个坑合起来造成过一次真实故障 ——
机器人完全不在线、OneBot 一律 401。当时的组合是：

```
launchCmd = 项目里的 snowluma\launcher.bat     ← 路径看着完全正确
cwd       = D:\QQagent_DeepSeek\snowluma       ← 但工作目录是另一份安装
```

而 `launcher.bat` 里写的是 `node ./index.mjs`（**相对路径**）—— 相对的是 `cwd`，
所以**真正跑起来的是 D: 那份代码、用 D: 的 token**，桥接当然每次都被 401。

界面上的对应要求：

- `launch.cwd` 要显示出来，并且**和 `launch.cmd` 放在一起**看 ——
  两者不一致时（入口在 A、工作目录在 B）必须醒目提示，因为那几乎一定是配错了。
- 排查「机器人不在线」时，先看 `launch.cmd` 与 `launch.cwd` 是不是同一份安装目录。

**★ 为什么要有 `installDir`（界面上值得写一句）**：

> 本机可能装了**不止一份** SnowLuma。本项目实测就遇到过：工作区里有一份、
> 参考项目目录里还有一份，**两份的 `index.mjs` 大小都不同**。
> 如果启动入口认错了，按钮启动的就不是你正在用的那个，甚至会在同一端口上撞车。

### ★★ 2.7.4 名单与权限（三级）— 谁能让机器人干什么

**三张名单，各管一件事**（不要合成一张，否则"这个人能私聊但不能在群里用"这种
情况就没法表达）：

| 字段 | 管什么 | 空时的含义 |
|---|---|---|
| `access.adminUsers` | **管理员**：满权限，可以命令机器人做有实际修改的动作 | **谁都不能用** |
| `access.dmAllowlist` | **私聊白名单**（普通用户：只能看和聊） | **只有管理员能私聊** |
| `access.groupAllowlist` | **群白名单**（哪些群能用） | **所有群都不回** |

**★ 两张白名单是**分开**的**：群聊**不再以"用户权限"作为回复条件**，
而是由 `groupAllowlist` 决定"这个群能不能用"；
而**发言人的权限**只由 `adminUsers` 决定 —— 群友一律是"用户"。

| 场景 | 回复？ | 权限 |
|---|---|---|
| 私聊 · 管理员 | ✅ | 管理员（可修改） |
| 私聊 · 在 `dmAllowlist` 里 | ✅ | 用户（**只读**） |
| 私聊 · 都不在 | ❌（回一句"只对名单内的人开放"） | — |
| 群里 · 群在 `groupAllowlist` 里 · 发言人是管理员 | ✅ | 管理员（可修改） |
| 群里 · 群在白名单里 · 普通群友 | ✅ | 用户（**只读**） |
| 群里 · 群**不在**白名单里 | ❌（**群里不说话**，避免刷屏与暴露） | — |

#### ★★★ 「只读」的边界必须如实告诉使用者（这一条不能含糊）

界面**必须**说明这是**提示词层**的限制，不是操作系统的硬墙。原文建议：

> 普通用户**不能**命令机器人做有实际修改的操作（建/删文件、改内容、跑命令）。
> 这是靠**在提示词里明确禁止**实现的 —— 机器人**有能力**做，只是被要求不做。
> 它防的是**误伤**（随口一句就让它动了你的文件），**不是**防恶意。
> 需要真正隔离的话，得给它单独跑一个只读沙箱的实例。

**为什么不能说得更强**（技术取证，别被"看起来更安全"的说法骗了）：

- DSH 的 SDK 只暴露 `initialize` / `session/prompt` / `shutdown` 三个方法；
- 在 SDK 服务器实现里搜 `sandbox` / `permissionMode` / `approval` —— **零匹配**；
- DSH 的沙箱模式是**整个 DSH 进程一份**，不是每个会话一份。

也就是说：**桥接无法按会话切换沙箱模式**。所以硬墙做不到，只能做到"明确要求"。

#### ★★ 身份核实：QQ 群里的"群管理"**不是**"管理员"（新增，必须讲清）

桥接会**从协议端核实发言人是谁**（私聊查好友昵称，群聊查 `get_group_member_info`
拿群名片与群内角色），并把结果同步到「对话」页签（见 §2.9）。

⚠️ **核实结果只用于显示与留痕，完全不参与权限判定。** 这一点必须在界面上说清，
因为两种"管理员"极容易混：

| 说法 | 指什么 | 谁能拿到 |
|---|---|---|
| **管理员**（本项目的权限级） | `access.adminUsers` 里的人 —— **主人亲手配的** | 满权限 |
| **群主 / 群管理**（QQ 群内角色） | 任意 QQ 群里的 `owner` / `admin` | **什么都没多给**，仍是"用户（只读）" |

**为什么不能按群内角色发权限**（如实写进界面，这不是小气）：

> 如果"群管理 = 满权限"，那么**任何一个陌生人**只要自己建个群、把机器人拉进去、
> 给自己一个群管理，就拿到了机器人工作区的**写权限**（能建文件、删文件、跑命令）。
> 所以本项目的规则是：**群内角色只影响显示，不影响权限。**

界面上建议在角色徽章旁加 `title`：
*这是 QQ 群内的角色，只用于显示与留痕；能不能动手由上面的管理员名单决定。*

#### ★★ 机器人**能**回答"你是不是管理员"，**不能**回答"管理员是谁"（新增，界面文案要对齐）

这条是补一个真实反馈的：使用者问机器人"谁是你的管理员"，机器人回"我无法查询"，
听起来像坏了。根因是**名单从来没有进过模型的上下文**，它说的是实话但没有用。

现在提示词里给了它一段**自解释的权限判据**，所以它的行为是：

| 对方问 | 它会 |
|---|---|
| "你是不是管理员 / 我有没有权限 / 谁能命令你" | **能答** —— 它知道**正在跟它说话的这个人**是什么级别（这是权威判据） |
| "管理员是谁 / 名单里有谁 / 某某是不是管理员" | **不能答**，会如实说"我只能确认正在跟我说话的人" |
| "那个群主是不是管理员" | 会说**群内角色与管理名单无关**（这正是 §2.7.4 那张表的意思） |

⚠️ **给界面生成者的要求**：不要在任何地方暗示"机器人知道管理员名单"。
它只知道**当前会话对象**的级别 —— 这是刻意的：**主人的 QQ 号与昵称不会泄露给群里任何人**。

#### ★ 非管理员会话里，机器人**不许复述记忆内容**（新增）

普通用户那一段权限说明里现在有一条硬规矩：**不要把记忆里的内容说出来**
（不复述、不总结、不提"我记着…"、不提"我有一份记录"；被追问就用"记不太清"带过）。

同样要如实说：这是**提示词层**的约束，不是硬墙 —— 记忆仍会注入到上下文里，
只是被明确要求不要说出去。想做硬墙就得在非管理员会话里**不注入**记忆，
代价是"机器人显得不记得你"，当前没有采用。

#### ★ 界面上的两条硬要求

**① 名单要能**从真实好友/群列表里选**，不能只让人手打号码。**

> 号码打错是这类配置最常见的错误，而且**症状是静默的**：那个人就是不回，
> 你也不知道是自己打错了还是别的原因。

所以接口给了 `GET /api/roster`，返回真实的好友与群列表，
并把"配置里的号码在不在真实名单里"标出来：

```
GET /api/roster            → 走缓存（好友/群不会秒变，而每次都要连协议端）
GET /api/roster?refresh=1  → 强制重拉
```

```json
{
  "friends": [{ "userId": "100000001", "nickname": "无忘远霞" }],
  "groups": [{ "groupId": "700000002", "name": "某个群" }],
  "unknownAdmins": [],
  "unknownDmUsers": ["1234567"],
  "unknownGroups": [],
  "friendsKnown": true,
  "groupsKnown": true,
  "cached": false,
  "warnings": []
}
```

| 字段 | 界面该做什么 |
|---|---|
| `unknownAdmins` / `unknownDmUsers` / `unknownGroups` | ★ **非空时醒目提示**：那些号码在好友/群列表里**找不到**，多半是打错了 |
| `friendsKnown` / `groupsKnown` | 为 `false` 时**不要**显示"找不到号码" —— 名单压根没拉到 |
| `warnings` | ★ **非空时显示出来**（例如"拉好友列表失败：…"）。不要吞掉 |
| `cached` | `true` 表示这次用的是缓存；界面可给一个「刷新」按钮走 `?refresh=1` |

**★ 一个必须做对的地方**：协议端连不上时，这个接口**仍返回 200**，
但 `friends` / `groups` 为空且 `warnings` 里说明原因。

> **不要**把"列表为空"直接显示成"你没有好友" —— 那会让使用者以为
> 自己的账号有问题，而实际只是 SnowLuma 没在跑。
> `friendsKnown: false` 就是给这一刻用的。

**② 三张名单的语义差别要在界面上写清**：空的时候行为**都不一样**
（谁都不能用 / 只有管理员能私聊 / 所有群都不回）。
不写清的话，使用者会以为"空着就是没限制"。

> 所以这里显式指明"用哪一份"。

**★ 两个 token 的界面提示（必须写，否则用户必踩）：**

> SnowLuma 的 HTTP 与 WebSocket 用的是**两个不同的 accessToken**。
> 这与 NapCat 的常见做法不同。填错的表现是"连上了但一直 401"。

**★ `adminUsers` 为空的提示（必须醒目，因为这是最常见的"为什么不回我"）：**

> 白名单为空 = **没有人可以使用这个机器人**（这是刻意的安全设计）。
> 请在这里填入你自己的 QQ 号（**不是机器人自己的号**）。

### ★★ 2.7.1 SnowLuma 进程卡（本页签的主角，请做成一张独立卡片）

这个页签顶部放一张 **SnowLuma 状态卡**。它解决的问题是：

> 每天早上要开三样东西：QQ、SnowLuma、桥接。
> 但界面只能告诉你"连不上"，**不告诉你是哪一环断了**，更没法帮你把 SnowLuma 拉起来。

卡片要同时给出**三件事**：SnowLuma 活没活 → QQ 登没登 → 桥接连没连上。

#### 界面元素

| 元素 | 内容 |
|---|---|
| 状态灯 | 🟢 运行中 / 🟡 在线但没登录 / 🔴 没在线 / ⚪ 桥接自己没在跑 |
| 一行说明 | 为什么是这个状态（见下方对照表，**必须照抄文案**） |
| `httpUrl` / `wsUrl` | 显示当前要连的地址（从配置读，不要自己拼） |
| **拉起 SnowLuma** 按钮 | 仅在 `snowluma.launchCmd` 有值且状态非🟢时启用 |
| 「刷新」按钮 | 重新调一次探测接口 |

#### 状态对照表（`GET /api/snowluma/detect` → `status`）

| `status` | 灯 | 界面文案 |
|---|---|---|
| `not-configured` | ⚪ | SnowLuma 没配启动入口。可以在下面填 `snowluma.launchCmd`，或自己去手动开它。 |
| `bridge-offline` | ⚪ | 机器人本体没在运行，探测不了。（这种情况界面本来也打不开，属于兜底） |
| `offline` | 🔴 | **SnowLuma 没在运行。** 请点「拉起 SnowLuma」，或手动开它。 |
| `up-not-logged-in` | 🟡 | **SnowLuma 在跑，但 QQ 还没登录。** 去看看它的窗口，可能要扫码。 |
| `auth-failed` | 🟡 | **SnowLuma 在跑，但不认我们的 token。** 检查上面两个 token 有没有填反。 |
| `connected` | 🟢 | 一切正常，机器人在线。 |

#### ⚠️ 三条必须在界面上说明的（否则用户会误解）

**① 只有 SnowLuma 和桥接在**同一台机器**上，这个按钮才有意义。**
接口只监听 `127.0.0.1`，**没有也是不可能有**"远程启动别人电脑上的 SnowLuma"的能力。
不要在文案里暗示它能跨机器。

**② "拉起"是"替你双击一下 launcher"，不是"托管进程"。**
桥接只是把它启动起来，**之后不管它**：SnowLuma 自己崩了，桥接不会自动重启它。
反过来，**关掉桥接也不会关掉 SnowLuma**（它不是桥接的子进程）。

**③ 拉起并不等于就连上了，要给几秒钟。**
SnowLuma 从启动到能接受连接需要时间。界面的正确做法是：

- 点击后按钮变「正在启动…」并**禁用**
- 之后**轮询** `detect`（建议 1 秒一次，最长 60 秒）
- 看到 `status` 变成 `connected` → 显示"已连上"
- 60 秒还是 `offline` → 提示"启动后一直没上线，可能是路径填错了（要填 `launcher.bat` 或 `index.mjs`，不是文件夹）"

### ★★ 2.7.2 「当连接断开时」（**没有配置项**，但界面必须正确反映）

这一条和上面的卡片是一体的，但它是**最容易被界面做错的地方**：

**桥接会自己无限重连，指数退避，最长等 30 秒。** 所以：

> **绝对不要**在界面上做一个"重新连接"按钮。**没有这个必要**，
> 而且会误导用户以为"不点就不重连"。

正确的界面表现是：

| 情况 | 界面该显示 |
|---|---|
| 刚断开 | 「连接断开，正在自动重连…」 |
| 断开超过 30 秒 | 「仍未连上。请确认 SnowLuma 在运行」（把用户引到上面的卡片） |
| 恢复了 | 自动变回 🟢，**不需要用户做任何操作** |

**一个必须做对的细节**：桥接重连成功后**不会重新登录**。
`login`（昵称/QQ 号）是**连接成功那一刻**问一次 `get_login_info` 拿到的，之后缓存在内存里。
所以界面**不能**用 `login === null` 来判断"没登录"——那个值只在**从没成功连过**时才是 `null`。
判断在线与否**只看 `connected`**。

### ★★ 2.7.3 SnowLuma 终端面板（**新增需求：输出显示在 UI 里，不在 CLI 里**）

**要解决的问题**：SnowLuma 是个控制台程序，以前只能靠一个**弹出来的黑窗口**看它的输出。
现在改成**在界面里看**，不用再留着那个窗口。

#### 界面形态

一个**像终端的滚动面板**（等宽字体、深色底、可滚动）。建议放在「协议端」页签的
SnowLuma 进程卡下面，或者单独一个折叠区。

| 元素 | 说明 |
|---|---|
| 日志行 | 每行显示 `时间 + 级别 + 内容`。**用等宽字体**，否则列对不齐 |
| 级别配色 | `ERROR`/`WARN` 红/黄，`OK` 绿，`DEBUG` 灰（默认也是灰的，不抢眼） |
| 「只看重要」开关 | 勾上则隐藏 `DEBUG`（对应接口的 `includeDebug=0`）。默认**勾上** |
| 「自动滚动」开关 | 打开时新日志到达自动滚到底；**用户手动往上滚时自动关掉**（否则没法看历史） |
| 「清屏」按钮 | 只清界面上的显示，**不删日志文件**（这一条要跟用户说清） |
| 「打开日志文件」 | 可选：给一个链接/按钮指向日志文件所在的目录 |

#### ★★ 一个必须讲清楚的实现事实：**输出是读日志文件，不是抓 stdout**

这不是实现细节，它决定了界面上能显示什么。

实测对比（同一条消息）：

```
SnowLuma 自己的日志文件（UTF-8，正确）:
  00:25:52 OK [200000001] [Event] 私聊 [无忘远霞(100000001)]: 确认一下群聊开关打开了吗

如果由我们接管它的 stdout 再重定向（GBK 乱码）:
  00:25:52 OK [200000001] [Event] 绉佽亰 [鏃犲繕杩滈湠(100000001)]: 纭...
```

SnowLuma 写自己的日志文件用 UTF-8，而 stdout 走**终端编码**。
所以**日志文件是唯一保真的来源** —— 要给人看的内容变成乱码，等于没显示。

**顺带的好处**：日志文件已经按天轮转（`snowluma-YYYY-MM-DD.log`），
界面不必担心"日志无限增长"。

#### 数据来源：`GET /api/snowluma/log`

**建议 2 秒轮询一次。** 首次加载用 `?lines=200`，之后用**增量**：

```
首次：GET /api/snowluma/log?lines=200&includeDebug=0
      → 拿到 data.lines 与 data.offset

之后：GET /api/snowluma/log?offset=<上次的 offset>&includeDebug=0
      → 只返回新增的行
```

**★ 必须处理 `rotated`（这是最容易漏的一条）：**

> 日志是**按天轮转**的。跨天之后（或文件被截断），你手上那个 `offset`
> 就**超出文件大小**了。这时接口会返回 `rotated: true` 并且**从头给一遍内容**。
>
> **界面收到 `rotated: true` 时必须清空面板再显示**，否则会把旧日志和新日志
> 拼在一起，看起来像时间倒流了 —— 而使用者根本不会想到是"换文件了"。

**响应字段：**

```json
{
  "available": true,
  "file": "D:\\...\\snowluma\\logs\\snowluma-2026-09-26.log",
  "date": "2026-09-26",
  "dir": "D:\\...\\snowluma\\logs",
  "lines": [
    { "time": "00:25:52", "level": "OK",    "rest": "[200000001] [Event] 私聊 [...]", "text": "完整原文" },
    { "time": "00:28:56", "level": "DEBUG", "rest": "[...] get_login_info params=", "text": "完整原文" }
  ],
  "offset": 11605,
  "rotated": false,
  "truncated": false,
  "droppedDebug": 78,
  "totalBytes": 11605
}
```

| 字段 | 含义 |
|---|---|
| `lines[].time` / `level` / `rest` | 解析出来的三段。**解析不出来时为 `null`**（见下） |
| `lines[].text` | **完整原文**，永远有值。渲染时用 `text` 最省事 |
| `offset` | 下次轮询回传这个值 |
| `rotated` | ★ 文件换过了 → **清空面板** |
| `truncated` | 本次只取了尾部一块（文件很大）。`true` 时说明**上面还有更早的日志**，界面可提示"只显示最近 N 行" |
| `droppedDebug` | 因为 `includeDebug=0` 被滤掉的行数 —— 显示"已隐藏 N 行调试日志"，让人知道不是没有输出 |
| `available` | `false` 时说明还没有日志文件（SnowLuma 没跑过）。**不是错误**，别报红 |

**★ 解析不出来的行也要显示。** 接口会照原样放在 `text` 里（`time`/`level` 为 `null`）。
界面**不要**因为解析失败就丢掉它 —— 这是"给人看的终端"，任何一行都可能是线索。

**★ `available: false` 显示什么**：一句平实的话，不要像报错：

> 还没有 SnowLuma 日志 —— 它还没运行过。

### ★★ 2.7.5 桥接自身的进程面板（启动 / 停止 / 重启 + 日志）— 0.2.3

**要解决的问题**：`start.bat` 以前在**前台**跑 `node src/index.mjs`，所以双击之后会留一个黑窗口。
**关掉那个窗口机器人就下线** —— cmd 窗口是 node 的父进程、与它共享同一个 console，
关窗（或 Ctrl+C）= 终止整个 console 的进程组。**那个窗口不是必需的**，只是启动方式带来的。

**现在改成**：`start.bat` 默认**后台启动** ——
`src/index.mjs --background`：`detached + stdio:'ignore' + unref`，
**与 `/api/restart` 走同一条 `respawnBridge()` 路径**（那条路径本来就与任何终端无关），
于是启动器**发起后立刻返回、不留窗口**。要看实时输出/要 Ctrl+C 时用 `start.bat --foreground`。

因此界面这一侧要做的是：把**启停**和**输出**都放进界面，让人不再需要那个窗口。

#### A. 输出：日志面板（与 2.7.3 同型，同一条关键结论）

> ★★ **读日志文件，不读 stdout。** 这一条在桥接上比 SnowLuma 更硬：
> `--background` 起的新进程 stdio 是 `'ignore'`（**刻意的** —— 父进程退出后管道会断，
> 那时再写日志反而会把新进程弄崩）。所以 **`logs/bridge.log` 是唯一保真来源**，
> 没有 stdout 可以接管。

| 元素 | 说明 |
|---|---|
| 数据来源 | 已有的 `GET /api/logs/stream`（增量 + `offset`，与 2.7.3 同一套协议形状） |
| 形态 | 等宽字体、深色底、可滚动；「自动滚动」在用户手动上滚时自动关掉 |
| 「清屏」 | 只清界面显示，**不删日志文件**（要跟用户说清） |
| `offset` 超界 / 文件被轮转 | ★ 与 2.7.3 一样：**必须清空面板**再显示，否则新旧日志拼在一起像时间倒流 |
| 无日志时 | 平实一句"还没有桥接日志"，**不是错误、别报红**（照 2.7.3 的 `available:false`） |

> ⚠️ **这块面板不是"顺便加的"**：桥接是**无窗口**运行的（`windowsHide`），
> 所以界面上的日志面板是**唯一能看到启动期信息的地方**。
> 0.2.3 起，启动期的告警（技能依赖缺失、MCP 挂载结果、进程登记清理）
> 会**补写进日志**（`earlyLogLines` 缓冲），因为它们以前只进 console ⇒ 无人可见。

#### B. 启停：状态条上的三个动作

| 动作 | 接口 | 现状 | 语义 |
|---|---|---|---|
| **重启** | `POST /api/restart` | ✅ 已有 | 先释放端口再 detached 拉起新进程。**永远能自愈，且不需要终端** —— 这是最该鼓励使用者用的那个 |
| **停止** | `POST /api/stop` | ✅ 已有 | 停掉后**没有任何东西在监听 3410** |
| **启动** | — | ❌ **架构上做不到** | 见 C |

#### ★★ C. 必须如实告诉使用者的一条硬约束：**桥接停着的时候，界面启动不了它**

界面是**由桥接自己**（`:3410`）托管的。桥接一停，3410 就没了 ⇒
浏览器里那张页面**问不到任何人**，"启动"按钮无处可点。

这**不是没做，是没有服务可问**。三种处理方式，建议按此顺序：

1. **现状（已在做，保留）**：离线时状态条显示「**如何启动**」而不是一个点不动的死按钮，
   并给一句可照做的话（例如"双击 `启动机器人.bat` —— 现在不会留窗口了"）。
   `Home.tsx` 的 toast 也在做同一件事。**这条要保留**，它是诚实的降级。
2. **推荐补充：把"启动"交给操作系统，而不是界面。**
   计划任务（登录时启动、失败重启），或一个只负责"拉起 + 保活"的常驻监督者。
   于是"界面里能不能点启动"变得不重要 —— **机器人本来就该一直在**。
3. **要真正的"界面一键启动"**：需要引入**常驻监督者（supervisor）**进程，它
   自己不占 3410（否则与桥接抢端口）、提供最小启停接口、必要时拉起桥接。
   ⚠️ 代价是**永远多一个常驻进程**，且它和桥接之间要做端口/生命周期协调 ——
   这正是 `/api/restart` 当初踩过的坑（"先起新的再关旧的"会端口冲突，见 `respawnBridge` 的注释）。
   **建议先做第 2 条**：用更小的代价解决同一个痛点。

#### D. 界面文案要点（不写会误导）

- 「停止」必须说明**停掉之后要用什么再起来** —— `POST /api/stop` 的 `hint` 已经在说
  "再次启动请用 start.bat"，界面应把它显示出来，而不是只显示"已停止"。
- **不要**给"停止"配一个看起来能再点起来的「启动」按钮 —— 在离线页面里它点不动，
  会让使用者以为界面坏了。
- 状态条上要能区分**桥接停了**与 **SnowLuma 停了**（后者见 2.7.2）：两者症状都是"不回话"，
  但处置完全不同（前者用 `start.bat`／重启，后者要扫码登录）。

**★ 表情包（`skills.sticker`）的界面必须做到**（0.2.4）：

这个功能的失败形状**天然是静默的** —— 库里没图、标签对不上、被配额挡住时，
表现都只是"它从来不发表情"。所以界面不许只给一个开关：

1. **必须显示库的状态**：已导入多少张 / 待定区多少张 / 每个标签各有多少张。
   ★ 某个标签**一张图都没有**时，提示词里根本不会出现这个标签 —— 界面要说出来
   （否则用户会以为"我写了它不认"，而事实是"库里没这类图"）。
2. **必须能看决策流水**（`<libraryDir>/decisions.jsonl`）：最近的"发/不发 + 原因"
   列表。这是三档频率与阈值**唯一**能调的依据；没有它，用户只能靠感觉猜。
3. **"关掉会怎样"要写明**：关掉本技能**只影响表情包**；
   聊天里的 `[sticker:名字]`（QQ 内置表情，`config.send.stickers` 那张表）**照旧可用**。
4. **频率档位的三个预设要在界面上写清数值**（上表括号里那串），
   否则 `low/medium/high` 对用户就是三个没有信息的词。
5. ★ 设置保存后的提示是「已保存，立即生效（不需要重启）」—— 判定与提示词段
   都是**每轮现读**（理由见下方 §表情包）。

#### ★★ 「重新打标签」按钮（技能卡上的动作，0.2.4）

表情包技能卡上**只有一个动作按钮**：**重新打标签**（`Tag` 图标）。
它是本功能**唯一会真花钱**的操作（每张图一次模型调用），所以它的流程是硬性的：

| 阶段 | 界面必须做到 | 为什么 |
|---|---|---|
| 进卡片 | `GET /api/extensions/sticker-retag` 拉一次状态，**空闲时也要显示**"会处理 N 张（库里共 M 张，跳过人工 K 张）" | 这个数就是**预检**（零模型调用）。没有它，用户点一下就是几十次调用，而他既不知道花多少、也不知道有几张会被跳过 |
| 点击 | **二次确认**，文案必须含："将调用模型 **N 次**"＋"**人工改过的标签不会被覆盖**"＋"跑完自动写回库，下一轮对话生效（不需要重启）" | 花钱的操作不能点一下就跑 |
| 运行中 | `POST` 发起（拿 jobId）→ 每 **1.5 秒**轮询 `GET`：显示 `done/total`、百分比进度条、**当前文件名**、**最近打上的标签**、新打/重打/失败计数 | 长任务不给进度 = 用户以为卡死然后连点（后端有防重入，但体验是坏的） |
| 运行中 | 提供**停止**按钮（`POST {action:'abort'}`）：当前那张跑完就停，**已打上的照常写回** | 长任务不能没有刹车 |
| 跑完 | 结果摘要**留在卡片上**（不用 toast 一闪而过）：新打/重打/失败/跳过人工 + **失败清单**（前 20 条，可展开） | "哪几张失败了"是用户会追问的事 |
| 出错 | 后端 422 的原因**原样显示**（例如"没有可用于打标签的模型通路：……需要一把能直连的 API key"） | 否则按钮点了没反应，用户只能猜 |

**接口**（三个动作走同一个路径）：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/extensions/sticker-retag` | 状态 + 空闲时的预检数字 |
| POST | `/api/extensions/sticker-retag` | `{action:'start', force?}` 发起 / `{action:'abort'}` 停止 |
| POST | `/api/extensions/sticker-retag` | `{action:'start'}` 返回 `{jobId, total, skippedManual}`；**立刻返回**，不等任务跑完 |

> ★ **为什么不是"一个请求把活干完"**：打几十张要几分钟到十几分钟，
> 任何浏览器/代理都不会挂着等那么久。所以是"发起 → 轮询 → 可停止"。
> ★ **模型通路在后端解析**（`resolveDirectTarget`，与唤醒判定共用 `wake.judge.apiKey`
> 的解析规则）——**密钥绝不下发到界面**。
> ★ **同一时刻只允许一个任务**：按钮能被连点，两个任务并发会同时写 `library.json`
> （后写覆盖先写、丢结果）而且账单翻倍。第二次发起会被**明确拒绝**（不是静默忽略）。

**★ 人工标注台在控制台之外**（0.2.4，刻意）：

打标签有两条自动路（视觉模型 / 文件名先验），但都只是**猜测** —— 实测模型把
「一切都好」（OK 手势）打成「无语」，语义相反。所以**人工标注是必需的**，
而它的形态必须是"能快速刷图 + 一键贴标签"，不是"在配置文件里找一条哈希名改 JSON"。
它是一个**独立文件夹 + 独立进程**（`sticker-label/`，默认 `127.0.0.1:4399`）：

```bash
cd packages/qq-bridge && node sticker-label/server.mjs --open   # 或双击 启动标注.bat
```

**它刻意不做进控制台**：控制台是"机器人整体状态"的地方，而标注台要
**整屏看图 + 键盘刷**（一张接一张），且要**零构建**（改一行不用 `npm run build`）。
混在一起会两边都别扭。它有两个页签：**逐张标注**（刷图贴标签）与
**按标签看图**（左边点标签 → 右边出这标签下的**图墙**，点图放大能当场改成别的标签；
同一页还能**新建/改名/删标签**，改完**下一轮对话就生效**）。

> ⚠️ **控制台不需要、也不应该**再实现一份标注界面。两条边的区别是：
> 控制台里的「重新打标签」是**批量重跑模型**（会花钱、覆盖非人工的标签），
> 标注台是**人工逐张过**（不花钱、花人的时间、写回 `source:"manual"` 于是重打会跳过）。
> 两者共用同一份 `library.json`，**别同时干**（后写的会覆盖先写的）。
> ★ 用户想扩标签词表也在标注台里做（写 `<libraryDir>/labels.json`）——
> 运行期一律读它，所以新建的标签立刻能贴、立刻进提示词、立刻参与选图判定，不用改代码。

**★ `usage.costEnabled` 为什么默认关**（界面要解释，否则用户会以为功能坏了）：

> 价格会变，而 DSH 不提供价格。所以价目表是你要自己维护的一个文件。
> 没维护时，界面显示 `—` 而不是 `¥0.00` —— 因为 `¥0.00` 会被读成"免费"。
> 维护好后把这里打开，成本卡片才会出现。

**★ `dsh.permissionMode` 的界面必须做到：**

| 值 | 界面显示 | 行为 |
|---|---|---|
| `read-only` | 只读 | 只能看，不能改 |
| `workspace-write` | **仅工作区（推荐）** | 只能动工作区内的文件；越界自动被拒 |
| `danger-full-access` | **全权（危险）** | 能读写整个磁盘且**免审批** |

选到 `danger-full-access` 时**必须弹二次确认**，文案：

> 这会让机器人能读写你**整个磁盘**上的任何文件，而且**不再需要你确认**。
> 当前设计是"权限只限工作区"，选它等于放弃这道防线。

**★ `dsh.apiKey` 的界面说明（发布包的主路径）：**

发布包**不随包分发 DSH**，所以用户手里不一定有 `$DSH_HOME/.credentials.yaml`。
这个框就是给他填 key 的地方。三处来源的优先级：

| 顺序 | 来源 | 谁会用 |
|---|---|---|
| ① | 环境变量 `DEEPSEEK_API_KEY` | 进阶用户 / CI |
| ② | **本框（`config.json` 的 `dsh.apiKey`）** | ★ 本发布包的普通用户 |
| ③ | `$DSH_HOME/.credentials.yaml` | 已装 DSH 桌面版并在「模型」页填过的人 |

**三处用的是同一把账号级 key** —— 也就是说已装桌面版的用户**什么都填**，桥接自己会去读③；
换 key 不需要重新申请，改任意一处即可。界面上要写清这一点，否则用户会以为必须新申请一个。

界面必须做到：

- 密码框（`type="password"`），placeholder 按 `hasApiKey` 显示"已配置（留空即不修改）"/"尚未配置"。
- 旁边一个「清除已配置的 Key」按钮，**只在 `hasApiKey` 为真时出现**，点击必须二次确认。
  文案：

  > 清除后桥接会回退到环境变量与 DSH 的凭据文件。如果那两处也没有 key，
  > 机器人**能收到消息但不会有任何回复内容**（只会回一句兜底话术）。

- 提示里要带一句"留空 = 保持原样"，否则用户会以为不填就是清空。

**★ `session.instance` 的界面说明：**

> **一般保持留空。** DSH 的会话是持久化到磁盘的，而它**不允许重启后复用同一个
> 会话标识**（没有 resume 接口）。所以这个字段留空时，程序会**每次启动自动换一套
> 新标识** —— 这是必须的，否则**当天第二次重启就会报**
> `session "..." already exists`，机器人完全不工作。
>
> 填了固定值 = 每次重启都复用同一套标识，**那只会在重启后报错**。

**建议：这个字段不要在界面上暴露。** 它是排障用的，不是给用户调的。
若一定要显示，请在用户填入非空值时给出警告。

### 2.9 「对话」页签 — QQ 对话同步界面（★ 新增需求）

**目标**：一眼看清**各个聊天里正在发生什么** —— 谁在说话、机器人是否正在处理、说了什么。

> 与"会话终端"的区别：这里要的是**像 QQ 一样的聊天视图**，多个会话并排/可切换，
> 而不是配置表单。它是**只读观察窗**，不做配置。

### 布局建议

```
┌─ 左：会话列表 ──────┬─ 右：选中会话的消息流 ──────────────┐
│ ● 无忘远霞           │  [你]   帮我看看最新版 DSH 更新    │
│   正在处理…          │  [机器人] 等下，我搜一下           │ ← notice
│   12:59              │  [机器人] 看了下，最新是 0.9.2…    │ ← bot
│                     │  [你]   谢谢                       │
│ ● 某某群             │                                   │
│   空闲 12:31         │                                   │
└─────────────────────┴───────────────────────────────────┘
```

**左侧列表**：按 `updatedAt` 倒序（最近的在上）。每条显示：
会话名（见下 `name`；没有就用 `peerId`）、`status` 的可读文案、最近活动时间。

★ **标题用 `name`，号码用小字放在旁边**：名字会重、会改，**号码才是身份**。
`nameVerified !== true` 时**只显示号码**，并标一个「未核实名称」——
绝不拿别的东西顶替（那会显示成一个群里根本没人用的名字）。

**右侧消息流**：按 `at` 升序。`role` 决定气泡方向：

| `role` | 界面表现 | 说明 |
|---|---|---|
| `user` | 右侧气泡（对方发的） | QQ 用户发来的消息 |
| `bot` | 左侧气泡（机器人发的） | 机器人的**正式回复** |
| `notice` | 左侧，**弱化样式**（浅色/斜体/小字） | "先应一声"、错误提示等**非正式回复** |

**`notice` 必须视觉上与 `bot` 区分开** —— 它是"我还在弄"的临时话，
混在一起会让使用者以为机器人已经答完了。

### 状态文案（`status` 字段 → 界面显示）

| 值 | 建议显示 |
|---|---|
| `idle` | 空闲 |
| `thinking` | 正在处理…（可加一个转圈） |
| 其他/缺失 | 原样显示或留空 |

|---|---|---|
| 群聊 `name` | `get_group_list` 的 `group_name` | 空串 + `nameVerified: false` |
| 私聊 `name` | 人设的 `callerName`（主人）或 `get_friend_list` 的昵称 | 空串 + `nameVerified: false` |

**界面硬要求**：

1. 标题显示 `name`，**同时把 `peerId` 用小字显示出来** —— 名字会重、会改，
   号码才是身份。
2. `nameVerified !== true` 时**只显示号码**，并标一个「未核实名称」。
   **绝不**拿 `用户<号码>` 之类拼出来的东西顶替 —— 那会让使用者以为核实成功了。
3. 拿不到名字**不影响机器人回话**（它只是少一个显示用的名字），界面不要报错。

> 同一个"不编名字"的规矩，这里和发言人昵称（下面那节）是一致的：
> **查得到才显示，查不到就说查不到。**

#### ★★ `messages[].senderId/senderName/senderRole` + `senders` — 发言人身份（新增）

**这是"收到指令时验证对话者身份"这条需求的界面部分。**

##### 数据是怎么来的（决定界面该怎么写文案）

| 场景 | 来源 | 能拿到什么 |
|---|---|---|
| 私聊 | 事件里的 `user_id` + `get_friend_list` | QQ 号（权威）、好友昵称 |
| 群聊 | 事件里的 `user_id` + **`get_group_member_info`** | QQ 号（权威）、**群名片**、群内角色 |

所以界面上显示的名字**不是猜的**，是从协议端现查的。

##### ⚠️⚠️ 三条必须做对（做错了就是安全事故）

1. **QQ 号是身份，昵称只是注释。** 判定"这个人是谁"永远用号码。
   昵称可以重复、可以随时改，**不能**作为身份依据 —— 界面上也必须
   把号码显示出来（我们现在的做法是「昵称 + 号码」同时显示）。
2. **`senderRole` 是"群内角色"，不是"权限"。** 它**完全不参与**谁能做什么的判定。
   权限只看配置里的 `adminUsers`（见 §2.7.4）。
   **如果界面暗示"群管理 = 有权限"，那就是在骗使用者**：
   真实的判定是"他不是管理员 → 只读"，哪怕是群主也一样。
   建议在角色徽章上加 `title`：*这是 QQ 群内的角色，只用于显示与留痕；
   能不能动手由配置里的管理员名单决定*。
3. **`verified: false` 时不要显示名字，也不要显示空白。**
   显示号码 + 一个「未核实昵称」小标。**绝不能**拿事件里的
   `sender.nickname`（协议端推上来的字段，我们**刻意没用**）或
   `用户<QQ号>` 这类拼出来的字符串去顶替 —— 那会让使用者以为核实成功了。

##### 界面元素

* 群聊消息气泡上方一行小字：`昵称 · 号码 · [角色徽章]`。
* **同一个人连续发言时只在第一条上写名字**（否则每行都挂一遍，很吵）。
* 会话列表标题：私聊显示「昵称（号码）」；群聊显示群号（群没有"群昵称"这个可信字段）。
* 群聊头部显示「N 位发言人」（来自 `senders` 的键数）。
* 身份核实失败**不影响机器人回话** —— 它只是少一个名字。界面上不要报错。

#### ★ `messages[].images` — 图片（新增）

**只在 `user` 消息上出现**，而且**只有这一轮真的会回复时才会有**。

为什么是"有条件"的：图片**只在确认要回复之后**才去下载（`image.enabled`
且通过唤醒与准入校验）。这不是省事，是**防 DoS** —— 否则群里任何人连发图片
就能让机器人不停发网络请求、不停写磁盘，而"不唤醒 = 零成本"是设计前提。
所以**没被 @ 的群消息**，它的镜像条目里**不会有** `images` 字段。

| 字段 | 说明 |
|---|---|
| `ok` | 这张图取到了没有 |
| `path` | **仅 `ok:true`**。工作区相对路径（如 `inbox/a1b2….png`），与记忆文件接口同一套路径规则 |
| `mediaType` | **仅 `ok:true`**。`image/png` / `image/jpeg` / `image/webp` / `image/gif` |
| `bytes` | **仅 `ok:true`**。文件字节数 |
| `reason` | **仅 `ok:false`**。失败原因（如 `HTTP 403`、`不是支持的图片格式…`） |

界面要求：

1. `ok:true` 的按 `path` 取图显示（取图通道是 `GET /api/workspace-file?path=<工作区相对路径>`，
   只认 `inbox/` 前缀与图片扩展名；记忆文件接口只放行 `.md`，取不了图）；`ok:false` 的**显示占位块 + `reason`，不要静默丢掉** ——
   "这里本来有张图但没取到"是用户需要知道的信息。
2. **不要**把 `images` 内联进 `text`。`text` 里的 `[图片]` 是对原始消息的
   忠实还原，删掉它会让"用户到底发了什么"不可考。
3. `image.enabled = false` 时不会去下载，所以那时也不会有 `images` 字段
   —— 界面不要把它当成错误。

#### ★★ 四种角色怎么渲染（`thinking` 是新增的）

| role | 是什么 | 界面该怎么做 |
|---|---|---|
| `user` | 对方发来的 | 左侧气泡 |
| `bot` | 机器人**实际发到 QQ** 的 | 右侧气泡 |
| `notice` | 桥接自己插的话（例如「先应一声」、「连接断开」） | 居中的灰色小字，**不要做成气泡** |
| **`thinking`** | 机器人的**思考过程** | ★ 独立的**可折叠块**（像网页版的「已深度思考」） |

**★ 关于 `thinking`，四条必须做对的：**

**① 它只在这个界面里可见，QQ 那边看不到。**
`thinking` 消息**不会**被发到 QQ —— QQ 通道发出去的只有 `bot` 那部分。
所以界面上最好标一句，免得使用者以为"对方也看到了它的内心戏"。

**② 默认折叠。** 思考过程往往很长（几千字），展开会把真正的回复挤没。
建议默认收起，显示成一行「💭 已思考（N 字）」+ 点击展开。

**③ 它可能很长，界面要能滚动，且不要让它抢走视觉重心** ——
淡化处理（灰字、小一号）比正常气泡合适。

**④ 一轮**可能没有** `thinking`。** 模型不一定每次都输出思考块（例如它直接回答，
或者只调工具不说话）。**没有就不显示这一块**，不要显示一个空的折叠条。

**⑤ 它是"这一轮"的思考，不是整段对话的。** 所以同一个会话里会交替出现
`user → thinking → bot → user → thinking → bot …`。这种交替是正常的。


### ⚠️ 三条必须在界面上说明的事（否则会误导使用者）

**① 这是内存镜像，不是历史记录。**
重启桥接就清空，且每个会话只保留最近若干条。**不要把界面做成"聊天记录归档"**，
否则使用者会以为消息丢了。界面上建议放一行小字：

> 这里只显示最近的消息，且重启机器人后清空。

**② 群聊默认是关闭的。**
`trigger.groupEnabled` 为 false 时**根本不会产生群会话**。所以左侧列表里
只会看到私聊 —— 这是正常的，不是 bug。

**③ 昵称要自己取。**
接口只给 `peerId`（QQ 号/群号），**不返回昵称**。
昵称需要 UI 通过 `/api/status` 的 `login`（机器人自己）或另接 OneBot 的
好友/群列表接口来补。**如果拿不到，就直接显示号码** —— 显示号码比显示
一个编造的昵称好。

### 刷新方式

用轮询即可（建议 2~3 秒一次，与顶部状态条共用同一个请求节奏）。
接口已带 `cache-control: no-store`，不会拿到缓存。

> 后续如果要改成长连接推送，属于 UI 侧的实现选择，本文档不约束。

| 字段类别 | 生效方式 |
|---|---|
| `persona.*`、`trigger.*`、`humanize.*`、`send.*`、`memory.*`、`ui.*` | **重启桥接后生效**（当前实现最简单可靠） |
| `onebot.*`、`access.*`、`dsh.*`、`session.*` | **必须重启桥接** |
| `skills.*`、`security.*`（只在「扩展」页签改） | ★ **即时生效**（0.2.2 起的唯一例外，见 §2.10） |

**界面要求**：任何保存操作后，显示一条明确提示：

> 已保存。需要**重启机器人**才会生效。[立即重启] [稍后]

并在有未生效改动时，在顶部状态条上打一个角标。

> ★ **「扩展」页签不走这条**：它有自己的开关与保存通道（`/api/extensions/*`），
> 返回里会明确写 `restartRequired: false`，界面**不要**在那里显示"需要重启"。

> （`skills/<id>/`，例如 pixiv 查图插件），**插件（plugin）**是**桥接自带的能力块**
> （记忆 / 看图 / QQ 工具 / 人味层 / 唤醒 / 用量 / 人设 / 名单）。

#### 为什么需要这一页（它解决的不是"功能"，是"看不见"）

1. 使用者无法回答"**我这台机器人现在开了哪些能力**" —— 开关原来散在 9 个页签里；
2. 更糟的是无法回答"**关掉会发生什么**"（`mcp.enabled=false` = 模型只能用文字回复，
   这句话以前只写在代码注释里）；
3. 装了第三方技能之后，没有地方能看出"它现在是什么状态、给了模型哪些工具、要不要重启"。

| `value` | `label` | `desc`（按钮下的小字） | 徽标 |
|---|---|---|---|
| `rule` | 规则唤醒（现状） | 私聊 / 被 @ / 命中关键词 → 必答。零额外调用、零新进程。 | —— |
| `semantic` | 语义唤醒（可沉默） | 规则先唤醒，再由判定器决定说不说 —— 它可以否决（让机器人沉默）。★ 默认是**影子模式**：判定照跑、结论只写进 oplog，行为不变。 | **「实验性」** |

★★ **`experimental: true` 的「实验性」徽标必须显示**，且**不能**只写成一个 tooltip：
口径是「从外部项目借来、尚未在本项目长期验证」。使用者有权知道自己在开一个
还没被时间检验的东西 —— 尤其这一项的失败方向是**静默的**（判错成"沉默"时，
没有人会收到任何提示，只是那个人永远等不到回复）。

★★ **卡片上必须显示当前是不是影子模式**（`wake.judge.shadow`）。
理由是"点了没反应"是这个项目最忌讳的控件状态，而 `semantic` + `shadow:true`
的组合**看起来**就是点了没反应。所以选中 `semantic` 时，卡片上要出现一行：

> 当前是**影子模式**：判定照跑、结论写进操作日志（`runtime/oplog/`），**行为不变**。
> 要让它真的生效，把 `wake.judge.shadow` 改成 `false`。

★★ **0.2.3（用户要求）：「唤醒方式」从「人设」页搬进这张卡，判定通路不再给按钮**

**① 判定通路不给用户选** —— 那两个按钮（直连 / 一次性 DSH 进程）**已去掉**。
规则只有一条，界面**只显示结论、不提供切换**：

| `wake.judge.apiKey` | 实际走哪条 | 界面要显示的话 |
|---|---|---|
| **留空** | **一次性 DSH 进程**（约 3~5 秒，用主对话那套凭据） | 「留空 = 用一次性 DSH 进程，不需要额外配钥匙」 |
| **填了** | **直连**一次 `/chat/completions`（约 1 秒），**只用这把 key** | 「已配专用 key ⇒ 走直连，不会碰主对话那把」 |

★ 为什么不给按钮：两条路在唤醒流程里做的是**同一件事**（让一个模型判断"这句话是不是
说给我听的"），让使用者选一个自己无法判断好坏的东西没有意义；而"要不要单独配一把 key"
本身就是那个选择的**可观察依据**。
★★ 这条推导必须与后端**完全一致**（`bridge.mjs` 的 `#ensureWakeJudge`、
`model-config.mjs` 的 `resolveDirectTarget`、`config.mjs` 的告警）——
否则界面说的和实际跑的不是一条路，那正是本项目最忌讳的"说了做不到"。

**② `wake.judge.apiKey` 是密文字段**（与 `dsh.apiKey` 同规格）：
`GET` 只回根部的 `hasJudgeKey: true/false`，**值不回显**；密码框留空 = 不修改；
「清除」按钮提交 `null`（清空 = 从直连退回一次性 DSH 进程）。
★ 界面**不要**把它放进普通的 `cfg` 回显路径里当成明文展示。

**③ 「唤醒方式」一节（从「人设」页搬过来，标题就叫这四个字）**
内容 = 原来的「什么时候回我」整段：`trigger.groupEnabled`（群聊总开关）、
`trigger.private` / `trigger.mention` / `trigger.keyword`、`trigger.keywords`。
它**不藏在「详细设置」里**（那是每天要看的东西），直接放在卡片正文里、
二选一按钮与影子模式提示之后。

★ 为什么搬：`wake.policy = rule` 时，**这一节就是那条策略的全部内容**；
`semantic` 也只是在它之上加一层否决。放在人设页会让"它用什么判据决定回不回"被劈成两处。
★ 同时**删掉了原来那张独立的「唤醒规则」插件卡**（`id: 'trigger'`，只显示群聊总开关）：
它与本卡回答同一个问题，两张卡却各说一半。
★ 搬家时**必须原样保留**三样（都是踩出来的）：
① 群聊总开关的**风控文案 + 二次确认**；② 关掉总开关时另外三个开关**一起变灰**；
③ 关键词的**高频词告警**与**成本提示**。

★ 这三个键属于这张卡的**展开区**（不是新的卡 —— 它们只为语义判定服务，
脱离判定器没有对象；口径同 §2.2 的"不独立就放一起"）：

| 子项 | 控件 | 默认 | 界面必须说清 |
|---|---|---|---|
| `wake.judge.apiKey` | 密码框 + 「清除」（**密文**） | 空（= 走一次性 DSH 进程） | 见上面 ①② |
| `wake.judge.model` | 文本输入（**只在配了 key 时才显示**） | 空（= 用 `dsh.model`） | 留空 = 用主对话那个。★ **换成更便宜的小模型是省钱的主要手段**。改它要重启 |
| `wake.judge.baseUrl` | 文本输入（**只在配了 key 时才显示**） | `https://api.deepseek.com` | ★ 默认**没有 `/v1`**（自己加会 404）。★ **只允许 https，或回环地址的 http** —— API key 放在请求头里，明文发出去等于裸奔。改它要重启 |
| `wake.judge.shadow` | Switch | **关** | 关（默认）= 判定**真的生效**（被判「沉默」的消息不会得到回复，**且没有任何提示**）；开 = 只记账不改行为（结论写进 `runtime/oplog/`）。**这一项即时生效** |
| `wake.judge.timeoutMs` | 数字（毫秒） | 6000 | ★ **必须小于 `humanize.interim.afterMs`**（默认 8000）：判定比"先应一声"还慢的话，用户会先看到"我在想"、然后什么都没有。超时一律按**放过**处理。**改它要重启** |
| `wake.judge.maxPerHour` | 数字 | 60 | ★ 这是**唯一挡住最坏情况**的上限（每条候选消息多一次模型调用）；超了一律**放过**（退回规则唤醒）。**改它要重启** |

★★ **"即时生效"的边界必须如实划**（`hot: true` 只对 `wake.policy`、`wake.judge.shadow`
与「唤醒方式」那一节（`trigger.*`）成立，它们都是每轮现读）：`apiKey` / `model` / `baseUrl` /
`timeoutMs` / `maxPerHour` 都在判定器**首次被用到时装配一次**（预算计数器必须跨消息
累积，不能每条重建）。所以改这几个时，界面要按 `restartRequired` **另外提示** ——
不要因为卡片头上写着"即时生效"就把它们也当成即时的。

★★ **两个键都不要做成"两个独立开关"**：那是这张卡存在的唯一理由（见下一节）。

#### ★★ 开关语义（**不许含糊，这是本页签的信任基础**）

| 语义 | 界面必须显示 | 判据 |
|---|---|---|
| **即时生效** | 「即时生效」（不要显示需要重启） | 返回 `restartRequired: false` |
| **要重启才生效** | 「★ 需要重启机器人」+ **把 `why` 的原因显示出来**（例如"这段代码只在启动时读一次配置"） | 返回 `restartRequired: true` |
| **不适用**（名单/列表类） | **不渲染 Switch**，改成一个「去维护」按钮跳到对应页签 | `switchKind === 'list'`（`enabled` 为 `null`） |
| **二选一**（冲突功能） | **不渲染 Switch**，改成一排按钮；**不显示"关掉会怎样"** | `switchKind === 'choice'`（`enabled` 为 `null`，`value` + `options[]` 给出当前值与候选） |

人设是**枚举**开关（`switchKind === 'enum'`）：关 = `persona.preset` 取 `none`，
开 = 回到精简档。**打开时用的是默认档，不是"你上次选的那档"** —— 界面上照实说一句。

#### ★★ 二选一（`switchKind === 'choice'`）— 0.2.3

**它解决什么**：当**两个功能冲突**时（启用一个必然要关掉另一个）的做法。
**不要**做成两个独立开关 —— 那会出现两种无意义状态：

- 两个都开 ⇒ 两套判据同时生效、互相打架；
- 两个都关 ⇒ 功能哑掉（例如机器人不知道该不该回）。

**做法**：两个功能放**同一个插槽 + 同一个单值配置键**。于是
「**启动一个自动关掉另一个**」是这个键的**天然语义** —— 选了 B 就等于 A 不存在，
**不需要任何额外机制**（后端没有"互斥检查"这种东西，也不该有）。

| 元素 | 要求 |
|---|---|
| 控件 | **不渲染 Switch**，渲染 **N 个并列按钮**，点另一个即切换 |
| 当前值 | 明确高亮**当前生效的那一个**。注意 `enabled` 是 `null`，**不能**靠它判断 |
| 每个按钮 | `label` 作标题、`desc` 作小字。**每个选项各自一句"选它会怎样"** |
| ★「实验性」标注 | `options[].experimental === true` 的那一项**必须显示「实验性」徽标**。口径：**从外部项目借来、尚未在本项目长期验证**的那一侧 —— 使用者有权知道自己在开一个还没被时间检验的东西 |
| ★ 文案 | **不要**显示「关掉会怎样」。二选一**没有"关"**；沿用那句话会让使用者以为"两个都不选"也是一种状态 |
| 重启语义 | 照旧：`hot:false` 时显示「★ 需要重启」+ `why`（切唤醒策略通常要重启 —— 判定器与状态机在启动时装配） |

**数据来源**：`GET /api/extensions` 的插件卡片多两个字段：

```jsonc
{
  "id": "wake-policy",
  "switchKind": "choice",
  "enabled": null,                     // 二选一没有"开/关"，恒为 null
  "value": "rule",                     // 当前生效的值
  "options": [
    { "value": "rule",     "label": "规则唤醒（现状）", "desc": "私聊/@/关键词 → 必答" },
    { "value": "semantic", "label": "语义唤醒（可沉默）", "desc": "……", "experimental": true }
  ]
}
```

**交互**：点某个按钮 ⇒ 把 `enabledPath` 写成该 `value`（走既有 `patch(path, value)` 通道，
含校验与 `.bak`）。**不做二次确认** —— 它是二选一，不是破坏性动作；但切换后若 `hot:false`，
要按上表提示需要重启。

> ⚠️ **后端不实现"互斥"**：冲突是靠"同一个单值键"表达的，不是靠两条记录互相取消。
> 如果哪天有人想加"两个键 + 互斥检查"，那说明这两个功能其实**不冲突** —— 应该做成两个独立插件。


#### 状态用词表（照抄，别自创）

| 情形 | 显示 | 依据 |
|---|---|---|
| 正常且开着 | 「已启用」 | `enabled && ready` |
| 正常但关着 | 「已关闭」 | `!enabled` |
| 装了但用不了 | 「装不上」+ `errors[]` 原文 | `errors.length > 0` |
| 依赖不满足 | 「暂时用不了」+ `available.reason` 原文 | `available.ok === false` |
| 开着但工具没注册 | 「开着，但没给模型任何工具」 | `enabled && tools.length === 0` |
| ★ QQ 工具总开关关着 | 「暂时用不了」+ `reasons` 原文（技能工具也是走 MCP 挂的，关了总开关就一起失效） | `reasons` 里含 `mcp.enabled` |

#### 设置表单（由 `configSchema` 驱动）

字段类型 → 控件：`boolean`→Switch；`string`→单行输入；`number`/`integer`→数字输入（带 `min`/`max`/`step`）；
`enum`→下拉（用 `values`）。每个字段用 `label` 作文案、`description` 作说明。

★ **密文字段**（`secret: true`，例如 Pixiv Cookie）三条硬要求：

1. 渲染成密码框，**不回显**；`GET` 返回的是 `secretSet.<字段>: true/false`，不是值；
2. 框留空 = **不修改**（提交时**不要**带这个键，或带空串）；按钮文案用「已配置（留空即不修改）」；
3. 提供「清除」动作时**必须二次确认**（提交 `null`）。

保存走 `POST /api/extensions/settings`，成功提示应明确写
「已保存，**立即生效**（不需要重启）」—— 与 §3 的"需要重启"完全相反，别抄错。

#### 空状态与安装指引

技能目录为空时显示：

> 还没有装任何技能。把技能目录拷到 `skills/<名字>/`（里面要有 `skill.json`），
> 然后**重启机器人**即可出现在这里。开关随时可改、即时生效；**装/卸**需要重启。

#### ★ 0.2.2 的四处「界面逻辑」修正（**做加减法时必须一起做**）

前三条是"把语义摆在它该在的地方"，第四条是去重复。**逐条都要落到代码里**，
不要只在文案上改字。

**① 生效方式要在**卡片**上说清（本版最重要的一条）。**
`POST /api/config` 恒回 `restartRequired: true`；而 §2.10 的扩展开关**是即时生效**的
（返回 `restartRequired: false`）。所以：

* 保存提示**按接口返回值渲染**（`restartRequired` / `hint` 由后端给），**不要在前端写死**
  「需要重启机器人」这句话；
* ★ **页签标题旁不放「即时 / 需重启」徽标**（2026-09-27 主人定稿，推翻本条的初版写法）：
  页签保持干净；**有改动需要重启时，由顶部状态条的「有改动待重启生效」角标统一提示**
  （`restartRequired` 一路接到 StatusBar，重启后自动消失）。后续版本**不要**再把徽标加回页签；
* 扩展页每张卡的徽标由 `hot` / `restartRequired` 决定，**`cold` 的必须把 `why` 显示出来**
  （卡片上的徽标保留 —— 被推翻的只是**页签**上的）。

**② 未保存的改动要**看得见**。** 现在只有底部浮条体现场景；切走就不知道哪一页改过。
给 TabsTrigger 加一个小圆点（`patch()` 里知道改的是哪个前缀，数据已经有了）。

**③ 扩展页不要跟着主轮询每 2~3 秒刷新。** `/api/status` 每 2~3 秒轮询没问题，
但 `/api/extensions` 会做文件系统扫描与技能 `promptSections()` 调用 ——
它应该**进页签时拉一次 + 操作后重拉 + 一个手动刷新按钮**。

**④ 去掉重复的空态/错误文案。** 原则一句话：**一处说结论（顶部），一处说下一步（卡片）**。
`Home.tsx` 里那句"你看到的界面不是当前源码构建的"与各卡片自己的空态有重叠；
启动条件卡片与顶部状态条也在讲同一件事的两半 —— 合并到各自唯一的位置，
并且**照抄后端给的 `why`/`advice` 原文**，不要自己编。

#### 界面**不可以**做的事

- ❌ 不要自己发明默认值（默认值全部来自技能的 `skill.json`，界面只显示）；
- ❌ 不要把"需要重启才生效"显示成"已生效"（`restartRequired` 是后端如实给的）；
- ❌ 不要隐藏 `warnings`（它们正是"静默失效"的告警）；
- ❌ 不要在技能卡上再造一套"启用方式"（唯一开关是 `config.skills.<id>.enabled`）；
- ❌ 不要把 `tools[].fullName` 里的 `mcp__skills__` 前缀"美化"掉 —— 那是排障时要搜的真名。

## 4. 校验与错误提示（重要）

前端**至少**要实现这几条，否则用户会配出一个"看起来正常但不工作"的配置：

| 校验 | 触发条件 | 提示文案 |
|---|---|---|
| 管理员为空 | `access.adminUsers` 长度为 0 | ⚠️ 白名单为空，**没有人能用**这个机器人 |
| 端口填反 | `wsUrl` 与 `httpUrl` 端口相同 | ❌ 两个地址指向了同一个端口；SnowLuma 默认 3001=WS、3000=HTTP |
| 工作区危险 | 值是盘符根或用户主目录 | ❌ 这等于把整个磁盘交给机器人，请换一个专用目录 |
| 关键词风险 | 关键词长度为 1，或命中高频词表 | ⚠️ 「我」只有 1 个字，几乎等于对每句话都响应 |
| 人设提到不存在的工具 | `persona.custom` 含疑似工具名 | ⚠️ 提示词提到不存在的工具会让模型乱调工具 |
| 打字速度过慢 | 200 字预估等待 > 60 秒 | ℹ️ 当前设置下，一条长回复要等约 N 秒 |

**最省事的做法**：不要让前端自己实现这些规则。
直接调用后端接口跑一次 `--check`（它会返回 `fatal` 和 `warn` 两个数组），
把结果原样渲染成提示即可 —— **规则只有一份，不会前后端漂移**。

## 5. 后端接口（**已实现，可直接用**）

桥接启动后会同时提供一个本地配置接口，**默认 `http://127.0.0.1:3410`**。

⚠️ **只监听 127.0.0.1，不要试图改成 0.0.0.0** —— 代码里会直接拒绝启动。
原因：配置里含 SnowLuma 的 accessToken 明文，绑到局域网等于把机器人控制权公开。

**控制台界面也伺服在同一个端口上**：`config-ui/dist`（React 应用的构建产物）
存在时，打开 `http://127.0.0.1:3410/` 就是完整控制台，与接口同源、无跨域问题，
也不需要另起任何服务。`start.bat` 启动桥接后会自动打开这个地址
（用 `start.bat --no-browser` 跳过）。开发 UI 时才需要 `npm run dev`
（Vite 已配置 `/api` 代理到 3410）。

**所有响应都是 JSON，形如：**

```json
{ "ok": true,  "data": { ... } }
{ "ok": false, "error": "错误说明", "fatal": ["..."] }
```

并带 `cache-control: no-store`（UI 轮询不会被缓存）。

| 方法 | 路径 | 请求体 | 返回 |
|---|---|---|---|
| GET | `/api/status` | — | 运行状态 + 统计 + **进程登记**（`processes`：有几个桥接在跑、有没有冲突；**不含 token**） |
| GET | `/api/config` | — | 脱敏后的配置（token 与 `dsh.apiKey` 被**删除**，另给 `hasWsToken` / `hasHttpToken` / `hasApiKey` 布尔） |
| POST | `/api/config` | 配置补丁 | `{saved:true, restartRequired:true, hint}` |
| POST | `/api/check` | 可选：待预检的配置 | `{fatal:[], warn:[]}` |
| POST | `/api/doctor` | — | `{fatal, warn, rows}` 逐项体检结果 |
| POST | `/api/restart` | — | `{restarting:true, hint}` **先响应，约 0.4 秒后**旧进程退出、新进程起来 |
| POST | `/api/stop` | — | `{stopping:true, hint}` 同样先响应再退出 |

**★ `processes`（进程登记，缺陷 3）—— 界面必须显示，理由如下：**

它回答的是"**现在有几个桥接在跑**"。两个桥接同时从同一个 OneBot 收事件时，
**每个实例自己看上去都完全正常**，合起来却表现为"同一句话被回答两次" ——
这是唯一一类"单看每个进程都没毛病、合起来出怪事"的故障，所以必须能一眼看到。

|---|---|
| `selfPid` | 当前进程 PID（显示出来，用户才能对照 `--kill`） |
| `running` | 在运行的桥接数（含自己） |
| `conflicts` | **非空即冲突**：与本进程同类、且仍在运行的其它进程（`pid` / `state` / `reason`） |

要求：

- 概览页「连接与环境」加一行**进程**：无冲突显示"只有本进程（pid N）"，
  有冲突显示"另有 N 个在跑"并用警示色；
- **协议端页签顶部**再加一条醒目提示（比概览更显眼），因为它和"协议端连不上"
  这类症状出现在同一页，用户会先看这里；
- 提示里**必须给出停止办法**：`node src/index.mjs --processes --kill <pid>`。
  只说"检测到冲突"而不给出路，等于把问题丢回给用户。
- 演示模式（`demo`）下显示 `—`，不要显示真实 PID。

### 5.1 SnowLuma 进程接口（**已实现**）


> ⚠️ **这一节描述的是"约定"，桥接侧尚未实现。** 现在调会得到 `501`。
> 界面照这份规格做即可，实现落地后无需改动。

#### `GET /api/snowluma/detect` — 探测在线状态

不传任何参数。桥接会**主动去连一次** `onebot.httpUrl`（用配置里的 `httpToken`），
所以这个接口有**几百毫秒到 `snowluma.probeTimeoutMs` 的耗时**，
界面请显示一个转圈，不要以为卡死了。

```json
{
  "status": "connected",
  "httpReachable": true,
  "wsConnected": true,
  "loggedIn": true,
  "login": { "userId": "200000001", "nickname": "DeepSeek小鲸鱼" },
  "endpoint": { "httpUrl": "http://127.0.0.1:3000", "wsUrl": "ws://127.0.0.1:3001" },
  "launch": { "configured": true, "cmd": "D:\\...\\snowluma\\launcher.bat", "cwd": "D:\\...\\snowluma" },
  "hint": "一切正常"
}
```

| 字段 | 含义（**界面务必照这个理解，别自己推断**） |
|---|---|
| `status` | 上面 §2.7.1 对照表里的六种之一，**直接用这个值驱动界面** |
| `httpReachable` | 桥接能不能连上 `httpUrl`（= "有没有东西在 3000 端口"） |
| `wsConnected` | **桥接自己那条事件通道**当前是否连着（等价于 `/api/status` 的 `connected`） |
| `loggedIn` | QQ 是否已登录。**以 SnowLuma 当下的回答为准**，不是缓存值 |
| `login` | 只有 `loggedIn` 为真时才有意义 |
| `endpoint` | 当前**实际**在用的地址（从配置读，不是猜的） |
| `launch.configured` | `snowluma.launchCmd` 填了没有 —— **按钮的启用条件就是它** |
| `hint` | 可以直接显示给用户的一句话；**不要**在这一层重写文案 |

**`status` 的判定顺序（后端按此实现，界面理解这个顺序就不会困惑）：**

```
桥接自己没在跑        → bridge-offline   （兜底，正常打不开界面）
httpUrl 连不上        → offline
连得上但 token 被拒   → auth-failed
连得上但 QQ 没登录    → up-not-logged-in
连得上且已登录        → connected
```

**注意 `offline` 和 `bridge-offline` 的区别**：前者是"SnowLuma 死了"，后者是"你自己死了"。
正常使用时界面打不开就说明是后者，所以这个分支平时看不到。

#### `GET /api/snowluma/log` — SnowLuma 的终端输出

查询串：

| 参数 | 默认 | 含义 |
|---|---|---|
| `lines` | `0` | 只回**最后 N 行**（首次加载用）。给了它就不看 `offset` |
| `offset` | `0` | 上次读到的字节位置（**增量轮询**用） |
| `includeDebug` | `1` | `0` = 滤掉 `DEBUG` 行 |

**★ 读的是 SnowLuma 自己的日志文件**（UTF-8），不是它的 stdout（终端编码 → 会乱码）。
详见 §2.7.3 的实测对比。

```json
{
  "available": true,
  "file": "C:\\...\\snowluma\\logs\\snowluma-2026-09-26.log",
  "date": "2026-09-26",
  "dir": "C:\\...\\snowluma\\logs",
  "lines": [
    { "time": "00:25:52", "level": "OK", "rest": "[200000001] [Event] 私聊 [...]", "text": "00:25:52 OK    [...]" }
  ],
  "offset": 11605,
  "rotated": false,
  "truncated": false,
  "droppedDebug": 78,
  "totalBytes": 11605
}
```

| 情况 | HTTP | 返回 |
|---|---|---|
| 正常 | 200 | 上面的结构 |
| 还没有日志文件 | 200 | `available:false` + `note`（**不是错误**，别报红） |
| 文件读不了（权限等） | 500 | `{ok:false, error}` |

**★ 三条必须做对的：**

**① `rotated: true` 时必须清空面板。** 日志按天轮转；跨天后你手上的 `offset`
超出文件大小，接口会从头再给一遍。不清空就会把新旧日志拼在一起，**看起来像时间倒流**。

**② `truncated: true` 说明上面还有更早的日志**（本次只取了尾部一块）。
界面可提示"仅显示最近 N 行"，而不是让人以为日志从这里开始。

**③ `available:false` 不要报红。** SnowLuma 还没跑过而已 —— 用一句平实的话说明。

#### `POST /api/snowluma/start` — **打开 SnowLuma 网页端**（界面按钮用它）


不传任何参数（打开哪个地址由 `snowluma.consoleUrl` 决定）。

**★ 这个按钮只做一件事：用系统默认浏览器打开 `snowluma.consoleUrl`。**

```
① 探一下 consoleUrl（好告诉界面"那边有没有服务"）
② 用系统默认浏览器打开它
③ 回报 { opened, consoleUrl, reachable, hint }
```

**★ 按钮为什么只管"打开网页"，不管"启动进程"：**

| | 打开网页（现在） | 启动进程（已移交给 `start.bat`） |
|---|---|---|
| 能做到吗 | 能确定做到 | 会开出**第二个实例**（端口冲突、抢登录态） |
| 该在哪做 | 界面上点一下 | 启动时做一次 |

**启动进程已经放进 `start.bat`**（见 README / `start.bat` 注释）：
启动桥接之前先拉起 SnowLuma，已在跑就跳过。所以按钮不必也不能重复这件事。

**返回形状：**

```json
// 网页端可达（SnowLuma 在跑）
{ "opened": true, "consoleUrl": "http://127.0.0.1:5099/", "reachable": true,
  "hint": "已打开 SnowLuma 网页端。" }

// 网页端不可达（SnowLuma 没在跑）
{ "opened": true, "consoleUrl": "http://127.0.0.1:5099/", "reachable": false,
  "hint": "已打开浏览器，但那个地址现在没有服务 —— SnowLuma 可能没在运行（它没跑时网页端也不存在）。请先启动 SnowLuma。" }
```

| 情况 | HTTP | 返回 |
|---|---|---|
| 打开了 | 200 | `{opened:true, consoleUrl, reachable}` |
| 浏览器没打开成功 | 500 | `{ok:false, error:"没能打开浏览器：…。你可以手动访问 <url>", consoleUrl, reachable}` |

**★ 界面必须用 `reachable` 区分两件事：**

> 「**浏览器打开了**」≠「**SnowLuma 在跑**」。
> 控制台是 SnowLuma 的一部分，**它没跑时那个网页根本不存在**。
> 所以 `reachable:false` 时不要把 `hint` 吞掉 —— 否则使用者会对着一个
> 打不开的页面发呆，还以为按钮坏了。

**★ 为什么由后端去开浏览器**（而不是界面 `window.open`）：

- 不依赖浏览器的弹窗拦截策略；
- 能**如实回报**"到底打开了没有"，而不是"我调用了一个 API"；
- 与 SnowLuma 不在同一台机器时能给出明确错误。

#### ★ token 从哪来（排查「令牌被拒」必读）

**`onebot.wsToken` / `onebot.httpToken` 现在以 SnowLuma 自己的
`config/onebot_<uin>.json` 为准**，`config.json` 里那份只作为回退。

为什么改成这样——踩过两次的真实事故：

```
config.json 里的 token 与【正在跑的那个】SnowLuma 不一致
   ↓
桥接被 401 拒绝 → 症状是「令牌被拒」+ 机器人完全不说话
   ↓
而最阴的一次是：脚本把 token 改对了，之后【通过网页保存了一次配置】，
那次保存把旧 token 当作非空值提交 → 被合法写回旧值 → 修复被静默推翻
```

病根是 **token 存在两处，必然漂移**。那份数据本来就是 SnowLuma 的
（它启动时按它校验），我们存副本只会有分歧、没有好处。

`GET /api/snowluma/detect` 会额外返回两个字段，专门用于排查：

| 字段 | 含义 |
|---|---|
| `tokenSource` | token 实际来自哪里（`SnowLuma 自己的配置` / `config.json`） |
| `tokenDiffersFromConfig` | 两者**不一致**时为 `true` —— 看到它就说明 `config.json` 里那份是过期的，**别用它** |

### 5.2 记忆文件接口（**已实现**）

> ⚠️ 同 §5.1 / §5.3，现在调会得到 `501`。

**这三个接口有一个共同的安全前提，界面必须理解**：
所有路径都是**相对工作区**的，后端会做**越界检查**（`..`、绝对路径、软链接一律拒绝），
并且**只允许 `.md` 文件**。
所以界面**不要自己去拼绝对路径** —— 传相对路径，让后端判断。

#### `GET /api/memory/tree` — 目录树

```json
{
  "workspace": "C:\\...\\workspace-qq",
  "enabled": true,
  "entries": [
    { "path": "MEMORY.md", "type": "file", "size": 168, "mtime": "2026-09-25T14:27:00+08:00" },
    { "path": "memory", "type": "dir", "children": [] }
  ],
  "totalBytes": 168,
  "note": "记忆由机器人自己在聊天过程中维护。没有 memory/ 目录是正常的（按需创建）。"
}
```

| 字段 | 说明 |
|---|---|
| `enabled` | 对应 `memory.enabled`。**为 `false` 时界面仍要能看和改**（见 §2.5 第 ③ 条） |
| `entries` | 树。`type` 为 `dir` 时带 `children`（可能为空数组） |
| `totalBytes` | 全部记忆文件加起来多大。给一个"记忆膨胀了没"的直观信号 |

**★ 空目录要显示成"（空）"，不是错误。** 实测里 `memory/` 目录**根本不存在**，
模型把两条信息都写进了 `MEMORY.md` —— 这是正常的，不是坏了。

#### `GET /api/memory/file?path=MEMORY.md` — 读一个文件

```json
{
  "path": "MEMORY.md",
  "content": "# 记忆索引\n\n- 管理员私聊：QQ 100000001（昵称\"无忘远霞\"）\n",
  "size": 168,
  "mtime": "2026-09-25T14:27:00+08:00",
  "sha256": "3f9a2c1b7d4e..."
}
```

| 情况 | HTTP | 返回 |
|---|---|---|
| 正常 | 200 | 上面的结构 |
| 文件不存在 | 404 | `{ok:false, error:"记忆文件不存在"}` |
| 路径越界 / 非 `.md` | 400 | `{ok:false, error:"路径不合法"}` |
| 后端未实现 | **501** | 现在是这个 |

**`sha256` 是版本标识，保存时要原样回传。** 界面**不要自己算**它 ——
算法（是否含 mtime、是否含路径）由后端定，界面只负责搬运。

#### `POST /api/memory/file` — 写一个文件

请求体：

```json
{ "path": "MEMORY.md", "content": "# 记忆索引\n...", "expectedSha256": "3f9a2c1b7d4e..." }
```

| 情况 | HTTP | 返回 |
|---|---|---|
| 保存成功 | 200 | `{saved:true, sha256:"<新值>", mtime, restartRequired:false}` |
| **磁盘内容已被改过** | **409** | `{ok:false, conflict:true, currentSha256, currentContent, error:"这份记忆在你编辑期间被改过了"}` |
| 路径不合法 | 400 | `{ok:false, error:"路径不合法"}` |
| 后端未实现 | **501** | 现在是这个 |

**★ `restartRequired` 恒为 `false`，这是刻意的。**
记忆是模型运行时读的普通文件，改完**下一次它读笔记时就是新的**。
界面**不要**弹"需要重启" —— 那是配置类改动的提示，两者完全不同。

**★ 409 是这套接口最重要的一个分支。**
模型**随时可能在写记忆**（你无法预知它什么时候决定"这事值得记住"），
所以"你编辑期间它写了一次"是**常态而非意外**。

界面收到 409 必须做到：

1. **不要**自动覆盖、也不要自动丢弃你的编辑
2. 明说发生了什么：**「这份记忆在你编辑期间被机器人改过了。」**
3. 给两个选择：**[重新载入（丢弃我的修改）]** / **[仍然覆盖]**
4. 若能拿到 `currentContent`，把差异展示出来——**这是用户唯一能判断"谁对"的依据**

> **`expectedSha256` 缺席时**（界面没传）：后端按"允许覆盖"处理，
> 并在响应里带 `overwroteWithoutCheck: true`，界面据此提醒用户。
> 这是为了不让界面因为少传一个字段就完全不能用，但**这条路径等于放弃了冲突保护**。

### 5.3 用量接口（**已实现**）

> ⚠️ 与 §5.1 一样，**这一节描述的是约定**，现在调会得到 `501`。

#### `GET /api/usage?days=7` — 用量汇总

查询串：

| 参数 | 默认 | 含义 |
|---|---|---|
| `days` | `7` | 取最近几天。`0` = 全部 |

**所有 token 字段都是"量出来的精确值"**，成本字段是"按 `prices.json` 估算的"。
两者在返回里**分开放在不同对象里**，就是为了让界面不可能把它们混为一谈。

```json
{
  "range": { "days": 7, "from": "2026-09-19T00:00:00+08:00", "to": "2026-09-25T14:39:00+08:00" },
  "totals": {
    "turns": 128,
    "tokens": { "input": 26315, "cacheRead": 207268, "cacheWrite": 0, "output": 3625, "reasoning": 512 },
    "cacheHitRate": 0.887,
    "lastContextTokens": 34709
  },
  "cost": { "available": true, "amount": 0.0344, "currency": "CNY", "basis": "prices.json@2026-09-25" },
  "byDay": [
    { "date": "2026-09-24", "turns": 93,
      "tokens": { "input": 1793712, "cacheRead": 1225728, "output": 23824 },
      "cacheHitRate": 0.406, "cost": 1.38 }
  ],
  "bySession": [
    { "chatKey": "private:100000001", "kind": "private", "label": "私聊 100000001",
      "turns": 51,
      "tokens": { "input": 1546095, "cacheRead": 0, "output": 19298 },
      "cacheHitRate": 0.0, "cost": 0.396 },
    { "chatKey": "group:700000002", "kind": "group", "label": "群 700000002",
      "turns": 72,
      "tokens": { "input": 2681700, "cacheRead": 0, "output": 36886 },
      "cacheHitRate": 0.0, "cost": 1.17 }
  ]
}
```

**字段口径（与 §2.1.1 完全一致，这里再钉一遍）：**

| 字段 | 含义 |
|---|---|
| `tokens.input` | **未缓存**的输入（贵的那个，实测占约 57% 费用） |
| `tokens.cacheRead` | 缓存命中的输入（便宜的那个，约 1/50 价） |
| `tokens.output` | 输出 |
| `tokens.cacheWrite` | 缓存写入。**可能缺席**（有的路由不报），缺失时**不要当 0**，界面上不显示这一列即可 |
| `tokens.reasoning` | 思考 token。**它是 output 的一部分**，可显示但**不可再计入总量** |
| `cacheHitRate` | `cacheRead / (input + cacheRead)`；分母为 0 时返回 `null`（**不是 0**） |
| `lastContextTokens` | 最近一回合**最后一步**的上下文总量。**是个快照**，不可累加、不可计价 |
| `cost.available` | `false` 时 `amount` 为 `null`，界面显示 `—` |
| `cost.amount` | 元。**估算值** |
| `cost.basis` | 计价依据摘要，界面上做成可点击 → 调 `/api/usage/prices` |

**★ `cacheHitRate` 为 `null` vs `0`**：`0%` 意思是"算了，一次都没命中"；
`null` 意思是"没有输入，无法计算"。前者是结论，后者是"没有数据"。
界面上分别是 `0%` 和 `—`。

**★ 缺失字段的约定**：某个路由不上报 `reasoningTokens` 时，该项就是 `null`，
**不要补 0**。理由同上：0 是"测到了 0"，null 是"没测到"。

#### `GET /api/usage/prices` — 当前生效的价目表 + **当前时段判定**

```json
{
  "source": "prices.json",
  "updatedAt": "2026-09-25",
  "loaded": true,
  "peak": { "timezone": "Asia/Shanghai", "windows": [{ "start": "09:00", "end": "12:00" }],
            "days": [1,2,3,4,5], "holidays": [] },

  "now": {
    "_说明": "桥接自己算的一份时段判定。★ 顶部指示灯【不用它】—— 灯由界面按浏览器时间算（见 §2.1.1）。这里保留它是为了排查问题：拿它和界面上显示的对照，能一眼看出两边时钟是否一致。",
    "at": "2026-09-25T10:30:00+08:00",
    "weekday": 5,
    "isPeak": true,
    "period": "peak",
    "rateKey": "peak",
    "indicator": "当前：高峰时段",
    "reason": "window",
    "reasonText": "落在高峰时段窗口 09:00–12:00 内",
    "holidaysKnown": false,
    "nextChangeAt": "2026-09-25T12:00:00+08:00"
  },

  "routes": { "deepseek-official/deepseek-flash": {
      "cacheHitPerM": { "offPeak": 0.02, "peak": 0.04 },
      "cacheMissPerM": { "offPeak": 1, "peak": 2 },
      "outputPerM": { "offPeak": 4, "peak": 8 } } },

  "warning": "holidays 为空：法定节假日会被按高峰计价（偏高）。价格会变，请定期核对官方页面。"
}
```

**`now` 对象：★ 顶部指示灯【不用它】，界面自己按浏览器时间算（见 §2.1.1）。**

保留它是**为了排查问题** —— 界面上显示的和这里的 `indicator` 一对照，
就能一眼看出"两边时钟是不是一致"。字段含义：

| 字段 | 含义 |
|---|---|
| `isPeak` | `true` = 高峰，`false` = 低谷 |
| `period` | `"peak"` / `"offPeak"` |
| `rateKey` | 当前该取价目表里的哪一组价（`"peak"` / `"offPeak"`）。等于 `period`，单列出来是为了方便直接索引 |
| `indicator` | 那行字，形如 `当前：高峰时段` / `当前：低谷时段` |
| `reason` | `window`（在高峰窗口内）/ `weekend`（周末）/ `holiday`（在节假日表里）/ `outside-window`（工作日但在窗口外） |
| `reasonText` | 一句人话，可做 tooltip |
| `holidaysKnown` | `holidays` 是否非空 |
| `nextChangeAt` | 下一次峰谷切换的时刻。**可能为 `null`**（例如次日无高峰） |
| `at` | **桥接**判定用的时刻 |

**★ 界面真正要做对的三条**（判定逻辑本身见 §2.1.1 的 `computePeriod`）：

**① 用 `peak` 规则段 + 浏览器时间算，不要用 `now`。**
理由：**你选择让灯的判定跟着浏览器走**（见 §2.1.1）。
`now` 是桥接按自己的钟算的另一份，拿来对照可以，拿来显示会造成两份数据源。

**② 拉不到价目表时显示「时段未知」，不是「低谷」。**
拿不到规则时我们**不知道**现在是什么时段。
显示"低谷"是撒谎 —— 万一正好在高峰，用户会以为便宜而放心烧 token。

**③ `holidaysKnown: false` 时，必须给一个温和的注解。**
因为 `holidays` 默认是空表，所以法定节假日会被判成**高峰**（保守计价，偏高）。
这时如果用户**明知**自己在放假，界面说"高峰"会显得很蠢。

建议的界面表现（不要做成弹窗，做成 `indicator` 旁边一个小问号）：

> 当前：高峰时段 ⓘ
> （悬停）节假日表未维护，节假日会按高峰计价。今天的判定可能有偏差。

**★ 边界规则**：时间窗口按**左闭右开** —— `09:00` 算高峰，`12:00` 算低谷。
不然 `12:00` 整那一刻会有两个答案。

**界面另外必须做的一件事**：成本卡片上留一个「计价依据」入口，
点开显示整张价目表 + `warning` 原文。
**不要让成本数字变成一个无法追溯的黑箱** —— 那比不显示更糟。

#### 记账规则（后端实现时按此做，界面不用管，但理解它能避免误解）

1. **一个"回合"记一条**（不是一步一条）。回合结束时把该回合所有步骤的
   `inputTokens / cacheReadTokens / cacheWriteTokens / outputTokens / reasoningTokens`
   **分别求和**写入。
2. **成本在记账当时算好并写进记录**，因为峰谷要按"调用发生的那一刻"判定。
3. 记录**追加写**在一个文件里（`logs/usage.jsonl`），**重启不清空**。
4. 记录里带 `chatKey` / `kind` / `label` / `route` / `at`，供按会话、按天聚合。
5. **`totalTokens` 不参与求和**，只取最后一步的值存为 `lastContextTokens`。

### ★ 两条必须遵守的规则（代码已按此实现，UI 也要配合）
**① 读配置拿到的是"删掉了密钥"的配置。**
所以：

- 不要用返回值里"有没有这些字段"来判断用户配没配 —— 用 `hasWsToken` / `hasHttpToken` / `hasApiKey`。
- 密码框的 placeholder 应该根据这些布尔显示"已配置（留空即不修改）"或"尚未配置"。

**② 写配置时，密钥字段留空 = 保持原样。**

这是刻意设计的：UI 拿到的是脱敏配置，回传时本来就没有这些字段；
如果后端把空值当作"清空"，**用户每保存一次就会把密钥弄丢**，
表现为"改了个打字速度，结果机器人连不上了"。

所以 UI 正确的做法是：**密码框留空时，提交的 JSON 里干脆不放这个字段**
（或者放空串也行，两种都被当成"不修改"）。

**③ 例外：`dsh.apiKey` 可以用 `null` 显式清除。**

密钥和 accessToken 不一样 —— 用户换号、key 泄露、想改用环境变量 `DEEPSEEK_API_KEY`，
都必须有一个"删掉它"的动作。而空串这条语义已经被②占用了，所以清除只能用 `null` 表达：

| 界面动作 | 提交的 JSON | 结果 |
|---|---|---|
| 没动密码框 | （不放该字段）或 `""` | 保持原样 |
| 填了新 key | `"dsh": { "apiKey": "sk-..." }` | 覆盖为新值 |
| 点「清除已配置的 Key」 | `"dsh": { "apiKey": null }` | **清空**（落盘为 `""`） |

清除按钮**必须二次确认**（文案见 §2.8 下方），并且**不能**顺手把 `hasApiKey` 这个标记
当成配置提交回后端 —— 它会变成 `config.json` 里一个永久垃圾键（见 §5.2 的 `delete` 要求）。

### ★ 保存会被后端校验拦下

`POST /api/config` 会先跑一遍和启动时**完全相同**的校验规则。
如果配置会导致机器人起不来（例如把工作区设成盘符根），会返回：

```json
{ "ok": false, "error": "配置有问题，已拒绝保存",
  "fatal": ["dsh.workspace 不能是盘符根（D:\\）—— 那等于把整个磁盘交给 agent"] }
```

**UI 应该把 `fatal` 原文展示给用户**，而不是吞掉或自己编一句。
（规则只有一份在后端，前端不需要重复实现。）

### 保存后的生效方式

当前实现里配置**只在启动时读一次**，所以保存后**需要重启桥接**。
接口返回 `restartRequired: true` 和一句 `hint`，UI 应据此提示：

> 已保存。需要**重启机器人**才会生效。[立即重启] [稍后]

「立即重启」直接调 `POST /api/restart` 即可。重启的完整交互流程：

1. 接口**先返回** `{restarting:true}`，约 0.4 秒后旧进程才退出 —— UI 一定拿得到响应。
2. 旧进程退出时会拉起一个新的桥接进程（detached，日志照旧写 `logs/bridge.log`）。
3. 新进程要初始化 DSH，**接口会断开几秒钟**。UI 应显示"正在重启"并每 2 秒轮询
   `/api/status`，通了就重新加载配置、清掉"待重启"角标。
4. 建议超时 90 秒：超时提示用户去看日志或用 `start.bat` 手动启动。

`POST /api/stop` 同理（先响应再退出）。**停止前必须二次确认**：

> 停止后本界面会断开，而且**无法从这里再启动** —— 需要到机器人目录
> 双击 `start.bat` 才能重新启动。

**为什么没有 `/api/start`**：接口本身就跑在桥接进程里，桥接停了接口也不在，
"远程启动一个没在跑的东西"无处受理。所以 UI 在离线状态下应显示手动启动指引
（`start.bat` 或 `node src/index.mjs`），而不是一个点了没用的启动按钮。

### 自定义端口

`config.json` 的 `ui.apiPort`（默认 3410），或 `ui.apiEnabled: false` 关掉接口。

**① `GET /api/preflight` —— 启动前置条件门控（概览页顶部）**

```json
{ "ok": false, "blockers": 1, "gates": [
  { "id": "onebot", "ok": false, "level": "blocker",
    "title": "协议端不可达",
    "hint": "fetch failed（层：network，可重试）",
    "action": "start.bat（或 start.bat --doctor）" } ] }
```

* `id`：`config` / `admins` / `onebot` / `login` / `dsh` / `credentials`（顺序稳定，可直接渲染）
* `level`：`blocker`（**必须**修，否则机器人不会说话）/ `warn` / `info`
* `action`：**给使用者看的下一步**（可复制去跑）。★ 不要只显示 `title` ——
  "协议端不可达"人人都看得懂，**该怎么修**才是这条接口存在的理由。
* ⚠️ 它会**真的去问一次协议端**（不读缓存），所以响应可能慢 1~2 秒；界面要给 loading 态。

**② `GET /api/snowluma/accounts` —— 账号发现（设置页）**

```json
{ "installDir": "…\\snowluma",
  "accounts": [ { "uin": "100000001", "file": "onebot_100000001.json", "isCurrent": false },
                { "uin": "200000001", "file": "onebot_200000001.json", "isCurrent": true } ],
  "current": "matched-config:onebot_200000001.json", "matchedByConfig": true, "why": "" }
```

* ★★★ **响应里永远没有 token**（后端做了**字段白名单**，即使上游实现出错也带不出来）。
  界面**不要**设计"显示 token / 复制 token"的功能 —— 那条路被刻意封死了。
* `isCurrent` **恰好一个为 true**（凭据发现的判定结果）；`matchedByConfig: true` 表示
  "这个账号的凭据与 config.json 里的一致"，是最可靠的判定依据。
* `why` 非空 = 判定不可靠，界面上要**提示使用者去 `onebot.selfId` 里写死账号**。

**③ `GET /api/logs/stream?since=<游标>&limit=<条数>` —— 日志面板**

```json
{ "lines": ["2026-09-26 16:30:11 桥接已启动…"], "cursor": 2731, "total": 2733, "eof": false }
```

* **轮询**（不是 SSE）：拿到 `cursor` 后下一次请求带上它，只取新增的行。
  ★ 为什么不做 SSE：本项目的 HTTP 层是"一次请求一次响应"（`serveApi` 直接 `res.end`），
  改成流式要重做那一层；而日志面板的需求是"近实时"，**秒级轮询已经够**，且实现与排查都更简单。
  这一条如实写在这里，避免界面作者以为"应该有个 SSE 端点"。
* 游标**超出总行数时会自动回到 0**（日志轮转后不会永远收不到新日志）。

**④-b `GET /api/memory/search?q=&limit=` —— 记忆条目检索（记忆页签）**

```json
{ "ok": true, "query": "冰美式", "files": 2,
  "rows": [ { "rel": "MEMORY.md", "line": 2, "preview": "- 他喜欢冰美式", "superseded": false } ] }
```

* 搜的是**沉淀下来的事实**（记忆条目），不是"说过什么"（那是 ④ 语料检索，
  两者分工不同：记忆跨重启生效、有 supersede 机制；语料是消息流水、有 30 天 TTL）。
* ★ **不需要会话参数**：记忆文件名本身就分了档（`MEMORY.md` / `private-<QQ>.md` /
  `group-<群号>.md`），不存在跨会话混淆的问题。
* ★ `rows[].preview` 是**行预览**（≤120 字）；`superseded: true` 表示这条**已被更正**
  （仍在文件里可追溯，但不再作为事实使用）—— 界面上要标出来，否则会让人以为模型还在用错的。
* 缺 `q` 会 **400**；搜不到是"空结果 + 200"（**搜索无结果不是故障**）。

**④ `GET /api/corpus/search?q=&kind=&peerId=&limit=` —— 历史检索（对话页）**

```json
{ "ok": true, "mode": "like",
  "rows": [ { "mid": "1", "at": 1790440454352, "chatKey": "group:700000001",
              "sender": "望仔", "isBot": false, "preview": "茶姬新出的那个好喝吗" } ] }
```

* ★★ **必须带会话**（`kind=private|group` + `peerId`）：缺了会 **400**，这不是"参数没填全"，
  而是**故意的 fail-closed** —— 语料库存着所有会话，不限定就等于把别的群/别人的私聊
  显示在这个页面上。界面应当**只允许搜当前打开的会话**。
* 字段叫 `preview`（**截断预览**，不是全文）：界面别把它当正文显示成"完整消息"。
* 想引用某条消息时用 `mid`（配合 `[reply:<mid>]` 机制）。

   而不是手打号码 —— 手打错了的表现是"机器人不回我"，很难排查。

## 7. 机器人撞到权限墙时的表现（界面要知道）

**这是设计行为，不是故障** —— 机器人被限制在一个专用工作区里（`dsh.permissionMode`
默认为 `workspace-write`），越界操作会被系统自动拒绝。

**使用者在 QQ 里看到的**：机器人**用自己的话**说「这件事我暂时没权限做」这类内容。
提示词里明确要求它：

- 不引用系统报错原文（`file access denied under workspace-write mode` 这种用户看不懂）
- 不报路径、不描述沙箱机制、不说"越界""被拦截"
- 如果有别的做法（在工作区内完成、或让用户自己动手），顺口提一句

**⚠️ 界面上的两点要求：**

1. **不要把它渲染成错误状态。** 它是"权限边界"不是"报错"，
   用普通消息气泡即可，不要加红色警告或 ❌ 图标。
2. **不要自作主张加"权限不足"标签。** 机器人已经在正文里说清楚了；
   界面再叠一层反而啰嗦。如果你确实想标注，用中性的浅色小字。

> **注意这是提示词层面的引导，不是硬保证。** 模型有可能偶尔用词不准。
> 若使用者反馈"它说的话看不懂"，先看具体说法再调提示词，
> **不要在 UI 上试图解析或改写机器人的回复** —— 那会让 UI 和提示词两处维护同一件事。
